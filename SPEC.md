# vault-sync — Specification

This is the authoritative technical reference for vault-sync: its purpose, design principles, architecture, data model, sync protocol, encryption scheme, and repository layout. It is a living document — update it in the same change that alters any behavior it describes. Where this document says "decision", the reasoning is recorded so that a later change can revisit it deliberately rather than by accident.

This project is bootstrapped to mirror the conventions of [`tape-archiver`](https://github.com/solidDoWant/tape-archiver) and [`media-processor`](https://github.com/solidDoWant/media-processor): Go, Nix-reproducible builds, issue-driven development with Given/When/Then acceptance criteria, and a testing-first philosophy.

## 1. Purpose

vault-sync is a self-hosted replacement for Obsidian Sync. It has two halves:

- an **Obsidian community plugin** (TypeScript) that watches a vault and synchronizes it, and
- a **sync server** (Go) that stores vault state in **PostgreSQL** (metadata, revisions) and an **S3-compatible object store** (file contents).

It exists because the available self-hosted option (obsidian-livesync) requires CouchDB, has a history of data-loss and reconciliation bugs, is thinly documented, and has no multi-user model. vault-sync targets a small number of users (one household / small team) on infrastructure the operator already runs.

## 2. Design principles

These are non-negotiable. When a trade-off arises, resolve it in favor of the principle, not convenience. Call out any change that touches one.

1. **No acknowledged write is ever lost.** Once the server has acknowledged a revision, that content is recoverable — as the current head, in revision history, or as a conflict copy — until an explicit, retention-governed purge. Neither the client nor the server ever silently discards a user edit. Deletion is a tombstone, never an erase.
2. **One source of truth per concern.** The server's revision log is the source of truth for vault history. The local vault on disk is the source of truth for un-pushed local edits. The client keeps exactly one durable journal bridging the two. No additional replicated databases or chunk layers.
3. **Everything is tested — including adversarially.** Sync correctness is proven by a deterministic, seeded, multi-client simulation with fault injection (partitions, crashes, reordering), not by example tests alone. If it is not tested, it does not work.
4. **Small, defensible attack surface.** The server is exposed to the internet. Keep the API small, typed, and authenticated by default; every endpoint enforces vault-level authorization; resource usage is bounded (request sizes, decompression, pagination).
5. **Operator infrastructure only.** PostgreSQL, S3-compatible storage, and OIDC. No new database types.

## 3. Target environment

- **Server:** Kubernetes (Talos) homelab. PostgreSQL 14 or newer via CloudNativePG (client-certificate auth; certificates rotate — the server must re-read them, never cache them for the process lifetime). Object storage via Ceph RGW (S3 API). Identity via Authentik (OIDC). Exposed through an Istio gateway with a Coraza WAF in front: **inspected request bodies above 1 MiB are rejected**, so every upload is chunked at or below a configurable size (default 768 KiB).
- **High availability:** the server runs as an HA deployment: two or more identical replicas behind one Service, sharing one PostgreSQL database and one S3 bucket. Terminating any replica, for example for node maintenance, must have **no client-visible impact**. The rules that make this hold are in §12.
- **Clients (required):** Obsidian desktop on **Windows** and **macOS**, Obsidian mobile on **Android**. Linux desktop is the development/test platform. **iOS is best-effort** (not a release blocker) — do not take design decisions that preclude it.
- **Backups:** a plaintext export of every vault (decrypted where escrow is enabled, §9.4) is written to a filesystem path that the operator's tape-archival tooling picks up. This replaces livesync-bridge. **No readable live document is ever left out of an export** (decision, #52/#178). Each vault's files sit in a browsable tree at `<out>/<vault-id>/<path>`. A document whose path that tree cannot hold (a file/folder collision such as `a` and `a/b.md`, a name the filesystem rejects such as one over 255 bytes, or an invalid or non-UTF-8 path) is written to `<out>/<vault-id>.unplaced/<document-id>` instead. A streamed JSON Lines manifest, `<out>/<vault-id>.manifest.jsonl`, lists every live document: id, original path, kind, head revision id, size, SHA-256, status (`placed`, `unplaced` or `missing`) and where its bytes are. The unplaced tree and the manifest sit beside the vault's directory, never inside it, so no user file can be mistaken for them. The layout and manifest are a versioned format (format 2, in the marker and every manifest), specified in `docs/export.md`, so the Phase 6 importer can restore exactly. Content that is missing or corrupt in S3 is the only reason a live document's bytes can be absent; the manifest lists it as `missing` and the run reports `partial`. History, tombstones and (until Phase 4) E2EE vaults are not exported.

## 4. Architecture

```
 Obsidian (desktop / Android)                       Kubernetes
 ┌──────────────────────────────┐    HTTPS     ┌──────────────────────────────┐
 │ plugin/src/obsidian  (adapter)│  ConnectRPC │ vault-sync-server (Go)        │
 │   vault events, editor, UI    │◄──────────►│   API (ConnectRPC, protobuf)  │
 │ plugin/src/core  (sync engine)│  WebSocket  │   realtime hub (WebSocket)    │──► PostgreSQL (CNPG)
 │   journal (IndexedDB), merge, │◄──────────►│   authz, quotas, retention     │──► S3 (Ceph RGW)
 │   crypto, protocol client     │             │                               │──► Authentik (OIDC JWKS)
 └──────────────────────────────┘             └──────────────────────────────┘
                                               ┌──────────────────────────────┐
                                               │ vault-sync export (CronJob)   │──► plaintext tree for tape
                                               │   holds escrow private key    │
                                               └──────────────────────────────┘
```

- **`plugin/src/core`** is a pure TypeScript library: the sync engine, journal, merge, crypto, and protocol client. It **must not import `obsidian`** (lint-enforced) or use Obsidian's globals: `make lint` type-checks it, with its tests and `sim/`, as a separate program (`plugin/tsconfig.core.json`) that has neither Obsidian's global augmentations nor DOM-only globals, and fails if any route (import, `/// <reference>`, `src/main.ts`) brings Obsidian into it. Core code must be plain `.ts` modules with no triple-slash directives, no `declare global` and no JavaScript imports, and the program may contain nothing from outside `src/core`, `sim/`, `src/gen` and dependencies. Packages that `src/core` and `sim/` import directly must be declared in `plugin/package.json` (`dependencies` or `devDependencies`, or their `@types` package) and are never `obsidian`, so Obsidian's own transitive dependencies (e.g. `@codemirror/view`, `moment`) cannot slip in. Any other code file under `src/core` (`.js`, `.mts`, `.tsx`, `.d.ts`, …) fails the check even if nothing imports it; non-code files there are ignored. It talks to the vault through a `VaultAdapter` interface so the simulation harness can drive it against an in-memory vault.
- **`plugin/src/obsidian`** is the thin adapter: `Vault`/`FileManager` events, editor integration, settings UI, status bar, conflict UI. `ObsidianVaultAdapter` implements `VaultAdapter` on the Vault API and passes the conformance suite inside real Obsidian (e2e). Paths with a hidden segment (`.obsidian/`, `.trash/`, any `.name`) and paths Obsidian's `normalizePath` would store under another name are outside it: never listed, read or reported, and a write or rename onto them is refused as `path-conflict`, so the engine defers such a revision instead of touching the disk (decision, #24; `.obsidian/` config sync is #28). Renames use `Vault.rename`, never `FileManager.renameFile`, because a synced rename must not rewrite links: the other device's link updates arrive as revisions of their own. `SyncSession` ties the adapter and the engine to the plugin's lifecycle: it starts once the workspace layout is ready, resumes from the journal's cursor, and stops in `onunload`, so disabling and re-enabling the plugin never starts a full resync. Sync wiring (decision, #25): `SyncController` runs a session exactly while the device is signed in and the local vault is connected to a server vault (recorded in plugin data with its server URL), and stops it on sign-out, on "sign-in required" and before switching vaults. A session pulls and then pushes when it starts, pushes 2 s after the last local change of a burst (`pushDebounceMs`), and pushes (which pulls first) every 30 s, the only way remote changes arrive until the realtime client exists (#193). Stopping a session refuses every further vault, journal and server call of its engine (a call waiting on the network is abandoned, its late response dropped) and resolves once the engine has settled, so two engines never run over one journal. Edits the stopped session had not pushed stay on disk and are found by the next session's full scan (principle 1). The device registers with `RegisterDevice` once per plugin install and account (server URL, issuer and the access token's `sub`) before its first sync; the id is stored in plugin data and reused on every later start and sign-in, because the server's device limit counts every registration. A `RESOURCE_EXHAUSTED` from `RegisterDevice` (other than the per-user concurrency limit) is shown as that limit, and sync does not start. Connecting a non-empty local vault to a remote vault with revisions asks for confirmation first: nothing is overwritten, but files at the same path with different content become conflict copies (§7). End-to-end encrypted vaults cannot be connected until Phase 4. Every request the plugin sends has a deadline (decision, #730): a server RPC the caller gave no timeout of its own fails as `UNAVAILABLE` once it has gone unanswered for 30 s, plus 1 s per 8 KiB (64 kbit/s) of blob bytes it carries (`PutBlobChunk`) or asks for (`DownloadBlob`, 1 MiB for a length of 0), and 10 minutes for `CommitBlob`, whose response waits for the server to compose the whole blob (§6.2); a request to the identity provider counts as unreachable after 30 s. The call's signal is aborted and a late response dropped, so a request whose packets are silently dropped shows `offline` and is retried like any other outage instead of leaving the session `syncing` (`protocol/client.ts` `withRequestTimeout`). The status bar shows `starting` (registering the device and opening the journal), `syncing`, `idle`, `offline` (the server or identity provider unreachable or not answering in time, or the identity provider answering with a 5xx), `error` (with the reason; this includes an identity provider whose answer is not a valid response, which points at a misconfiguration, #413), `signed out`, `sign-in needed`, `no vault connected`, or `waiting for another window` (a blocked journal upgrade), plus the number of pending local changes and of open conflicts: conflict copies that still exist, and conflicts without a copy whose remote revision still waits.
- **`vault-sync-server`** is a single Go binary. The server **never merges content**: it orders revisions, enforces optimistic concurrency, stores bytes, and fans out notifications. All merging happens on clients (this keeps the server compatible with end-to-end encryption).
- **`vault-sync export`** is a subcommand of the same binary, run as a separate Deployment/CronJob with its own credentials. It is the only component that may hold the escrow private key. It only reads PostgreSQL (its sessions are `default_transaction_read_only`) and S3. Each vault is exported as of its `head_seq` (every document's latest revision at or below it; tombstoned documents are left out) to `<out>/<vault-id>/<path>`, byte for byte; the directory is named by id because vault names are mutable, user-chosen and can collide (decision, #29). The tree is written to a staging directory beside `<out>` and swapped in atomically (`renameat2` `RENAME_EXCHANGE`), so an interrupted run leaves the previous export untouched. Every path is re-checked with the shared vault-relative rule (§6.2) and written through a handle confined to the vault directory, without following symbolic links. A document whose path cannot be placed in that tree goes to the vault's unplaced tree by document id, and every live document is listed in the vault's manifest (§3). A document whose content is missing or corrupt has no bytes in the export: it is listed in the manifest as `missing` and reported by id, and the run still swaps in its tree (decision, #52). The job prints a JSON summary and exits non-zero on any failure or missing content; it has no metrics endpoint. Until Phase 4, E2EE vaults are skipped. Details: `docs/export.md`.

### 4.1 Protocol transport (decision)

The API is defined in **protobuf** under `proto/` and served with **ConnectRPC** (Connect protocol over HTTP/1.1 + JSON or binary) — one schema generates both the Go server stubs and the TypeScript client. Realtime traffic (change notifications now, Yjs updates and awareness later) uses a **WebSocket** carrying protobuf-framed messages, because browsers/Electron cannot do client-streaming over fetch. The server sets CORS headers for Obsidian's app origins (`app://obsidian.md`, `capacitor://localhost`, `http://localhost`) and validates `Origin` on WebSocket upgrade.

Generated code is committed (`make generate` regenerates; CI fails on drift). Schema changes must stay backward compatible: `make lint` (and CI) runs `buf breaking` with the `FILE` rule set against `master`, and any deliberate exception is a narrowly scoped, temporary `ignore_only` entry in `buf.yaml` (`docs/testing/proto-compatibility.md`).

## 5. Data model

All identifiers are UUIDv7 unless stated. Every table below is scoped by `vault_id`; every query filters by it.

|---|---|---|

| `devices` | `id`, `user_id`, `name`, `public_key` (X25519), `last_seen`, `removed_at` | One per plugin install; at most 100 per user that are not removed (§9.2). A removed device keeps its row (`removed_at` set), since its revisions reference it. `last_seen` is the device's last commit, to within a minute. `registration_id` is the client-chosen idempotency key of the registration (§9.2), unique among a user's devices that are not removed. |
| `vaults` | `id`, `name`, `encryption` (`none` \| `e2ee`), `escrow` (bool), `head_seq`, `current_epoch`, `rotation_pending` | `head_seq` is the vault-wide change counter. `current_epoch` is the key epoch new revisions must use (0 while an E2EE vault has none, always 0 for plaintext vaults); `rotation_pending` asks an owner client to create the next epoch (§9.3). |

| `vault_invitations` | `id`, `vault_id`, `code_hash`, `role`, `created_by`, `created_at`, `expires_at` | Pending invitations (§9.2). Only the SHA-256 of the invite code is stored, unique. A row exists only while the invitation is pending: redeeming or revoking it deletes the row, and expired rows are pruned when an owner of the vault creates another invitation. |
| `documents` | `id`, `vault_id`, `kind` (`blob` \| `text` \| `yjs`), `head_rev_id`, `path_key`, `deleted` | Stable identity across renames. `deleted` mirrors the head revision's tombstone flag. `path_key` unique per vault among live (`deleted = false`) documents, enforced by a unique partial index on the SHA-256 digest of `path_key` (decision, #121): a btree entry holds at most 2704 bytes, while a `path_key` may be up to 8192, so the key itself cannot be indexed. A digest collision could only refuse a commit, never treat two paths as one, since nothing looks documents up by `path_key`. |
| `revisions` | `id`, `document_id`, `vault_id`, `seq`, `parent_rev_id`, `content_ref`, `path`, `deleted`, `device_id`, `created_at`, `anchor`, `epoch` | Append-only. `epoch` is the key epoch the revision is encrypted under (0 in plaintext vaults). `seq` is assigned from `vaults.head_seq` in the same transaction. `anchor` is a random UUID drawn by PostgreSQL (`gen_random_uuid()`) when the row is inserted, the cursor anchor of §6.1. `parent_rev_id` is the commit's base, the previous head, so a document's history is a linear chain; once retention purges a revision (§11), its child is re-parented onto the purged revision's parent, so `parent_rev_id` always names a revision that exists: the nearest retained ancestor, or none. |
| `blobs` | `vault_id`, `blob_id`, `size`, `state` (`uploading` \| `complete`), `released_at` | Content-addressed per vault; bytes live in S3 at `vaults/{vault_id}/blobs/{hex(blob_id)}`. A row is written only once the blob is complete; upload progress lives in `blob_uploads` (§6.2). `released_at` is when the blob was stored or a retention purge last removed a revision referencing it (§11); the collector clears it on a blob it finds referenced. |
| `blob_deletions` | `vault_id`, `blob_id` | Blobs whose row garbage collection deleted and whose S3 object it has not deleted yet (§11). |

The anchor checks of `ListChanges` accept a marker as they accept a live revision (§6.1), so a purge is never taken for a restore. | `retention_scans` | `keep_all`, `keep_daily`, `overrides`, `scanned_through` | At most one row: the policy, a digest of every per-vault override, and the start time of the last complete retention scan, which later scans start from (§11). |
| `vault_retention` | `vault_id` (PK), `keep_all`, `keep_daily`, `updated_at` | The operator's per-vault retention overrides (§11); a vault without a row follows the deployment-wide policy. |

An epoch key wrapped to one recipient (1 to 256 opaque bytes); unique per `(vault_id, epoch, recipient_kind, recipient_id)` and never replaced. No column holds an unwrapped key. |

**Paths.** A path is an attribute of a revision, not an identity. Uniqueness is enforced on `path_key`, a normalized form of the path: Unicode NFC, then case-folded, so that two clients cannot create paths that collide on case-insensitive (Windows, macOS, Android/iOS) filesystems. Precisely (decision): `normalize(path) = NFC(toCasefold(NFD(path)))` — Unicode canonical caseless matching (Unicode §3.13, D145) emitted in NFC, using **full, locale-independent** case folding (`CaseFolding.txt` statuses C and F; never the Turkic T mappings), so `Straße`/`STRASSE` collide, `İ` folds to `i̇` and dotless `ı` folds to itself. Full folding was chosen over simple folding because it catches strictly more collisions; locale independence keeps the key identical on every device. Separators, whitespace and dots are not altered and no validation happens here. Go (`internal/pathkey`) and TypeScript (`plugin/src/core/pathkey`) share one folding table generated from a vendored `CaseFolding.txt` and must agree on every vector in `testdata/paths/`. Normalization (NFD, NFC) likewise uses tables generated from the vendored `UnicodeData.txt` and `CompositionExclusions.txt`, never the runtime's own (`golang.org/x/text/unicode/norm`, `String.prototype.normalize`), whose Unicode version depends on the Go module or the Electron/WebView release (decision, #63): all tables come from one pinned Unicode version (17.0.0), so every client and the server compute the same key whatever Unicode version they run, also for characters added in recent versions. Both implementations pass that version's `NormalizationTest.txt` (`testdata/paths/`). Raising the pinned version changes the key only of paths with characters whose normalization or folding data changed, and needs a decision on keys already stored. For E2EE vaults the path itself is ciphertext and `path_key = HMAC-SHA256(path_key_secret, normalize(path))`, so the server can still enforce uniqueness without learning the path. **Files and folders (decision, #134).** Folders are implicit, so a live document's path cannot name the folder of another live document's: a file `notes` and a document `notes/c.md` cannot both exist on any filesystem. The server refuses a live document whose `path_key` has a folder (a proper prefix ending before a `/`) that is another live document's `path_key`, or is itself a folder of another live document's `path_key`. Because the comparison is on `path_key`, `Folder` collides with `folder/c.md` and `straße` with `STRASSE/a.md`. Tombstones never collide. Only `/` is a folder boundary here, and `path_key` keeps `\` as it is, so `a/b` and `a\b` do not share a `path_key` and `notes\c.md` (a document under `notes` on Windows) is not compared with `notes`. Instead no new path may contain `\` (§6.2, decision #191), so such pairs can only come from documents committed before that rule. Both directions are index probes, not scans: the live `path_key` digest index answers whether a folder of the new key is a live key, and a GIN index over the digests of every live key's folders (each digest covering the vault id) answers whether the new key is a folder of one. Each probe then compares the real `path_key` of the few rows whose digests matched, so a digest collision cannot refuse a commit (#428). There is no maximum folder depth (decision, #428): the deepest key the 8192-byte `path_key` limit allows (about 4095 folders) costs about 130 ms of database time per create or rename and up to about 4095 GIN entries per document, which the `path_key` limit and the per-user RPC concurrency limit (§12) already bound; a depth limit would make deep files permanently unsyncable, which the plugin has no way to show yet. The check starts with the release that added migration 0004: during a rolling upgrade, replicas of the previous release still accept file/folder collisions until every replica runs the new release (§12), and collisions committed before then stay (they remain editable and deletable). For E2EE vaults the `path_key` is an HMAC that cannot be split into folders, so the server cannot enforce this there; whether and how to enforce it in E2EE vaults is a Phase 4 decision.

**Content addressing.** For plaintext vaults `blob_id = SHA-256(content)`. For E2EE vaults `blob_id = HMAC-SHA256(blob_id_secret, plaintext)` (equality leaks only within a vault), and clients verify the id after decryption.

## 6. Sync protocol

### 6.1 Pull

`ListChanges(vault_id, since_seq, page_size)` returns revisions with `seq > since_seq` in `seq` order, paginated (the client passes the last `seq` it received as the next `since_seq` until `has_more` is false; the server caps `page_size` at 1000 and defaults it to 500, and also ends a page early where its encoding would exceed the send limit, so a page of long paths never fails as too large; every page holds at least one revision if one exists, and startup requires the send limit to fit a response with one maximum-size revision). A client's durable cursor is the highest `seq` it has fully applied to disk. A device's own acknowledged commit is already on its disk: when its `seq` is the one right after the cursor, the client records it and moves the cursor onto it, as a pull would (decision, #261). Seqs are gapless, so this skips nothing; if another device committed in between, the cursor stays and the next pull fetches that commit (and skips the device's own). **Cursor anchor (decision, #52/#155).** Every revision carries an `anchor`: 16 random bytes that the server draws when it stores the revision. Revision ids are chosen by clients, so a client can commit an id again after a restore, but no restored database reproduces a random anchor. The client stores the anchor of the revision at its cursor together with the cursor, in one journal write, and sends it as `since_anchor` with every `ListChanges` from a nonzero cursor. Before it reads the page, the server checks in the same snapshot that the vault holds a revision with exactly that `seq` and anchor, or a purge marker with them (§5, §11: retention purged that revision); the check is two lookups on `(vault_id, seq)` unique indexes, answered from PostgreSQL alone, so any replica gives the same answer. If neither exists, the response sets `diverged` and carries no revisions, and the client resyncs (§8). That happens when the database was restored to below the cursor, whatever `head_seq` is now; a purge never causes it (decision, #52/#488). A false negative cannot happen: no other revision has the anchor. **Own-commit anchor (decision, #52/#494).** A device's own acknowledged commit may lie above its cursor (#261), and a restore to between the two keeps the cursor's revision, so the cursor anchor alone misses it. The client therefore records the anchor of each of its acknowledged commits with the document's journal state, and while one lies above the cursor it also sends the `seq` and anchor of the highest such commit as `own_commit_seq` and `own_commit_anchor`. The server checks them in the same snapshot and the same way, a live revision or a purge marker, and sets `diverged` if neither exists, which also covers a restored `head_seq` still below that commit. The commits below it need no check: a restore that lost one of them lost it too. `own_commit_anchor` must be 16 bytes and `own_commit_seq` above `since_seq` and at most 2^63−1, both given or neither (`INVALID_ARGUMENT` otherwise). A server from before them ignores the fields (unknown protobuf fields), so against it the client keeps only the cursor check; an old client sends none. Revisions purged before purge markers existed (migration 0008), or by a release without them during a rolling upgrade, have no marker, and nor do those whose marker retention pruned past the marker horizon (§11): a device whose cursor sat on one gets one false-positive `diverged`, as every purge did before, and merges (§8). The check depends on no operator step and on no PostgreSQL timeline or system identifier, which change on an HA failover that loses no data. `since_anchor` must be empty or 16 bytes, and empty when `since_seq` is 0 (`INVALID_ARGUMENT` otherwise). A request without one (a client from before #155, or a cursor stored without an anchor) gets no check, as before. Clients pull on startup, on a realtime `subscribed{head_seq}` or `vault_changed{seq}` whose head is above the durable cursor (§6.4), and on a timer as a fallback.

### 6.2 Push (optimistic concurrency)

1. Upload content: `BeginBlob` → `PutBlobChunk`* → `CommitBlob`. Idempotent: an already-complete `blob_id` short-circuits. Resumable: `BeginBlob` reports the bytes already received, and chunks are appended strictly sequentially by offset. Chunks are at most the configured size (§3). The server verifies the content hash on commit for plaintext vaults. The client first looks the blob up with a zero-length `DownloadBlob` at offset `size` and, if the server already holds it, uploads nothing and does not read the local file (#386). Otherwise it reads the local content and checks its hash before `BeginBlob`, so content that changed or disappeared since the operation was recorded never opens a session: the blob is then only looked up with a zero-length `DownloadBlob` at offset `size`, and the operation is committed if the server already holds it and otherwise replaced by the file's current content (decision, #370). Downloads are ranged (`DownloadBlob(offset, length)`), each response bounded by the server; a client continues from the end of a shorter range than it asked for. Both limits hold in the request's codec (decision, #135): `BeginBlob` advertises, as `max_chunk_size`, the configured chunk size to binary clients and to JSON clients the largest chunk whose base64 encoding (four bytes for every three), plus 1 KiB of framing and a thousandth for gzip, fits the request limit; `DownloadBlob` caps a range at the same size, and a binary range also at the request limit less a thousandth and 512 bytes, so a gzip-compressed response of incompressible (for example E2EE) content still fits the send limit when the chunk size sits right at the limit (#161; with the default and smallest limits a binary range is still the chunk size). The size depends only on the request, so every replica agrees.

   Server-side details (decision): S3 multipart parts must be at least 5 MiB (except the last), which chunks below the 1 MiB body limit never are, so chunks are **staged objects plus a server-side compose**. Each accepted chunk is its own object under `vaults/{vault_id}/uploads/{upload_id}/`, its key unique to the write so a writer that lost a race for an offset never overwrites the accepted chunk; a chunk is accepted by a compare-and-set on the session's `received_size`, so concurrent uploaders of one blob share a session and a loser gets `FAILED_PRECONDITION` and resumes from `BeginBlob`. Every chunk but the last is at least 64 KiB (or the maximum chunk size for the request's codec, if smaller), bounding the objects per upload. `CommitBlob` streams the staged chunks in order into the blob's object, with one `PutObject` up to 8 MiB and a multipart upload of 8 MiB parts above that, hashing as it goes; the object is written or its multipart upload completed only after the hash matched, and the `blobs` row is written only after that, so a mismatching upload never becomes visible and its session is discarded. Bounds: the maximum chunk size plus 1 KiB of framing must fit the maximum request body (checked at startup), the Connect send limit equals the request limit, a blob is at most the configured maximum (at most 80 GiB, S3's 10,000 parts of 8 MiB), and a vault has a bounded number of sessions in progress (`VAULT_SYNC_BLOB_MAX_UPLOADS_PER_VAULT`). There is no RPC to abandon a session, and a client whose upload was interrupted and whose file then changed leaves its session behind, so a `BeginBlob` that would create a session in a vault at the limit first reclaims that vault's sessions idle for longer than `VAULT_SYNC_BLOB_UPLOAD_RECLAIM_IDLE` (default 10 minutes, at least 10 minutes, at most the upload TTL), and refuses with `RESOURCE_EXHAUSTED` only if none was reclaimed (decision, #370). An upload in progress records activity on every chunk, so a session idle that long has been abandoned. Reclaiming finishes the sessions in the same transaction, under the same vault row lock, that counts them, so concurrent `BeginBlob`s on any instance reclaim each session once and never overshoot the limit; a chunk or commit racing it either records its activity first (and the session is kept) or finds the session finished. A reclaimed session refuses further chunks (`FAILED_PRECONDITION`) and its commit (`NOT_FOUND`), on which the client starts the upload again from `BeginBlob` with a new session, its operation still pending; the cleanup below removes its staged objects and row like any finished session's. Sessions idle for longer than the upload TTL are reaped by a periodic, bounded cleanup that deletes their staged objects and then the session, and aborts multipart uploads older than the TTL (an interrupted commit's are otherwise invisible and leak storage) unless their blob has a session active within the TTL. Every server instance runs the cleanup at the same time, so every step is idempotent: a session is claimed atomically, and an upload or object another instance already removed counts as removed. A commit records session activity after every 8 MiB part it composes (and at least every minute while it waits for a compose slot), so a commit in progress, on any instance, is never reaped however long it takes, unless composing one part takes longer than the TTL. A commit whose session was finished or reaped meanwhile, on any instance, returns `FAILED_PRECONDITION` and the client uploads again, whether composing noticed that when recording activity or by failing to read a staged chunk the cleanup deleted: the cleanup claims a session in PostgreSQL before deleting any of its objects, so a failed commit checks the session there; a staged chunk missing from a session still active is `INTERNAL`; upload sessions hold no per-instance state, so chunks and the commit may go to different instances, and a commit interrupted by an instance dying is retried to success on another. Compose slots (decision, #367): each replica composes at most 4 blobs at once, and at most 2 of them for one user, so one user can never hold every slot and another user's commit always finds one; a user's further commits wait for that user's slots, holding none of the replica's. A `CommitBlob` of a blob whose commit is already in progress on the same replica waits for that commit, holding none of the replica's slots, and then returns its result (the blob complete, or the same failure the session's state implies), so duplicates (a retry of a slow commit, another device committing the same content, or a client repeating it) neither compose the blob again nor hold a replica slot. A commit takes one of its user's slots before it claims the blob, so a commit queued behind its own user's other compositions never keeps another user's commit of the same blob waiting behind that queue (#388). Both limits are in-process and per replica: no state is shared between replicas, and duplicates sent to different replicas can still each compose the blob once.
2. `CommitRevision(document_id, revision_id, base_rev_id, kind, content_ref, path, path_key, deleted, device_id)`. The server accepts only if `base_rev_id` equals the document's current head (or the document is new and `base_rev_id` is empty). It assigns `seq`, advances `head_seq`, and broadcasts `vault_changed`. Document and revision ids are client-generated UUIDv7s; retrying a commit with the same `revision_id` and identical fields returns the already-committed revision, so a lost response does not turn into a spurious head-moved conflict. `path_key` is sent only for E2EE vaults (§5); for plaintext vaults the server derives it from `path`.

   Server-side details (decision): a commit is one PostgreSQL transaction that first locks the vault row, so commits to one vault are serialized by the database across every server replica, with no per-process state: `seq` comes from `UPDATE vaults SET head_seq = head_seq + 1 … RETURNING` in that transaction, so it is gapless, and a revision commits (becomes visible to `ListChanges`) only after every lower `seq`, so a cursor never skips one. Within the transaction the checks run in this order: the device belongs to the caller and is not removed (`NOT_FOUND` with an `ErrorDetail` of reason `ERROR_REASON_DEVICE_NOT_FOUND`, #590); an existing revision with this `revision_id` in this vault is returned if its fields are identical (a base that retention has since purged matches the re-parented revision, §11; a `device_id` other than the revision's matches only if the revision's device is the caller's and removed, because that is the same installation retrying a commit whose response was lost after it registered again, decision #590) and is `INVALID_ARGUMENT` otherwise — **before** the head comparison, so a retry whose first attempt was applied still succeeds after other commits moved the head; the head comparison (`FAILED_PRECONDITION` carrying the document, with its current `head_rev_id`, as a `Document` error detail; also `FAILED_PRECONDITION` if a base is given for a document that does not exist in the vault); the kind matches the document's; the content is a `complete` blob in the same vault whose stored size equals `content_ref.size` (`FAILED_PRECONDITION` if not complete, `INVALID_ARGUMENT` on a size mismatch; the stored size is what is ever returned). The document row's `head_rev_id`, `path_key` and `deleted` are updated in the same transaction as the revision insert, so `deleted` always mirrors the head and the live `path_key` index is exact; a collision on it is `ALREADY_EXISTS`. Then, if the revision is live and its `path_key` is new to the document (or the document was a tombstone), a file/folder collision with another live document (§5) is also `ALREADY_EXISTS`; this check runs under the vault row lock, so two commits that would each complete a collision, on any replicas, are serialized and the second is refused. A revision that keeps its document's live `path_key` (an edit) or deletes it is never refused for this, so a collision committed before the rule existed never blocks an edit or a delete. Client-generated ids already used in another vault are `INVALID_ARGUMENT`; all lookups are scoped to the authorized vault, so another vault's ids are otherwise simply not found. Plaintext paths are at most 4096 bytes of UTF-8 without control characters (Unicode category `Cc`), vault-relative, and at most 8192 bytes once normalized. Vault-relative is defined for every supported client platform (decision): `/` and `\` are both separators; the path must not start with a separator (which also rules out UNC, `\\?\` and `\\.\` prefixes) or with an ASCII letter and a colon (a drive prefix such as `C:`, `C:\x` or the drive-relative `C:x`); and no segment may be empty or consist only of dots and spaces (`.`, `..`, and forms such as `.. ` or `...` that Windows reduces to them). Names that are merely unmaterializable on Windows (reserved device names such as `CON.md`, a colon anywhere but a leading drive prefix, trailing dots or spaces on other names) are accepted; the client handles them. Look-alike characters are not separators or dots (decision, #148): U+FF0F, U+FF3C, U+2215 and U+29F5 are ordinary characters, and a segment of fullwidth full stops (U+FF0E) is an ordinary name. Windows' wide APIs, which Electron and Node use, do not treat them as separators, and `path_key` uses NFC, not NFKC. A path a commit gives a document must also contain no `\` at all (decision, #191): Windows reads it as a separator and other platforms as part of a name, so `a/b` and `a\b`, or a file `notes` and a document `notes\c.md`, would otherwise both be live while naming one file on Windows. Nor may it start with any single code point followed by `:` (decision, #148), such as `1:x.md` or `é:x.md`: Win32 reads any first character followed by a colon as a drive, and drives that are not letters can be created with `subst`. A path that is vault-relative but breaks either rule is accepted only as the unchanged path of the document's live head, so a document committed before the rules can still be edited and deleted in place, or renamed to a valid path; creating a document there, moving one there, or bringing a tombstone back there is `INVALID_ARGUMENT` (checked under the document's lock in the commit transaction). No stored path is migrated, and such documents stay readable and exportable. Clients apply every one of these path rules before committing (`pathProblem` in `plugin/src/core/vaultpath`, decision #100): a local file at a path the server would refuse is never uploaded or committed, on any push, stays on disk, untouched, with its operation pending, and every push reports it as rejected with the rule it breaks, until the user renames or removes it (§8). Go (`internal/vaultpath`: `Check`, and `CheckNew` for the `\` and drive-prefix rules, used by `CommitRevision`) and TypeScript (`isVaultRelativePath` and `isNewVaultPath` in `plugin/src/core/vaultpath`) must agree on every vector in `testdata/paths/validity.json` (its `valid` and `new` fields). They must also agree on the length and character-set rule (Go `CheckText`, TypeScript `isPathText`) for every vector in `testdata/paths/text.json`, and `CommitRevision` and TypeScript's `fitsPathKeyLimit` on the normalized length rule for every vector in `testdata/paths/key.json` (a path can grow when normalized: U+1D160 decomposes into three code points that NFC does not recompose, so 683 of them, 2732 bytes, have an 8196-byte `path_key`). A client must apply both rules to every path it receives before touching its disk, including E2EE paths after decryption, which the server cannot check. It must apply them to the exact string handed to the file system: the Obsidian vault and config folder adapters refuse any path that Obsidian's `normalizePath` would change (#148). Obsidian's `DataAdapter` normalizes every path it is given, and `normalizePath` turns, for example, the accepted `..` followed by U+00A0 into the traversal segment `.. `. A path that breaks the rule is `INVALID_ARGUMENT` and nothing is written; a path or `path_key` the database refuses (empty, over its bound, or text it cannot store) is `INVALID_ARGUMENT`, never `INTERNAL`. Until Phase 4, commits to E2EE vaults are `FAILED_PRECONDITION` (§9.3). The commit transaction also queues a PostgreSQL `NOTIFY` on channel `vault_changed` (payload `<vault_id>:<seq>`), which PostgreSQL delivers to every replica exactly when, and only if, the transaction commits; an idempotent retry notifies nothing (§6.4).
3. On `FAILED_PRECONDITION` (head moved), the client pulls the new head, merges (§7) against the common base, and retries with the new head as base.

A revision is **acknowledged** only when `CommitRevision` returns success. Principle 1 applies from that moment.

### 6.3 Renames, deletes, creates

- **Rename** is a revision with a new `path` and the same `content_ref`. A folder rename is one such revision per file in the folder: no content is uploaded or downloaded again.
- **Delete** is a revision with `deleted = true` (tombstone). Its content stays reachable through history.
- **Create** races: if two clients create documents whose `path_key` collides, the second commit fails with `ALREADY_EXISTS`; that client renames its document to `<name> (conflict <device> <date>).<ext>` and commits again.
- **File/folder** collisions (§5) are `ALREADY_EXISTS` too, for creates, renames and resurrections alike: a live document cannot be committed at the path of another live document's folder, or under a path another live document holds as a file. Renaming the file name is enough when the document's own path is the folder of another document (`notes` becomes `notes (conflict <device> <date>)`). When the document lies under another document's file, renaming its file name does not help (`notes/c (conflict …).md` is still under `notes`); the client must move it out of that folder, for example by applying the conflict suffix to the colliding folder segment (`notes (conflict <device> <date>)/c.md`).
- Concurrent **rename vs. edit** of the same document merges cleanly: path and content are independent fields of the merge.
- Concurrent **delete vs. edit**: the edit wins (the document is resurrected with the edited content) — never lose an edit to a delete.
- Concurrent **delete vs. rename**: a rename, like an edit, wins over the delete, whichever commit reaches the server first (decision, #52, revised for refactor step R5; design PO-7, PO-9). If the rename is committed first, the delete is refused (head moved) and the deleting client's merge keeps the rename: the document stays under its own id at its new path, and the delete is dropped. If the delete is committed first, the renaming client's pull merges it with the unpushed rename, which the document's binding records: the document comes back on its tombstone under its own id at its new path, with any edit made. Either way nothing is lost, and the delete is not undone at the old path.

### 6.4 Realtime channel

One WebSocket per device (`GET /v1/realtime`), multiplexing subscriptions to any number of the user's vaults up to a server cap (`GetServerInfo.max_realtime_subscriptions`), authenticated with the same bearer token. Each binary WebSocket message is one protobuf frame (`ClientFrame` / `ServerFrame` in `proto/vaultsync/v1/realtime.proto`, each a `oneof` envelope). Client → server: `subscribe{vault_id}`, `unsubscribe{vault_id}`. Server → client: `subscribed{vault_id, head_seq}`, `vault_changed{vault_id, seq}`, `error`, and later membership/key-epoch changes. Field numbers 100–199 of both envelopes are reserved for the Phase 5 Yjs frames. Phase 5 adds Yjs subscribe/update/awareness messages multiplexed by `document_id`. The channel is a latency optimization only; correctness never depends on receiving a notification.

Server-side details (decision, #52):

- **Upgrade.** The client offers the subprotocols `vaultsync.v1` and `vaultsync.bearer.<access token>` (browsers cannot set headers on a WebSocket request; non-browser clients may send `Authorization: Bearer` instead, but not both). The server validates `Origin` against the CORS allow-list (an absent `Origin` is allowed for non-browser clients), authenticates the token with the RPC authenticator, and echoes only `vaultsync.v1`. It refuses the upgrade with 403 (origin), 401 (missing or invalid token), 400 (no `vaultsync.v1`), 429 (too many connections for the user) or 503 (instance full or draining). The token never appears in a URL, and the `Sec-WebSocket-Protocol` header is never logged.
- **Authorization.** Every `subscribe` resolves the caller's `vault_members` role; a non-member and a vault that does not exist get the same non-fatal `NOT_FOUND` error frame. Membership is checked again before every delivery, in one query per vault for up to 1,000 subscribed users (more take one query per 1,000): a removed member's subscription ends with an unsolicited `NOT_FOUND` error frame naming the vault, and no further notifications for it are sent. Removing a member (`RemoveMember`, `LeaveVault`; §9.2) queues a `vault_changed` notification at the vault's current `head_seq` in the same transaction, so every replica runs that check at once and the removed member's subscriptions end without waiting for a commit; the other subscribers receive a head they already have, which starts no pull (#33). If the check fails (a database error), that notification is not sent and the subscription is kept; clients' periodic pull catches up.
- **Token expiry.** There is no in-band refresh. When the access token's `exp` passes, the server sends a fatal `UNAUTHENTICATED` error frame and closes (1008); the client reconnects with a fresh token and re-subscribes.
- **Fan-out.** Each replica holds one PostgreSQL connection that `LISTEN`s on `vault_changed` and delivers each notification to its local subscribers, so a commit on any replica reaches subscribers on every replica. Undelivered notifications of one vault are coalesced to the newest `seq`. If the listening connection is lost the replica reconnects with jittered backoff and then sends every locally subscribed vault's current `head_seq`, so commits made meanwhile are not missed. Subscriptions are per-connection state only: a client reconnecting to another replica re-subscribes and pulls from its cursor.
- **Bounds.** Inbound frames are at most 4 KiB (larger closes with 1009); the inbound rate is 20 frames per second with a burst of the subscription cap plus 32 (excess is a fatal `RESOURCE_EXHAUSTED`); subscriptions per connection, connections per user and connections per replica are capped (`docs/configuration.md`). Each connection's send queue is bounded; a client too slow to drain it, or that does not answer pings, is disconnected rather than buffered. Malformed or text frames are a fatal `INVALID_ARGUMENT`.
- **Drain.** On shutdown every socket is closed with 1001 ("going away"); clients reconnect with backoff and jitter.

Client-side details (decision, #193):

- **Token.** The plugin offers the token only as the `vaultsync.bearer.` subprotocol, never in the URL, and never logs it. It takes the token from its token manager, which refreshes it ahead of expiry. On the fatal `UNAUTHENTICATED` frame it invalidates that token in the token manager, so the reconnect carries a freshly refreshed one, with no user interaction.
- **Pull.** It pulls from its durable cursor after every `subscribed` whose `head_seq` is above the durable cursor (notifications sent while it was not subscribed are gone, so the head tells it whether it missed any) and on every `vault_changed` of its vault whose `seq` is above the durable cursor (decision, #261). This is safe because the server registers the subscription before it reads the head and reports the larger of that head and any `seq` announced meanwhile: every commit above the reported `head_seq` reaches the client as a `vault_changed`, and a cursor at or above `head_seq` has nothing to fetch. So a subscribe that completes after the startup push, with nothing new, starts no pull and leaves the status idle. A skipped pull is not a successful sync either: it keeps an earlier `offline` or `error` status. The server notifies the committing device too; since an acknowledged commit that is the next `seq` moves the cursor onto it (§6.1), a device's own commit's notification starts no pull, and its status stays idle. The cursor is checked when the notification arrives and again when the pull's turn comes after a running push, so a notification that overtakes its commit's response does not pull either. A notification above the cursor always pulls, including one coalesced from another device's commit and the device's own (the newest `seq` is above the cursor while the other commit is not applied). Pulls never overlap: `subscribed` and `vault_changed` frames that arrive during a pull cause one more pull after it, if the cursor is below the highest head among them. The pull timer runs whether or not the channel is up, so a server whose history was restored to below the cursor (whose `subscribed` and notifications then announce heads at or below the cursor, and start no pull) is still found by the timer's pull.
- **Reconnect.** Every close, or a failed upgrade, reconnects after a delay with equal jitter: half of a ceiling that starts at 1 s and doubles with each consecutive failure up to 60 s, plus a uniformly random part of the other half. It starts over only once a subscription has stayed up for 30 s, so a server that subscribes and then closes at once (a replica that keeps draining, say) still sees the delay grow (#413). A browser does not expose a refused upgrade's HTTP status (401, 429, 503 all look like a 1006 close), so these back off alike; a token the server no longer accepts is also invalidated by the next RPC that fails as unauthenticated. A non-fatal error frame for the vault (`NOT_FOUND` after a membership change, say) drops the connection and retries with the same backoff.

## 7. Merge rules (client side)

Classification is by extension only, never by content: the default text extensions are `md`, `txt`, `css` and `js`, and every other file, UTF-8 text or not (`.json`, `.csv`, `.ts`, a file with no extension), is a `blob`. The text extensions are an option of each engine (see Engine details below); the plugin has no setting for them.

| Kind | Default for | Concurrent-edit behavior |
|---|---|---|
| `text` | `.md`, `.txt`, `.css`, `.js` | 3-way merge (`base`, `local`, `remote`). Non-overlapping changes merge silently. Overlapping changes: remote wins in place, and the local version is written as a conflict copy next to it. Never inject conflict markers into the note. |
| `blob` | everything else (images, PDFs, `.json`, `.canvas` until a JSON merge exists) | Remote wins in place; local version becomes a conflict copy. |
| `yjs` | `.md` in vaults with live editing enabled (Phase 5) | CRDT merge; no conflicts. |

Conflict copies are ordinary documents and sync like any other file. Every conflict is also logged to the client's conflict view.

**Path ownership.** Which file is which document, who keeps a path, and how a multi-step change survives a crash follow the engine's path-ownership model, `docs/design/engine-path-ownership.md` (the *design*), cited here by rule (PO-1 to PO-14, design §4.9) and invariant (INV-1 to INV-10, §5.1). Two path equivalences apply (PO-10): the *path key* (§5) decides what the server holds apart and which copy names are free; the platform's *file key* (case on Windows and Android, case and NFC/NFD on macOS, exact on Linux) decides which spellings are one file here. Neither implies the other: `Straße.md`/`STRASSE.md` are two files with one key on NTFS or APFS, `ı.md`/`I.md` one file with two.

Engine details (decision, #18):

- **Classification.** A document's kind is chosen at creation from its extension (`classifyByExtensions`, `plugin/src/core/engine/remote.ts`) and never changes. A `text` document is merged as a blob if any of its three versions is not valid UTF-8.
- **Text merge.** The default hook (`threeWayMerge`) is the line-level merge of editor-safe writes (§8; `plugin/src/core/merge/text-merge.ts`, a Myers diff of each side against the base). Changes overlap if they touch the same base line or both insert at one place; identical changes count once; adjacent lines merge; if only one side changed, its bytes are taken. Line-ending style (CRLF or LF, by majority) and the final newline are each merged as one field, the changing side winning (local if both), so neither conflicts with an edit. If neither side changed the style, lines keep their own terminators unless that overlaps or would join lines (#176, #750). A merge never joins two lines. An emptied note has no last line, so it never counts as removing the final newline.
- **Content and path are merged apart (PO-9).** The hook merges content; the engine picks the path (design §4.7). An edit wins over a concurrent delete either way (§6.3). A local rename wins over a remote edit, rename or earlier delete: the document stays under its own id at the user's path with any edit, also when another device's re-create brings it back first (#790). A remote rename meets a local edit at the remote path (a case-only move renames the same file, #343). A deleted file holds no path. For a document bound on its tombstone only the user's move counts; a file the engine moved aside takes the server's path (#802).
- **When a copy is made.** For overlapping edits, concurrent blob edits, two versions with no common base (a remote create or rename onto an untracked file with other bytes, `concurrent-create`; a document brought back on both sides), and concurrent edits whose base retention purged (`base-purged`, §11). A local version still at the purged base takes a feed revision of an undiverged server, which descends from it, with any local rename (#719); a resync's head, or a revision deferred behind one, still gets a copy. The remote version stays in place; the local version goes to the copy.
- **Copy names (PO-14).** `<name> (conflict <device> <date>).<ext>` in the same folder. `<device>` is the device name with whitespace runs made one space; control characters, `/ \ : * ? " < > |`, `(` and `)` made `-`; trimmed, cut to 40 characters, `device` if empty. `<date>` is UTC `YYYY-MM-DD HHmmss`. A taken name gets a counter (`… HHmmss 2)`). One namer (`freeCopyName`) chooses every copy and `path-taken` name: a name is taken if it collides by path key with any claim (file, folder, document, deferred revision, pending operation, logged copy) or by file key with a vault file (#243, #596). Pending operations and logged copies hold names, not folders; only claims the operation vacates are exempt (#299, #319), and folders of the result's path never block (#352). If a claim is named like a folder of the copy's path, the outermost such folder gets the suffix (`Notes (conflict <device> <date>)/C.md`, #359). Names are shortened from the end of `<name>` until they fit 255 bytes, §6.2's limits and the platform. If none fits, nothing is written: the local version stays, the revision stays deferred, and the conflict is logged without a copy (#100).
- **Who keeps a path (PO-4, PO-11).** The server's assignment wins the path; the loser moves and keeps its bytes. When a revision of D needs a path another file holds (by file key, folders included): an untracked file with D's bytes becomes D's file; one with other bytes is kept as a `concurrent-create` copy and pushed as new; another document E that a local move put there moves on to a `path-taken` copy under its own id (rule W(a)); E at its own synced path, which the server moved away, follows its newest revision the pull has, and only if it is blocked is its file detached, renamed to a copy and pushed as new (W(b)). A detach waits until the pull has read the whole feed (#792, #803); meanwhile D's revision waits as `path-conflict`. Rule W moves files by renaming them; a merge removes a file in the way only after writing its copy. A document whose path is one file with another live document's under the file key but not the path key is `unmaterializable(alias)` (§8). A blocked document (`unmaterializable`, `out-of-scope`, `too-large`) keeps its file and local changes while no server claim needs the path.
- **Refused commits.** A create or rename refused with `ALREADY_EXISTS` (§6.3) pulls first; if the operation is still live, the document moves to a free copy name under its own id (`path-taken`, W(a), folder rule included) and is committed there, and revisions and merges that waited on the path are retried in the same push (#307). Refused again with no claim explaining it, it stays pending and rejected (`path-taken`), so the engine never hops between names; a document just pulled into the name explains it, and the next name is taken (#243). A refused operation whose file is gone is dropped. A revision deferred for a path in the way is retried once it is free: after such a move, and once per start.
- **Conflict log.** The journal records every conflict (`ConflictRecord`): the document, the path, the reason (`overlapping-edits`, `binary`, `concurrent-create`, `path-taken`, `base-purged`), the copy's path and content hash, the remote revision, and the time. It is a UI log: a merge or a move is journaled as an intent (§8, PO-8), so a copy interrupted by a crash is finished under its recorded name and never written twice, and the record is logged when the step finishes.
- **Conflict view (decision, #27).** A read-only projection of the journal, never pruned (so copy names are never reused). `openConflicts` (`engine/conflicts.ts`) lists open conflicts, newest first: one with a copy is open while the copy exists (deleting or renaming it, on any device, resolves it); one without, while the document still waits. Each entry links the version in place, at the document's current path, and the copy, with a side-by-side comparison. The view also lists unmaterializable, too-large and not-synced documents (§8). The status bar's count uses the same rule.

## 8. Client durability

- **Journal (decision, #21; design §4.1).** Per document the journal holds its *base* (the last server revision it agreed on), its *binding* (which local file is the document, or why it has none: `user-deleted`, `released`, `never`), at most one *outbox* operation (sealed before it is first sent), and a *deferral* (the newest revision not applied, with its blocker); plus open *intents*, the conflict log and the cursor with its anchor. `IndexedDbJournal` (`plugin/src/core/journal/indexeddb.ts`) is handed its `IDBFactory`, so Node runs it on `fake-indexeddb`. Every method is one `strict`-durability transaction (`transact` spans stores), resolved only once complete. Migrations are append-only and carry every record forward; a failed one leaves the old version with its data, and a newer schema is refused (`JournalVersionError`), never deleted or downgraded. A connection closes when another upgrades the schema; a blocked upgrade is reported (`onBlocked`, #184). `openVaultJournal` opens one database per local vault (`app.appId`) and server vault (id, URL origin and path; never credentials, query or fragment), and none without a vault id. The journal is not encrypted at rest.
- **Identity follows the file (PO-1, PO-2, PO-10).** Only the binding says which file is a document. A vault event changes it in one journal transaction before it counts as handled: a rename moves the binding (renames chain; a case-only or respelled rename of the same file is a rename), a delete makes the document `user-deleted`, and a file no binding names is *untracked* and pushed as a new document. So a file created at a path a document's file left is a new document (#254, #303), and a file another note's rename brought onto a synced path is never that path's document's. Matching names or contents moves identity only as the start-up scan, rule W's adoption and tombstone re-creation allow (INV-3). A folder rename is one rename event per file (#19). A folder has one spelling on disk: the engine respells file names, never folders, so the server's `Notes/x.md` is held as `notes/x.md` when `notes/` exists (#737). A window remains (#325): a pull does not wait for queued events, so a rename handled after a pull wrote another document at its old path counts as that document's; nothing is lost.
- **Start-up scan (PO-3).** Events are lost while Obsidian is closed or killed, and its startup `create` storm is ignored (no events before the layout is ready). At start, a document whose bound file is missing is bound to the one file holding exactly the content the engine last read or wrote there, of its kind and in scope, when the match is one-to-one; that file may be untracked or another document's file no longer holding its own content, which document is then deleted (#793). Pasting the content into that file in place while deleting the missing file looks the same and is taken for the move: the other document is deleted, its previous content kept in its history (#827). Otherwise the document is `user-deleted`. So an offline rename is a rename unless the content changed or is ambiguous. A binding takes the one other spelling the vault lists for its file, except in folders alone (#737).
- **Never overwrite unsynced local edits; conditional writes (PO-5, decision #163).** The engine overwrites or deletes only the bound file of the document it applies, and only while it holds the content the engine last read: every write and delete names that hash, or "no file", as a `VaultAdapter` precondition, refused (`VaultError` `changed`) with nothing changed if it fails. A refused apply goes to the merge path; a refused merge result defers the revision. An untracked file is never deleted unless its copy is written. The Obsidian adapter checks text inside the `Vault.process` call that writes it; one read's window remains for binary writes, deletes and plain writes on mobile. Renames carry no precondition.
- **Content hashes, never mtimes,** detect changes. A merge's base content is fetched by `rev_id` when not cached.
- **Crash safety (PO-8, INV-7).** A change touching the disk and more than one journal row is an *intent* (`apply`, `merge`, `displace`, `detach`, `commit`, `resync`; design §4.4): recorded first, its disk steps precondition-checked, finished by one transaction that also moves the cursor for a feed revision. Every start, pull and push first recovers open intents: done steps count, missing ones are redone, and a user change meanwhile drops the intent so the change is merged again; a copy already written stays and is pushed (#345). A crash at any write ends where no crash would.
- **Echo suppression (INV-10).** Each engine write, rename and delete is recorded (spelling the vault holds, content hash) before it is made and dropped if it fails, so its events are not taken for user changes. A matching event also drops older records at that path (#156). Events match by file key, never path key (#380, #737), and a create or modify is an echo only if the file holds what the engine wrote. In doubt, it is a user change; a lost record costs a no-op push round.
- **Editor-safe writes (decision, #24).** A remote write to a UTF-8 file open in a Markdown editor is a line-level three-way merge inside `Vault.process`, with the disk text (checked to be the base) as base, the editor buffer as local and the remote content as remote. Only the remote changes reach the editor, as one transaction, so cursor, selection and unsaved keystrokes survive; the disk gets the same text (the user's edit, if keystrokes were unsaved). An overlap with an unsaved change makes the adapter save the editor and reject the write, so the next pull merges the saved edit. CRLF files are written only when nothing is unsaved. A file open in another editing view is written only if every such view is a text file view and all equal the disk, or exactly one is a canvas whose unsaved changes merge three-way with the remote JSON Canvas by node and edge `id` (decision, #418; refused for conflicting changes, a dangling edge, a side that is not a canvas, or JSON that parsing would rewrite); each view is then given the written content as its data and `lastSavedData` (Obsidian 1.14.4), so the reload that follows replaces nothing. Otherwise the adapter saves the views and rejects the write. Read-only viewers (images, PDFs, audio, video) are written as usual; a text file view registered under their view types is not taken for one.
- **Editor-safe deletes (decision, #181).** A delete never discards what an open view has not saved. The adapter compares the file with its open text views before `Vault.delete`; if one differs, it saves the view and refuses the delete (`changed`, or `UnsavedEditsError` without a precondition), so the saved text is a local edit: it wins over a remote delete, and a file to be removed after its copy was written stays until the next merge (two copies at worst; nothing is lost).
- **Platform path rules (decision, #20).** Paths the platform cannot hold are never silently dropped. `pathRules` names the platform (`posix` for Linux, `android` for Android's shared storage, `macos` for macOS and iOS, `windows`) and, where known, the vault's absolute path; `unmaterializableReason` (`plugin/src/core/vaultpath/platform.ts`) applies them. Everywhere a name is at most 255 bytes of UTF-8 (255 UTF-16 units on Windows) without NUL, and the absolute path is below PATH_MAX (4096 bytes; 1024 on macOS) or Windows' MAX_PATH (260 UTF-16 units). Windows also forbids `<>:"|?*`, `\` (#191), control characters, reserved device names (`CON`, `PRN`, `AUX`, `NUL`, `COM0`–`COM9`, `LPT0`–`LPT9`, their superscript-digit forms, `CONIN$`, `CONOUT$`, in any case, alone or before an extension) and names ending in a dot or space; Android's storage refuses `"*:<>?\|` (#418). `windows`, `macos` and `android` are case-insensitive with §7's file keys (#544). An OS error saying a path cannot exist (`ENAMETOOLONG`, `EINVAL`, `EILSEQ`, Windows' `ENOENT` under an existing parent, Android's `FILE_NOTCREATED`, #705) is `VaultError` `unmaterializable` (`refused-by-vault`, retried each start). A revision whose path or merge result's path breaks the rules, or the second of two live documents that are one file here (`alias`, #736), is deferred `unmaterializable`: a blocker (PO-11) that touches no file, claims no path and never makes the client rename the document on the server. The document's local changes are not pushed, and its file stays, with them, until a server claim needs the path and rule W(b) detaches it (§7). A later revision the platform can hold applies, merged with any kept change; a deferral the rules allow again is retried once per start. `unmaterializable()` lists them for the conflict view. File keys are checked against `testdata/paths/vectors.json`.
- **Pull and apply (decision, #16).** The feed is applied in `seq` order, and each revision's step moves the cursor in its own final transaction, so it never passes an effect not yet durable. Content is verified (size; SHA-256 in plaintext vaults) first. `decideRemote` (`plugin/src/core/engine/decide.ts`) then decides: this device's own commit is recorded without touching the disk (another device's re-create of a shared document id is never taken for it, #816); a blocker defers the revision; the path claim settles who keeps the path (§7); a *clean* document (bound file at the base, nothing to push) is applied; a *dirty* one (changed or missing file, pending operation) goes to the merge hook with base, local and remote. A base that is a tombstone or that retention purged (`NOT_FOUND`) has no content, so the merge keeps both versions (decision #26). A hook may defer (`local-changes`): the cursor moves on, later revisions replace the deferral, and every push retries it. A path that fails §6.2's vault-relative rule or is not UTF-8, or that the vault refuses, is deferred (`invalid-path`, `path-conflict`) without touching the disk; `deferredDocuments` (`engine/deferred.ts`) lists these, and `out-of-scope` deferrals whose document still has a file here (#417), under "Files that are not synced".
- **Download cap (decision, #316).** Downloads are held in memory whole, so `maxDownloadBytes` caps them (1 GiB on desktop and by default, 256 MiB when `Platform.isMobile`; not a user setting). A revision above the cap (equal is applied) is deferred `too-large`, a blocker: nothing is downloaded and the cursor moves on; a resync defers such a head the same way, never merging it. A later revision within the cap, or a larger cap at a start, applies. `SyncEngine.tooLarge()` lists them. Other repeating errors fail the pull at that revision.
- **Divergence (decision, #16; PO-12, design §4.6).** A `head_seq` below the cursor, or a `diverged` anchor check (§6.1, #155), means a restore lost history this device applied; a retention purge passes the anchor check through its marker and changes no claim (§11). The engine resyncs from the feed's heads through `decideRemote`, every known document forced dirty, so nothing local is overwritten or deleted. A head this device synced before its base (proven by the journal's `prior` revisions): the head becomes the base and the next push commits this device's version, with no copy (#700). Any other head: merged, or a `base-purged` copy. A document the server lacks keeps its file, gets `seq` 0, and is re-created by the next push under its own id, at a copy name if its path is taken (#700, #801); another device's re-create of it is merged (#816). An operation on a base the server lacks, a lost tombstone's revival included, is sent as a create under its own id, and a delete of such a document is dropped (#829). A lost document with no file and nothing to send is forgotten with its deferral, and any other deferral the server no longer has is dropped unless it is `local-changes` (#768, #784, #810, #838). Only then is the cursor reset, with its anchor; an interrupted resync runs again. A server from before purge markers reports a purge at the cursor as divergence: the resync loses nothing, but keeps a note another device deleted, which the next push brings back, until the server is upgraded (#480).
- **Push (decision, #17; `engine/push-plan.ts`).** Every push recovers intents and pulls first. It resumes the outbox and derives at most one operation per document from base and binding: a `user-deleted` document is deleted; one bound at another spelling than its synced path is renamed there, with its content; a changed bound file is an edit; a document bound on a tombstone is committed live; an untracked file is a create. A file at a pulled tombstone's path becomes that document's revision on its tombstone (decision #17) unless this device's user deleted the document since or it has an operation pending (PO-13). It reads changed paths, and the whole vault on a start's first push. Deletes go first, then renames and edits in dependency order, then creates; a swap commits one rename at a copy path. A document with an operation pending, or held by a merge or blocker, waits with its paths, which later pushes look at again (#167). A push commits no operation whose file changed or moved since it looked, or whose document a pull rebased meanwhile (#280, #482). A remote edit of a document whose delete event a restart lost is kept beside it, as a new document at a copy path if it reached the server after the delete (#526). An operation is journaled with its revision id before it is sent; uploads resume from `received_size`, and a commit is retried with identical fields (§6.2). One transaction records the acknowledged base and removes the operation (moving the cursor when it is the next `seq`, §6.1). A file changed before its upload completed is pushed with its current content, keeping any rename (#286). Head moved (`FAILED_PRECONDITION`): pull, merge, rebase. `ALREADY_EXISTS`: §7's refused commits. Content no longer a complete blob (§11): upload again, a bounded number of times. An operation whose path breaks §6.2 is never sent; it is reported as rejected with the rule until its file is gone (decision #100), and one refused with `INVALID_ARGUMENT` otherwise as `refused`. Rejections are shown in the status and conflict view (`docs/plugin.md`). Automatic pushes are debounced (`pushDebounceMs`, default 2 s, restarted by every change), and an edit made during a push triggers another.
- **Deliberate changes (design §6.4).** The path-ownership refactor changed on purpose: a rename or delete handled before a crash stays one, and the start-up scan finds a rename by a unique content match; rule W moves a file by a rename, and detaches a blocked document's file in one step; a blocked document keeps its file and local changes while no server claim needs its path; of two documents that are one file here with two path keys, the second is `unmaterializable(alias)`; the merge hook no longer chooses the path; a user's delete lasts until something binds the document again; an unpushed local rename wins over a remote delete; tombstone re-creation follows PO-13; after a restore a lost document is re-created and a rolled-back one committed without a copy; a folder has one spelling on disk.
- **`.obsidian/` config sync (decision, #28).** Opt-in per local vault, off by default, kept on the device, never synced or set by the server (#52); its help warns that synced plugin code runs on the device. `plugin/src/core/config/policy.ts` allow-lists categories (themes, snippets, hotkeys on by default; main settings, plugin list, core plugin settings (without graph, workspaces and sync), plugin code and data off); a stored setting without a category takes its default, so an upgrade starts syncing no new category (#256); files sync whole, listed in `docs/plugin.md`. `workspace*.json`, `graph.json` and the plugin's own folder never sync, matched ignoring case, Unicode form and Windows' trailing dots and spaces. `ConfigSyncVault` (`plugin/src/core/config/config-vault.ts`) maps the server's `.obsidian/` to `app.vault.configDir` and, with the toggle off, never touches it. The engine's scope is `VaultAdapter.isSynced`: nothing outside it is pushed (turning sync off deletes no server config), and a remote revision outside it is deferred `out-of-scope` until a start finds it in scope. A settings change restarts the session. Config conflict copies are in no category and stay on the device; one an older build committed is deferred `out-of-scope`, never applied or deleted. After sync changes a config file the plugin asks the user to reload; it never reloads Obsidian itself.

## 9. Authentication, authorization, encryption

### 9.1 Authentication

The plugin authenticates against Authentik with the **OAuth 2.0 Device Authorization Grant** (works identically on desktop and Android, with no redirect handling). The plugin stores the refresh token in plugin data; access tokens are JWTs validated by the server against the issuer's JWKS (refreshed on unknown `kid`, with a bounded refresh rate). `iss`, `aud`, and `exp` are always checked.

Client-side details (decision, #25):

- The OAuth calls live in `plugin/src/core/auth` and go through an injected HTTP client: Obsidian's `requestUrl` in the plugin, which is not subject to CORS and behaves the same on desktop and Android. The plugin's ConnectRPC transport uses `requestUrl` too; `requestUrl` cannot be cancelled, so an aborted or timed-out RPC rejects at once and its late response is dropped. Identity provider responses are bounded at 64 KiB of UTF-8 (checked once `requestUrl` has buffered the body, as it offers no streaming). The discovery document must name the configured issuer exactly, and the issuer, every endpoint and the server URL must be `https` (plain `http` only to loopback hosts). The plugin checks `GetServerInfo`'s protocol version before it signs in, and takes the identity provider from it (decision, #194): `GetServerInfo` advertises the issuer (`VAULT_SYNC_OIDC_ISSUER_URL`) and the plugin's public client id (`VAULT_SYNC_OIDC_CLIENT_ID`, by default the audience), both public, so only the server URL must be entered. The plugin's issuer and client id settings are optional overrides: an entered client id wins, and an entered issuer is used only when the server advertises none (one that differs from the advertised issuer is refused). So the server URL decides the identity provider unless the issuer is entered: with none entered, the first sign-in trusts the issuer the server advertises, and a malicious or compromised server can send the user to a verification page of its choosing. This is accepted, because the user already trusts that server with the vault's notes; entering the issuer pins it. The advertised issuer must pass the same `https` rule, and an advertised client id must be 1 to 255 printable ASCII characters. The issuer and client id a sign-in used are stored with the refresh token and used for its refreshes, so refreshing never depends on the server. The device flow requests `openid offline_access`, follows RFC 8628 polling (the provider's interval, plus 5 s on every `slow_down`; network failures and 5xx responses are retried until the code expires), and is cancelled when its dialog closes, leaving the authentication state as it was. The server and identity provider settings are locked while a sign-in runs and while signed in. A signed-in device must sign out before it can sign in again. A grant without a refresh token is refused.
- The refresh token is the only token stored (plugin data, never synced). The access token is kept in memory and refreshed a minute before its `exp` (from the JWT, else `expires_in`), or halfway through its lifetime if that is shorter. Concurrent callers share one refresh. A rotated refresh token is persisted before the new access token is used. Writes of the refresh token never overlap, and a sign-in or sign-out wins over a refresh still running: that refresh's tokens are dropped and its rotated refresh token is never left on disk. A sign-in forgets the previous session's tokens before it stores the new refresh token, so while that write runs no caller gets the previous session's access token, and a failed write leaves the device signed out and then removes the stored refresh token (best effort), so a restart does not resume the session the sign-in replaced. A unary RPC refused with `UNAUTHENTICATED` invalidates its token and is sent once more, unchanged, with a fresh one, so a retried `CommitRevision` keeps its `revision_id` (§6.2). `GetServerInfo`, the one public procedure, never waits for a token.
- A refresh refused with `invalid_grant` (the refresh token expired or was revoked, or the provider session ended) deletes the refresh token and moves to "sign-in required". From then on authenticated calls fail with `UNAUTHENTICATED` without reaching the server, and the engine keeps its pending operations (principle 1) until a new sign-in. A provider that cannot be reached fails calls with `UNAVAILABLE` and keeps the device signed in. A request `requestUrl` could not deliver at all (no network, DNS, TLS) fails with `UNAVAILABLE` too. "Sign-in required" stops sync; the session that starts after the next sign-in pushes what was changed meanwhile. Tokens are never logged.

Server-side details (decision):

- Only RS256, ES256 and EdDSA signatures are accepted; `none` and HMAC algorithms are rejected. Tokens are size-bounded before parsing. `exp` has no leeway; `nbf`, when present, tolerates one minute of clock skew.
- The JWKS (discovered from the issuer's OpenID configuration) is fetched lazily, refetched on an unknown `kid` and when older than one hour, and never more than once per 30 seconds. A failed refetch keeps the cached keys. At most one fetch is in flight and no lock is held across it: while hour-old keys are being refetched, other requests use the cached keys rather than wait. The discovery document, `jwks_uri` and redirects must be `https` (plain `http` only to loopback hosts, and only for a loopback `http` issuer); redirects must stay on the requested host and never downgrade to `http`.
- Users are created on their first authenticated request, keyed by `(issuer, subject)`; concurrent first requests create exactly one user. `sub` must be non-empty, at most 255 bytes, and free of control characters (Unicode `Cc`); other tokens are rejected as unauthenticated before any user lookup.
- Authentication is **default-deny**: one interceptor on every ConnectRPC service authenticates every procedure that is not on an explicit public allow-list (only `ServerInfoService/GetServerInfo`, which returns only public, configuration-derived data: versions, the realtime subscription cap, the issuer and the plugin's public client id). The realtime WebSocket upgrade (§6.4) authenticates with the same authenticator. A test enumerates every procedure in the schema and asserts it is authenticated or allow-listed.

### 9.2 Authorization

Every RPC and every WebSocket message resolves `(user, vault_id)` to a `vault_members` role before touching data. `viewer` can read; `editor` can read and write; `owner` can also manage members and vault settings. There is no admin bypass in the API.

Server-side details (decision):

- Authorization is **central and runs before the handler**: one interceptor, after authentication, on every ConnectRPC service. A single table (`server.VaultProcedures`) classifies every vault-scoped procedure — every procedure whose request carries `vault_id` — as read or write. A request carrying a `vault_id` for an unclassified procedure is rejected, and a test derived from the schema descriptors fails if any such procedure is missing from the table. The interceptor reads only the top-level `vault_id`, so a request must name its vault nowhere else: a second schema-derived test walks every RPC input message (nested messages, `oneof` members, repeated and map fields, stopping at recursive types) and fails, naming the procedure and field path, on any vault-identifying field other than a single top-level, singular, non-`oneof` `string vault_id`. A field is vault-identifying if its name ends in `vault`, `vaults`, `vault_id` or `vault_ids` (also without the underscore before `id`; for example `target_vault_id`) or its type is the `Vault` message. Streaming calls to vault-scoped procedures are rejected before the handler runs, because their messages arrive only after it starts.
- `vault_id` must be a canonical lowercase UUID (`INVALID_ARGUMENT` otherwise) and is checked before any query. The role is then resolved with one `vault_members` lookup: a vault that does not exist and a vault the caller is not a member of take the same path and return the same `NOT_FOUND` error. A `viewer` calling a write procedure gets `PERMISSION_DENIED`.
- Handlers take the authorized vault from the interceptor, never from the request, and query through a vault-scoped store handle whose every query filters by that vault, so ids from another vault (documents, revisions, blobs) are simply not found.
- `CreateVault` makes the caller the `owner` (a user may own at most 100 vaults); `ListVaults` returns only vaults the caller is a member of, with the caller's role, paginated by an opaque `page_token` (`page_size` defaults to 100 and is capped at 1000; like `ListChanges`, a page also ends early where its encoding would exceed the send limit, with a `next_page_token` to continue, and holds at least one vault if one remains; startup requires the send limit to fit a response with one vault with a maximum-length name). Vault names are non-blank, at most 256 bytes, and contain no control characters (Unicode category `Cc`, including U+0000, which PostgreSQL `text` cannot store), no format characters (`Cf`: bidi embeddings, overrides, isolates and marks, zero-width characters, the byte order mark, tag characters) and no line or paragraph separator (`Zl`, `Zp`; decision, #548), so a name other members see cannot hide text or reorder the label around it; anything else is `INVALID_ARGUMENT` before the database is touched.
- **Membership (decision, #33).** `MembershipService` manages members. `CreateInvitation`, `ListInvitations`, `RevokeInvitation`, `ListMembers`, `UpdateMemberRole` and `RemoveMember` are owner-only (the `Manage` class of `server.VaultProcedures`, PERMISSION_DENIED for editors and viewers); `LeaveVault` is open to every member (`Read`); `RedeemInvitation` is not vault-scoped, since the person redeeming is not a member yet: it carries only the code. An invitation grants one role (owner, editor or viewer) and expires after `ttl_seconds` (default 7 days, at most 30 days; more is `INVALID_ARGUMENT`). Its code is 32 random bytes, base64url-encoded without padding, returned only by `CreateInvitation`; the server stores only its SHA-256. Redeeming makes the caller a member with the invitation's role and deletes the invitation in one transaction, so a code works once even when redeemed concurrently. A code that is malformed, unknown, expired, revoked or used gets one and the same `NOT_FOUND` error, which names no vault. Redeeming as an existing member is `ALREADY_EXISTS` and leaves both the role and the invitation as they were. A vault has at most 100 members and 100 pending invitations (`RESOURCE_EXHAUSTED`; a redemption refused by the member limit keeps the invitation), so `ListMembers` and `ListInvitations` are not paginated. A vault always has at least one owner: demoting or removing its last owner, and the last owner leaving, is `FAILED_PRECONDITION`. Every membership change locks the vault row (as commits do), so concurrent changes cannot leave a vault without an owner or over the member limit. Changes take effect on the member's next request on every replica, because authorization reads `vault_members` on every request and nothing caches roles, and a removal ends the member's realtime subscriptions at once (§6.4). An in-flight request authorized before the change may still complete. An owner role granted by invitation or promotion counts toward `CreateVault`'s limit of 100 owned vaults, but is never refused by it.
- `RegisterDevice` registers a device for the caller (one per plugin installation, so every reinstall adds one). A user may have at most 100 devices that are not removed (decision #52 item 8 counted every registration over the account's lifetime; #205 made devices removable, so the limit can be recovered from). The 101st call gets `RESOURCE_EXHAUSTED` ("at most 100 devices may be registered") with an `ErrorDetail` of reason `ERROR_REASON_DEVICE_LIMIT`, which clients match instead of the message (#428); registrations are serialized on the user row, so concurrent calls cannot overshoot the cap. Registration is idempotent with a client-chosen `registration_id` (a canonical lowercase UUID; #428): the plugin saves one before its first attempt and sends it with every retry, and a retry with the same id, name and public key returns the device the first call registered, without using another place, even at the cap. So a crash or a lost response between the server registering the device and the plugin saving it does not burn a place. The plugin drops the saved id after `INVALID_ARGUMENT` or `ALREADY_EXISTS`, which mean nothing was registered under it, so its next attempt uses a new id and the current Device name; after any other error it keeps the id, since the first call may have registered the device. The same id with a different name or public key is `ALREADY_EXISTS`; the id is scoped to the caller and to devices that are not removed, so after removal it registers a new device; an empty id registers a new device on every call (older plugins). Device names follow the same character rule as vault names (no `Cc`, `Cf`, `Zl` or `Zp`; #548), are non-blank and at most 256 bytes; names stored before #548 are kept as they are, and the plugin strips those characters, replaces double quotation marks, bounds the shown length and isolates the name (Unicode FSI/PDI) wherever it shows another device's or a vault's name, writes invisible characters in file paths it shows as `\uXXXX` and a backslash as `\\`, except the zero-width joiners of an emoji sequence, and lays each path out on its own (an element with `dir="auto"`) inside the label that shows it (display only; #557, #605), and registers at most 256 bytes of its Device name setting (§11). The public key is empty or exactly 32 bytes. Anything else is `INVALID_ARGUMENT` before the database is touched.
- `ListDevices` returns the caller's devices that are not removed, oldest first, each with its id, name, registration time and last activity (its last commit, to within a minute; unset if it never committed), and nothing secret (no public key). It is not paginated: the device limit bounds it to 100 entries. `RemoveDevice` removes one of the caller's devices (decision, #205): `device_id` must be a canonical lowercase UUID (`INVALID_ARGUMENT`), and a device that is not the caller's, does not exist or is already removed is `NOT_FOUND`, so a user can neither see nor remove another user's devices. The row is kept with `removed_at` set, because `revisions.device_id` references it: the device's revisions keep their history and attribution, and their device name is still shown (§11). A removed device no longer counts toward the limit, is not listed, and can no longer commit (`CommitRevision` answers `NOT_FOUND`, as for an unknown device, with the reason `ERROR_REASON_DEVICE_NOT_FOUND`); the installation must register again to sync. The plugin lists the user's devices in its settings and removes another one there, never its own (#590). When a commit of its own is refused with that reason, it stops sync, says so, and waits for the user to register the installation again, which it never does by itself (the device may have been removed because it was lost); its pending operations stay in the journal and are pushed under the new device, and a retry of a commit that landed before the removal gets the committed revision back (§6.2). Removal is not undoable. It takes effect on every replica once the call returns, with PostgreSQL as the only coordination: every commit locks its device row (after the vault row, so no deadlock) until it ends and checks `removed_at` under that lock, and the removal updates that row, so it waits for the device's commits in flight and every later commit, on any replica, sees it. No replica caches devices. Removed rows are not deleted, so a user's device rows grow by one per removal; each removal needs an authenticated registration and removal, and the rows are small. They are kept on purpose (decision, #428): deleting one is only safe once no revision references it, and checking that needs an index on `revisions (device_id)`, which every commit would have to maintain, for rows of about a hundred bytes.

### 9.3 End-to-end encryption (opt-in per vault)

Until Phase 4 (§15) delivers key management, the server rejects `CreateVault` for an E2EE vault (with or without escrow) with `FAILED_PRECONDITION` ("end-to-end encrypted vaults are not supported yet"), so that no client can commit plaintext into a vault marked as encrypted, whose `path_key` the server could not derive (§5; principle 1). Escrow on a plaintext vault is `INVALID_ARGUMENT`.

Envelope encryption with multiple recipients:

- Each **user** has an X25519 key pair. The private key is stored server-side wrapped by a key derived from a user recovery passphrase (Argon2id). The Argon2id output is split with HKDF-SHA256 into a `wrap_key`, which wraps the private key and never leaves the device, and an `auth_key`, a verifier the device presents so the server releases the wrapped key. The server stores only `SHA-256(auth_key)`, compares in constant time, and rate-limits failed attempts per user in PostgreSQL. Neither key can be derived from the other, so the server cannot unwrap the key. A stolen session therefore allows only a rate-limited online guessing attack; a dump of the database allows an offline attack at Argon2id cost per guess; and a lockout ends with its window. Devices unwrap it once and keep it in local storage. (Device-to-device linking and Shamir-split recovery are later enhancements.)
- **User key storage (decision, #52, #665).** `UserKeyService` stores each user's key pair; every procedure acts on the caller's own key only and none names a user, so another user can neither read, unlock nor replace it. The server stores the public key, the wrapped private key, the wrapping's public parameters (suite, Argon2id memory, passes, lanes and salt) and `SHA-256(auth_key)`, never `auth_key`, the passphrase, the Argon2id output or the private key, and never logs `auth_key` or key material. `GetUserKeyParams` returns the public key and parameters a device needs to derive `auth_key`. `CreateUserKey` is create-only: a user who has a key gets `ALREADY_EXISTS` and the stored key is unchanged, so two devices enabling encryption at once cannot replace each other's key. `UnlockUserKey` returns the wrapped private key only for the matching `auth_key`; a wrong one is `PERMISSION_DENIED` with reason `ERROR_REASON_WRONG_PASSPHRASE` and no key material. `ChangePassphrase` takes the current `auth_key` and the stored public key and replaces the wrapped key, its parameters and the verifier in one transaction, as a compare-and-swap on the public key (a different public key is `FAILED_PRECONDITION` and changes nothing); key rotation and reset are out of scope. A user without a key gets `NOT_FOUND`. Wrong `auth_key`s presented to `UnlockUserKey` or `ChangePassphrase` are counted per user in the `user_keys` row, under its row lock and with the database clock, so every replica sees one count: after 10 within one hour (the hour starting at the first counted failure), every attempt is `RESOURCE_EXHAUSTED` with reason `ERROR_REASON_PASSPHRASE_ATTEMPTS_EXHAUSTED` and `ErrorDetail.retry_time` set to the end of the hour, even with the right `auth_key`; refused attempts are not counted and do not extend the hour, and a success does not reset the count. Inputs are bounded before the database is touched (`INVALID_ARGUMENT`): public key and `auth_key` exactly 32 bytes, wrapped private key 1 to 256 bytes, suite 1, salt exactly 16 bytes, and the Argon2id bounds below.
- **Plugin key manager (decision, #667).** Enabling E2EE creates the key pair on the device (`plugin/src/core/keys`) and calls `CreateUserKey` with only the public key, the wrapped private key, its parameters and `auth_key`; a new passphrase has at least 10 characters. The wrap binds the associated data `"vault-sync/v1/user-key" || public_key`, so a wrapped key cannot be passed off as another key pair's, and after unwrapping the device checks that the private key yields the stored public key. A device that gets `ALREADY_EXISTS` (another device enabled E2EE first) unlocks the stored key with the passphrase it was given instead of replacing it. Unlocking derives `auth_key` from the parameters `GetUserKeyParams` returns, presents it to `UnlockUserKey` and unwraps the released key on the device; a wrong passphrase and the attempt limit (with the server's `retry_time`) are reported to the user. The unlocked key pair is cached only in the plugin's device-local data (`data.json` in its own plugin folder, never synced, §8), with the server and account it belongs to, is never logged, and is dropped on sign-out. A cached key is used only while its public key is the one `GetUserKeyParams` returns (decision, #692): otherwise the device reports the key as locked, says the server's key is not the one it unlocked, and asks for the passphrase again; the cached key is replaced only by that unlock, never deleted silently.
- Each **vault** has a symmetric vault key per **epoch**. `key_slots` hold the epoch key wrapped (X25519 + HKDF + XChaCha20-Poly1305, sealed-box style) to every member, and to the escrow public key if escrow is enabled.
- **Key slots and key commitments (decision, #52).** A slot binds `"vault-sync/v1/key-slot" || vault_id || epoch || recipient_kind || recipient_id` as associated data, so it opens only as the slot of that vault, epoch and recipient. Every epoch stores a key commitment, `HMAC-SHA256(epoch_key, "vault-sync/v1/key-commitment" || vault_id || epoch)`, which a recipient verifies after unwrapping. Byte encodings: `docs/design/crypto.md`.
- Sub-keys are derived from the epoch key with HKDF: `content`, `path`, `path_key_secret`, `blob_id_secret`.
- Content and paths are encrypted with **XChaCha20-Poly1305**, random nonce, the revision's document id and epoch bound as associated data.
- Every ciphertext carries a **suite version** byte so that the algorithms can change later, and every open authenticates the whole header (suite byte included) with the caller's associated data, so a ciphertext with an unknown suite, a changed header or associated data, or a truncated tag fails closed. Suite 1 (byte formats in `docs/design/crypto.md`): HKDF-SHA256 sub-keys; XChaCha20-Poly1305 with a random 24-byte nonce from the platform CSPRNG; sealed box = ephemeral X25519, HKDF-SHA256 salted with both public keys, XChaCha20-Poly1305, refusing low-order keys; HMAC-SHA256 `path_key` and `blob_id`; the user's private key wrapped under a `wrap_key` split by HKDF-SHA256 (with an `auth_key` under a separate label) from Argon2id (default 64 MiB, 3 passes, 1 lane) of the passphrase in NFC (the pinned tables of §5, so every device derives the same key), with the parameters stored in the header and bounded (19–128 MiB, 2–8 passes, 1–4 lanes) before any derivation, so a stored value can neither weaken the derivation nor exhaust a device.
- **Member removal** creates a new epoch. Subsequent revisions use it; historical content is not re-encrypted (the removed member may already hold it).
- **Epochs and key slots (decision, #52, #694).** `VaultKeyService` stores epochs and slots as opaque bytes; the server never sees an epoch key. A new E2EE vault has no epoch (`current_epoch = 0`) and a pending rotation; an owner client creates epoch 1. Every epoch change is a compare-and-set on `vaults.current_epoch` under the vault row lock (which commits and membership changes take too), so of concurrent changes with the same `expected_epoch` exactly one wins, on any replica, and the others get `FAILED_PRECONDITION` with reason `ERROR_REASON_EPOCH_NOT_CURRENT` and adopt the winner's epoch. An epoch's recipients are exactly the vault's members **who have a user key**, plus at most one escrow slot in an escrow vault (requiring it is #40); a member without a user key cannot be wrapped to and is not required, and missing or extra recipients are `INVALID_ARGUMENT`. An owner's `RemoveMember` on an E2EE vault must carry `next_epoch` (commitment and a slot for every remaining recipient, not the removed member) and commits the removal and epoch N+1 in one transaction; without a valid one the member stays. A plaintext vault takes no `next_epoch`. An owner cannot remove themselves from an E2EE vault with `RemoveMember`, since they would create, and so know, the epoch meant to exclude them: it is `FAILED_PRECONDITION`, names `LeaveVault`, and changes nothing (#710). Self-removal from an E2EE vault goes through `LeaveVault`. In a plaintext vault an owner may still remove themselves with `RemoveMember`. `LeaveVault` (no owner client involved) sets `rotation_pending`; an owner client then calls `RotateEpoch(expected_epoch = N)`, which creates N+1 and clears the flag. `CommitRevision` carries the revision's `epoch`: 0 in a plaintext vault and the vault's current epoch in an E2EE vault, checked under the vault row lock after the idempotency check (a retry of a commit applied before a rotation gets its revision back); any other epoch is `FAILED_PRECONDITION` with reason `ERROR_REASON_EPOCH_NOT_CURRENT`. A pending rotation does not change the current epoch, so commits under it continue until the next epoch exists. A new member gets slots for every epoch (decision #52): `ListMissingSlots` (owner-only) lists every (epoch, member with a user key) pair without a slot, with the member's public key, until an owner grants it with `AddKeySlots`, which keeps an existing slot rather than replacing it. `ListKeySlots` returns only the caller's own slots, and `ListEpochs` the epochs with their commitments and the vault's key state; both are open to every member, viewers included. `ListMembers` reports each member's user public key. Inputs are bounded before the database is touched (`INVALID_ARGUMENT`): commitment exactly 32 bytes, wrapped key 1 to 256 bytes, user recipient ids canonical lowercase UUIDs, escrow recipient ids 1 to 255 printable ASCII bytes (the key-slot format allows 255), at most 101 slots in a new epoch and 1 to 1000 per `AddKeySlots`, no duplicate slots, and list pages of 100 by default and at most 1000, cut to the send limit. Until #39 lifts the `CreateVault` guard, E2EE commits are refused, and tests reach this path through a test-only `SyncService.AllowE2EE` option.
- **Plugin vault key manager (decision, #695).** `plugin/src/core/keys` keeps an E2EE vault's epoch keys on the device. Each sync reads every page of `ListEpochs` and `ListKeySlots` and unwraps each of the user's slots it does not hold yet with the unlocked user key. It uses a key only once it matches its epoch's key commitment. A slot that does not open, has no commitment or does not match is refused and reported to the user, never used. A held key whose epoch's commitment changes is refused too: an epoch's key never changes, so the device then stops using and sharing it. The keys are cached only in the plugin's device-local data (`data.json`, never synced, §8), for the server, account and vault they belong to, are never logged, and are dropped on sign-out together with the user key. Only an owner device rotates and grants. When the vault is rotation-pending (a new vault has no epoch yet, or a member left), it creates the next epoch with `RotateEpoch(expected_epoch = current)`. The next epoch has a fresh random key, wrapped for every member `ListMembers` lists with a user public key, and a member without one is skipped. If the device gets `ERROR_REASON_EPOCH_NOT_CURRENT` because another owner device won, it re-reads and adopts that epoch without creating another. An owner's removal of a member sends `RemoveMember` with the next epoch built the same way, without the removed member, and retries over a newer epoch at most three times when another epoch change wins. Once a sync is done reading, an owner device grants every `ListMissingSlots` entry for an epoch whose key it holds, in `AddKeySlots` batches of at most 1000. A new epoch's key is kept once the server accepted it: should the response be lost, the device's own slot in that epoch still holds it. Until the device holds the key of every epoch up to the current one, the member sees "Waiting for an owner to share the vault key."
- Implementations: `@noble/ciphers`, `@noble/curves`, `@noble/hashes` in TypeScript (pure JS, audited, identical on Electron and Android WebView); `golang.org/x/crypto` in Go. A shared set of **cross-language test vectors** in `testdata/crypto/` (generated by the Go tests, including published known answers for the primitives and ciphertexts that must be refused) must pass in both (`internal/e2ee`, `plugin/src/core/e2ee`).
- With E2EE, the server cannot merge, search, or render content — none of which it does anyway (§4).

### 9.4 Escrow for plaintext backups

A vault with `escrow = true` also wraps each epoch key to a deployment-wide **escrow public key**. The escrow private key exists only in the export job's Secret, which is never mounted into the internet-facing server. A compromise of the API server, PostgreSQL, or S3 therefore exposes only ciphertext. The export job decrypts and writes plaintext for tape archival. Escrow is chosen at vault creation and shown clearly in the UI. Optionally, the escrow private key may be split with Shamir secret sharing for offline disaster recovery; this is not used by the automated path.

## 10. Live collaborative editing (Phase 5)

The v1 protocol includes the hooks for this from the start: stable document ids, the `kind` field, the multiplexed WebSocket, and an append-only per-document log.

- A `yjs` document's state is its ordered `yjs_updates` log plus periodic snapshots. For E2EE vaults each update is encrypted (the server stores and relays opaque bytes).
- **Conversion** of a `text` document to `yjs` happens **exactly once**, as a server-side compare-and-set on `documents.kind` performed by a single elected client (the server grants a lease). Two clients independently initializing a `Y.Text` from the same file duplicates the content — the classic Yjs bug — and must be impossible.
- The plugin binds `Y.Text` to Obsidian's CodeMirror 6 editor (`y-codemirror.next`) and to the file on disk. Edits that arrive outside the editor (other plugins, `processFrontMatter`, external editors, git) are diffed into the `Y.Text`.
- Awareness (cursors, presence) is ephemeral over the WebSocket and never persisted.
- **Compaction** folds the update log into a snapshot. Plaintext and escrow vaults can compact server-side (the export job can do it for escrow vaults); other E2EE vaults compact on clients. The compaction runtime (a Go Yjs implementation is not mature) is an open question for Phase 5.

## 11. Retention and history

- Revisions are append-only. A retention policy purges old **non-head** revisions, including tombstones that are not the head. The policy is deployment-wide (`docs/configuration.md`), with per-vault overrides set by the operator (below). By default every revision younger than 90 days is kept; older revisions are thinned to the newest revision of each document per UTC day until they are a year old, and to the newest per ISO week (from Monday, UTC) after that. Ages are measured by the database clock from `created_at`, and a revision is in the daily or the weekly zone, never both, so a day and the week starting on it are separate buckets.
- **A document's head revision is never purged** (decision, #52), however old, and that includes a head tombstone: a deleted document keeps its tombstone indefinitely, so it stays findable and restorable, and a client offline for longer than the policy still learns of the delete instead of resurrecting the document. ListChanges skips purged revisions, so a cursor may skip `seq` values. **Purge markers (decision, #52/#488).** The purge keeps each purged revision's `seq` and `anchor` in `purged_revisions` (§5), in the transaction that deletes it, so every snapshot sees either the revision or its marker, on any replica. A client whose cursor (or own commit above it) sits on a purged revision therefore passes the anchor check and pulls on as usual (§6.1): a document it did not change takes the newer heads, remote deletes included (#480). Revisions purged before migration 0008 have none (§6.1). **Marker horizon (decision, #514).** Each marker records its purge time (`purged_at`, migration 0009), and the retention job deletes the markers older than `VAULT_SYNC_RETENTION_PURGE_MARKER_HORIZON` (default 365 days, at least one day), so `purged_revisions` is bounded by one horizon of purges (principle 4). Pruning is bounded per run (at most 100,000 markers, in statements of 1,000, oldest first), so the table stays bounded by one horizon of purges only while the sustained purge rate stays below about 100,000 revisions per hour per replica (a run starts every hour on each replica, and one run may purge up to 1,000 x 1,000 revisions); far above the expected scale, and `vault_sync_retention_purge_markers_pruned_total` growing by the cap every run is the signal that pruning falls behind (#519). It is safe on concurrent replicas: each statement locks the rows it deletes with `SKIP LOCKED`, so replicas take disjoint markers, never wait for each other, and together delete what one run would. It never loses an acknowledged write (principle 1): a marker is only consulted by a device that has not pulled since the purge, since a purged revision always has a newer revision of its document, so any later pull moves the cursor (and the device's own commits) past it. Such a device, once its marker is gone, gets a false-positive `diverged` and resyncs (§8), merging every note it holds with the server's: nothing is lost, although an unchanged note another device deleted comes back (an edit wins over a delete) and a note whose merge base was purged gets a conflict copy. Deleting a marker can only turn a passing anchor check into `diverged`, never the reverse, so pruning never hides a restore.
- **Per-vault overrides (decision, #52/#468).** The operator can give a vault its own `keep_all` and `keep_daily` with `vault-sync-server retention set|unset|list` (`docs/configuration.md`), stored in `vault_retention`; a vault without one follows the deployment-wide policy. There is no API or plugin setting for it (principle 4): only the operator, who already holds the database, can shorten a vault's history, and purges are irreversible. `set` refuses a `keep_all` below one day or below the operator's `VAULT_SYNC_RETENTION_OVERRIDE_MIN_KEEP_ALL`, a `keep_daily` below `VAULT_SYNC_RETENTION_OVERRIDE_MIN_KEEP_DAILY`, and a `keep_daily` below its `keep_all`; the table's checks refuse a non-positive `keep_all` and a `keep_daily` below it. The purge query joins the override and applies `coalesce(override, deployment)` per revision (one policy per document, since a document belongs to one vault), and bounds its scan by the shortest `keep_all` in force so the `created_at` index still applies. Overrides need no per-replica state: every replica reads them in each run. Replicas of a release before migration 0010 ignore them, so overrides are set only after a rollout completes (`docs/deployment.md`).
- **Parent links after a purge (decision, #58).** A purged revision is almost always another's parent. The purge re-parents the child onto the purged revision's parent in the same transaction, so `parent_rev_id` keeps naming a revision that exists (the foreign key is unchanged and still enforced): the nearest retained ancestor, or none once every older revision is gone. History stays a connected chain. Re-parenting was chosen over nulling the link because it keeps that chain, and it needs no PostgreSQL 15 `ON DELETE SET NULL (column)`. It is compatible with "append-only": revisions are never added out of order or changed by clients, and the only later change to a revision is this rewrite of its parent link when an ancestor is purged; content, path, tombstone flag, device and time never change. A commit retried after its base was purged is still the same commit (§6.2): its base no longer exists, so it matches whatever parent the revision has now.
- **Blob garbage collection.** A blob row starts released (`released_at` defaults to the time it is stored, since `CommitBlob` stores a blob before any revision references it), and each purge sets `released_at` on the blobs its revisions referenced. A blob that no revision references and that was released longer than the grace period ago (default 24 hours) is collected in two steps. First, its row is deleted and a `blob_deletions` record written, in one transaction under `FOR UPDATE SKIP LOCKED` on the row. A commit holds `FOR KEY SHARE` on the blob it references until it commits, so a blob being committed is skipped, and a commit that starts while the blob is being collected finds it not complete (`FAILED_PRECONDITION`, and the client uploads it again). Second, the S3 object is deleted and then the record, under `FOR UPDATE SKIP LOCKED` on the record; the object is left alone and the record dropped if the blob is complete again, and the record stays for a later run while an upload of the blob is in progress. `CommitBlob` waits for a deletion of its blob in progress before writing the object, so a re-uploaded object is never deleted; each object deletion, retries included, is bounded by four S3 idle timeouts (`VAULT_SYNC_S3_IDLE_TIMEOUT`), so even a store that keeps sending a byte now and then holds the record's lock, and that commit, no longer than that (#225). The row goes first so that no revision can ever reference a blob whose object is gone. The grace period lets a client that just read a purged revision restore its content without uploading it again. A blob that never had a referencing revision (an upload whose revision was never committed) is collected the same way, the grace period counted from its upload (#225); one a revision references when the collector looks is kept and no longer released.
- **Concurrency.** The retention job runs on every replica (§12): each document is purged in its own transaction under `FOR NO KEY UPDATE SKIP LOCKED` on the document row, so concurrent purges skip each other and a purge's first pass never waits for a commit to the document; the documents it skipped are purged again afterwards, one at a time while the run holds no other lock, waiting for each lock (see incremental scans below), while a commit waits at most for one document's bounded purge. Every step is idempotent and bounded per run.
- **Incremental scans (#225).** A revision only becomes purgeable when it, or a newer revision of its bucket, crosses the policy's 90-day or one-year age. So a run that found fewer candidate documents than its bound and purged each of them fully records, in the single-row `retention_scans`, the policy and the database time it started; later runs under the same policy only consider documents with revisions whose `created_at` crossed one of the two ages since then (indexed on `created_at`). A document a run skipped because it was locked (a commit, or another replica's purge) is purged again, waiting for the lock, before the run counts as complete. Replicas record their own complete scans; the record only moves forward, and a run under another policy (a configuration change) scans every document and replaces it. The record also holds a digest of every per-vault override, read before the scan's candidate query: setting, changing or removing any override makes the next run, on every replica, a full scan, since a changed override can make revisions purgeable that crossed no age. Incremental runs also consider documents with revisions that crossed an overridden vault's own ages.
- Users can browse a document's history and restore any revision (a restore is a new revision: a `CommitRevision` based on the current head with the old revision's `content_ref`, and `deleted = false` to restore a deleted document).
- **Client history and restore (decision, #26).** The engine pages `GetDocumentHistory` into entries with each revision's time (`create_time`) and device (`device_id`, named by the response's `device_names`, decision #420: each device that committed a revision on the page, once, by its registered name; every member of the vault, a viewer included, sees them, and a non-member gets `NOT_FOUND` as for any history; a device the server does not name is shown by id), downloads any revision for a preview (only its first 256 KiB, in `DownloadBlob` ranges, when it is larger, #656: that start cannot be checked against the content hash, so it is shown only, never written or uploaded; a revision no larger is downloaded whole and verified), and restores one serialized with its pulls and pushes: it pushes first, so local edits not yet pushed land in history instead of being replaced, then commits the revision's `content_ref` on the current head, at the head's path (a restore never moves a document, except as below) and with `deleted = false`, then pulls, so the disk shows the result. A head that moves meanwhile is read again and the commit retried on it. `FAILED_PRECONDITION` without a `Document` detail (the blob was garbage-collected after a purge) uploads the content again, from the user's preview if it is the whole revision and hashes right or else from a download of the whole revision, and retries; if neither has it, the restore fails with nothing committed. `ALREADY_EXISTS` (a deleted document's path now belongs to another live document) fails the restore too; the user may then restore it at another path they choose (#420), the same commit with that path, which the client first checks as it checks a new document's path (§6.2), against the platform (§8) and against the vault's sync scope, so a path that would be refused, could not be written here or would not sync fails with nothing committed. So does `INVALID_ARGUMENT` for a deleted document whose path contains a `\` (§6.2, decision #191): nothing is committed, and its history stays readable. Deleted files are found in the journal: every document whose synced state is a tombstone, except one only released because the platform cannot hold its path (§8). Since head tombstones are never purged and every device pulls them, that is every deleted document of the vault once the device has caught up.

## 12. Operations

- Single static Go binary; one OCI image (server and export) built by Nix (`streamLayeredImage`, with the flake's pinned Go, checked with `govulncheck -mode=binary`), mirroring tape-archiver. The Helm chart under `deploy/charts/vault-sync` is built on the bjw-s `common` library chart and renders the server Deployment, the export CronJob, Services and a ServiceMonitor; it references operator-created Secrets and creates none. It mounts the escrow Secret (§9.4) into the export job only and refuses to render any values that would put it into the server, which `make chart-lint` checks (decision, #30). Deployment: `docs/deployment.md`.
- Configuration by environment variables, documented in `docs/configuration.md`.
- **JSON structured logs** (`log/slog`), Prometheus metrics on a separate port, `/healthz` and `/readyz`.
- PostgreSQL client certificates and S3 credentials are re-read from disk on change.
- Schema migrations are embedded (`internal/store/migrations`) and run on startup behind a PostgreSQL advisory lock, each in its own transaction, recorded in `schema_migrations`; migrations are forward-only and must be backward-compatible with the previous release. Released migrations are never edited (the runner rejects a changed name for an applied version). Migrations may use any feature of PostgreSQL 14, the minimum supported version (0003 defines its index function with a SQL-standard `RETURN` body, which binds its references at creation so `search_path` cannot change what the index computes). A migration that rebuilds an index holds an exclusive lock on its table until it commits; 0003 rebuilds the live-path index on `documents`, briefly blocking commits and reads of documents on every replica while it is applied. 0004 builds the live-folder GIN index (§5), which holds a lock that blocks commits, but not reads, while it is applied. 0005 builds the `revisions` indexes retention needs (§11), which block commits, but not reads, while it is applied. 0006 adds `revisions.anchor` (§6.1) and backfills it in the same transaction: its `ADD COLUMN` takes an exclusive lock (`ACCESS EXCLUSIVE`) on `revisions` that it holds through the `UPDATE` of every revision and the scan for `SET NOT NULL` until it commits, so while it is applied every commit, `ListChanges` and retention run blocks on every replica of both releases; the pause grows with the number of revisions (#427). 0007 sets a default on `blobs.released_at`, which takes an exclusive lock on `blobs` that it holds until it commits, through its backfill of unreferenced blobs and its build of the `revisions (created_at, document_id)` index: while it is applied, every blob read and write blocks on every replica, the previous release's included (downloads, `CommitBlob`, the blob checks of `CommitRevision`), and commits also block on the index build. 0008 only creates the empty `purged_revisions` table (§11), which the previous release never names; its retention job, while it still runs during a rollout, purges without writing markers, which costs a device whose cursor sat on such a revision one false-positive resync (§6.1). Markers cannot be backfilled for revisions purged before it, since their anchors are gone. 0009 adds `purged_revisions.purged_at` with a `now()` default (no table rewrite on PostgreSQL 11 and later) and its index; the previous release never names the table, and markers written before it get the migration's time, which only delays their pruning. Its `ADD COLUMN` takes an exclusive lock (`ACCESS EXCLUSIVE`) on `purged_revisions` that it holds through the index build until it commits: while it is applied, purges and the anchor check of every `ListChanges` with a cursor (§6.1, a read of the table) block on every replica that knows the table. That is brief, since 0008 was never released without 0009, so the table is empty or small when 0009 runs (#519). 0012 adds the nullable `devices.registration_id` and a unique index on the small `devices` table (§9.2); the previous release never names the column and registers every call as a new device until every replica runs the new release.
- **High availability (§3).** Every replica must obey these rules, and every new feature must keep them:
  - **Stateless replicas.** A replica keeps no per-client state that lives only in its own process. Sessions, cursors and upload progress live in PostgreSQL (and S3). Consecutive requests of one client, including the chunks of one upload and its commit, may land on different replicas and must behave exactly as against one. Caches every replica can rebuild (the OIDC key set, credentials) are fine.
  - **Coordination through PostgreSQL only.** Advisory locks, `SELECT … FOR UPDATE SKIP LOCKED`, conditional updates and `LISTEN/NOTIFY` are the only cross-replica mechanisms (principle 5): no new infrastructure. Realtime fan-out (§6.4) must therefore reach clients connected to any replica. `LISTEN` needs a session that lasts, so the server needs a direct PostgreSQL connection or a pooler in session mode; transaction or statement pooling (such as PgBouncer's) is unsupported. Every commit transaction issues `NOTIFY`, and PostgreSQL serializes the commits of notifying transactions on one database-wide lock; this is accepted at the expected scale.
  - **Background jobs run on every replica** and must be safe to run concurrently. Their combined effect equals one run, and a replica finding that another got there first is not an error and is not logged as one.
  - **Retry-safe RPCs.** A replica may be killed without warning (`SIGKILL`) at any point. Every RPC must therefore be safe for the client to retry on another replica: the retry succeeds, and no acknowledged write is lost or applied twice. Blob uploads are content-addressed and resumable; revision commits are deduplicated by their client-chosen revision id.
  - **Graceful drain.** On `SIGTERM` a replica fails `/readyz` at once and keeps serving for a configurable delay (`VAULT_SYNC_SHUTDOWN_DELAY`), closing each connection after its response (idle keep-alive connections stay open until the delay ends, so a request sent on one as the signal arrives is not reset) so traffic moves to other replicas before any connection is refused. It then stops accepting connections and closes open WebSockets with close code 1001 ("going away") so clients reconnect elsewhere. In-flight RPCs get a configurable drain timeout (`VAULT_SYNC_SHUTDOWN_TIMEOUT`), and the process exits 0 after a clean drain.
  - **Database connection resets** (a PostgreSQL restart or switchover) are tolerated: connections are checked before use and replaced, and a request that fails mid-query is retried by the client. Managing PostgreSQL failover is the operator's concern (CloudNativePG).
  - **Rolling upgrades.** The previous and the new release serve side by side during a rollout. This is why migrations must be backward-compatible with the previous release (below). An integration test runs both releases against one database. A check a release adds holds only once every replica runs it: for example, replicas of a release before migration 0004 still accept file/folder collisions (§5) until the rollout completes.
  - **Server before plugin (#511).** Users update the plugin independently of the server, so a plugin may be newer than the server it syncs with. A plugin from purge markers on (#506), against a server without them, sees every retention purge of a revision at a device's cursor (or own commit above it) as divergence and resyncs (§8): nothing is lost, but a note another device deleted can come back after a retention purge, and a note whose merge base was purged gets a conflict copy. This lasts until the server is upgraded, so operators upgrade the server first (or together with the plugin), as `docs/deployment.md` (Upgrading) recommends.
  - The recommended deployment (at least 2 replicas, a PodDisruptionBudget, readiness and termination-grace ordering) is documented in `docs/configuration.md`.
- Bounded resource use: max request size, max chunk size, decompression limits, pagination caps, per-user rate limits. Each user may have at most `VAULT_SYNC_MAX_CONCURRENT_RPCS_PER_USER` authenticated RPCs in flight per replica, counted from authentication until the response is fully written; a further call is rejected at once with `RESOURCE_EXHAUSTED`, with an `ErrorDetail` of reason `ERROR_REASON_TOO_MANY_CONCURRENT_REQUESTS`, before its handler runs (no queueing). The client backs off. After a sync call is refused with `RESOURCE_EXHAUSTED`, the engine's next pull or push waits before it calls the server. The wait uses the realtime reconnect's equal jitter (§6.4): half of a ceiling plus a random part of the other half. The ceiling starts at 1 s and doubles with each consecutive refusal, up to 60 s, and a pull or push that succeeds resets it. When the wait ends, the engine pushes. Refused operations stay pending and are retried with their revision ids. The server sends no retry hint. The limit is an in-process count keyed by user ID, dropped when the user's last call ends, so it needs no cross-replica state and no client-visible state is lost with a replica. Responses are bounded by the same size as requests (the bytes sent). Writing each API response is bounded by `VAULT_SYNC_WRITE_TIMEOUT`, counted from the response's first byte, so a client that stops reading releases its connection. It does not bound the time before the response starts, so a long commit is not cut short (§6.2). The upgraded realtime WebSocket is exempt and bounded by its own pings and send queue (§6.4). Concurrent `/readyz` checks share one database ping. Every object-store request fails once its connection makes no progress in either direction for `VAULT_SYNC_S3_IDLE_TIMEOUT` (retried a bounded number of times by the S3 SDK), so a store that stops answering cannot hold a request, a compose slot or the cleanup routine forever; the bound is on silence, not on a whole operation, so a long commit or export that keeps moving is not cut short (§6.2). Each cleanup run is cut short when the next is due.
- The plugin is distributed through GitHub releases (installable with BRAT) carrying `main.js`, `manifest.json` and `styles.css`; `make release` cuts them (a dry run unless `PUSH_ALL=true`). A release's tag, its name and the version in its `manifest.json` are the same semantic version, without a `v`, as Obsidian and BRAT require; the image and chart use the same version (decision, #30). Publishing to the Obsidian community catalog is a non-goal for now.

## 13. Testing strategy

| Layer | Tooling | Runs in |
|---|---|---|
| Go unit | `go test -race`, testify | `make test`, CI |
| TS unit | vitest | `make test`, CI |
| Server integration | real PostgreSQL + S3-compatible store via `docker compose` | `make test-integration`, CI |
| **Sync simulation** | Seeded multi-client harness (`sim/`, TypeScript): N `core` engines over in-memory vaults against a real `vault-sync-server` process (real PostgreSQL + S3). Each client's transport is wrapped in a seeded fault injector (drop request, drop response after the server applied it, delay, reorder, partition, client crash/restart losing in-memory state). Operation schedules are derived from the seed so a failing seed replays the same client-side schedule. Invariants: convergence, no lost acknowledged writes, no resurrected deletes without a concurrent edit, no duplicate content. Failing seeds are minimized and committed as regression cases. Phase 1 (decision): scripted protocol clients stand in for the engines, and the invariants are server-side, checked by the Go driver directly in PostgreSQL. Every acknowledged revision is in history unchanged; `seq` is exactly `1..head_seq`; no two live documents share a `path_key`; and each document's revisions form one chain, so no commit succeeded against a stale base. Messages are delivered one at a time in logical (step) time, so a seed replays deterministically, and concurrency is modelled by interleaving. Phase 2 adds the real engine's pull side (#16) as an extra client behind the same faulty network. Scripted scenarios also drive its push (#17) and run two engines that edit the same documents concurrently (#18): non-overlapping and overlapping edits, a binary file, a line-ending change, and creates at one path and at case-colliding paths, under a lost response and a crash. It pulls whenever the schedule asks a client to pull, and it crashes with client 0, keeping its in-memory vault and journal as a device keeps its disk. After quiescence its vault must equal the server's live heads, its cursor must equal the feed's last `seq`, and it must have deferred nothing and reported none of its own writes as local changes (`engine-convergence`, `engine-deferred`, `engine-echo`). In seeded runs (#22) every engine has a user who creates, edits, renames and deletes files at random, also while it syncs, and the engines' platforms differ, so Windows rules run next to others. After the faults heal the engines push until a round commits nothing, then all must converge (modulo the documents their platforms cannot hold) and three user-visible invariants must hold. `lost-write`: every write the user did not replace themselves survives in a final vault, in history (verified by download), or in what a merge made of it. Which file is which document the harness learns from its own inodes, never from the engine's journal (`sim/lineage.ts`): a create mints an inode, a write or rename keeps it, a delete ends it, and an inode is bound to a document when the engine commits it or writes a revision of it there. `phantom-delete`: every tombstone follows the user's delete of a file bound to that document. The one exception is the crash window of a lost rename (#167 item 2): the app was killed after the user's rename and before the engine settled, and after the crash the engine committed that same file as a new document (the start-up scan found no unique content match). Never as an edit of an existing document: the start-up scan matches a bound file holding another missing document's content to that document (#793). `resurrected-delete` (#276): every deleted document brought back was brought back by a scripted client, or by an engine from a change of its user's to that file (or to an untracked file at its path) not already committed, or by the user's restore. `identity`: no engine commit of a document comes from another document's file. `journal-holder`, after every step: no two documents' bindings name one file, no two live outboxes share a path key, and, once the engine's pull has reached the server's head, no two newest server claims do. Mutation tests prove each catches an engine that loses a write, drops a file, skips a remote delete and pushes the file back, takes one document's file for another's, or lets two documents hold one file. A nightly job runs a long simulation and files an issue with the failing seeds. The network also flags a `protocol` violation when the server refuses (`FAILED_PRECONDITION` or `ALREADY_EXISTS`) a retry of a commit it already applied; in seeded schedules such a retry waits out a backoff of logical steps, so other commits can move the head first, the interleaving of #12. A server built with the `simfault` tag skips the base-revision check, one built with `simfault_retry` refuses an applied retry once the head moved, and CI proves the harness catches both; no runtime switch exists. Multi-user runs (#35) give the vault an owner and two members on their own scripted clients. Between steps the owner demotes members to viewer, promotes them, removes them and invites them again. Each call of a member is checked against its role when it reaches the server: no write of a viewer or removed member is accepted (`revoked-write`), no call of a removed member is answered (`removed-read`), and refusals carry the right code (`authorization`). Every other invariant must still hold, so every acknowledged commit, including those made before a demotion, stays. A server built with `simfault_authz` accepts viewers' writes, and CI proves the harness catches it. See `docs/testing/simulation.md`. | `make test-sim`, CI (short), nightly (long) |
| Crypto vectors | shared `testdata/crypto/` vectors | Go + TS unit tests |
| Path vectors | shared `testdata/paths/` vectors: `path_key` (`vectors.json`) and validity (`validity.json`) | Go + TS unit tests; validity also through `CommitRevision` (integration) |
| Plugin e2e | `wdio-obsidian-service`: the built plugin in a real Obsidian whose version is pinned (Renovate bumps it), driven by WebdriverIO against a real `vault-sync-server` that an `e2e`-tagged Go driver starts. Specs check that the plugin loads, that a second vault opens, that the server is reachable with a test token, and run the `VaultAdapter` conformance suite inside Obsidian against the Obsidian adapter through a test-only harness plugin. The `Journal` conformance suite runs there too, against the IndexedDB journal on Obsidian's own IndexedDB. They also cover editor-safe writes to an open note, that startup indexing is not reported as changes, that each vault's journal is keyed by its own vault id, and that disabling and re-enabling the plugin resumes sync from the IndexedDB journal. Also runs in emulated mobile mode. See `docs/testing/e2e.md`. | `make test-e2e` (Linux, headless via xvfb, in the dev VM); CI on Linux, Windows and macOS, plus emulated mobile |
| Android | checklist in `docs/testing/android.md`: each check the layers above can make is an automated test there (including that the manifest allows mobile and the bundle loads no Node or Electron module); only what needs a physical device (BRAT on Android, Android pausing or killing the app, real network changes, battery) is manual. An Android emulator job is recommended (partially) by spike #187 (`docs/testing/e2e.md`). | CI for the automated checks; a human, on a device, before each release |

## 15. Phases

Work is tracked as GitHub milestones and parent issues. Each phase ends with a bug hunt (and a security review where the phase touches the attack surface) before the next starts.

1. **Foundations** — protocol schema, server core (store, blobs, revisions, auth, authz), simulation harness skeleton, CI.
2. **Single-user file sync** — plugin engine + adapter for desktop and Android, merge, conflicts, history/restore, export job, Helm chart. Dogfooding starts here.
3. **Vault sharing** — membership management, invitations, roles in UI.
4. **End-to-end encryption** — key hierarchy, escrow, export decryption, crypto vectors, independent crypto review. Until then, creating an E2EE vault is rejected (§9.3).
5. **Live collaborative editing** — Yjs documents, conversion, editor binding, awareness, compaction.
