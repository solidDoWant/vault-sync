# vault-sync — Specification

This is the authoritative technical reference for vault-sync: its purpose, design principles, architecture, data model, sync protocol, encryption scheme, and repository layout. It is a living document — update it in the same change that alters any behavior it describes. Where this document says "decision", the reasoning is recorded so that a later change can revisit it deliberately rather than by accident.

This project is bootstrapped to mirror the conventions of [`tape-archiver`](https://github.com/solidDoWant/tape-archiver) and [`media-processor`](https://github.com/solidDoWant/media-processor): Go, Nix-reproducible builds, issue-driven development with Given/When/Then acceptance criteria, and a testing-first philosophy.

## 1. Purpose

vault-sync is a self-hosted replacement for Obsidian Sync. It has two halves:

- an **Obsidian community plugin** (TypeScript) that watches a vault and synchronizes it, and
- a **sync server** (Go) that stores vault state in **PostgreSQL** (metadata, revisions) and an **S3-compatible object store** (file contents).

It exists because the available self-hosted option (obsidian-livesync) requires CouchDB, has a history of data-loss and reconciliation bugs, is thinly documented, and has no multi-user model. vault-sync targets a small number of users (one household / small team) on infrastructure the operator already runs.

## 2. Design principles

These are non-negotiable. When a trade-off arises, resolve it in favor of the principle, not convenience. Call out any change that touches one.

1. **No acknowledged write is ever lost.** Once the server has acknowledged a revision, that content is recoverable — as the current head, in revision history, or as a conflict copy — until an explicit, retention-governed purge. Neither the client nor the server ever silently discards a user edit. Deletion is a tombstone, never an erase.
2. **One source of truth per concern.** The server's revision log is the source of truth for vault history. The local vault on disk is the source of truth for un-pushed local edits. The client keeps exactly one durable journal bridging the two. No additional replicated databases or chunk layers.
3. **Everything is tested — including adversarially.** Sync correctness is proven by a deterministic, seeded, multi-client simulation with fault injection (partitions, crashes, reordering), not by example tests alone. If it is not tested, it does not work.
4. **Small, defensible attack surface.** The server is exposed to the internet. Keep the API small, typed, and authenticated by default; every endpoint enforces vault-level authorization; resource usage is bounded (request sizes, decompression, pagination).
5. **Operator infrastructure only.** PostgreSQL, S3-compatible storage, and OIDC. No new database types.

## 3. Target environment

- **Server:** Kubernetes (Talos) homelab. PostgreSQL 14 or newer via CloudNativePG (client-certificate auth; certificates rotate — the server must re-read them, never cache them for the process lifetime). Object storage via Ceph RGW (S3 API). Identity via Authentik (OIDC). Exposed through an Istio gateway with a Coraza WAF in front: **inspected request bodies above 1 MiB are rejected**, so every upload is chunked at or below a configurable size (default 768 KiB).
- **High availability:** the server runs as an HA deployment: two or more identical replicas behind one Service, sharing one PostgreSQL database and one S3 bucket. Terminating any replica, for example for node maintenance, must have **no client-visible impact**. The rules that make this hold are in §12.
- **Clients (required):** Obsidian desktop on **Windows** and **macOS**, Obsidian mobile on **Android**. Linux desktop is the development/test platform. **iOS is best-effort** (not a release blocker) — do not take design decisions that preclude it.
- **Backups:** a plaintext export of every vault (decrypted where escrow is enabled, §9.4) is written to a filesystem path that the operator's tape-archival tooling picks up. This replaces livesync-bridge. **No readable live document is ever left out of an export** (decision, #52/#178). Each vault's files sit in a browsable tree at `<out>/<vault-id>/<path>`. A document whose path that tree cannot hold (a file/folder collision such as `a` and `a/b.md`, a name the filesystem rejects such as one over 255 bytes, or an invalid or non-UTF-8 path) is written to `<out>/<vault-id>.unplaced/<document-id>` instead. A streamed JSON Lines manifest, `<out>/<vault-id>.manifest.jsonl`, lists every live document: id, original path, kind, head revision id, size, SHA-256, status (`placed`, `unplaced` or `missing`) and where its bytes are. The unplaced tree and the manifest sit beside the vault's directory, never inside it, so no user file can be mistaken for them. The layout and manifest are a versioned format (format 2, in the marker and every manifest), specified in `docs/export.md`, so the Phase 6 importer can restore exactly. Content that is missing or corrupt in S3 is the only reason a live document's bytes can be absent; the manifest lists it as `missing` and the run reports `partial`. History, tombstones and (until Phase 4) E2EE vaults are not exported.

## 4. Architecture

```
 Obsidian (desktop / Android)                       Kubernetes
 ┌──────────────────────────────┐    HTTPS     ┌──────────────────────────────┐
 │ plugin/src/obsidian  (adapter)│  ConnectRPC │ vault-sync-server (Go)        │
 │   vault events, editor, UI    │◄──────────►│   API (ConnectRPC, protobuf)  │
 │ plugin/src/core  (sync engine)│  WebSocket  │   realtime hub (WebSocket)    │──► PostgreSQL (CNPG)
 │   journal (IndexedDB), merge, │◄──────────►│   authz, quotas, retention     │──► S3 (Ceph RGW)
 │   crypto, protocol client     │             │                               │──► Authentik (OIDC JWKS)
 └──────────────────────────────┘             └──────────────────────────────┘
                                               ┌──────────────────────────────┐
                                               │ vault-sync export (CronJob)   │──► plaintext tree for tape
                                               │   holds escrow private key    │
                                               └──────────────────────────────┘
```

- **`plugin/src/core`** is a pure TypeScript library: the sync engine, journal, merge, crypto, and protocol client. It **must not import `obsidian`** (lint-enforced) or use Obsidian's globals: `make lint` type-checks it, with its tests and `sim/`, as a separate program (`plugin/tsconfig.core.json`) that has neither Obsidian's global augmentations nor DOM-only globals, and fails if any route (import, `/// <reference>`, `src/main.ts`) brings Obsidian into it. Core code must be plain `.ts` modules with no triple-slash directives, no `declare global` and no JavaScript imports, and the program may contain nothing from outside `src/core`, `sim/`, `src/gen` and dependencies. Packages that `src/core` and `sim/` import directly must be declared in `plugin/package.json` (`dependencies` or `devDependencies`, or their `@types` package) and are never `obsidian`, so Obsidian's own transitive dependencies (e.g. `@codemirror/view`, `moment`) cannot slip in. Any other code file under `src/core` (`.js`, `.mts`, `.tsx`, `.d.ts`, …) fails the check even if nothing imports it; non-code files there are ignored. It talks to the vault through a `VaultAdapter` interface so the simulation harness can drive it against an in-memory vault.
- **`plugin/src/obsidian`** is the thin adapter: `Vault`/`FileManager` events, editor integration, settings UI, status bar, conflict UI. `ObsidianVaultAdapter` implements `VaultAdapter` on the Vault API and passes the conformance suite inside real Obsidian (e2e). Paths with a hidden segment (`.obsidian/`, `.trash/`, any `.name`) and paths Obsidian's `normalizePath` would store under another name are outside it: never listed, read or reported, and a write or rename onto them is refused as `path-conflict`, so the engine defers such a revision instead of touching the disk (decision, #24; `.obsidian/` config sync is #28). Renames use `Vault.rename`, never `FileManager.renameFile`, because a synced rename must not rewrite links: the other device's link updates arrive as revisions of their own. `SyncSession` ties the adapter and the engine to the plugin's lifecycle: it starts once the workspace layout is ready, resumes from the journal's cursor, and stops in `onunload`, so disabling and re-enabling the plugin never starts a full resync.
- **`vault-sync-server`** is a single Go binary. The server **never merges content**: it orders revisions, enforces optimistic concurrency, stores bytes, and fans out notifications. All merging happens on clients (this keeps the server compatible with end-to-end encryption).
- **`vault-sync export`** is a subcommand of the same binary, run as a separate Deployment/CronJob with its own credentials. It is the only component that may hold the escrow private key. It only reads PostgreSQL (its sessions are `default_transaction_read_only`) and S3. Each vault is exported as of its `head_seq` (every document's latest revision at or below it; tombstoned documents are left out) to `<out>/<vault-id>/<path>`, byte for byte; the directory is named by id because vault names are mutable, user-chosen and can collide (decision, #29). The tree is written to a staging directory beside `<out>` and swapped in atomically (`renameat2` `RENAME_EXCHANGE`), so an interrupted run leaves the previous export untouched. Every path is re-checked with the shared vault-relative rule (§6.2) and written through a handle confined to the vault directory, without following symbolic links. A document whose path cannot be placed in that tree goes to the vault's unplaced tree by document id, and every live document is listed in the vault's manifest (§3). A document whose content is missing or corrupt has no bytes in the export: it is listed in the manifest as `missing` and reported by id, and the run still swaps in its tree (decision, #52). The job prints a JSON summary and exits non-zero on any failure or missing content; it has no metrics endpoint. Until Phase 4, E2EE vaults are skipped. Details: `docs/export.md`.

### 4.1 Protocol transport (decision)

The API is defined in **protobuf** under `proto/` and served with **ConnectRPC** (Connect protocol over HTTP/1.1 + JSON or binary) — one schema generates both the Go server stubs and the TypeScript client. Realtime traffic (change notifications now, Yjs updates and awareness later) uses a **WebSocket** carrying protobuf-framed messages, because browsers/Electron cannot do client-streaming over fetch. The server sets CORS headers for Obsidian's app origins (`app://obsidian.md`, `capacitor://localhost`, `http://localhost`) and validates `Origin` on WebSocket upgrade.

Generated code is committed (`make generate` regenerates; CI fails on drift). Schema changes must stay backward compatible: `make lint` (and CI) runs `buf breaking` with the `FILE` rule set against `master`, and any deliberate exception is a narrowly scoped, temporary `ignore_only` entry in `buf.yaml` (`docs/testing/proto-compatibility.md`).

## 5. Data model

All identifiers are UUIDv7 unless stated. Every table below is scoped by `vault_id`; every query filters by it.

| Entity | Key fields | Notes |
|---|---|---|
| `users` | `id`, `oidc_issuer`, `oidc_subject`, `display_name` | Created on first authenticated request (JIT). |
| `devices` | `id`, `user_id`, `name`, `public_key` (X25519), `last_seen` | One per plugin install; at most 100 per user, never removed in v1 (§9.2). |
| `vaults` | `id`, `name`, `encryption` (`none` \| `e2ee`), `escrow` (bool), `head_seq` | `head_seq` is the vault-wide change counter. |
| `vault_members` | `vault_id`, `user_id`, `role` (`owner` \| `editor` \| `viewer`) | Authorization source of truth. |
| `documents` | `id`, `vault_id`, `kind` (`blob` \| `text` \| `yjs`), `head_rev_id`, `path_key`, `deleted` | Stable identity across renames. `deleted` mirrors the head revision's tombstone flag. `path_key` unique per vault among live (`deleted = false`) documents, enforced by a unique partial index on the SHA-256 digest of `path_key` (decision, #121): a btree entry holds at most 2704 bytes, while a `path_key` may be up to 8192, so the key itself cannot be indexed. A digest collision could only refuse a commit, never treat two paths as one, since nothing looks documents up by `path_key`. |
| `revisions` | `id`, `document_id`, `vault_id`, `seq`, `parent_rev_id`, `content_ref`, `path`, `deleted`, `device_id`, `created_at` | Append-only. `seq` is assigned from `vaults.head_seq` in the same transaction. |
| `blobs` | `vault_id`, `blob_id`, `size`, `state` (`uploading` \| `complete`) | Content-addressed per vault; bytes live in S3 at `vaults/{vault_id}/blobs/{hex(blob_id)}`. A row is written only once the blob is complete; upload progress lives in `blob_uploads` (§6.2). |
| `blob_uploads`, `blob_upload_chunks` | `id`, `vault_id`, `blob_id`, `size`, `received_size`, `state` (`uploading` \| `finished`); accepted chunks by `offset` | Resumable upload sessions (§6.2). At most one `uploading` session per `(vault_id, blob_id)`. |
| `key_slots` | `vault_id`, `epoch`, `recipient_kind` (`user` \| `escrow`), `recipient_id`, `wrapped_key` | E2EE only (§9). |
| `yjs_updates` | `document_id`, `seq`, `update` | Phase 5 (§10). |

**Paths.** A path is an attribute of a revision, not an identity. Uniqueness is enforced on `path_key`, a normalized form of the path: Unicode NFC, then case-folded, so that two clients cannot create paths that collide on case-insensitive (Windows, macOS, Android/iOS) filesystems. Precisely (decision): `normalize(path) = NFC(toCasefold(NFD(path)))` — Unicode canonical caseless matching (Unicode §3.13, D145) emitted in NFC, using **full, locale-independent** case folding (`CaseFolding.txt` statuses C and F; never the Turkic T mappings), so `Straße`/`STRASSE` collide, `İ` folds to `i̇` and dotless `ı` folds to itself. Full folding was chosen over simple folding because it catches strictly more collisions; locale independence keeps the key identical on every device. Separators, whitespace and dots are not altered and no validation happens here. Go (`internal/pathkey`) and TypeScript (`plugin/src/core/pathkey`) share one folding table generated from a vendored `CaseFolding.txt` and must agree on every vector in `testdata/paths/`. Normalization uses each platform's NFC/NFD (`golang.org/x/text/unicode/norm`, `String.prototype.normalize`), so keys can differ only for characters whose normalization data one side does not yet have (characters added in recent Unicode versions); closing that gap is deferred to [#63](https://github.com/solidDoWant/vault-sync/issues/63). For E2EE vaults the path itself is ciphertext and `path_key = HMAC-SHA256(path_key_secret, normalize(path))`, so the server can still enforce uniqueness without learning the path. **Files and folders (decision, #134).** Folders are implicit, so a live document's path cannot name the folder of another live document's: a file `notes` and a document `notes/c.md` cannot both exist on any filesystem. The server refuses a live document whose `path_key` has a folder (a proper prefix ending before a `/`) that is another live document's `path_key`, or is itself a folder of another live document's `path_key`. Because the comparison is on `path_key`, `Folder` collides with `folder/c.md` and `straße` with `STRASSE/a.md`. Tombstones never collide. Only `/` is a folder boundary here: `path_key` keeps `\` as it is, so `notes\c.md` (a document under `notes` on Windows) is not compared with `notes` yet, just as `a/b` and `a\b` do not share a `path_key`. Both directions are index probes, not scans: the live `path_key` digest index answers whether a folder of the new key is a live key, and a GIN index over the digests of every live key's folders (each digest covering the vault id) answers whether the new key is a folder of one. For E2EE vaults the `path_key` is an HMAC that cannot be split into folders, so the server cannot enforce this there; whether and how to enforce it in E2EE vaults is a Phase 4 decision.

**Content addressing.** For plaintext vaults `blob_id = SHA-256(content)`. For E2EE vaults `blob_id = HMAC-SHA256(blob_id_secret, plaintext)` (equality leaks only within a vault), and clients verify the id after decryption.

## 6. Sync protocol

### 6.1 Pull

`ListChanges(vault_id, since_seq, page_size)` returns revisions with `seq > since_seq` in `seq` order, paginated (the client passes the last `seq` it received as the next `since_seq` until `has_more` is false; the server caps `page_size` at 1000 and defaults it to 500, and also ends a page early where its encoding would exceed the send limit, so a page of long paths never fails as too large; every page holds at least one revision if one exists, and startup requires the send limit to fit a response with one maximum-size revision). A client's durable cursor is the highest `seq` it has fully applied to disk. Clients pull on startup, on a realtime `vault_changed{seq}` notification, and on a timer as a fallback.

### 6.2 Push (optimistic concurrency)

1. Upload content: `BeginBlob` → `PutBlobChunk`* → `CommitBlob`. Idempotent: an already-complete `blob_id` short-circuits. Resumable: `BeginBlob` reports the bytes already received, and chunks are appended strictly sequentially by offset. Chunks are at most the configured size (§3). The server verifies the content hash on commit for plaintext vaults. Downloads are ranged (`DownloadBlob(offset, length)`), each response bounded by the server; a client continues from the end of a shorter range than it asked for. Both limits hold in the request's codec (decision, #135): `BeginBlob` advertises, as `max_chunk_size`, the configured chunk size to binary clients and to JSON clients the largest chunk whose base64 encoding (four bytes for every three), plus 1 KiB of framing and a thousandth for gzip, fits the request limit; `DownloadBlob` caps a range at the same size. The size depends only on the request, so every replica agrees.

   Server-side details (decision): S3 multipart parts must be at least 5 MiB (except the last), which chunks below the 1 MiB body limit never are, so chunks are **staged objects plus a server-side compose**. Each accepted chunk is its own object under `vaults/{vault_id}/uploads/{upload_id}/`, its key unique to the write so a writer that lost a race for an offset never overwrites the accepted chunk; a chunk is accepted by a compare-and-set on the session's `received_size`, so concurrent uploaders of one blob share a session and a loser gets `FAILED_PRECONDITION` and resumes from `BeginBlob`. Every chunk but the last is at least 64 KiB (or the maximum chunk size for the request's codec, if smaller), bounding the objects per upload. `CommitBlob` streams the staged chunks in order into the blob's object, with one `PutObject` up to 8 MiB and a multipart upload of 8 MiB parts above that, hashing as it goes; the object is written or its multipart upload completed only after the hash matched, and the `blobs` row is written only after that, so a mismatching upload never becomes visible and its session is discarded. Bounds: the maximum chunk size plus 1 KiB of framing must fit the maximum request body (checked at startup), the Connect send limit equals the request limit, a blob is at most the configured maximum (at most 80 GiB, S3's 10,000 parts of 8 MiB), and a vault has a bounded number of sessions in progress. Sessions idle for longer than the upload TTL are reaped by a periodic, bounded cleanup that deletes their staged objects and then the session, and aborts multipart uploads older than the TTL (an interrupted commit's are otherwise invisible and leak storage) unless their blob has a session active within the TTL. Every server instance runs the cleanup at the same time, so every step is idempotent: a session is claimed atomically, and an upload or object another instance already removed counts as removed. A commit records session activity after every 8 MiB part it composes (and at least every minute while it waits for a compose slot), so a commit in progress, on any instance, is never reaped however long it takes; upload sessions hold no per-instance state, so chunks and the commit may go to different instances, and a commit interrupted by an instance dying is retried to success on another.
2. `CommitRevision(document_id, revision_id, base_rev_id, kind, content_ref, path, path_key, deleted, device_id)`. The server accepts only if `base_rev_id` equals the document's current head (or the document is new and `base_rev_id` is empty). It assigns `seq`, advances `head_seq`, and broadcasts `vault_changed`. Document and revision ids are client-generated UUIDv7s; retrying a commit with the same `revision_id` and identical fields returns the already-committed revision, so a lost response does not turn into a spurious head-moved conflict. `path_key` is sent only for E2EE vaults (§5); for plaintext vaults the server derives it from `path`.

   Server-side details (decision): a commit is one PostgreSQL transaction that first locks the vault row, so commits to one vault are serialized by the database across every server replica, with no per-process state: `seq` comes from `UPDATE vaults SET head_seq = head_seq + 1 … RETURNING` in that transaction, so it is gapless, and a revision commits (becomes visible to `ListChanges`) only after every lower `seq`, so a cursor never skips one. Within the transaction the checks run in this order: the device belongs to the caller (`NOT_FOUND`); an existing revision with this `revision_id` in this vault is returned if its fields are identical and is `INVALID_ARGUMENT` otherwise — **before** the head comparison, so a retry whose first attempt was applied still succeeds after other commits moved the head; the head comparison (`FAILED_PRECONDITION` carrying the document, with its current `head_rev_id`, as a `Document` error detail; also `FAILED_PRECONDITION` if a base is given for a document that does not exist in the vault); the kind matches the document's; the content is a `complete` blob in the same vault whose stored size equals `content_ref.size` (`FAILED_PRECONDITION` if not complete, `INVALID_ARGUMENT` on a size mismatch; the stored size is what is ever returned). The document row's `head_rev_id`, `path_key` and `deleted` are updated in the same transaction as the revision insert, so `deleted` always mirrors the head and the live `path_key` index is exact; a collision on it is `ALREADY_EXISTS`. Then, if the revision is live and its `path_key` is new to the document (or the document was a tombstone), a file/folder collision with another live document (§5) is also `ALREADY_EXISTS`; this check runs under the vault row lock, so two commits that would each complete a collision, on any replicas, are serialized and the second is refused. A revision that keeps its document's live `path_key` (an edit) or deletes it is never refused for this, so a collision committed before the rule existed never blocks an edit or a delete. Client-generated ids already used in another vault are `INVALID_ARGUMENT`; all lookups are scoped to the authorized vault, so another vault's ids are otherwise simply not found. Plaintext paths are at most 4096 bytes of UTF-8 without control characters, vault-relative, and at most 8192 bytes once normalized. Vault-relative is defined for every supported client platform (decision): `/` and `\` are both separators; the path must not start with a separator (which also rules out UNC, `\\?\` and `\\.\` prefixes) or with an ASCII letter and a colon (a drive prefix such as `C:`, `C:\x` or the drive-relative `C:x`); and no segment may be empty or consist only of dots and spaces (`.`, `..`, and forms such as `.. ` or `...` that Windows reduces to them). Names that are merely unmaterializable on Windows (reserved device names such as `CON.md`, a colon anywhere but a leading drive prefix, trailing dots or spaces on other names) are accepted; the client handles them. Go (`internal/vaultpath`, used by `CommitRevision`) and TypeScript (`isVaultRelativePath` in `plugin/src/core/vaultpath`) must agree on every vector in `testdata/paths/validity.json`, and a client must apply the rule to every path it receives before touching its disk, including E2EE paths after decryption, which the server cannot check. A path that breaks the rule is `INVALID_ARGUMENT` and nothing is written; a path or `path_key` the database refuses (empty, over its bound, or text it cannot store) is `INVALID_ARGUMENT`, never `INTERNAL`. Until Phase 4, commits to E2EE vaults are `FAILED_PRECONDITION` (§9.3). The commit transaction also queues a PostgreSQL `NOTIFY` on channel `vault_changed` (payload `<vault_id>:<seq>`), which PostgreSQL delivers to every replica exactly when, and only if, the transaction commits; an idempotent retry notifies nothing (§6.4).
3. On `FAILED_PRECONDITION` (head moved), the client pulls the new head, merges (§7) against the common base, and retries with the new head as base.

A revision is **acknowledged** only when `CommitRevision` returns success. Principle 1 applies from that moment.

### 6.3 Renames, deletes, creates

- **Rename** is a revision with a new `path` and the same `content_ref`.
- **Delete** is a revision with `deleted = true` (tombstone). Its content stays reachable through history.
- **Create** races: if two clients create documents whose `path_key` collides, the second commit fails with `ALREADY_EXISTS`; that client renames its document to `<name> (conflict <device> <date>).<ext>` and commits again.
- **File/folder** collisions (§5) are `ALREADY_EXISTS` too, for creates, renames and resurrections alike: a live document cannot be committed at the path of another live document's folder, or under a path another live document holds as a file. Renaming the file name is enough when the document's own path is the folder of another document (`notes` becomes `notes (conflict <device> <date>)`). When the document lies under another document's file, renaming its file name does not help (`notes/c (conflict …).md` is still under `notes`); the client must move it out of that folder, for example by applying the conflict suffix to the colliding folder segment (`notes (conflict <device> <date>)/c.md`).
- Concurrent **rename vs. edit** of the same document merges cleanly: path and content are independent fields of the merge.
- Concurrent **delete vs. edit**: the edit wins (the document is resurrected with the edited content) — never lose an edit to a delete.

### 6.4 Realtime channel

One WebSocket per device (`GET /v1/realtime`), multiplexing subscriptions to any number of the user's vaults up to a server cap (`GetServerInfo.max_realtime_subscriptions`), authenticated with the same bearer token. Each binary WebSocket message is one protobuf frame (`ClientFrame` / `ServerFrame` in `proto/vaultsync/v1/realtime.proto`, each a `oneof` envelope). Client → server: `subscribe{vault_id}`, `unsubscribe{vault_id}`. Server → client: `subscribed{vault_id, head_seq}`, `vault_changed{vault_id, seq}`, `error`, and later membership/key-epoch changes. Field numbers 100–199 of both envelopes are reserved for the Phase 5 Yjs frames. Phase 5 adds Yjs subscribe/update/awareness messages multiplexed by `document_id`. The channel is a latency optimization only; correctness never depends on receiving a notification.

Server-side details (decision, #52):

- **Upgrade.** The client offers the subprotocols `vaultsync.v1` and `vaultsync.bearer.<access token>` (browsers cannot set headers on a WebSocket request; non-browser clients may send `Authorization: Bearer` instead, but not both). The server validates `Origin` against the CORS allow-list (an absent `Origin` is allowed for non-browser clients), authenticates the token with the RPC authenticator, and echoes only `vaultsync.v1`. It refuses the upgrade with 403 (origin), 401 (missing or invalid token), 400 (no `vaultsync.v1`), 429 (too many connections for the user) or 503 (instance full or draining). The token never appears in a URL, and the `Sec-WebSocket-Protocol` header is never logged.
- **Authorization.** Every `subscribe` resolves the caller's `vault_members` role; a non-member and a vault that does not exist get the same non-fatal `NOT_FOUND` error frame. Membership is checked again before every delivery: a removed member's subscription ends with an unsolicited `NOT_FOUND` error frame naming the vault, and no further notifications for it are sent.
- **Token expiry.** There is no in-band refresh. When the access token's `exp` passes, the server sends a fatal `UNAUTHENTICATED` error frame and closes (1008); the client reconnects with a fresh token and re-subscribes.
- **Fan-out.** Each replica holds one PostgreSQL connection that `LISTEN`s on `vault_changed` and delivers each notification to its local subscribers, so a commit on any replica reaches subscribers on every replica. Undelivered notifications of one vault are coalesced to the newest `seq`. If the listening connection is lost the replica reconnects with jittered backoff and then sends every locally subscribed vault's current `head_seq`, so commits made meanwhile are not missed. Subscriptions are per-connection state only: a client reconnecting to another replica re-subscribes and pulls from its cursor.
- **Bounds.** Inbound frames are at most 4 KiB (larger closes with 1009); the inbound rate is 20 frames per second with a burst of the subscription cap plus 32 (excess is a fatal `RESOURCE_EXHAUSTED`); subscriptions per connection, connections per user and connections per replica are capped (`docs/configuration.md`). Each connection's send queue is bounded; a client too slow to drain it, or that does not answer pings, is disconnected rather than buffered. Malformed or text frames are a fatal `INVALID_ARGUMENT`.
- **Drain.** On shutdown every socket is closed with 1001 ("going away"); clients reconnect with backoff and jitter.

## 7. Merge rules (client side)

Classification is by extension and is configurable:

| Kind | Default for | Concurrent-edit behavior |
|---|---|---|
| `text` | `.md`, `.txt`, `.css`, `.js`, other UTF-8 text | 3-way merge (`base`, `local`, `remote`). Non-overlapping changes merge silently. Overlapping changes: remote wins in place, and the local version is written as a conflict copy next to it. Never inject conflict markers into the note. |
| `blob` | everything else (images, PDFs, `.canvas` until a JSON merge exists) | Remote wins in place; local version becomes a conflict copy. |
| `yjs` | `.md` in vaults with live editing enabled (Phase 5) | CRDT merge; no conflicts. |

Conflict copies are ordinary documents and sync like any other file. Every conflict is also logged to the client's conflict view.

Engine details (decision, #18):

- **Classification.** A document's kind is chosen when it is created, from its path's extension (`classifyByExtensions` in `plugin/src/core/engine/remote.ts`, configurable per engine; the default text extensions are `md`, `txt`, `css` and `js`), and never changes. The merge follows the document's kind, so changing the configuration affects only new documents. A `text` document is also merged as a blob if any of its three versions is not valid UTF-8.
- **Text merge.** The engine's default merge hook (`threeWayMerge`) uses the same line-level three-way merge as editor-safe writes (§8; `plugin/src/core/merge/text-merge.ts`, a Myers diff of each side against the base). Two changes overlap if they touch the same base line, or if both insert at the same place. A change made identically on both sides counts once. Changes on adjacent lines merge. If only one side changed, its bytes are taken as they are. Otherwise lines are compared without their terminators. The line-ending style (CRLF or LF, whichever a version mostly uses) and the presence of a final newline are each merged as one field of their own: the side that changed it from the base wins, and the local side wins if both did. So converting line endings, or adding or removing the final newline, never conflicts with an edit.
- **Deletes and renames.** An edit wins over a concurrent delete on either side (§6.3). The path is merged apart from the content. A local rename wins over a remote edit and over a concurrent remote rename.
- **Conflict copies.** A conflict copy is made for overlapping edits, for concurrent edits of a blob, and for two versions with no common base: a remote create or rename onto a path a local file holds that is no document's, or a document brought back on both sides after a delete. The remote version stays in place, and the local version is written to `<name> (conflict <device> <date>).<ext>` in the same folder. `<device>` is the device's name, with characters that some platform forbids in file names replaced by `-`. `<date>` is the UTC time as `YYYY-MM-DD HHmmss`. If that name is taken, a counter is added (`… HHmmss 2)`). The name is shortened, from the end of `<name>` and by whole characters, until the file name fits 255 bytes and the path fits §6.2's limits (4096 bytes, 8192 normalized). If no name fits, nothing is written: the local version stays in place, the remote revision stays deferred, and the conflict is logged without a copy, so it can be surfaced (#100). A file in the way at a renamed document's new path is never taken for that document's local version: the document's own file (at its synced path, or where a local rename moved it) is merged, and the file in the way, if no document's, is kept as a `concurrent-create` copy, its unacknowledged create dropped, and then removed so the document can move there (review of #173). If the file in the way is another document's (the journal has it there, or a pending operation or an unpushed rename of a known document put it there), the merge does nothing and the revision stays deferred, so nothing is lost, but the two documents wait until the user frees the path (resolving that case like a refused create is #176 item 2). A create refused with `ALREADY_EXISTS` (§6.3) whose path the pull did not resolve (the other document's path differs only by case or Unicode form) is moved to such a name and committed there under its own document id. If no name fits, it stays pending and is reported as rejected.
- **Conflict log.** The journal records every conflict before acting on it (`ConflictRecord`): the document, the path, the reason (`overlapping-edits`, `binary`, `concurrent-create`, `path-taken`), the copy's path and content hash, the remote revision, and the time. This log is what the UI's conflict view reads. A copy interrupted by a crash is finished under the logged name and never written twice.

## 8. Client durability

- **Journal.** The engine keeps a journal in IndexedDB: per document, the last synced `rev_id`, the base content hash, and pending local operations. A pending operation is removed only after `CommitRevision` succeeds.
- **IndexedDB journal (decision, #21).** `IndexedDbJournal` (`plugin/src/core/journal/indexeddb.ts`) lives in `core` because IndexedDB is a standard Web API that the core program's `WebWorker` lib types. It is handed its `IDBFactory` and never reads a global, so Node (vitest, the simulation) runs it on `fake-indexeddb`. Every `Journal` method is exactly one IndexedDB transaction, with `strict` durability for writes, and its promise resolves only when that transaction has completed. Each durable step of the engine is therefore all-or-nothing, and a step whose promise resolved survives a crash. The schema is an append-only list of migrations, run inside one `versionchange` transaction. v1 holds the cursor, document states, pending operations (auto-incremented keys keep their order) and deferrals, which are stored whole, `merging` marker included. v2 adds the conflict log. Its keys are auto-incremented too, so the log stays oldest first, and a record replaced by `id` keeps its key and so its place. A migration carries existing data forward, the cursor included, so an upgrade never forces a full resync. A migration that fails leaves the journal at its old version with its data. A journal written by a newer schema is refused (`JournalVersionError`), never deleted or downgraded. When another connection upgrades the schema, this one closes and its later calls fail. All vaults of one Obsidian install share one IndexedDB origin, so `openVaultJournal` (`plugin/src/obsidian/journal.ts`) opens one database per local vault and server vault. The database name is built from Obsidian's id for the open vault (`app.appId`, which is not in Obsidian's public typings), the server vault id and the normalized server URL. Two local vaults therefore never share a journal, even when they sync the same server vault. Without a vault id the journal does not open. The journal is not encrypted at rest.
- **Never overwrite unsynced local edits.** Before writing remote content to disk, the engine checks the on-disk content hash against the journal's base hash. On a mismatch it treats the disk content as a local edit and merges first.
- **Base content.** For 3-way merge the client needs the base content. It is fetched from the server by `rev_id` when it is not cached locally.
- **Echo suppression.** Writes performed by the engine are recorded (path + content hash) so that the resulting vault events are not treated as user edits. Each write, rename and delete is recorded before it is made and dropped if it fails. A create or modify event is an echo only if the file then holds content the engine wrote to that path, so a user edit that lands on top of an engine write, even one a debouncing watcher folds into the same event, is still reported. In doubt, an event is reported as a user edit: reporting one twice is harmless, missing one is not.
- **Editor-safe writes (decision, #24).** A remote write to a UTF-8 file open in a Markdown editor is a line-level three-way merge inside `Vault.process`: the disk text is the base (the engine has checked it equals the journal's base), the editor buffer is the base plus any unsaved keystrokes, and the remote content is the other side. Only the remote changes are applied to the editor, as one editor transaction, so the cursor, selection and unsaved keystrokes survive; the disk gets the same merged text. With nothing unsaved that is exactly the remote content (an echo). With unsaved keystrokes it is the remote content plus them, which the engine then reports as the user's edit it is. If a remote change touches a line the user changed (or both insert at the same place), the adapter saves the editor and rejects the write, so neither side is overwritten: the pull fails at that revision, and the next pull finds the saved edit and hands the document to the merge path. Files with CRLF line endings get no line merge: the editor takes the whole new text only when nothing is unsaved. A file open in any other editing view (a canvas, Bases, a plugin's file view) gets no merge, because Obsidian replaces such a view's state with the disk's: the write goes ahead only if every such view is a text file view whose data equals the disk, checked inside `Vault.process`. Otherwise the adapter saves the views and rejects the write in the same way, so their unsaved state is never discarded (canvas merging is #163). Read-only viewers (images, PDFs, audio, video) hold nothing unsaved and are written as usual.
- **Startup indexing.** While Obsidian loads a vault it fires `create` for every existing file. The Obsidian adapter reports no vault events before the workspace layout is ready, so that storm is never taken for user edits; changes made while Obsidian was not running are found by content hash against the journal, not by events.
- **Change detection uses content hashes, never mtimes.** mtimes are unreliable across platforms and sync tools.
- **Crash safety.** Mobile apps are killed without warning. Every step must be resumable from the journal: an interrupted upload resumes, an interrupted apply re-checks hashes.
- **Platform path rules.** Paths that cannot be materialized on the local platform (Windows reserved names `CON`/`NUL`/…, trailing dots or spaces, `\`, `:` and other forbidden characters, over-long paths) are not silently dropped: the document is tracked as "unmaterializable" and surfaced in the UI.
- **Pull and apply (decision, #16).** The engine (`plugin/src/core/engine`) applies the change feed in `seq` order. For each revision it changes the disk first, then records the document's journal state, then advances the cursor, so the cursor never passes a revision whose effects are not durable. Content is downloaded before the disk is examined and verified: its size and, for plaintext vaults, SHA-256 must equal the blob id. Each document's disk state is classified by content hash against the journal's base and the remote revision. If the disk shows the base, the revision is applied. If it already shows the remote result (an apply interrupted after its disk step), only the journal is updated. Anything else is a local change, and so is a file in the way at the target path, a local delete, or an unpushed pending operation. For a renamed document, a file in the way at its new path is not its local version: the merge hook gets the document's own file, and the merge path decides about the other file (§7). The engine then never writes. It hands the revision to an engine-level **merge hook** with the local content, the remote revision and the base (the remote and base contents are fetched on demand, the base by `rev_id`; a tombstone base has no content). The default hook is the merge of §7. A hook may instead leave the file alone; the engine then records the remote revision as **deferred** (pending) in the journal. From then on the merge path owns the document: every later remote revision of it goes to the hook, and the deferral is replaced by the newest one until the merge path resolves it. The deferral still advances the cursor, since it is itself durable. A revision whose path fails the vault-relative rule (§6.2) or is not valid UTF-8, or whose path the vault refuses (a file or folder in the way), is deferred with that reason and never touches the disk (surfacing it is #20/#100). A later applied revision of the document clears that deferral.
- **Divergence (decision, #16).** A `ListChanges` response whose `head_seq` is below the stored cursor means the server lost history this device applied, for example after a database restore. That is divergence, never "nothing new". The engine resyncs: it scans the whole feed for each document's head and applies heads of documents the journal does not know. A document at the same revision only has its `seq` renumbered. A document the journal knows at another revision goes to the merge hook, because the server may have lost acknowledged revisions that only this device still has. Nothing local is overwritten or deleted. Only then is the cursor reset to the feed's last `seq`, so an interrupted resync runs again. A restored server whose `head_seq` has already passed the cursor again cannot be detected this way (follow-up issue).
- **Push (decision, #17).** Local changes are found by content hash against the journal's base: from vault events since the last push, and by a scan of the whole vault on the first push after a start, since events are lost when the app dies. Every push pulls first, so interrupted applies finish and bases are fresh. It then resumes the journal's pending operations and records a new operation for each changed file: deletes and renames first, then edits, then creates, so a path a change frees is free before a create takes it. A file that appears at the path of a deleted document is committed as a new revision of that document, on top of its tombstone, rather than as a new document (decision, #17). A rename is recognized from the vault's rename event. Without one (a change made while the app was closed), it is a delete plus a create. Each operation is written to the journal with its revision id before anything is sent. Its upload resumes from the server's `received_size` in chunks of the server's `max_chunk_size`, and an already-complete blob sends nothing. Its commit is retried with identical fields, so a lost response returns the committed revision. The pull also recognizes the device's own revision in the feed and marks the operation done without touching the disk. On success the journal records the new base and only then drops the operation. If the file changed before its upload completed, the operation was never committed (the server commits only complete blobs), so it is dropped and the file's current content is pushed instead. On a moved head (§6.2 step 3) the engine pulls, and the pull hands the document to the merge hook because it has a pending operation. A hook that returns a merge result has it written to disk. The document's superseded operations are then dropped, the document is rebased onto the remote head, and the result is committed with the remote head as its base. The merge is journaled before it acts, whether it started in a pull or a push (decision, #18). The result's path and hash are recorded on the document's deferral first. A file in the way at the result's new path is kept as a copy and removed before that (§7), so after a crash a file at the recorded path is always the document's own, which the resumed merge takes as its local version. A conflict and its copy's name go into the conflict log before the copy is written. The operations are dropped before the rebase, and the deferral is removed last. So a crash at any point leaves one of two states. Either the remote revision is still unapplied and goes back to the merge path, which finishes from the record if the disk already shows the result and otherwise asks the hook again (which reuses the logged copy name), or the merge result is a plain local edit on the new base. A hook that defers parks the document: its operation stays pending, its local content stays on disk, and the engine pushes nothing for it until a later push's call merges it. A commit refused with `ALREADY_EXISTS` pulls. If the other document arrives at the same path, it goes to the merge path, which keeps the local file as a conflict copy. Otherwise the local document moves to a conflict-copy path (§7). One refused with `INVALID_ARGUMENT` stays pending and is reported (surfacing it is #100). Automatic pushes are debounced (`pushDebounceMs`, default 2 s, restarted by every change), and a push reads the disk when it runs, so the last edit of a burst is the one pushed, and an edit made during a push triggers another one.
- **`.obsidian/` config sync** is opt-in and allow-listed per category (themes, snippets, hotkeys, plugin list, plugin data). `workspace*.json` and the plugin's own state are never synced.

## 9. Authentication, authorization, encryption

### 9.1 Authentication

The plugin authenticates against Authentik with the **OAuth 2.0 Device Authorization Grant** (works identically on desktop and Android, with no redirect handling). The plugin stores the refresh token in plugin data; access tokens are JWTs validated by the server against the issuer's JWKS (refreshed on unknown `kid`, with a bounded refresh rate). `iss`, `aud`, and `exp` are always checked.

Server-side details (decision):

- Only RS256, ES256 and EdDSA signatures are accepted; `none` and HMAC algorithms are rejected. Tokens are size-bounded before parsing. `exp` has no leeway; `nbf`, when present, tolerates one minute of clock skew.
- The JWKS (discovered from the issuer's OpenID configuration) is fetched lazily, refetched on an unknown `kid` and when older than one hour, and never more than once per 30 seconds. A failed refetch keeps the cached keys. At most one fetch is in flight and no lock is held across it: while hour-old keys are being refetched, other requests use the cached keys rather than wait. The discovery document, `jwks_uri` and redirects must be `https` (plain `http` only to loopback hosts, and only for a loopback `http` issuer); redirects must stay on the requested host and never downgrade to `http`.
- Users are created on their first authenticated request, keyed by `(issuer, subject)`; concurrent first requests create exactly one user. `sub` must be non-empty, at most 255 bytes, and free of control characters (Unicode `Cc`); other tokens are rejected as unauthenticated before any user lookup.
- Authentication is **default-deny**: one interceptor on every ConnectRPC service authenticates every procedure that is not on an explicit public allow-list (only `ServerInfoService/GetServerInfo`). The realtime WebSocket upgrade (§6.4) authenticates with the same authenticator. A test enumerates every procedure in the schema and asserts it is authenticated or allow-listed.

### 9.2 Authorization

Every RPC and every WebSocket message resolves `(user, vault_id)` to a `vault_members` role before touching data. `viewer` can read; `editor` can read and write; `owner` can also manage members and vault settings. There is no admin bypass in the API.

Server-side details (decision):

- Authorization is **central and runs before the handler**: one interceptor, after authentication, on every ConnectRPC service. A single table (`server.VaultProcedures`) classifies every vault-scoped procedure — every procedure whose request carries `vault_id` — as read or write. A request carrying a `vault_id` for an unclassified procedure is rejected, and a test derived from the schema descriptors fails if any such procedure is missing from the table. The interceptor reads only the top-level `vault_id`, so a request must name its vault nowhere else: a second schema-derived test walks every RPC input message (nested messages, `oneof` members, repeated and map fields, stopping at recursive types) and fails, naming the procedure and field path, on any vault-identifying field other than a single top-level, singular, non-`oneof` `string vault_id`. A field is vault-identifying if its name ends in `vault`, `vaults`, `vault_id` or `vault_ids` (also without the underscore before `id`; for example `target_vault_id`) or its type is the `Vault` message. Streaming calls to vault-scoped procedures are rejected before the handler runs, because their messages arrive only after it starts.
- `vault_id` must be a canonical lowercase UUID (`INVALID_ARGUMENT` otherwise) and is checked before any query. The role is then resolved with one `vault_members` lookup: a vault that does not exist and a vault the caller is not a member of take the same path and return the same `NOT_FOUND` error. A `viewer` calling a write procedure gets `PERMISSION_DENIED`.
- Handlers take the authorized vault from the interceptor, never from the request, and query through a vault-scoped store handle whose every query filters by that vault, so ids from another vault (documents, revisions, blobs) are simply not found.
- `CreateVault` makes the caller the `owner` (a user may own at most 100 vaults); `ListVaults` returns only vaults the caller is a member of, with the caller's role, paginated by an opaque `page_token` (`page_size` defaults to 100 and is capped at 1000; like `ListChanges`, a page also ends early where its encoding would exceed the send limit, with a `next_page_token` to continue, and holds at least one vault if one remains; startup requires the send limit to fit a response with one vault with a maximum-length name). Vault names are non-blank, at most 256 bytes, and contain no control characters (Unicode category `Cc`, including U+0000, which PostgreSQL `text` cannot store); anything else is `INVALID_ARGUMENT` before the database is touched.
- `RegisterDevice` registers a device for the caller (one per plugin installation, so every reinstall adds one). A user may register at most 100 devices, counted over the account's lifetime: v1 has no RPC to list, remove or revoke devices (decision #52, item 8), so the count never goes down. The 101st call gets `RESOURCE_EXHAUSTED` ("at most 100 devices may be registered"); registrations are serialized on the user row, so concurrent calls cannot overshoot the cap. Device names are non-blank, at most 256 bytes, and contain no control characters (Unicode category `Cc`); the public key is empty or exactly 32 bytes. Anything else is `INVALID_ARGUMENT` before the database is touched. There is no supported operator remedy for a user at the cap yet.

### 9.3 End-to-end encryption (opt-in per vault)

Until Phase 4 (§15) delivers key management, the server rejects `CreateVault` for an E2EE vault (with or without escrow) with `FAILED_PRECONDITION` ("end-to-end encrypted vaults are not supported yet"), so that no client can commit plaintext into a vault marked as encrypted, whose `path_key` the server could not derive (§5; principle 1). Escrow on a plaintext vault is `INVALID_ARGUMENT`.

Envelope encryption with multiple recipients:

- Each **user** has an X25519 key pair. The private key is stored server-side wrapped by a key derived from a user recovery passphrase (Argon2id). Devices unwrap it once and keep it in local storage. (Device-to-device linking and Shamir-split recovery are later enhancements.)
- Each **vault** has a symmetric vault key per **epoch**. `key_slots` hold the epoch key wrapped (X25519 + HKDF + XChaCha20-Poly1305, sealed-box style) to every member, and to the escrow public key if escrow is enabled.
- Sub-keys are derived from the epoch key with HKDF: `content`, `path`, `path_key_secret`, `blob_id_secret`.
- Content and paths are encrypted with **XChaCha20-Poly1305**, random nonce, the revision's document id and epoch bound as associated data.
- Every ciphertext carries a **suite version** byte so that the algorithms can change later.
- **Member removal** creates a new epoch. Subsequent revisions use it; historical content is not re-encrypted (the removed member may already hold it).
- Implementations: `@noble/ciphers`, `@noble/curves`, `@noble/hashes` in TypeScript (pure JS, audited, identical on Electron and Android WebView); `golang.org/x/crypto` in Go. A shared set of **cross-language test vectors** in `testdata/crypto/` must pass in both.
- With E2EE, the server cannot merge, search, or render content — none of which it does anyway (§4).

### 9.4 Escrow for plaintext backups

A vault with `escrow = true` also wraps each epoch key to a deployment-wide **escrow public key**. The escrow private key exists only in the export job's Secret, which is never mounted into the internet-facing server. A compromise of the API server, PostgreSQL, or S3 therefore exposes only ciphertext. The export job decrypts and writes plaintext for tape archival. Escrow is chosen at vault creation and shown clearly in the UI. Optionally, the escrow private key may be split with Shamir secret sharing for offline disaster recovery; this is not used by the automated path.

## 10. Live collaborative editing (Phase 5)

The v1 protocol includes the hooks for this from the start: stable document ids, the `kind` field, the multiplexed WebSocket, and an append-only per-document log.

- A `yjs` document's state is its ordered `yjs_updates` log plus periodic snapshots. For E2EE vaults each update is encrypted (the server stores and relays opaque bytes).
- **Conversion** of a `text` document to `yjs` happens **exactly once**, as a server-side compare-and-set on `documents.kind` performed by a single elected client (the server grants a lease). Two clients independently initializing a `Y.Text` from the same file duplicates the content — the classic Yjs bug — and must be impossible.
- The plugin binds `Y.Text` to Obsidian's CodeMirror 6 editor (`y-codemirror.next`) and to the file on disk. Edits that arrive outside the editor (other plugins, `processFrontMatter`, external editors, git) are diffed into the `Y.Text`.
- Awareness (cursors, presence) is ephemeral over the WebSocket and never persisted.
- **Compaction** folds the update log into a snapshot. Plaintext and escrow vaults can compact server-side (the export job can do it for escrow vaults); other E2EE vaults compact on clients. The compaction runtime (a Go Yjs implementation is not mature) is an open question for Phase 5.

## 11. Retention and history

- Revisions are append-only. A retention policy (per vault; default: keep everything for 90 days, then thin to daily/weekly) purges **non-head** revisions and tombstones only. Unreferenced blobs are garbage-collected after their last referencing revision is purged, with a grace period.
- Users can browse a document's history and restore any revision (a restore is a new revision).

## 12. Operations

- Single static Go binary; OCI images built by Nix (`streamLayeredImage`), mirroring tape-archiver. Helm chart built on bjw-s `app-template` under `deploy/charts/`.
- Configuration by environment variables, documented in `docs/configuration.md`.
- **JSON structured logs** (`log/slog`), Prometheus metrics on a separate port, `/healthz` and `/readyz`.
- PostgreSQL client certificates and S3 credentials are re-read from disk on change.
- Schema migrations are embedded (`internal/store/migrations`) and run on startup behind a PostgreSQL advisory lock, each in its own transaction, recorded in `schema_migrations`; migrations are forward-only and must be backward-compatible with the previous release. Released migrations are never edited (the runner rejects a changed name for an applied version). Migrations may use any feature of PostgreSQL 14, the minimum supported version (0003 defines its index function with a SQL-standard `RETURN` body, which binds its references at creation so `search_path` cannot change what the index computes). A migration that rebuilds an index holds an exclusive lock on its table until it commits; 0003 rebuilds the live-path index on `documents`, briefly blocking commits and reads of documents on every replica while it is applied. 0004 builds the live-folder GIN index (§5), which holds a lock that blocks commits, but not reads, while it is applied.
- **High availability (§3).** Every replica must obey these rules, and every new feature must keep them:
  - **Stateless replicas.** A replica keeps no per-client state that lives only in its own process. Sessions, cursors and upload progress live in PostgreSQL (and S3). Consecutive requests of one client, including the chunks of one upload and its commit, may land on different replicas and must behave exactly as against one. Caches every replica can rebuild (the OIDC key set, credentials) are fine.
  - **Coordination through PostgreSQL only.** Advisory locks, `SELECT … FOR UPDATE SKIP LOCKED`, conditional updates and `LISTEN/NOTIFY` are the only cross-replica mechanisms (principle 5): no new infrastructure. Realtime fan-out (§6.4) must therefore reach clients connected to any replica.
  - **Background jobs run on every replica** and must be safe to run concurrently. Their combined effect equals one run, and a replica finding that another got there first is not an error and is not logged as one.
  - **Retry-safe RPCs.** A replica may be killed without warning (`SIGKILL`) at any point. Every RPC must therefore be safe for the client to retry on another replica: the retry succeeds, and no acknowledged write is lost or applied twice. Blob uploads are content-addressed and resumable; revision commits are deduplicated by their client-chosen revision id.
  - **Graceful drain.** On `SIGTERM` a replica fails `/readyz` at once and keeps serving for a configurable delay (`VAULT_SYNC_SHUTDOWN_DELAY`), closing each connection after its response (idle keep-alive connections stay open until the delay ends, so a request sent on one as the signal arrives is not reset) so traffic moves to other replicas before any connection is refused. It then stops accepting connections and closes open WebSockets with close code 1001 ("going away") so clients reconnect elsewhere. In-flight RPCs get a configurable drain timeout (`VAULT_SYNC_SHUTDOWN_TIMEOUT`), and the process exits 0 after a clean drain.
  - **Database connection resets** (a PostgreSQL restart or switchover) are tolerated: connections are checked before use and replaced, and a request that fails mid-query is retried by the client. Managing PostgreSQL failover is the operator's concern (CloudNativePG).
  - **Rolling upgrades.** The previous and the new release serve side by side during a rollout. This is why migrations must be backward-compatible with the previous release (below). An integration test runs both releases against one database.
  - The recommended deployment (at least 2 replicas, a PodDisruptionBudget, readiness and termination-grace ordering) is documented in `docs/configuration.md`.
- Bounded resource use: max request size, max chunk size, decompression limits, pagination caps, per-user rate limits. Each user may have at most `VAULT_SYNC_MAX_CONCURRENT_RPCS_PER_USER` authenticated RPCs in flight per replica, counted from authentication until the response is fully written; a further call is rejected at once with `RESOURCE_EXHAUSTED` before its handler runs (no queueing). The limit is an in-process count keyed by user ID, dropped when the user's last call ends, so it needs no cross-replica state and no client-visible state is lost with a replica. Responses are bounded by the same size as requests (the bytes sent). Writing each API response is bounded by `VAULT_SYNC_WRITE_TIMEOUT`, counted from the response's first byte, so a client that stops reading releases its connection. It does not bound the time before the response starts, so a long commit is not cut short (§6.2). The upgraded realtime WebSocket is exempt and bounded by its own pings and send queue (§6.4). Concurrent `/readyz` checks share one database ping. Every object-store request fails once its connection makes no progress in either direction for `VAULT_SYNC_S3_IDLE_TIMEOUT` (retried a bounded number of times by the S3 SDK), so a store that stops answering cannot hold a request, a compose slot or the cleanup routine forever; the bound is on silence, not on a whole operation, so a long commit or export that keeps moving is not cut short (§6.2). Each cleanup run is cut short when the next is due.
- The plugin is distributed through GitHub releases (installable with BRAT); publishing to the Obsidian community catalog is a non-goal for now.

## 13. Testing strategy

| Layer | Tooling | Runs in |
|---|---|---|
| Go unit | `go test -race`, testify | `make test`, CI |
| TS unit | vitest | `make test`, CI |
| Server integration | real PostgreSQL + S3-compatible store via `docker compose` | `make test-integration`, CI |
| **Sync simulation** | Seeded multi-client harness (`sim/`, TypeScript): N `core` engines over in-memory vaults against a real `vault-sync-server` process (real PostgreSQL + S3). Each client's transport is wrapped in a seeded fault injector (drop request, drop response after the server applied it, delay, reorder, partition, client crash/restart losing in-memory state). Operation schedules are derived from the seed so a failing seed replays the same client-side schedule. Invariants: convergence, no lost acknowledged writes, no resurrected deletes without a concurrent edit, no duplicate content. Failing seeds are minimized and committed as regression cases. Phase 1 (decision): scripted protocol clients stand in for the engines, and the invariants are server-side, checked by the Go driver directly in PostgreSQL. Every acknowledged revision is in history unchanged; `seq` is exactly `1..head_seq`; no two live documents share a `path_key`; and each document's revisions form one chain, so no commit succeeded against a stale base. Messages are delivered one at a time in logical (step) time, so a seed replays deterministically, and concurrency is modelled by interleaving. Phase 2 adds the real engine's pull side (#16) as an extra client behind the same faulty network. Scripted scenarios also drive its push (#17) and run two engines that edit the same documents concurrently (#18): non-overlapping and overlapping edits, a binary file, a line-ending change, and creates at one path and at case-colliding paths, under a lost response and a crash. It pulls whenever the schedule asks a client to pull, and it crashes with client 0, keeping its in-memory vault and journal as a device keeps its disk. After quiescence its vault must equal the server's live heads, its cursor must equal the feed's last `seq`, and it must have deferred nothing and reported none of its own writes as local changes (`engine-convergence`, `engine-deferred`, `engine-echo`). A server built with the `simfault` tag skips the base-revision check, and CI proves the harness catches it; no runtime switch exists. ## 15. Phases

Work is tracked as GitHub milestones and parent issues. Each phase ends with a bug hunt (and a security review where the phase touches the attack surface) before the next starts.

1. **Foundations** — protocol schema, server core (store, blobs, revisions, auth, authz), simulation harness skeleton, CI.
2. **Single-user file sync** — plugin engine + adapter for desktop and Android, merge, conflicts, history/restore, export job, Helm chart. Dogfooding starts here.
3. **Vault sharing** — membership management, invitations, roles in UI.
4. **End-to-end encryption** — key hierarchy, escrow, export decryption, crypto vectors, independent crypto review. Until then, creating an E2EE vault is rejected (§9.3).
5. **Live collaborative editing** — Yjs documents, conversion, editor binding, awareness, compaction.
