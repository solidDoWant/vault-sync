# vault-sync — Specification

This is the authoritative technical reference for vault-sync: its purpose, design principles, architecture, data model, sync protocol, encryption scheme, and repository layout. It is a living document — update it in the same change that alters any behavior it describes. Where this document says "decision", the reasoning is recorded so that a later change can revisit it deliberately rather than by accident.

This project is bootstrapped to mirror the conventions of [`tape-archiver`](https://github.com/solidDoWant/tape-archiver) and [`media-processor`](https://github.com/solidDoWant/media-processor): Go, Nix-reproducible builds, issue-driven development with Given/When/Then acceptance criteria, and a testing-first philosophy.

## 1. Purpose

vault-sync is a self-hosted replacement for Obsidian Sync. It has two halves:

- an **Obsidian community plugin** (TypeScript) that watches a vault and synchronizes it, and
- a **sync server** (Go) that stores vault state in **PostgreSQL** (metadata, revisions) and an **S3-compatible object store** (file contents).

It exists because the available self-hosted option (obsidian-livesync) requires CouchDB, has a history of data-loss and reconciliation bugs, is thinly documented, and has no multi-user model. vault-sync targets a small number of users (one household / small team) on infrastructure the operator already runs.

## 2. Design principles

These are non-negotiable. When a trade-off arises, resolve it in favor of the principle, not convenience. Call out any change that touches one.

1. **No acknowledged write is ever lost.** Once the server has acknowledged a revision, that content is recoverable — as the current head, in revision history, or as a conflict copy — until an explicit, retention-governed purge. Neither the client nor the server ever silently discards a user edit. Deletion is a tombstone, never an erase.
2. **One source of truth per concern.** The server's revision log is the source of truth for vault history. The local vault on disk is the source of truth for un-pushed local edits. The client keeps exactly one durable journal bridging the two. No additional replicated databases or chunk layers.
3. **Done means the owner's acceptance checklist passes.** Each phase has an owner-approved checklist of user-visible scenarios (`docs/acceptance/`), each tested automatically. Tests guard behaviour and catch regressions. They never raise the bar beyond the checklist and principle 1.
4. **Small, defensible attack surface.** The server is exposed to the internet. Keep the API small, typed, and authenticated by default; every endpoint enforces vault-level authorization; resource usage is bounded (request sizes, decompression, pagination).
5. **Operator infrastructure only.** PostgreSQL, S3-compatible storage, and OIDC. No new database types.

## 3. Target environment

- **Server:** Kubernetes (Talos) homelab. PostgreSQL 14 or newer via CloudNativePG (client-certificate auth; certificates rotate — the server must re-read them, never cache them for the process lifetime). Object storage via Ceph RGW (S3 API). Identity via Authentik (OIDC). Exposed through an Istio gateway with a Coraza WAF in front: **inspected request bodies above 1 MiB are rejected**, so every upload is chunked at or below a configurable size (default 768 KiB).
- **High availability:** the server runs as an HA deployment: two or more identical replicas behind one Service, sharing one PostgreSQL database and one S3 bucket. Terminating any replica, for example for node maintenance, must have **no client-visible impact**. The rules that make this hold are in §12.
- **Clients (required):** Obsidian desktop on **Windows** and **macOS**, Obsidian mobile on **Android**. Linux desktop is the development/test platform. **iOS is best-effort** (not a release blocker) — do not take design decisions that preclude it.
- **Backups:** a plaintext export of every vault (decrypted where escrow is enabled, §9.4) is written to a filesystem path that the operator's tape-archival tooling picks up. This replaces livesync-bridge. **No readable live document is ever left out of an export** (decision, #52/#178). Each vault's files sit in a browsable tree at `<out>/<vault-id>/<path>`. A document whose path that tree cannot hold (a file/folder collision such as `a` and `a/b.md`, a name the filesystem rejects such as one over 255 bytes, or an invalid or non-UTF-8 path) is written to `<out>/<vault-id>.unplaced/<document-id>` instead. A streamed JSON Lines manifest, `<out>/<vault-id>.manifest.jsonl`, lists every live document: id, original path, kind, head revision id, size, SHA-256, status (`placed`, `unplaced` or `missing`) and where its bytes are. The unplaced tree and the manifest sit beside the vault's directory, never inside it, so no user file can be mistaken for them. The layout and manifest are a versioned format (format 2, in the marker and every manifest), specified in `docs/export.md`, so the Phase 6 importer can restore exactly. Content that is missing or corrupt in S3, or in an escrowed vault cannot be decrypted, is the only reason a live document's bytes can be absent; the manifest lists it as `missing` and the run reports `partial`. History, tombstones and E2EE vaults without escrow are not exported.

## 4. Architecture

```
 Obsidian (desktop / Android)                       Kubernetes
 ┌──────────────────────────────┐    HTTPS     ┌──────────────────────────────┐
 │ plugin/src/obsidian  (adapter)│  ConnectRPC │ vault-sync-server (Go)        │
 │   vault events, editor, UI    │◄──────────►│   API (ConnectRPC, protobuf)  │
 │ plugin/src/core  (sync engine)│  WebSocket  │   realtime hub (WebSocket)    │──► PostgreSQL (CNPG)
 │   journal (IndexedDB), merge, │◄──────────►│   authz, quotas, retention     │──► S3 (Ceph RGW)
 │   crypto, protocol client     │             │                               │──► Authentik (OIDC JWKS)
 └──────────────────────────────┘             └──────────────────────────────┘
                                               ┌──────────────────────────────┐
                                               │ vault-sync export (CronJob)   │──► plaintext tree for tape
                                               │   holds escrow private key    │
                                               └──────────────────────────────┘
```

- **`plugin/src/core`** is a pure TypeScript library: the sync engine, journal, merge, crypto, and protocol client. It **must not import `obsidian`** (lint-enforced) or use Obsidian's globals: `make lint` type-checks it, with its tests, as a separate program (`plugin/tsconfig.core.json`) that has neither Obsidian's global augmentations nor DOM-only globals, and fails if any route (import, `/// <reference>`, `src/main.ts`) brings Obsidian into it. Core code must be plain `.ts` modules with no triple-slash directives, no `declare global` and no JavaScript imports, and the program may contain nothing from outside `src/core`, `src/gen` and dependencies. Packages that `src/core` imports directly must be declared in `plugin/package.json` (`dependencies` or `devDependencies`, or their `@types` package) and are never `obsidian`, so Obsidian's own transitive dependencies (e.g. `@codemirror/view`, `moment`) cannot slip in. Any other code file under `src/core` (`.js`, `.mts`, `.tsx`, `.d.ts`, …) fails the check even if nothing imports it; non-code files there are ignored. It talks to the vault through a `VaultAdapter` interface so its tests can drive it against an in-memory vault.
- **`plugin/src/obsidian`** is the thin adapter: `Vault`/`FileManager` events, editor integration, settings UI, status bar, conflict UI. `ObsidianVaultAdapter` implements `VaultAdapter` on the Vault API and passes the conformance suite inside real Obsidian (e2e). Paths with a hidden segment (`.obsidian/`, `.trash/`, any `.name`) and paths Obsidian's `normalizePath` would store under another name are outside it: never listed, read or reported, and a write or rename onto them is refused as `path-conflict`, so the engine defers such a revision instead of touching the disk (decision, #24; `.obsidian/` config sync is #28). Renames use `Vault.rename`, never `FileManager.renameFile`, because a synced rename must not rewrite links: the other device's link updates arrive as revisions of their own. `SyncSession` ties the adapter and the engine to the plugin's lifecycle: it starts once the workspace layout is ready, resumes from the journal's cursor, and stops in `onunload`, so disabling and re-enabling the plugin never starts a full resync. Sync wiring (decision, #25): `SyncController` runs a session exactly while the device is signed in and the local vault is connected to a server vault (recorded in plugin data with its server URL), and stops it on sign-out, on "sign-in required" and before switching vaults. A session runs the sync engine of `docs/design/engine.md` (`plugin/src/core/sync/`) over its IndexedDB journal: it syncs (detect, pull, push) when it starts, 2 s after the last local change of a burst (`pushDebounceMs`), when the realtime channel reports a change, and every 30 s as a fallback. Stopping a session refuses every further vault, journal and server call of its engine (a call waiting on the network is abandoned, its late response dropped) and resolves once the engine has settled, so two engines never run over one journal. Edits the stopped session had not pushed stay on disk and are found by the next session's full scan (principle 1). The device registers with `RegisterDevice` once per plugin install and account (server URL, issuer and the access token's `sub`) before its first sync; the id is stored in plugin data and reused on every later start and sign-in, because the server's device limit counts every registration. A `RESOURCE_EXHAUSTED` from `RegisterDevice` (other than the per-user concurrency limit) is shown as that limit, and sync does not start. Connecting a non-empty local vault to a remote vault with revisions asks for confirmation first: nothing is overwritten, but files at the same path with different content become conflict copies (§7). End-to-end encrypted vaults cannot be connected until Phase 4. Every request the plugin sends has a deadline (decision, #730): a server RPC the caller gave no timeout of its own fails as `UNAVAILABLE` once it has gone unanswered for 30 s, plus 1 s per 8 KiB (64 kbit/s) of blob bytes it carries (`PutBlobChunk`) or asks for (`DownloadBlob`, 1 MiB for a length of 0), and 10 minutes for `CommitBlob`, whose response waits for the server to compose the whole blob (§6.2); a request to the identity provider counts as unreachable after 30 s. The call's signal is aborted and a late response dropped, so a request whose packets are silently dropped shows `offline` and is retried like any other outage instead of leaving the session `syncing` (`protocol/client.ts` `withRequestTimeout`). The status bar shows `starting` (registering the device and opening the journal), `syncing`, `idle`, `offline` (the server or identity provider unreachable or not answering in time, or the identity provider answering with a 5xx), `error` (with the reason; this includes an identity provider whose answer is not a valid response, which points at a misconfiguration, #413), `signed out`, `sign-in needed`, `no vault connected`, plus the number of pending local changes and of open conflicts: conflict copies this device made that still exist.
- **`vault-sync-server`** is a single Go binary. The server **never merges content**: it orders revisions, enforces optimistic concurrency, stores bytes, and fans out notifications. All merging happens on clients (this keeps the server compatible with end-to-end encryption).
- **`vault-sync export`** is a subcommand of the same binary, run as a separate Deployment/CronJob with its own credentials. It is the only component that may hold the escrow private key. It only reads PostgreSQL (its sessions are `default_transaction_read_only`) and S3. Each vault is exported as of its `head_seq` (every document's latest revision at or below it; tombstoned documents are left out) to `<out>/<vault-id>/<path>`, byte for byte; the directory is named by id because vault names are mutable, user-chosen and can collide (decision, #29). The tree is written to a staging directory beside `<out>` and swapped in atomically (`renameat2` `RENAME_EXCHANGE`), so an interrupted run leaves the previous export untouched. Every path is re-checked with the shared vault-relative rule (§6.2) and written through a handle confined to the vault directory, without following symbolic links. A document whose path cannot be placed in that tree goes to the vault's unplaced tree by document id, and every live document is listed in the vault's manifest (§3). A document whose content is missing or corrupt has no bytes in the export: it is listed in the manifest as `missing` and reported by id, and the run still swaps in its tree (decision, #52). The job prints a JSON summary and exits non-zero on any failure or missing content; it has no metrics endpoint. E2EE vaults with escrow are decrypted with the escrow identity (`VAULT_SYNC_ESCROW_IDENTITY_FILE`, one or more age hybrid identities): before writing anything of a vault, the job opens every epoch's escrow slot and checks its key against the epoch's key commitment, and a slot that does not open or does not match leaves the vault out as `failed` (the run is `partial`), so nothing is written with a wrong key. Each document's path and content are then opened with its head revision's epoch key (`docs/design/crypto.md`) and its content checked against its `blob_id`, and the tree and manifest hold plaintext. E2EE vaults without escrow, and every E2EE vault when the job has no escrow identity, are skipped and reported. `vault-sync export rotate-escrow` rotates the escrow key to a bundle the operator names: it reads the escrow chain and every escrow slot (deleted, unpurged vaults included) from PostgreSQL, appends the escrow rotation statement signed by the chain head's escrow signing key (`VAULT_SYNC_ESCROW_SIGNING_KEY_FILE`) unless the head is already the target, and re-wraps every slot not on the target after checking it against its epoch's key commitment, writing only through `EscrowJobService` (§9.4); a slot that fails is reported and left in place, and the run exits non-zero while any slot is left on an old key. Details: `docs/export.md`.

### 4.1 Protocol transport (decision)

The API is defined in **protobuf** under `proto/` and served with **ConnectRPC** (Connect protocol over HTTP/1.1 + JSON or binary) — one schema generates both the Go server stubs and the TypeScript client. Realtime traffic (change notifications now, Yjs updates and awareness later) uses a **WebSocket** carrying protobuf-framed messages, because browsers/Electron cannot do client-streaming over fetch. The server sets CORS headers for Obsidian's app origins (`app://obsidian.md`, `capacitor://localhost`, `http://localhost`) and validates `Origin` on WebSocket upgrade.

Generated code is committed (`make generate` regenerates; CI fails on drift). Schema changes must stay backward compatible: `make lint` (and CI) runs `buf breaking` with the `FILE` rule set against `master`, and any deliberate exception is a narrowly scoped, temporary `ignore_only` entry in `buf.yaml` (`docs/testing/proto-compatibility.md`).

**Paths.** A path is an attribute of a revision, not an identity. Uniqueness is enforced on `path_key`, a normalized form of the path: Unicode NFC, then case-folded, then the NTFS upcase mapping (`docs/design/engine.md` §6), so that two clients cannot create paths that collide on case-insensitive (Windows, macOS, Android/iOS) filesystems. Precisely (decision): `normalize(path) = NFC(toCasefold(NFD(path)))` — Unicode canonical caseless matching (Unicode §3.13, D145) emitted in NFC, using **full, locale-independent** case folding (`CaseFolding.txt` statuses C and F; never the Turkic T mappings), so `Straße`/`STRASSE` collide and `İ` folds to `i̇`. On top of that, a code point whose simple uppercase (as NTFS's upcase table compares names) folds differently from it folds as that uppercase does: this is only the dotless `ı`, whose uppercase is `I`, so `ı.md` and `I.md` share the key `i.md` and every other key is plain canonical caseless matching. Full folding was chosen over simple folding because it catches strictly more collisions; locale independence keeps the key identical on every device. Separators, whitespace and dots are not altered and no validation happens here. Normalization and case folding come from maintained libraries, never hand-written tables (owner decision, 2026-10-29): Go (`internal/pathkey`) uses `golang.org/x/text/unicode/norm` and `golang.org/x/text/cases`, TypeScript (`plugin/src/core/pathkey`) `String.prototype.normalize` and the `unicode-case-folding` package. New names may only use code points assigned in Unicode 15.0 (`docs/design/engine.md` §6, §6.2), whose normalization and case folding Unicode keeps stable, so both compute the same key on every runtime with Unicode 15.0 or later; they must agree on every vector in `testdata/paths/`. Documents committed before that rule with characters added in Unicode 16 or 17 keep their paths; their key is now computed with the libraries' Unicode data. Adding the NTFS upcase merge changed the key only of paths with `ı`; keys already stored are not rewritten. For E2EE vaults the path itself is ciphertext and `path_key = HMAC-SHA256(path_key_secret, normalize(path))`, so the server can still enforce uniqueness without learning the path. Both are arbitrary bytes, which the `text` columns `revisions.path` and `documents.path_key` cannot hold (NUL, invalid UTF-8), so for a revision with an epoch of 1 or more the server stores them as unpadded base64url and returns the path's original bytes; epoch-0 revisions keep their plaintext path and key as they are. **Files and folders (decision, #134).** Apart from `folder` documents, folders are implicit, so a live document's path cannot name the folder of another live document's: a file `notes` and a document `notes/c.md` cannot both exist on any filesystem. The server refuses a live document whose `path_key` has a folder (a proper prefix ending before a `/`) that is another live document's `path_key`, or is itself a folder of another live document's `path_key`. A `folder` document is the exception (decision, #52/#1139): it is the folder its path names, so the server refuses the first case only when the live document whose `path_key` is the folder is not a `folder` document, and the second only when the new document is not a `folder` document. A `folder` document `Projects` and a file `Projects/Plan.md` may both be live, in either commit order; a file `Projects` and a `folder` document `Projects/Q` may not, and a `folder` document and a file never share a `path_key` (the unique live `path_key` index). Because the comparison is on `path_key`, `Folder` collides with `folder/c.md` and `straße` with `STRASSE/a.md`. Tombstones never collide. Only `/` is a folder boundary here, and `path_key` keeps `\` as it is, so `a/b` and `a\b` do not share a `path_key` and `notes\c.md` (a document under `notes` on Windows) is not compared with `notes`. Instead no new path may contain `\` (§6.2, decision #191), so such pairs can only come from documents committed before that rule. Both directions are index probes, not scans: the live `path_key` digest index answers whether a folder of the new key is a live key, and a GIN index over the digests of every live key's folders (each digest covering the vault id) answers whether the new key is a folder of one. Each probe then compares the real `path_key` of the few rows whose digests matched, so a digest collision cannot refuse a commit (#428). There is no maximum folder depth (decision, #428): the deepest key the 8192-byte `path_key` limit allows (about 4095 folders) costs about 130 ms of database time per create or rename and up to about 4095 GIN entries per document, which the `path_key` limit and the per-user RPC concurrency limit (§12) already bound; a depth limit would make deep files permanently unsyncable, which the plugin has no way to show yet. The check starts with the release that added migration 0004: during a rolling upgrade, replicas of the previous release still accept file/folder collisions until every replica runs the new release (§12), and collisions committed before then stay (they remain editable and deletable). Likewise, replicas of a release before the `folder` exemption refuse a document under a live `folder` document until every replica runs the new release. For E2EE vaults the `path_key` is an HMAC that cannot be split into folders, so the server enforces only the exact `path_key` rule there, and devices resolve a clash between a file and a folder of the same name with `docs/design/engine.md` rule C (decision, `docs/design/encryption.md` *Formats and rules settled during implementation*).

**Content addressing.** For plaintext vaults `blob_id = SHA-256(content)`. For E2EE vaults `blob_id = HMAC-SHA256(blob_id_secret, plaintext)` (equality leaks only within a vault), and clients verify the id after decryption.

## 6. Sync protocol

### 6.1 Pull

`ListChanges(vault_id, since_seq, page_size)` returns revisions with `seq > since_seq` in `seq` order, paginated (the client passes the last `seq` it received as the next `since_seq` until `has_more` is false; the server caps `page_size` at 1000 and defaults it to 500, and also ends a page early where its encoding would exceed the send limit, so a page of long paths never fails as too large; every page holds at least one revision if one exists, and startup requires the send limit to fit a response with one maximum-size revision). A client's durable cursor is the highest `seq` it has fully applied to disk. A device's own acknowledged commit is already on its disk: when its `seq` is the one right after the cursor, the client records it and moves the cursor onto it, as a pull would (decision, #261). Seqs are gapless, so this skips nothing; if another device committed in between, the cursor stays and the next pull fetches that commit (and skips the device's own). **Cursor anchor (decision, #52/#155).** Every revision carries an `anchor`: 16 random bytes that the server draws when it stores the revision. Revision ids are chosen by clients, so a client can commit an id again after a restore, but no restored database reproduces a random anchor. The client stores the anchor of the revision at its cursor together with the cursor, in one journal write, and sends it as `since_anchor` with every `ListChanges` from a nonzero cursor. Before it reads the page, the server checks in the same snapshot that the vault holds a revision with exactly that `seq` and anchor, or a purge marker with them (§5, §11: retention purged that revision); the check is two lookups on `(vault_id, seq)` unique indexes, answered from PostgreSQL alone, so any replica gives the same answer. If neither exists, the response sets `diverged` and carries no revisions, and the client resyncs (§8). That happens when the database was restored to below the cursor, whatever `head_seq` is now; a purge never causes it (decision, #52/#488). A false negative cannot happen: no other revision has the anchor. **Own-commit anchor (decision, #52/#494).** A device's own acknowledged commit may lie above its cursor (#261), and a restore to between the two keeps the cursor's revision, so the cursor anchor alone misses it. The client therefore records the anchor of each of its acknowledged commits with the document's journal state, and while one lies above the cursor it also sends the `seq` and anchor of the highest such commit as `own_commit_seq` and `own_commit_anchor`. The server checks them in the same snapshot and the same way, a live revision or a purge marker, and sets `diverged` if neither exists, which also covers a restored `head_seq` still below that commit. The commits below it need no check: a restore that lost one of them lost it too. `own_commit_anchor` must be 16 bytes and `own_commit_seq` above `since_seq` and at most 2^63−1, both given or neither (`INVALID_ARGUMENT` otherwise). A server from before them ignores the fields (unknown protobuf fields), so against it the client keeps only the cursor check; an old client sends none. Revisions purged before purge markers existed (migration 0008), or by a release without them during a rolling upgrade, have no marker, and nor do those whose marker retention pruned past the marker horizon (§11): a device whose cursor sat on one gets one false-positive `diverged`, as every purge did before, and merges (§8). The check depends on no operator step and on no PostgreSQL timeline or system identifier, which change on an HA failover that loses no data. `since_anchor` must be empty or 16 bytes, and empty when `since_seq` is 0 (`INVALID_ARGUMENT` otherwise). A request without one (a client from before #155, or a cursor stored without an anchor) gets no check, as before. Clients pull on startup, on a realtime `subscribed{head_seq}` or `vault_changed{seq}` whose head is above the durable cursor (§6.4), and on a timer as a fallback.

### 6.2 Push (optimistic concurrency)

1. Upload content: `BeginBlob` → `PutBlobChunk`* → `CommitBlob`. Idempotent: an already-complete `blob_id` short-circuits. Resumable: `BeginBlob` reports the bytes already received, and chunks are appended strictly sequentially by offset. Chunks are at most the configured size (§3). The server verifies the content hash on commit for plaintext vaults. The client first looks the blob up with a zero-length `DownloadBlob` at offset `size` and, if the server already holds it, uploads nothing and does not read the local file (#386). Otherwise it reads the local content and checks its hash before `BeginBlob`, so content that changed or disappeared since the operation was recorded never opens a session: the blob is then only looked up with a zero-length `DownloadBlob` at offset `size`, and the operation is committed if the server already holds it and otherwise replaced by the file's current content (decision, #370). Downloads are ranged (`DownloadBlob(offset, length)`), each response bounded by the server; a client continues from the end of a shorter range than it asked for. Both limits hold in the request's codec (decision, #135): `BeginBlob` advertises, as `max_chunk_size`, the configured chunk size to binary clients and to JSON clients the largest chunk whose base64 encoding (four bytes for every three), plus 1 KiB of framing and a thousandth for gzip, fits the request limit; `DownloadBlob` caps a range at the same size, and a binary range also at the request limit less a thousandth and 512 bytes, so a gzip-compressed response of incompressible (for example E2EE) content still fits the send limit when the chunk size sits right at the limit (#161; with the default and smallest limits a binary range is still the chunk size). The size depends only on the request, so every replica agrees.

   Server-side details (decision): S3 multipart parts must be at least 5 MiB (except the last), which chunks below the 1 MiB body limit never are, so chunks are **staged objects plus a server-side compose**. Each accepted chunk is its own object under `vaults/{vault_id}/uploads/{upload_id}/`, its key unique to the write so a writer that lost a race for an offset never overwrites the accepted chunk; a chunk is accepted by a compare-and-set on the session's `received_size`, so concurrent uploaders of one blob share a session and a loser gets `FAILED_PRECONDITION` and resumes from `BeginBlob`. Every chunk but the last is at least 64 KiB (or the maximum chunk size for the request's codec, if smaller), bounding the objects per upload. `CommitBlob` streams the staged chunks in order into the blob's object, with one `PutObject` up to 8 MiB and a multipart upload of 8 MiB parts above that, hashing as it goes; the object is written or its multipart upload completed only after the hash matched, and the `blobs` row is written only after that, so a mismatching upload never becomes visible and its session is discarded. Bounds: the maximum chunk size plus 1 KiB of framing must fit the maximum request body (checked at startup), the Connect send limit equals the request limit, a blob is at most the configured maximum (at most 80 GiB, S3's 10,000 parts of 8 MiB), and a vault has a bounded number of sessions in progress (`VAULT_SYNC_BLOB_MAX_UPLOADS_PER_VAULT`). There is no RPC to abandon a session, and a client whose upload was interrupted and whose file then changed leaves its session behind, so a `BeginBlob` that would create a session in a vault at the limit first reclaims that vault's sessions idle for longer than `VAULT_SYNC_BLOB_UPLOAD_RECLAIM_IDLE` (default 10 minutes, at least 10 minutes, at most the upload TTL), and refuses with `RESOURCE_EXHAUSTED` only if none was reclaimed (decision, #370). An upload in progress records activity on every chunk, so a session idle that long has been abandoned. Reclaiming finishes the sessions in the same transaction, under the same vault row lock, that counts them, so concurrent `BeginBlob`s on any instance reclaim each session once and never overshoot the limit; a chunk or commit racing it either records its activity first (and the session is kept) or finds the session finished. A reclaimed session refuses further chunks (`FAILED_PRECONDITION`) and its commit (`NOT_FOUND`), on which the client starts the upload again from `BeginBlob` with a new session, its operation still pending; the cleanup below removes its staged objects and row like any finished session's. Sessions idle for longer than the upload TTL are reaped by a periodic, bounded cleanup that deletes their staged objects and then the session, and aborts multipart uploads older than the TTL (an interrupted commit's are otherwise invisible and leak storage) unless their blob has a session active within the TTL. Every server instance runs the cleanup at the same time, so every step is idempotent: a session is claimed atomically, and an upload or object another instance already removed counts as removed. A commit records session activity after every 8 MiB part it composes (and at least every minute while it waits for a compose slot), so a commit in progress, on any instance, is never reaped however long it takes, unless composing one part takes longer than the TTL. A commit whose session was finished or reaped meanwhile, on any instance, returns `FAILED_PRECONDITION` and the client uploads again, whether composing noticed that when recording activity or by failing to read a staged chunk the cleanup deleted: the cleanup claims a session in PostgreSQL before deleting any of its objects, so a failed commit checks the session there; a staged chunk missing from a session still active is `INTERNAL`; upload sessions hold no per-instance state, so chunks and the commit may go to different instances, and a commit interrupted by an instance dying is retried to success on another. Compose slots (decision, #367): each replica composes at most 4 blobs at once, and at most 2 of them for one user, so one user can never hold every slot and another user's commit always finds one; a user's further commits wait for that user's slots, holding none of the replica's. A `CommitBlob` of a blob whose commit is already in progress on the same replica waits for that commit, holding none of the replica's slots, and then returns its result (the blob complete, or the same failure the session's state implies), so duplicates (a retry of a slow commit, another device committing the same content, or a client repeating it) neither compose the blob again nor hold a replica slot. A commit takes one of its user's slots before it claims the blob, so a commit queued behind its own user's other compositions never keeps another user's commit of the same blob waiting behind that queue (#388). Both limits are in-process and per replica: no state is shared between replicas, and duplicates sent to different replicas can still each compose the blob once.
2. `CommitRevision(document_id, revision_id, base_rev_id, kind, content_ref, path, path_key, deleted, device_id)`. The server accepts only if `base_rev_id` equals the document's current head (or the document is new and `base_rev_id` is empty). It assigns `seq`, advances `head_seq`, and broadcasts `vault_changed`. Document and revision ids are client-generated UUIDv7s; retrying a commit with the same `revision_id` and identical fields returns the already-committed revision, so a lost response does not turn into a spurious head-moved conflict. `path_key` is sent only for E2EE vaults (§5), where it is the client's 32-byte HMAC and `path` is ciphertext of 1 to 4137 bytes (a sealed 4096-byte path: suite byte, 24-byte nonce and 16-byte tag added), both opaque to the server, which checks only their sizes (`INVALID_ARGUMENT` otherwise) and applies none of the plaintext path rules below; for plaintext vaults `path_key` must be empty and the server derives it from `path`.

   Server-side details (decision): a commit is one PostgreSQL transaction that first locks the vault row, so commits to one vault are serialized by the database across every server replica, with no per-process state: `seq` comes from `UPDATE vaults SET head_seq = head_seq + 1 … RETURNING` in that transaction, so it is gapless, and a revision commits (becomes visible to `ListChanges`) only after every lower `seq`, so a cursor never skips one. Within the transaction the checks run in this order: the device belongs to the caller and is not removed (`NOT_FOUND` with an `ErrorDetail` of reason `ERROR_REASON_DEVICE_NOT_FOUND`, #590); an existing revision with this `revision_id` in this vault is returned if its fields are identical (a base that retention has since purged matches the re-parented revision, §11; a `device_id` other than the revision's matches only if the revision's device is the caller's and removed, because that is the same installation retrying a commit whose response was lost after it registered again, decision #590) and is `INVALID_ARGUMENT` otherwise — **before** the head comparison, so a retry whose first attempt was applied still succeeds after other commits moved the head (a retry of a revision that retention has since purged, §11, is a new commit: the server has no record of the id any more, so it is judged against the head; decision #52/#845); the head comparison (`FAILED_PRECONDITION` carrying the document, with its current `head_rev_id`, as a `Document` error detail; also `FAILED_PRECONDITION` if a base is given for a document that does not exist in the vault); the kind matches the document's; the content is a `complete` blob in the same vault whose stored size equals `content_ref.size` (a `DOCUMENT_KIND_FOLDER` commit carries no `content_ref`, and one that does is `INVALID_ARGUMENT`; every other kind needs one, tombstones included) (`FAILED_PRECONDITION` if not complete, `INVALID_ARGUMENT` on a size mismatch; the stored size is what is ever returned). The document row's `head_rev_id`, `path_key` and `deleted` are updated in the same transaction as the revision insert, so `deleted` always mirrors the head and the live `path_key` index is exact; a collision on it is `ALREADY_EXISTS`. Then, if the revision is live and its `path_key` is new to the document (or the document was a tombstone), a file/folder collision with another live document (§5) is also `ALREADY_EXISTS`; this check runs under the vault row lock, so two commits that would each complete a collision, on any replicas, are serialized and the second is refused. A revision that keeps its document's live `path_key` (an edit) or deletes it is never refused for this, so a collision committed before the rule existed never blocks an edit or a delete. Client-generated ids already used in another vault are `INVALID_ARGUMENT`; all lookups are scoped to the authorized vault, so another vault's ids are otherwise simply not found. Plaintext paths are at most 4096 bytes of UTF-8 without control characters (Unicode category `Cc`), vault-relative, and at most 8192 bytes once normalized; a path a commit gives a document is also portable and at most 1024 bytes (below). Vault-relative is defined for every supported client platform (decision): `/` and `\` are both separators; the path must not start with a separator (which also rules out UNC, `\\?\` and `\\.\` prefixes) or with an ASCII letter and a colon (a drive prefix such as `C:`, `C:\x` or the drive-relative `C:x`); and no segment may be empty or consist only of dots and spaces (`.`, `..`, and forms such as `.. ` or `...` that Windows reduces to them). Names that are merely unmaterializable on Windows (reserved device names such as `CON.md`, a colon anywhere but a leading drive prefix, trailing dots or spaces on other names) pass this rule, but a new path must be portable (below). Look-alike characters are not separators or dots (decision, #148): U+FF0F, U+FF3C, U+2215 and U+29F5 are ordinary characters, and a segment of fullwidth full stops (U+FF0E) is an ordinary name. Windows' wide APIs, which Electron and Node use, do not treat them as separators, and `path_key` uses NFC, not NFKC. A path a commit gives a document must also contain no `\` at all (decision, #191): Windows reads it as a separator and other platforms as part of a name, so `a/b` and `a\b`, or a file `notes` and a document `notes\c.md`, would otherwise both be live while naming one file on Windows. Nor may it start with any single code point followed by `:` (decision, #148), such as `1:x.md` or `é:x.md`: Win32 reads any first character followed by a colon as a drive, and drives that are not letters can be created with `subst`. And it must be portable (`docs/design/engine.md` §6): no part (between `/`) contains any of `< > : " | ? *`, starts or ends with a space, ends in a dot, or is a Windows reserved name (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`, in any case, with or without an extension: the part up to its first dot); no part is longer than 255 bytes of UTF-8; and the whole path is at most 1024 bytes. Every code point must be assigned in Unicode 15.0 (`docs/design/engine.md` §6; private-use characters are assigned, noncharacters and code points added in Unicode 15.1 or later are not), so that both languages' libraries normalize and fold it identically (§5). And it must be in Unicode NFC (`docs/design/engine.md` §6): Obsidian stores every path in NFC, so a decomposed spelling such as `Cafe` followed by U+0301 could never match a file on any device. The refusal names the rule broken. A path that is vault-relative but breaks any of these rules is accepted only as the unchanged path of the document's live head, so a document committed before the rules can still be edited and deleted in place, or renamed to a valid path; creating a document there, moving one there, or bringing a tombstone back there is `INVALID_ARGUMENT` (checked under the document's lock in the commit transaction). No stored path is migrated, and such documents stay readable and exportable. Clients apply every one of these path rules before committing (`pathProblem` in `plugin/src/core/vaultpath`, decision #100): a local file at a path the server would refuse is never uploaded or committed, on any push, stays on disk, untouched, with its operation pending, and every push reports it as rejected with the rule it breaks, until the user renames or removes it (§8). Go (`internal/vaultpath`: `Check`, and `CheckNew` for the new-path rules, used by `CommitRevision`) and TypeScript (`isVaultRelativePath` and `isNewVaultPath` in `plugin/src/core/vaultpath`) must agree on every vector in `testdata/paths/validity.json` (its `valid` and `new` fields). They must also agree on the length and character-set rule (Go `CheckText`, TypeScript `isPathText`) for every vector in `testdata/paths/text.json`, and `CommitRevision` and TypeScript's `fitsPathKeyLimit` on the normalized length rule for every vector in `testdata/paths/key.json` (a path can grow when normalized: U+1D160 decomposes into three code points that NFC does not recompose, so 683 of them, 2732 bytes, have an 8196-byte `path_key`). A client must apply both rules to every path it receives before touching its disk, including E2EE paths after decryption, which the server cannot check. It must apply them to the exact string handed to the file system: the Obsidian vault and config folder adapters refuse any path that Obsidian's `normalizePath` would change (#148). Obsidian's `DataAdapter` normalizes every path it is given, and `normalizePath` turns, for example, the accepted `..` followed by U+00A0 into the traversal segment `.. `. A path that breaks the rule is `INVALID_ARGUMENT` and nothing is written; a path or `path_key` the database refuses (empty, over its bound, or text it cannot store) is `INVALID_ARGUMENT`, never `INTERNAL`. The commit transaction also queues a PostgreSQL `NOTIFY` on channel `vault_changed` (payload `<vault_id>:<seq>`), which PostgreSQL delivers to every replica exactly when, and only if, the transaction commits; an idempotent retry notifies nothing (§6.4).
3. On `FAILED_PRECONDITION` (head moved), the client pulls the new head, merges (§7) against the common base, and retries with the new head as base.

A revision is **acknowledged** only when `CommitRevision` returns success. Principle 1 applies from that moment.

### 6.3 Renames, deletes, creates

Client behaviour for renames, deletes and creates is defined by the engine design, `docs/design/engine.md` §5. The server rules still apply: a rename is a new revision with a new path; a delete is a tombstone revision; a create is a revision with an empty `base_rev_id`; a live path must not collide with another live document's `path_key`.

### 6.4 Realtime channel

One WebSocket per device (`GET /v1/realtime`), multiplexing subscriptions to any number of the user's vaults up to a server cap (`GetServerInfo.max_realtime_subscriptions`), authenticated with the same bearer token. Each binary WebSocket message is one protobuf frame (`ClientFrame` / `ServerFrame` in `proto/vaultsync/v1/realtime.proto`, each a `oneof` envelope). Client → server: `subscribe{vault_id}`, `unsubscribe{vault_id}`. Server → client: `subscribed{vault_id, head_seq}`, `vault_changed{vault_id, seq}`, `error`, and later membership/key-epoch changes. Field numbers 100–199 of both envelopes are reserved for the Phase 5 Yjs frames. Phase 5 adds Yjs subscribe/update/awareness messages multiplexed by `document_id`. The channel is a latency optimization only; correctness never depends on receiving a notification.

Server-side details (decision, #52):

- **Upgrade.** The client offers the subprotocols `vaultsync.v1` and `vaultsync.bearer.<access token>` (browsers cannot set headers on a WebSocket request; non-browser clients may send `Authorization: Bearer` instead, but not both). The server validates `Origin` against the CORS allow-list (an absent `Origin` is allowed for non-browser clients), authenticates the token with the RPC authenticator, and echoes only `vaultsync.v1`. It refuses the upgrade with 403 (origin), 401 (missing or invalid token), 400 (no `vaultsync.v1`), 429 (too many connections for the user) or 503 (instance full or draining). The token never appears in a URL, and the `Sec-WebSocket-Protocol` header is never logged.
- **Authorization.** Every `subscribe` resolves the caller's `vault_members` role; a non-member and a vault that does not exist get the same non-fatal `NOT_FOUND` error frame. Membership is checked again before every delivery, in one query per vault for up to 1,000 subscribed users (more take one query per 1,000): a removed member's subscription ends with an unsolicited `NOT_FOUND` error frame naming the vault, and no further notifications for it are sent. Removing a member (`RemoveMember`, `LeaveVault`; §9.2) queues a `vault_changed` notification at the vault's current `head_seq` in the same transaction, so every replica runs that check at once and the removed member's subscriptions end without waiting for a commit; the other subscribers receive a head they already have, which starts no pull (#33). If the check fails (a database error), that notification is not sent and the subscription is kept; clients' periodic pull catches up. A member subscribing to a deleted vault, and every subscriber when an owner deletes one (`DeleteVault`, which queues the same notification), gets a `NOT_FOUND` error frame whose `reason` is `ERROR_REASON_VAULT_DELETED`; a non-member still gets the plain `NOT_FOUND` frame.
- **Token expiry.** There is no in-band refresh. When the access token's `exp` passes, the server sends a fatal `UNAUTHENTICATED` error frame and closes (1008); the client reconnects with a fresh token and re-subscribes.
- **Fan-out.** Each replica holds one PostgreSQL connection that `LISTEN`s on `vault_changed` and delivers each notification to its local subscribers, so a commit on any replica reaches subscribers on every replica. Undelivered notifications of one vault are coalesced to the newest `seq`. If the listening connection is lost the replica reconnects with jittered backoff and then sends every locally subscribed vault's current `head_seq`, so commits made meanwhile are not missed. Subscriptions are per-connection state only: a client reconnecting to another replica re-subscribes and pulls from its cursor.
- **Bounds.** Inbound frames are at most 4 KiB (larger closes with 1009); the inbound rate is 20 frames per second with a burst of the subscription cap plus 32 (excess is a fatal `RESOURCE_EXHAUSTED`); subscriptions per connection, connections per user and connections per replica are capped (`docs/configuration.md`). Each connection's send queue is bounded; a client too slow to drain it, or that does not answer pings, is disconnected rather than buffered. Malformed or text frames are a fatal `INVALID_ARGUMENT`.
- **Drain.** On shutdown every socket is closed with 1001 ("going away"); clients reconnect with backoff and jitter.

Client-side details (decision, #193):

- **Token.** The plugin offers the token only as the `vaultsync.bearer.` subprotocol, never in the URL, and never logs it. It takes the token from its token manager, which refreshes it ahead of expiry. On the fatal `UNAUTHENTICATED` frame it invalidates that token in the token manager, so the reconnect carries a freshly refreshed one, with no user interaction.
- **Pull.** It pulls from its durable cursor after every `subscribed` whose `head_seq` is above the durable cursor (notifications sent while it was not subscribed are gone, so the head tells it whether it missed any) and on every `vault_changed` of its vault whose `seq` is above the durable cursor (decision, #261). This is safe because the server registers the subscription before it reads the head and reports the larger of that head and any `seq` announced meanwhile: every commit above the reported `head_seq` reaches the client as a `vault_changed`, and a cursor at or above `head_seq` has nothing to fetch. So a subscribe that completes after the startup push, with nothing new, starts no pull and leaves the status idle. A skipped pull is not a successful sync either: it keeps an earlier `offline` or `error` status. The server notifies the committing device too; since an acknowledged commit that is the next `seq` moves the cursor onto it (§6.1), a device's own commit's notification starts no pull, and its status stays idle. The cursor is checked when the notification arrives and again when the pull's turn comes after a running push, so a notification that overtakes its commit's response does not pull either. A notification above the cursor always pulls, including one coalesced from another device's commit and the device's own (the newest `seq` is above the cursor while the other commit is not applied). Pulls never overlap: `subscribed` and `vault_changed` frames that arrive during a pull cause one more pull after it, if the cursor is below the highest head among them. The pull timer runs whether or not the channel is up, so a server whose history was restored to below the cursor (whose `subscribed` and notifications then announce heads at or below the cursor, and start no pull) is still found by the timer's pull.
- **Reconnect.** Every close, or a failed upgrade, reconnects after a delay with equal jitter: half of a ceiling that starts at 1 s and doubles with each consecutive failure up to 60 s, plus a uniformly random part of the other half. It starts over only once a subscription has stayed up for 30 s, so a server that subscribes and then closes at once (a replica that keeps draining, say) still sees the delay grow (#413). A browser does not expose a refused upgrade's HTTP status (401, 429, 503 all look like a 1006 close), so these back off alike; a token the server no longer accepts is also invalidated by the next RPC that fails as unauthenticated. A non-fatal error frame for the vault (`NOT_FOUND` after a membership change, say) drops the connection and retries with the same backoff.

## 7. Merge rules (client side)

Defined by `docs/design/engine.md` §5 (rule M, rule W, rule C). Summary: Markdown (`TEXT`) is merged three-way. Other files (`BLOB`): the newest wins and the other is kept as a conflict copy. Overlapping Markdown edits: the server's version stays at the path, and the local version is saved as a conflict copy, named `<name> (Conflicted copy <user> <device> <YYYYMMDDHHMM>).<ext>` after the local user and device.

## 9. Authentication, authorization, encryption

### 9.1 Authentication

The plugin authenticates against Authentik with the **OAuth 2.0 Device Authorization Grant** (works identically on desktop and Android, with no redirect handling). The plugin stores the refresh token in Obsidian's per-vault, device-local storage (`app.saveLocalStorage`, key `vault-sync-refresh-token`), never in `data.json`, so tools that back up or sync the vault folder never copy it (the unlocked encryption keys are kept the same way, §9.3); access tokens are JWTs validated by the server against the issuer's JWKS (refreshed on unknown `kid`, with a bounded refresh rate). `iss`, `aud`, and `exp` are always checked.

Client-side details (decision, #25):

- The OAuth calls live in `plugin/src/core/auth` and go through an injected HTTP client: Obsidian's `requestUrl` in the plugin, which is not subject to CORS and behaves the same on desktop and Android. The plugin's ConnectRPC transport uses `requestUrl` too; `requestUrl` cannot be cancelled, so an aborted or timed-out RPC rejects at once and its late response is dropped. Identity provider responses are bounded at 64 KiB of UTF-8 (checked once `requestUrl` has buffered the body, as it offers no streaming). The discovery document must name the configured issuer exactly, and the issuer, every endpoint and the server URL must be `https` (plain `http` only to loopback hosts). The plugin checks `GetServerInfo`'s protocol version before it signs in, and takes the identity provider from it (decision, #194): `GetServerInfo` advertises the issuer (`VAULT_SYNC_OIDC_ISSUER_URL`) and the plugin's public client id (`VAULT_SYNC_OIDC_CLIENT_ID`, by default the audience), both public, so only the server URL must be entered. The plugin's issuer and client id settings are optional overrides: an entered client id wins, and an entered issuer is used only when the server advertises none (one that differs from the advertised issuer is refused). So the server URL decides the identity provider unless the issuer is entered: with none entered, the first sign-in trusts the issuer the server advertises, and a malicious or compromised server can send the user to a verification page of its choosing. This is accepted, because the user already trusts that server with the vault's notes; entering the issuer pins it. The advertised issuer must pass the same `https` rule, and an advertised client id must be 1 to 255 printable ASCII characters. The issuer and client id a sign-in used are stored with the refresh token and used for its refreshes, so refreshing never depends on the server. The device flow requests `openid offline_access`, follows RFC 8628 polling (the provider's interval, plus 5 s on every `slow_down`; network failures and 5xx responses are retried until the code expires), and is cancelled when its dialog closes, leaving the authentication state as it was. The server and identity provider settings are locked while a sign-in runs and while signed in. A signed-in device must sign out before it can sign in again. A grant without a refresh token is refused.
- The refresh token is the only token stored (device-local storage, never synced). A refresh token found in `data.json` (written by older versions) is moved to local storage on load and removed from `data.json`. When `data.json` still names the sign-in's identity provider but local storage holds no token (it was cleared), the device starts in "sign-in required", as after a revoked token. The access token is kept in memory and refreshed a minute before its `exp` (from the JWT, else `expires_in`), or halfway through its lifetime if that is shorter. Concurrent callers share one refresh. A rotated refresh token is persisted before the new access token is used. Writes of the refresh token never overlap, and a sign-in or sign-out wins over a refresh still running: that refresh's tokens are dropped and its rotated refresh token is never left on disk. A sign-in forgets the previous session's tokens before it stores the new refresh token, so while that write runs no caller gets the previous session's access token, and a failed write leaves the device signed out and then removes the stored refresh token (best effort), so a restart does not resume the session the sign-in replaced. A unary RPC refused with `UNAUTHENTICATED` invalidates its token and is sent once more, unchanged, with a fresh one, so a retried `CommitRevision` keeps its `revision_id` (§6.2). `GetServerInfo`, the one public procedure, never waits for a token.
- A refresh refused with `invalid_grant` (the refresh token expired or was revoked, or the provider session ended) deletes the refresh token and moves to "sign-in required". From then on authenticated calls fail with `UNAUTHENTICATED` without reaching the server, and the engine keeps its pending operations (principle 1) until a new sign-in. A provider that cannot be reached fails calls with `UNAVAILABLE` and keeps the device signed in. A request `requestUrl` could not deliver at all (no network, DNS, TLS) fails with `UNAVAILABLE` too. "Sign-in required" stops sync; the session that starts after the next sign-in pushes what was changed meanwhile. Tokens are never logged.

Server-side details (decision):

- Only RS256, ES256 and EdDSA signatures are accepted; `none` and HMAC algorithms are rejected. Tokens are size-bounded before parsing. `exp` has no leeway; `nbf`, when present, tolerates one minute of clock skew.
- The JWKS (discovered from the issuer's OpenID configuration) is fetched lazily, refetched on an unknown `kid` and when older than one hour, and never more than once per 30 seconds. A failed refetch keeps the cached keys. At most one fetch is in flight and no lock is held across it: while hour-old keys are being refetched, other requests use the cached keys rather than wait. The discovery document, `jwks_uri` and redirects must be `https` (plain `http` only to loopback hosts, and only for a loopback `http` issuer); redirects must stay on the requested host and never downgrade to `http`.
- Users are created on their first authenticated request, keyed by `(issuer, subject)`; concurrent first requests create exactly one user. `sub` must be non-empty, at most 255 bytes, and free of control characters (Unicode `Cc`); other tokens are rejected as unauthenticated before any user lookup.
- Authentication is **default-deny**: one interceptor on every ConnectRPC service authenticates every procedure that is not on an explicit public allow-list (only `ServerInfoService/GetServerInfo`, which returns only public, configuration-derived data: versions, the realtime subscription cap, the issuer and the plugin's public client id). The realtime WebSocket upgrade (§6.4) authenticates with the same authenticator. A test enumerates every procedure in the schema and asserts it is authenticated or allow-listed.

### 9.2 Authorization

Every RPC and every WebSocket message resolves `(user, vault_id)` to a `vault_members` role before touching data. `viewer` can read; `editor` can read and write; `owner` can also manage members and vault settings. There is no admin bypass in the API.

Server-side details (decision):

- Authorization is **central and runs before the handler**: one interceptor, after authentication, on every ConnectRPC service. A single table (`server.VaultProcedures`) classifies every vault-scoped procedure — every procedure whose request carries `vault_id` — as read or write. A request carrying a `vault_id` for an unclassified procedure is rejected, and a test derived from the schema descriptors fails if any such procedure is missing from the table. The interceptor reads only the top-level `vault_id`, so a request must name its vault nowhere else: a second schema-derived test walks every RPC input message (nested messages, `oneof` members, repeated and map fields, stopping at recursive types) and fails, naming the procedure and field path, on any vault-identifying field other than a single top-level, singular, non-`oneof` `string vault_id`. A field is vault-identifying if its name ends in `vault`, `vaults`, `vault_id` or `vault_ids` (also without the underscore before `id`; for example `target_vault_id`) or its type is the `Vault` message. Streaming calls to vault-scoped procedures are rejected before the handler runs, because their messages arrive only after it starts.
- `vault_id` must be a canonical lowercase UUID (`INVALID_ARGUMENT` otherwise) and is checked before any query. The role is then resolved with one `vault_members` lookup: a vault that does not exist and a vault the caller is not a member of take the same path and return the same `NOT_FOUND` error. A `viewer` calling a write procedure gets `PERMISSION_DENIED`.
- Handlers take the authorized vault from the interceptor, never from the request, and query through a vault-scoped store handle whose every query filters by that vault, so ids from another vault (documents, revisions, blobs) are simply not found.
- `CreateVault` makes the caller the `owner` (a user may own at most 100 vaults that are not deleted); `ListVaults` returns only vaults the caller is a member of, with the caller's role, paginated by an opaque `page_token` (`page_size` defaults to 100 and is capped at 1000; like `ListChanges`, a page also ends early where its encoding would exceed the send limit, with a `next_page_token` to continue, and holds at least one vault if one remains; startup requires the send limit to fit a response with one vault with a maximum-length name). Vault names are non-blank, at most 256 bytes, and contain no control characters (Unicode category `Cc`, including U+0000, which PostgreSQL `text` cannot store), no format characters (`Cf`: bidi embeddings, overrides, isolates and marks, zero-width characters, the byte order mark, tag characters) and no line or paragraph separator (`Zl`, `Zp`; decision, #548), so a name other members see cannot hide text or reorder the label around it; anything else is `INVALID_ARGUMENT` before the database is touched.
- **Deleting a vault (`docs/design/sharing.md`).** `VaultService.DeleteVault(vault_id)` is owner-only (`Manage`; `PERMISSION_DENIED` for editors and viewers, and the vault is unchanged). It sets `vaults.deleted_at` under the vault row lock and keeps every row and blob. From then on every vault-scoped RPC from a member of the vault, `DeleteVault` included, is `NOT_FOUND` with an `ErrorDetail` of reason `ERROR_REASON_VAULT_DELETED`, and its realtime subscriptions end the same way (§6.4). A non-member gets the same `NOT_FOUND` as for a vault that does not exist. `ListVaults` no longer lists it, its pending invitations no longer redeem, and it no longer counts toward its owners' limit of 100 owned vaults. The check is read from PostgreSQL on every request, so it takes effect on every replica at once. **Purge and undelete.** The retention job (§11) purges a vault deleted more than 30 days ago: one transaction sets `vaults.purged_at` (migration 0018) and deletes every row of the vault, then the job deletes every object under the vault's S3 prefix, at most 10,000 per run, then the `vaults` row; a purge cut short resumes on the next run. `vault-sync-server vault undelete <vault-id>` clears `deleted_at` while `purged_at` is unset; an unknown vault or one whose purge has started exits 1. The export keeps writing a deleted vault until its purge starts, with a `<vault-id>.DELETED` file holding the deletion time (`docs/export.md`).
- **Membership (decision, #33).** `MembershipService` manages members. `CreateInvitation`, `ListInvitations`, `RevokeInvitation`, `ListMembers`, `UpdateMemberRole` and `RemoveMember` are owner-only (the `Manage` class of `server.VaultProcedures`, PERMISSION_DENIED for editors and viewers); `LeaveVault` is open to every member (`Read`); `RedeemInvitation` is not vault-scoped, since the person redeeming is not a member yet: it carries only the code. An invitation grants one role (owner, editor or viewer) and expires after `ttl_seconds` (default 7 days, at most 30 days; more is `INVALID_ARGUMENT`). Its code is 32 random bytes, base64url-encoded without padding, returned only by `CreateInvitation`; the server stores only its SHA-256. Redeeming makes the caller a member with the invitation's role and deletes the invitation in one transaction, so a code works once even when redeemed concurrently. A code that is malformed, unknown, expired, revoked or used gets one and the same `NOT_FOUND` error, which names no vault. When a member is removed or leaves, or an owner is demoted, the invitations they created are deleted in the same transaction: their codes get that same `NOT_FOUND` and `ListInvitations` no longer lists them, so a former owner cannot use a code they created earlier to get back in. Redeeming as an existing member is `ALREADY_EXISTS` and leaves both the role and the invitation as they were. A vault has at most 100 members and 100 pending invitations (`RESOURCE_EXHAUSTED`; a redemption refused by the member limit keeps the invitation), so `ListMembers` and `ListInvitations` are not paginated. A vault always has at least one owner: demoting or removing its last owner, and the last owner leaving, is `FAILED_PRECONDITION`. Every membership change locks the vault row (as commits do), so concurrent changes cannot leave a vault without an owner or over the member limit. Changes take effect on the member's next request on every replica, because authorization reads `vault_members` on every request and nothing caches roles, and a removal ends the member's realtime subscriptions at once (§6.4). An in-flight request authorized before the change may still complete, except a commit: `CommitRevision` re-reads the caller's role and the vault's `deleted_at` under the vault row lock that membership changes and `DeleteVault` also take, so once a removal, a demotion to viewer or a vault deletion returns, no revision by that member lands after it (a commit waiting for the lock is refused with `NOT_FOUND`, with reason `ERROR_REASON_VAULT_DELETED` for a deleted vault, or `PERMISSION_DENIED` for a viewer). An owner role granted by invitation or promotion counts toward `CreateVault`'s limit of 100 owned vaults, but is never refused by it.
- `RegisterDevice` registers a device for the caller (one per plugin installation, so every reinstall adds one). A user may have at most 100 devices that are not removed (decision #52 item 8 counted every registration over the account's lifetime; #205 made devices removable, so the limit can be recovered from). The 101st call gets `RESOURCE_EXHAUSTED` ("at most 100 devices may be registered") with an `ErrorDetail` of reason `ERROR_REASON_DEVICE_LIMIT`, which clients match instead of the message (#428); registrations are serialized on the user row, so concurrent calls cannot overshoot the cap. Registration is idempotent with a client-chosen `registration_id` (a canonical lowercase UUID; #428): the plugin saves one before its first attempt and sends it with every retry, and a retry with the same id, name and public key returns the device the first call registered, without using another place, even at the cap. So a crash or a lost response between the server registering the device and the plugin saving it does not burn a place. The plugin drops the saved id after `INVALID_ARGUMENT` or `ALREADY_EXISTS`, which mean nothing was registered under it, so its next attempt uses a new id and the current Device name; after any other error it keeps the id, since the first call may have registered the device. The same id with a different name or public key is `ALREADY_EXISTS`; the id is scoped to the caller and to devices that are not removed, so after removal it registers a new device; an empty id registers a new device on every call (older plugins). Device names follow the same character rule as vault names (no `Cc`, `Cf`, `Zl` or `Zp`; #548), are non-blank and at most 256 bytes; names stored before #548 are kept as they are, and the plugin strips those characters, replaces double quotation marks, bounds the shown length and isolates the name (Unicode FSI/PDI) wherever it shows another device's or a vault's name, writes invisible characters in file paths it shows as `\uXXXX` and a backslash as `\\`, except the zero-width joiners of an emoji sequence, and lays each path out on its own (an element with `dir="auto"`) inside the label that shows it (display only; #557, #605), and registers at most 256 bytes of its Device name setting (§11). The public key is empty or exactly 32 bytes. Anything else is `INVALID_ARGUMENT` before the database is touched.
- `ListDevices` returns the caller's devices that are not removed, oldest first, each with its id, name, registration time and last activity (its last commit, to within a minute; unset if it never committed), and nothing secret (no public key). It is not paginated: the device limit bounds it to 100 entries. `RemoveDevice` removes one of the caller's devices (decision, #205): `device_id` must be a canonical lowercase UUID (`INVALID_ARGUMENT`), and a device that is not the caller's, does not exist or is already removed is `NOT_FOUND`, so a user can neither see nor remove another user's devices. The row is kept with `removed_at` set, because `revisions.device_id` references it: the device's revisions keep their history and attribution, and their device name is still shown (§11). A removed device no longer counts toward the limit, is not listed, and can no longer commit (`CommitRevision` answers `NOT_FOUND`, as for an unknown device, with the reason `ERROR_REASON_DEVICE_NOT_FOUND`); the installation must register again to sync. The plugin lists the user's devices in its settings and removes another one there, never its own (#590). When a commit of its own is refused with that reason, it stops sync, says so, and waits for the user to register the installation again, which it never does by itself (the device may have been removed because it was lost); its pending operations stay in the journal and are pushed under the new device, and a retry of a commit that landed before the removal gets the committed revision back (§6.2). Removal is not undoable. It takes effect on every replica once the call returns, with PostgreSQL as the only coordination: every commit locks its device row (after the vault row, so no deadlock) until it ends and checks `removed_at` under that lock, and the removal updates that row, so it waits for the device's commits in flight and every later commit, on any replica, sees it. No replica caches devices. Removed rows are not deleted, so a user's device rows grow by one per removal; each removal needs an authenticated registration and removal, and the rows are small. They are kept on purpose (decision, #428): deleting one is only safe once no revision references it, and checking that needs an index on `revisions (device_id)`, which every commit would have to maintain, for rows of about a hundred bytes.

### 9.3 End-to-end encryption (opt-in per vault)

Encryption is chosen when a vault is created (`CreateVault` with `VAULT_ENCRYPTION_E2EE`); the owner's device then creates epoch 1 itself (`RotateEpoch(expected_epoch = 0)`), wrapping its key to the owner and, with escrow, to the escrow key (§9.4), so the server never sees an epoch key. Escrow on a plaintext vault is `INVALID_ARGUMENT`, and escrow on a server without an escrow key is `FAILED_PRECONDITION`. An E2EE `CreateVault` carries the vault's id (`new_vault_id`, chosen by the creator's device) and the genesis entry of its membership log, which the creator signs over that id (`docs/design/crypto.md`). The server checks the genesis with the log replay (`e2ee.ReplayLog`): it must be the first entry of that vault's log, signed by its creator, the creator must be the caller, and it records an escrow bundle exactly when escrow is requested. Otherwise the request is `INVALID_ARGUMENT`, and an id naming an existing vault is `ALREADY_EXISTS`; a refused request creates no vault. The vault and its genesis are stored in one transaction. A plaintext `CreateVault` takes neither field, and the server chooses its id. `VaultKeyService.ListLogEntries` returns the vault's log in `seq` order to every member, viewers included (non-members get `NOT_FOUND`), in pages of 100 by default and at most 1000, cut to the send limit; a plaintext vault's log is empty. A non-member may also read it with `invitation_id`, the `<id>` of an E2EE invite code (22 characters of base64url), so that a newcomer can verify the log and sign its redeem entry before redeeming (`docs/design/encryption.md`, *Redemption takes two steps*): the request is served when SHA-256 of the id's 16 bytes names a pending, unexpired invitation to the requested vault (the `ReadOrInvitation` class of `server.VaultProcedures`); a malformed, unknown, expired, revoked or redeemed id, or one for another vault, gets the same `NOT_FOUND` as `GetInvitationSlots`. Members are served whatever `invitation_id` they send, and anonymous callers are still `UNAUTHENTICATED`. In an E2EE vault, `CreateInvitation`, `RevokeInvitation`, `RedeemInvitation`, `UpdateMemberRole`, `RemoveMember` and `LeaveVault` each carry their signed log entry (`log_entry`: invite, revoke invitation, redeem, set role, remove member, leave). Under the vault row lock, in the change's transaction, the server requires the entry's `seq` to be the log's next (otherwise `ABORTED`: the client lists the log and retries on top of the new head), replays it onto the stored log (signatures, hash chain, the signer's right to sign), checks that it records exactly the requested change (an invitation's id is its invite entry's; a redeem names the redeemed invitation and the caller; a leave names the caller), and appends it; a missing entry or one that fails these checks is `INVALID_ARGUMENT`. A refused change changes nothing. An E2EE `RevokeInvitation` also accepts an invitation that has expired but is still pending in the log, so owner devices can record its end. A plaintext vault's membership changes take no entry (`INVALID_ARGUMENT` with one). **Invitations carry key slots** (`docs/design/encryption.md`, *Invitations*). For an E2EE vault the inviting device generates the code `<id>.<secret>` (128 random bits each, base64url without padding) and `CreateInvitation` carries only `id_hash` (SHA-256 of the 16 bytes of `<id>`), the invite anchor (96 bytes) and the invitation's key slots: exactly one per existing epoch, each for this invitation (`KEY_RECIPIENT_KIND_INVITATION`), otherwise `INVALID_ARGUMENT` (or `FAILED_PRECONDITION` with reason `ERROR_REASON_EPOCH_NOT_CURRENT` when an epoch is missing); the response carries no code, and an `id_hash` in use is `ALREADY_EXISTS`. A plaintext invitation takes none of these fields and keeps its server-generated code. `MembershipService.GetInvitationSlots(id)` is open to any authenticated user and names no vault: for a pending E2EE invitation it returns the invitation id, vault id and role, its slots, the vault's epochs with their commitments and records, and the invite anchor; a malformed, unknown, expired, revoked or used id gets the same `NOT_FOUND` as a failed redemption. `RedeemInvitation(code, slots)` then takes the redeemer's own slots, exactly one per existing epoch, all for the caller's user id; the caller must have a user key. Under the vault row lock it stores them, makes the caller a member and deletes the invitation and its slots in one transaction, so a member never lacks a slot for an epoch that existed when they joined. A missing epoch (the vault rotated since `GetInvitationSlots`) is `FAILED_PRECONDITION` with reason `ERROR_REASON_EPOCH_NOT_CURRENT`; other mismatches, or slots on a plaintext redemption, are `INVALID_ARGUMENT`; a refused redemption changes nothing. Revoking, redeeming, pruning expired rows and deleting a former owner's invitations delete the invitations' slots in the same transaction; the vault purge deletes the rest. Invitation slots are never listed by `ListKeySlots` and are refused by `AddKeySlots`. An E2EE `RotateEpoch` carries the new epoch's signed record (`record`: the log position, the sorted recipients with their key hashes, and an owner's signature over `epoch_body`, `docs/design/crypto.md`). Under the vault row lock the server replays the stored log, and the record must verify there with `e2ee.VerifyEpochRecord`: signed by an owner at the position it names, over this vault, epoch, commitment and the current epoch's commitment, with exactly the recipients the log names there. The user, invitation and escrow slots must be exactly the record's user, invitation and escrow recipients, and every stored invitation (expired ones included, until revoked) needs its slot; a slot for a pending invitation whose expired row was already pruned is accepted and dropped. To turn escrow on or off, the request also carries the owner's signed escrow entry (`escrow_entry`, type 8), and the record's position must be that entry. The server appends the entry, sets the vault's escrow flag, and creates the epoch in one transaction. A record or entry that does not verify is `INVALID_ARGUMENT`, and nothing changes. An E2EE `RemoveMember` carries its `next_epoch`'s signed record the same way (`record`), and its position must be the request's remove-member entry: the record must be signed by an owner at that entry, and its recipients must be the log's after it. The server appends the entry, creates the epoch with its record and removes the member in one transaction. A missing record, another signer, another position or other recipients are `INVALID_ARGUMENT`, as for `RotateEpoch`, and nothing changes; a plaintext vault's removal takes no `record`. The compare-and-set on the current epoch is unchanged, and a plaintext vault's `RotateEpoch` is still `FAILED_PRECONDITION`. `ListEpochs` and `RotateEpoch` return each epoch's stored record. `CommitRevision` in an E2EE vault takes a ciphertext path and a client-computed `path_key` under the vault's current epoch (§5, §6.2); the server never derives a `path_key` there.

Envelope encryption with multiple recipients:

- Each **user** has a hybrid post-quantum key pair, ML-KEM-768 + X25519 in age's `mlkem768x25519` format (cipher suite 2, `docs/design/encryption.md`): a 32-byte private key (an age hybrid identity) and a 1216-byte public key. The private key is stored server-side wrapped by a key derived from a user recovery passphrase (Argon2id). The Argon2id output is split with HKDF-SHA256 into a `wrap_key`, which wraps the private key and never leaves the device, and an `auth_key`, a verifier the device presents so the server releases the wrapped key. The server stores only `SHA-256(auth_key)`, compares in constant time, and rate-limits failed attempts per user in PostgreSQL. Neither key can be derived from the other, so the server cannot unwrap the key. A stolen session therefore allows only a rate-limited online guessing attack; a dump of the database allows an offline attack at Argon2id cost per guess; and a lockout ends with its window. Devices unwrap it once and keep it in local storage. (Device-to-device linking and Shamir-split recovery are later enhancements.)
- **User key storage (decision, #52, #665).** `UserKeyService` stores each user's key pair; every procedure acts on the caller's own key only and none names a user, so another user can neither read, unlock nor replace it. The server stores the public key, the wrapped private key, the wrapping's public parameters (suite, Argon2id memory, passes, lanes and salt) and `SHA-256(auth_key)`, never `auth_key`, the passphrase, the Argon2id output or the private key, and never logs `auth_key` or key material. `GetUserKeyParams` returns the public key and parameters a device needs to derive `auth_key`. `CreateUserKey` is create-only: a user who has a key gets `ALREADY_EXISTS` and the stored key is unchanged, so two devices enabling encryption at once cannot replace each other's key. `UnlockUserKey` returns the wrapped private key only for the matching `auth_key`; a wrong one is `PERMISSION_DENIED` with reason `ERROR_REASON_WRONG_PASSPHRASE` and no key material. `ChangePassphrase` takes the current `auth_key` and the stored public key and replaces the wrapped key, its parameters and the verifier in one transaction, as a compare-and-swap on the public key (a different public key is `FAILED_PRECONDITION` and changes nothing); key rotation and reset are out of scope. A user without a key gets `NOT_FOUND`. `GetUserKeyParams`, `CreateUserKey` and `UnlockUserKey` also return `user_id`, the caller's server user id (`Member.user_id`, a canonical lowercase UUID): the id a signed genesis, redeem or leave entry must name for the caller, which a device cannot learn from its token (whose `sub` is the OIDC subject). Wrong `auth_key`s presented to `UnlockUserKey` or `ChangePassphrase` are counted per user in the `user_keys` row, under its row lock and with the database clock, so every replica sees one count: after 10 within one hour (the hour starting at the first counted failure), every attempt is `RESOURCE_EXHAUSTED` with reason `ERROR_REASON_PASSPHRASE_ATTEMPTS_EXHAUSTED` and `ErrorDetail.retry_time` set to the end of the hour, even with the right `auth_key`; refused attempts are not counted and do not extend the hour, and a success does not reset the count. Inputs are bounded before the database is touched (`INVALID_ARGUMENT`): public key exactly 1216 bytes, `auth_key` exactly 32 bytes, wrapped private key 1 to 256 bytes, suite 2, salt exactly 16 bytes, and the Argon2id bounds below. A device remembers, per account, the Argon2id parameters it has seen (in its plugin data, kept on sign-out). It refuses to unlock or change the passphrase with parameters lower in memory, passes or lanes, before it derives or sends anything (`docs/design/encryption.md`, *Passphrase parameters*).
- **Anchor list storage.** `UserKeyService` also stores each user's sealed anchor list (`docs/design/encryption.md`, *Trust anchors*): opaque bytes and a version, which the server never opens. `GetAnchorList` and `PutAnchorList` act on the caller's own list only and name no user. A user without a list reads version 0 and an empty list. `PutAnchorList` is a compare-and-set: it stores the list only when its version is the stored version plus one (1 for the first list), and otherwise returns `FAILED_PRECONDITION` and leaves the stored list unchanged, so of concurrent writers of one version exactly one succeeds. Inputs are bounded before the database is touched (`INVALID_ARGUMENT`): version 1 to 2^63 - 1, and sealed list 1 to 4,800,045 bytes, the sealed size of `MaxAnchors` (100,000) vaults. The request size limit (`VAULT_SYNC_MAX_REQUEST_BYTES`) also applies.
- **Plugin key manager (decision, #667).** Enabling E2EE creates the key pair on the device (`plugin/src/core/keys`) and calls `CreateUserKey` with only the public key, the wrapped private key, its parameters and `auth_key`; a new passphrase has at least 10 characters. The wrap binds the associated data `"vault-sync/v1/user-key" || public_key`, so a wrapped key cannot be passed off as another key pair's, and after unwrapping the device checks that the private key yields the stored public key. A device that gets `ALREADY_EXISTS` (another device enabled E2EE first) unlocks the stored key with the passphrase it was given instead of replacing it. Unlocking derives `auth_key` from the parameters `GetUserKeyParams` returns, presents it to `UnlockUserKey` and unwraps the released key on the device; a wrong passphrase and the attempt limit (with the server's `retry_time`) are reported to the user. The unlocked key pair is cached only in Obsidian's per-vault, device-local storage (`app.saveLocalStorage`, key `vault-sync-user-key`), never in `data.json`, so tools that back up or sync the vault folder never copy it, with the server and account it belongs to, is never logged, and is dropped on sign-out. A cached key is used only while its public key is the one `GetUserKeyParams` returns (decision, #692): otherwise the device reports the key as locked, says the server's key is not the one it unlocked, and asks for the passphrase again; the cached key is replaced only by that unlock, never deleted silently.
- Each **vault** has a symmetric vault key per **epoch**. `key_slots` hold the epoch key wrapped to every member, and to the escrow public key if escrow is enabled. Every wrapping is a binary age file to the recipient's hybrid ML-KEM-768 + X25519 key, 1 to 2048 bytes, so the standard `age` tool opens an escrow slot with the escrow identity. User keys stored under suite 1 (X25519, 32 bytes) before migration 0019 stay stored as they are; the server accepts only suite 2 keys.
- **Key slots and key commitments (decision, #52).** A slot's payload is the epoch key followed by `"vault-sync/v1/key-slot" || vault_id || epoch || recipient_kind || recipient_id`, which the reader checks, so it opens only as the slot of that vault, epoch and recipient. Every epoch stores a key commitment, `HMAC-SHA256(epoch_key, "vault-sync/v1/key-commitment" || vault_id || epoch)`, which a recipient verifies after unwrapping. Byte encodings: `docs/design/crypto.md`.
- Sub-keys are derived from the epoch key with HKDF: `content`, `path`, `path_key_secret`, `blob_id_secret`.
- Content and paths are encrypted with **XChaCha20-Poly1305**, random nonce, the revision's document id and epoch bound as associated data.
- Every ciphertext carries a **suite version** byte so that the algorithms can change later, and every open authenticates the whole header (suite byte included) with the caller's associated data, so a ciphertext with an unknown suite, a changed header or associated data, or a truncated tag fails closed. Suite 1 (byte formats in `docs/design/crypto.md`): HKDF-SHA256 sub-keys; XChaCha20-Poly1305 with a random 24-byte nonce from the platform CSPRNG; sealed box = ephemeral X25519, HKDF-SHA256 salted with both public keys, XChaCha20-Poly1305, refusing low-order keys; HMAC-SHA256 `path_key` and `blob_id`; the user's private key wrapped under a `wrap_key` split by HKDF-SHA256 (with an `auth_key` under a separate label) from Argon2id (default 64 MiB, 3 passes, 1 lane) of the passphrase in NFC (the libraries of §5; a passphrase may use only code points assigned in Unicode 15.0 and any other is refused when it is set or used, so every device derives the same key), with the parameters stored in the header and bounded (19–128 MiB, 2–8 passes, 1–4 lanes) before any derivation, so a stored value can neither weaken the derivation nor exhaust a device.
- **Member removal** creates a new epoch. Subsequent revisions use it; historical content is not re-encrypted (the removed member may already hold it).
- **Epochs and key slots (decision, #52, #694).** `VaultKeyService` stores epochs and slots as opaque bytes; the server never sees an epoch key. A new E2EE vault has no epoch (`current_epoch = 0`) and a pending rotation; an owner client creates epoch 1. Every epoch change is a compare-and-set on `vaults.current_epoch` under the vault row lock (which commits and membership changes take too), so of concurrent changes with the same `expected_epoch` exactly one wins, on any replica, and the others get `FAILED_PRECONDITION` with reason `ERROR_REASON_EPOCH_NOT_CURRENT` and adopt the winner's epoch. An epoch's recipients are exactly the vault's members **who have a user key**, plus at most one escrow slot in an escrow vault (requiring it is #40); a member without a user key cannot be wrapped to and is not required, and missing or extra recipients are `INVALID_ARGUMENT`. An owner's `RemoveMember` on an E2EE vault must carry `next_epoch` (commitment and a slot for every remaining recipient, not the removed member) and commits the removal and epoch N+1 in one transaction; without a valid one the member stays. A plaintext vault takes no `next_epoch`. An owner cannot remove themselves from an E2EE vault with `RemoveMember`, since they would create, and so know, the epoch meant to exclude them: it is `FAILED_PRECONDITION`, names `LeaveVault`, and changes nothing (#710). Self-removal from an E2EE vault goes through `LeaveVault`. In a plaintext vault an owner may still remove themselves with `RemoveMember`. `LeaveVault` (no owner client involved) sets `rotation_pending`; an owner client then calls `RotateEpoch(expected_epoch = N)`, which creates N+1 and clears the flag. `CommitRevision` carries the revision's `epoch`: 0 in a plaintext vault and the vault's current epoch in an E2EE vault, checked under the vault row lock after the idempotency check (a retry of a commit applied before a rotation gets its revision back); any other epoch is `FAILED_PRECONDITION` with reason `ERROR_REASON_EPOCH_NOT_CURRENT`. A pending rotation does not change the current epoch, so commits under it continue until the next epoch exists. A new member gets slots for every epoch (decision #52): `ListMissingSlots` (owner-only) lists every (epoch, member with a user key) pair without a slot, with the member's public key, until an owner grants it with `AddKeySlots`, which keeps an existing slot rather than replacing it. `ListKeySlots` returns the caller's own slots, and `ListEpochs` the epochs with their commitments and the vault's key state; both are open to every member, viewers included. With `recipient_kind = KEY_RECIPIENT_KIND_ESCROW`, `ListKeySlots` returns the vault's escrow slots instead, to editors and owners only (a viewer gets `PERMISSION_DENIED`), so that the import can open them with the escrow identity; an escrow slot is useless without that identity. No call returns another member's slots. `ListMembers` reports each member's user public key. Inputs are bounded before the database is touched (`INVALID_ARGUMENT`): commitment exactly 32 bytes, wrapped key 1 to 256 bytes, user recipient ids canonical lowercase UUIDs, escrow recipient ids 1 to 255 printable ASCII bytes (the key-slot format allows 255), at most 101 slots in a new epoch and 1 to 1000 per `AddKeySlots`, no duplicate slots, and list pages of 100 by default and at most 1000, cut to the send limit.
- **Plugin vault key manager (decision, #695).** `plugin/src/core/keys` keeps an E2EE vault's epoch keys on the device. Each sync reads every page of `ListEpochs` and `ListKeySlots` and unwraps each of the user's slots it does not hold yet with the unlocked user key. It uses a key only once it matches its epoch's key commitment. A slot that does not open, has no commitment or does not match is refused and reported to the user, never used. A held key whose epoch's commitment changes is refused too: an epoch's key never changes, so the device then stops using and sharing it. The keys are cached only in Obsidian's device-local storage (key `vault-sync-vault-keys`), never in `data.json`, for the server, account and vault they belong to, are never logged, and are dropped on sign-out together with the user key. Only an owner device rotates and grants. When the vault is rotation-pending (a new vault has no epoch yet, or a member left), it creates the next epoch with `RotateEpoch(expected_epoch = current)`. The next epoch has a fresh random key, wrapped for every member `ListMembers` lists with a user public key, and a member without one is skipped. If the device gets `ERROR_REASON_EPOCH_NOT_CURRENT` because another owner device won, it re-reads and adopts that epoch without creating another. An owner's removal of a member sends `RemoveMember` with the next epoch built the same way, without the removed member, and retries over a newer epoch at most three times when another epoch change wins. Once a sync is done reading, an owner device grants every `ListMissingSlots` entry for an epoch whose key it holds, in `AddKeySlots` batches of at most 1000. A new epoch's key is kept once the server accepted it: should the response be lost, the device's own slot in that epoch still holds it. Until the device holds the key of every epoch up to the current one, the member sees "Waiting for an owner to share the vault key."
- Implementations: `@noble/ciphers`, `@noble/curves`, `@noble/hashes` in TypeScript (pure JS, audited, identical on Electron and Android WebView); `golang.org/x/crypto` in Go. A shared set of **cross-language test vectors** in `testdata/crypto/` (generated by the Go tests, including published known answers for the primitives and ciphertexts that must be refused) must pass in both (`internal/e2ee`, `plugin/src/core/e2ee`).
- With E2EE, the server cannot merge, search, or render content — none of which it does anyway (§4).

### 9.4 Escrow for plaintext backups

A vault with `escrow = true` also wraps each epoch key to a deployment-wide **escrow public key**. The escrow private key exists only in the export job's Secret, which is never mounted into the internet-facing server. A compromise of the API server, PostgreSQL, or S3 therefore exposes only ciphertext. The export job decrypts and writes plaintext for tape archival. Escrow is chosen at vault creation and shown clearly in the UI. The server publishes its escrow public key (`VAULT_SYNC_ESCROW_RECIPIENT`, an age hybrid recipient), the key's id (`sha256:` and the hex SHA-256 of the 1216-byte key, the `recipient_id` of escrow slots) and its escrow default (`VAULT_SYNC_ESCROW_DEFAULT`, on unless configured otherwise) in `GetServerInfo`; the plugin's escrow toggle starts at that default, and the owner can turn it off. A client refuses a published key whose id does not name it. The plugin pins the current escrow bundle per server the first time it sees it, after checking the published chain. Afterwards it accepts a different current bundle only when rotation statements, each signed by the key it replaces, chain it to the pinned one, and then moves the pin. Any other change is refused at vault creation and at rotation, so no epoch key is wrapped to it. The escrow key comes with an Ed25519 escrow signing key (`VAULT_SYNC_ESCROW_SIGNING_KEY`); together they are the deployment's escrow bundle. The escrow chain, the root bundle and the escrow rotation statements after it, each signed by the previous bundle's signing key, is stored in PostgreSQL (`escrow_chain`), and `GetServerInfo` publishes it (`docs/design/encryption.md`, *Escrow key*). On the first start with an escrow key the configured bundle becomes the root. At every start the chain must link and its head must be the configured bundle, or the server stops. During an escrow key rotation the export job writes through the job-only `EscrowJobService`, authenticated only by a static bearer token (`VAULT_SYNC_ESCROW_JOB_TOKEN_FILE`, compared in constant time; user tokens are refused, and without a token the service refuses every call): it appends the next rotation statement and replaces escrow slots conditionally (§5). Optionally, the escrow private key may be split with Shamir secret sharing for offline disaster recovery; this is not used by the automated path.

## 10. Live collaborative editing (Phase 5)

The v1 protocol includes the hooks for this from the start: stable document ids, the `kind` field, the multiplexed WebSocket, and an append-only per-document log.

- A `yjs` document's state is its ordered `yjs_updates` log plus periodic snapshots. For E2EE vaults each update is encrypted (the server stores and relays opaque bytes).
- **Conversion** of a `text` document to `yjs` happens **exactly once**, as a server-side compare-and-set on `documents.kind` performed by a single elected client (the server grants a lease). Two clients independently initializing a `Y.Text` from the same file duplicates the content — the classic Yjs bug — and must be impossible.
- The plugin binds `Y.Text` to Obsidian's CodeMirror 6 editor (`y-codemirror.next`) and to the file on disk. Edits that arrive outside the editor (other plugins, `processFrontMatter`, external editors, git) are diffed into the `Y.Text`.
- Awareness (cursors, presence) is ephemeral over the WebSocket and never persisted.
- **Compaction** folds the update log into a snapshot. Plaintext and escrow vaults can compact server-side (the export job can do it for escrow vaults); other E2EE vaults compact on clients. The compaction runtime (a Go Yjs implementation is not mature) is an open question for Phase 5.

## 11. Retention and history

- Revisions are append-only. A retention policy purges old **non-head** revisions, including tombstones that are not the head. The policy is deployment-wide (`docs/configuration.md`), with per-vault overrides set by the operator (below). By default every revision younger than 90 days is kept; older revisions are thinned to the newest revision of each document per UTC day until they are a year old, and to the newest per ISO week (from Monday, UTC) after that. Ages are measured by the database clock from `created_at`, and a revision is in the daily or the weekly zone, never both, so a day and the week starting on it are separate buckets.
- **A document's head revision is never purged** (decision, #52), however old, and that includes a head tombstone: a deleted document keeps its tombstone indefinitely, so it stays findable and restorable, and a client offline for longer than the policy still learns of the delete instead of resurrecting the document. ListChanges skips purged revisions, so a cursor may skip `seq` values. **Purge markers (decision, #52/#488).** The purge keeps each purged revision's `seq` and `anchor` in `purged_revisions` (§5), in the transaction that deletes it, so every snapshot sees either the revision or its marker, on any replica. A client whose cursor (or own commit above it) sits on a purged revision therefore passes the anchor check and pulls on as usual (§6.1): a document it did not change takes the newer heads, remote deletes included (#480). Revisions purged before migration 0008 have none (§6.1). **Marker horizon (decision, #514).** Each marker records its purge time (`purged_at`, migration 0009), and the retention job deletes the markers older than `VAULT_SYNC_RETENTION_PURGE_MARKER_HORIZON` (default 365 days, at least one day), so `purged_revisions` is bounded by one horizon of purges (principle 4). Pruning is bounded per run (at most 100,000 markers, in statements of 1,000, oldest first), so the table stays bounded by one horizon of purges only while the sustained purge rate stays below about 100,000 revisions per hour per replica (a run starts every hour on each replica, and one run may purge up to 1,000 x 1,000 revisions); far above the expected scale, and `vault_sync_retention_purge_markers_pruned_total` growing by the cap every run is the signal that pruning falls behind (#519). It is safe on concurrent replicas: each statement locks the rows it deletes with `SKIP LOCKED`, so replicas take disjoint markers, never wait for each other, and together delete what one run would. It never loses an acknowledged write (principle 1): a marker is only consulted by a device that has not pulled since the purge, since a purged revision always has a newer revision of its document, so any later pull moves the cursor (and the device's own commits) past it. Such a device, once its marker is gone, gets a false-positive `diverged` and resyncs (§8): it pulls the server's heads over the notes it never changed at revisions it only pulled (#874) and merges every other note it holds with the server's: nothing is lost, although a note it last committed itself that another device deleted comes back (an edit wins over a delete) and a note whose merge base was purged gets a conflict copy. Deleting a marker can only turn a passing anchor check into `diverged`, never the reverse, so pruning never hides a restore.
- **Per-vault overrides (decision, #52/#468).** The operator can give a vault its own `keep_all` and `keep_daily` with `vault-sync-server retention set|unset|list` (`docs/configuration.md`), stored in `vault_retention`; a vault without one follows the deployment-wide policy. There is no API or plugin setting for it (principle 4): only the operator, who already holds the database, can shorten a vault's history, and purges are irreversible. `set` refuses a `keep_all` below one day or below the operator's `VAULT_SYNC_RETENTION_OVERRIDE_MIN_KEEP_ALL`, a `keep_daily` below `VAULT_SYNC_RETENTION_OVERRIDE_MIN_KEEP_DAILY`, and a `keep_daily` below its `keep_all`; the table's checks refuse a non-positive `keep_all` and a `keep_daily` below it. The purge query joins the override and applies `coalesce(override, deployment)` per revision (one policy per document, since a document belongs to one vault), and bounds its scan by the shortest `keep_all` in force so the `created_at` index still applies. Overrides need no per-replica state: every replica reads them in each run. Replicas of a release before migration 0010 ignore them, so overrides are set only after a rollout completes (`docs/deployment.md`).
- **Parent links after a purge (decision, #58).** A purged revision is almost always another's parent. The purge re-parents the child onto the purged revision's parent in the same transaction, so `parent_rev_id` keeps naming a revision that exists (the foreign key is unchanged and still enforced): the nearest retained ancestor, or none once every older revision is gone. History stays a connected chain. Re-parenting was chosen over nulling the link because it keeps that chain, and it needs no PostgreSQL 15 `ON DELETE SET NULL (column)`. It is compatible with "append-only": revisions are never added out of order or changed by clients, and the only later change to a revision is this rewrite of its parent link when an ancestor is purged; content, path, tombstone flag, device and time never change. A commit retried after its base was purged is still the same commit (§6.2): its base no longer exists, so it matches whatever parent the revision has now.
- **Blob garbage collection.** A blob row starts released (`released_at` defaults to the time it is stored, since `CommitBlob` stores a blob before any revision references it), and each purge sets `released_at` on the blobs its revisions referenced. A blob that no revision references and that was released longer than the grace period ago (default 24 hours) is collected in two steps. First, its row is deleted and a `blob_deletions` record written, in one transaction under `FOR UPDATE SKIP LOCKED` on the row. A commit holds `FOR KEY SHARE` on the blob it references until it commits, so a blob being committed is skipped, and a commit that starts while the blob is being collected finds it not complete (`FAILED_PRECONDITION`, and the client uploads it again). Second, the S3 object is deleted and then the record, under `FOR UPDATE SKIP LOCKED` on the record; the object is left alone and the record dropped if the blob is complete again, and the record stays for a later run while an upload of the blob is in progress. `CommitBlob` waits for a deletion of its blob in progress before writing the object, so a re-uploaded object is never deleted; each object deletion, retries included, is bounded by four S3 idle timeouts (`VAULT_SYNC_S3_IDLE_TIMEOUT`), so even a store that keeps sending a byte now and then holds the record's lock, and that commit, no longer than that (#225). The row goes first so that no revision can ever reference a blob whose object is gone. The grace period lets a client that just read a purged revision restore its content without uploading it again. A blob that never had a referencing revision (an upload whose revision was never committed) is collected the same way, the grace period counted from its upload (#225); one a revision references when the collector looks is kept and no longer released.
- **Concurrency.** The retention job runs on every replica (§12): each document is purged in its own transaction under `FOR NO KEY UPDATE SKIP LOCKED` on the document row, so concurrent purges skip each other and a purge's first pass never waits for a commit to the document; the documents it skipped are purged again afterwards, one at a time while the run holds no other lock, waiting for each lock (see incremental scans below), while a commit waits at most for one document's bounded purge. Every step is idempotent and bounded per run.
- **Incremental scans (#225).** A revision only becomes purgeable when it, or a newer revision of its bucket, crosses the policy's 90-day or one-year age. So a run that found fewer candidate documents than its bound and purged each of them fully records, in the single-row `retention_scans`, the policy and the database time it started; later runs under the same policy only consider documents with revisions whose `created_at` crossed one of the two ages since then (indexed on `created_at`). A document a run skipped because it was locked (a commit, or another replica's purge) is purged again, waiting for the lock, before the run counts as complete. Replicas record their own complete scans; the record only moves forward, and a run under another policy (a configuration change) scans every document and replaces it. The record also holds a digest of every per-vault override, read before the scan's candidate query: setting, changing or removing any override makes the next run, on every replica, a full scan, since a changed override can make revisions purgeable that crossed no age. Incremental runs also consider documents with revisions that crossed an overridden vault's own ages.
- Users can browse a document's history and restore any revision (a restore is a new revision: a `CommitRevision` based on the current head with the old revision's `content_ref`, and `deleted = false` to restore a deleted document).
- **Client history and restore (decision, #26).** The engine pages `GetDocumentHistory` into entries with each revision's time (`create_time`) user (`user_id`, named by the response's `user_names`: each user who committed a revision on the page, once, by their display name, the identity provider's `name` claim or else `preferred_username`, which the server records from the user's latest token; `docs/design/sharing.md`, Attribution) and device (`device_id`, named by the response's `device_names`, decision #420: each device that committed a revision on the page, once, by its registered name; every member of the vault, a viewer included, sees them, and a non-member gets `NOT_FOUND` as for any history; a device the server does not name is shown by id), downloads any revision for a preview (only its first 256 KiB, in `DownloadBlob` ranges, when it is larger, #656: that start cannot be checked against the content hash, so it is shown only, never written or uploaded; a revision no larger is downloaded whole and verified), and restores one by committing the revision's `content_ref` on the current head, at the head's path (a restore never moves a document, except as below) and with `deleted = false`, then syncing, so the disk shows the result; a local edit not pushed yet meets the restored head through the decision table like any remote change (`docs/design/engine.md` §5). A head that moves meanwhile is read again and the commit retried on it. `FAILED_PRECONDITION` without a `Document` detail (the blob was garbage-collected after a purge) uploads the content again, from the user's preview if it is the whole revision and hashes right or else from a download of the whole revision, and retries; if neither has it, the restore fails with nothing committed. `ALREADY_EXISTS` (a deleted document's path now belongs to another live document) fails the restore too; the user may then restore it at another path they choose (#420), the same commit with that path, which the client first checks as it checks a new document's path (§6.2), against the platform (§8) and against the vault's sync scope, so a path that would be refused, could not be written here or would not sync fails with nothing committed. So does `INVALID_ARGUMENT` for a deleted document whose path contains a `\` (§6.2, decision #191): nothing is committed, and its history stays readable. The plugin restores a revision of a note it holds (per-note history, `docs/design/engine.md` §10); it has no list of deleted files.

## 12. Operations

- Single static Go binary; one OCI image (server and export) built by Nix (`streamLayeredImage`, with the flake's pinned Go, checked with `govulncheck -mode=binary`), mirroring tape-archiver. The Helm chart under `deploy/charts/vault-sync` is built on the bjw-s `common` library chart and renders the server Deployment, the export CronJob, Services and a ServiceMonitor; it references operator-created Secrets and creates none. It mounts the escrow Secret (§9.4) into the export job only and refuses to render any values that would put it into the server, which `make chart-lint` checks (decision, #30). Deployment: `docs/deployment.md`.
- Configuration by environment variables, documented in `docs/configuration.md`.
- **JSON structured logs** (`log/slog`), Prometheus metrics on a separate port, `/healthz` and `/readyz`.
- PostgreSQL client certificates and S3 credentials are re-read from disk on change.
- Schema migrations are embedded (`internal/store/migrations`) and run on startup behind a PostgreSQL advisory lock, each in its own transaction, recorded in `schema_migrations`; migrations are forward-only and must be backward-compatible with the previous release. Released migrations are never edited (the runner rejects a changed name for an applied version). Migrations may use any feature of PostgreSQL 14, the minimum supported version (0003 defines its index function with a SQL-standard `RETURN` body, which binds its references at creation so `search_path` cannot change what the index computes). A migration that rebuilds an index holds an exclusive lock on its table until it commits; 0003 rebuilds the live-path index on `documents`, briefly blocking commits and reads of documents on every replica while it is applied. 0004 builds the live-folder GIN index (§5), which holds a lock that blocks commits, but not reads, while it is applied. 0005 builds the `revisions` indexes retention needs (§11), which block commits, but not reads, while it is applied. 0006 adds `revisions.anchor` (§6.1) and backfills it in the same transaction: its `ADD COLUMN` takes an exclusive lock (`ACCESS EXCLUSIVE`) on `revisions` that it holds through the `UPDATE` of every revision and the scan for `SET NOT NULL` until it commits, so while it is applied every commit, `ListChanges` and retention run blocks on every replica of both releases; the pause grows with the number of revisions (#427). 0007 sets a default on `blobs.released_at`, which takes an exclusive lock on `blobs` that it holds until it commits, through its backfill of unreferenced blobs and its build of the `revisions (created_at, document_id)` index: while it is applied, every blob read and write blocks on every replica, the previous release's included (downloads, `CommitBlob`, the blob checks of `CommitRevision`), and commits also block on the index build. 0008 only creates the empty `purged_revisions` table (§11), which the previous release never names; its retention job, while it still runs during a rollout, purges without writing markers, which costs a device whose cursor sat on such a revision one false-positive resync (§6.1). Markers cannot be backfilled for revisions purged before it, since their anchors are gone. 0009 adds `purged_revisions.purged_at` with a `now()` default (no table rewrite on PostgreSQL 11 and later) and its index; the previous release never names the table, and markers written before it get the migration's time, which only delays their pruning. Its `ADD COLUMN` takes an exclusive lock (`ACCESS EXCLUSIVE`) on `purged_revisions` that it holds through the index build until it commits: while it is applied, purges and the anchor check of every `ListChanges` with a cursor (§6.1, a read of the table) block on every replica that knows the table. That is brief, since 0008 was never released without 0009, so the table is empty or small when 0009 runs (#519). 0012 adds the nullable `devices.registration_id` and a unique index on the small `devices` table (§9.2); the previous release never names the column and registers every call as a new device until every replica runs the new release. 0016 allows the `folder` document kind and drops the `revisions` check that every live revision has content (a check on `revisions` cannot see the document's kind, so `CommitRevision` enforces it); re-adding the kind check scans `documents` under an exclusive lock that blocks commits and document reads until it commits. The previous release refuses `DOCUMENT_KIND_FOLDER` commits and lists a folder revision with kind `DOCUMENT_KIND_UNSPECIFIED` until every replica runs the new release. 0019 widens the `user_keys.public_key` check to 32 or 1216 bytes and the `key_slots.wrapped_key` check to 1 to 2048 bytes (cipher suite 2); re-adding each check scans its small table under an exclusive lock until it commits. The previous release keeps accepting only suite 1 keys, which the new checks still allow.
- **High availability (§3).** Every replica must obey these rules, and every new feature must keep them:
  - **Stateless replicas.** A replica keeps no per-client state that lives only in its own process. Sessions, cursors and upload progress live in PostgreSQL (and S3). Consecutive requests of one client, including the chunks of one upload and its commit, may land on different replicas and must behave exactly as against one. Caches every replica can rebuild (the OIDC key set, credentials) are fine.
  - **Coordination through PostgreSQL only.** Advisory locks, `SELECT … FOR UPDATE SKIP LOCKED`, conditional updates and `LISTEN/NOTIFY` are the only cross-replica mechanisms (principle 5): no new infrastructure. Realtime fan-out (§6.4) must therefore reach clients connected to any replica. `LISTEN` needs a session that lasts, so the server needs a direct PostgreSQL connection or a pooler in session mode; transaction or statement pooling (such as PgBouncer's) is unsupported. Every commit transaction issues `NOTIFY`, and PostgreSQL serializes the commits of notifying transactions on one database-wide lock; this is accepted at the expected scale.
  - **Background jobs run on every replica** and must be safe to run concurrently. Their combined effect equals one run, and a replica finding that another got there first is not an error and is not logged as one.
  - **Retry-safe RPCs.** A replica may be killed without warning (`SIGKILL`) at any point. Every RPC must therefore be safe for the client to retry on another replica: the retry succeeds, and no acknowledged write is lost or applied twice. Blob uploads are content-addressed and resumable; revision commits are deduplicated by their client-chosen revision id.
  - **Graceful drain.** On `SIGTERM` a replica fails `/readyz` at once and keeps serving for a configurable delay (`VAULT_SYNC_SHUTDOWN_DELAY`), closing each connection after its response (idle keep-alive connections stay open until the delay ends, so a request sent on one as the signal arrives is not reset) so traffic moves to other replicas before any connection is refused. It then stops accepting connections and closes open WebSockets with close code 1001 ("going away") so clients reconnect elsewhere. In-flight RPCs get a configurable drain timeout (`VAULT_SYNC_SHUTDOWN_TIMEOUT`), and the process exits 0 after a clean drain.
  - **Database connection resets** (a PostgreSQL restart or switchover) are tolerated: connections are checked before use and replaced, and a request that fails mid-query is retried by the client. Managing PostgreSQL failover is the operator's concern (CloudNativePG).
  - **Rolling upgrades.** The previous and the new release serve side by side during a rollout. This is why migrations must be backward-compatible with the previous release (below). An integration test runs both releases against one database. A check a release adds holds only once every replica runs it: for example, replicas of a release before migration 0004 still accept file/folder collisions (§5) until the rollout completes.
  - **Server before plugin (#511).** Users update the plugin independently of the server, so a plugin may be newer than the server it syncs with. A plugin from purge markers on (#506), against a server without them, sees every retention purge of a revision at a device's cursor (or own commit above it) as divergence and resyncs (§8): nothing is lost, but a note another device deleted can come back after a retention purge, and a note whose merge base was purged gets a conflict copy. This lasts until the server is upgraded, so operators upgrade the server first (or together with the plugin), as `docs/deployment.md` (Upgrading) recommends.
  - The recommended deployment (at least 2 replicas, a PodDisruptionBudget, readiness and termination-grace ordering) is documented in `docs/configuration.md`.
- Bounded resource use: max request size, max chunk size, decompression limits, pagination caps, per-user rate limits. Each user may have at most `VAULT_SYNC_MAX_CONCURRENT_RPCS_PER_USER` authenticated RPCs in flight per replica, counted from authentication until the response is fully written; a further call is rejected at once with `RESOURCE_EXHAUSTED`, with an `ErrorDetail` of reason `ERROR_REASON_TOO_MANY_CONCURRENT_REQUESTS`, before its handler runs (no queueing). The client backs off. After a sync call is refused with `RESOURCE_EXHAUSTED`, the engine's next pull or push waits before it calls the server. The wait uses the realtime reconnect's equal jitter (§6.4): half of a ceiling plus a random part of the other half. The ceiling starts at 1 s and doubles with each consecutive refusal, up to 60 s, and a pull or push that succeeds resets it. When the wait ends, the engine pushes. Refused operations stay pending and are retried with their revision ids. The server sends no retry hint. The limit is an in-process count keyed by user ID, dropped when the user's last call ends, so it needs no cross-replica state and no client-visible state is lost with a replica. Responses are bounded by the same size as requests (the bytes sent). Writing each API response is bounded by `VAULT_SYNC_WRITE_TIMEOUT`, counted from the response's first byte, so a client that stops reading releases its connection. It does not bound the time before the response starts, so a long commit is not cut short (§6.2). The upgraded realtime WebSocket is exempt and bounded by its own pings and send queue (§6.4). Concurrent `/readyz` checks share one database ping. Every object-store request fails once its connection makes no progress in either direction for `VAULT_SYNC_S3_IDLE_TIMEOUT` (retried a bounded number of times by the S3 SDK), so a store that stops answering cannot hold a request, a compose slot or the cleanup routine forever; the bound is on silence, not on a whole operation, so a long commit or export that keeps moving is not cut short (§6.2). Each cleanup run is cut short when the next is due.
- The plugin is distributed through GitHub releases (installable with BRAT) carrying `main.js`, `manifest.json` and `styles.css`; `make release` cuts them (a dry run unless `PUSH_ALL=true`). A release's tag, its name and the version in its `manifest.json` are the same semantic version, without a `v`, as Obsidian and BRAT require; the image and chart use the same version (decision, #30). Publishing to the Obsidian community catalog is a non-goal for now.

## 15. Phases

Work is tracked as GitHub milestones and parent issues. A phase is done when its owner-approved acceptance checklist passes; a security review runs where a phase touches the attack surface.

1. **Foundations** — protocol schema, server core (store, blobs, revisions, auth, authz), simulation harness skeleton, CI.
2. **Single-user file sync**: a new plugin engine (`docs/design/engine.md`) plus the adapter for desktop and Android, conflicts, history and restore, Markdown import, and the Helm chart. Done as defined in `docs/acceptance/phase-2.md`: the checklist passes on `master`, a security review and a narrow bug hunt have run with critical and high findings fixed, and `0.2.0` is released.
3. **Vault sharing** — membership management, invitations, roles in UI.
4. **End-to-end encryption** — key hierarchy, escrow, export decryption, crypto vectors, independent crypto review. Until then, creating an E2EE vault is rejected (§9.3).
5. **Live collaborative editing** — Yjs documents, conversion, editor binding, awareness, compaction.
