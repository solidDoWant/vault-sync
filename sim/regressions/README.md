# Simulation regression cases

Each `*.json` file here is a minimized schedule that once violated an invariant. `make test-sim` replays every one of them on each run, and each must pass. When a seed fails, the harness minimizes it and writes `seed-<seed>.json` to this directory. Fix the bug, then commit the file in the same change as the fix. See `docs/testing/simulation.md`.

`simfault-stale-base.json` is the exception: it is seed 1 of CI's short run, minimized against the deliberately broken `simfault` server (see "The harness has teeth" in `docs/testing/simulation.md`), where it commits against a stale base. Against the real server the commit is rejected and rebased, so it keeps the base-revision check covered by a short committed case. `simfault-refused-retry.json` is the same for the `simfault_retry` server (#110): seed 2 of CI's short run, minimized to a commit whose response is lost and whose retry, held back by the commit retry backoff, lands after another commit moved the head. The real server returns the applied revision to the retry.

`seed-10-engine-echo.json` is seed 10 minimized with two engines (#22), and its file name keeps it apart from the older single-engine `seed-10.json`. Under Windows rules, a user's write of `A.md` over the synced `a.md` is reported as a modify of `a.md`. That case and `seed-16.json` (`STRASSE.md` over `straße.md` under macOS rules) once failed `engine-echo` because the harness matched the user's paths exactly, not as the case-insensitive vault matches them (#247).

The `seed-21*`, `seed-22*`, `seed-23*` and `seed-25*` cases come from #280: each minimization of those seeds, fixed in turn, found the next mechanism. All of them once ended with a rename pushed as a delete plus a create, which `phantom-delete` reports.

- `seed-21.json`, `seed-22.json` and `seed-21-crash-chain.json`: a user renames a synced note (in the last one, and then renames and edits it again), and the app is killed before the engine records the rename (#167 item 2). `phantom-delete` excuses exactly that case.
- `seed-22-crash-deleted-path.json`: the same, where the user had deleted the file of the note synced at the new path, so the restarted engine takes the renamed file for that note (#254). Excused the same way.
- `seed-23.json`: a merge during a push did not see the push's own rename, and took the renamed file for an untracked one. `seed-23-stale-rename.json`: once it did, the push still committed the rename to the path the merge had moved the file away from.
- `seed-25.json`: a rename chain was followed across a delete of the renamed file. `seed-25-refused-rename.json`, `seed-25-inflight-rename.json` and `seed-25-moved-aside.json`: the user renamed a file again while the push was committing its earlier rename (refused, landing, or moved to a `path-taken` copy). `seed-22-pending-create.json`: the user renamed a new file while a push retried its create, and the same push's full scan took it for a delete plus a create.

`seed-22-vacated-path.json` and `seed-24-vacated-path.json` are seeds 22 and 24 minimized in #254: a file at a path the user just vacated was taken for the old document (in seed 22 a create at `straße.md` after renaming `STRASSE.md` away under macOS rules, in seed 24 a rename onto `a.md` after deleting `A.md` under Windows rules). The seeds' full 1000-step schedules stopped reaching it after the path changes of #291 and #294, but the minimized cases kept failing until #254 was fixed. The scripted scenarios of #254 (`fileAtVacatedPath`, `sim/scenarios.ts`) cover the mechanism too.

`seed-24-drift.json` is retention seed 24 of #300, minimized there and replayed without its purges (#319). Under POSIX rules another device creates the file `NOTES` and renames it to `notes/c.md` while the user creates `notes/c.md`. The merge found no free conflict-copy name in `notes/`, because it counted the renamed document's own file `NOTES` as a file named like that folder, so the rename stayed deferred and the user's file never synced.

`seed-20-kind.json` is seed 20 minimized to a harness bug (#306): the scripted clients committed every revision as `TEXT`, so the server refused a scripted rename of an engine's document at `trailing.`, which the engine had created as a blob, and the run reported a `protocol` violation. A document's kind never changes (`SPEC.md` §7), so the scripted clients now commit edits, renames and deletes with the kind the server reported for the document.

`seed-1-spelling.json` is seed 1 minimized in #305, with no retention purge. On a case-insensitive client, another device renamed a synced note onto another spelling (`straße.md`) of an unpushed local file (`STRASSE.md`) while the user renamed the note away locally, and the client took that file for the note. The fix of #254 (#311) already covers it. The scripted scenario `remoteRenameOntoSpellingOfUnpushedFile` (`sim/scenarios.ts`) covers the mechanism under macOS and Windows rules.

`seed-21-drift.json` is seed 21 minimized with two engines (#323): under Windows rules, a user renamed a synced note to `a.md` and deleted it, while another device created `A.md` and edited the note. The engine followed the note's rename to `a.md`, took the other note's `A.md` there for the note's local version, and put the edit off forever. A file the journal has as another live document's that no local move took away is never followed as a rename's target.

`seed-25-pending-create-rename.json` and `seed-20-inflight-create.json` come from #286. In the first (seed 25 of #280's run, Windows rules), the user renamed a new file whose create was pending (content uploaded, commit not acknowledged), and another device's document arrived at the new path before the push. The pull kept the file as a `concurrent-create` copy, and the push committed the create at the path the file had left, then its tombstone, then the copy as a new document (`phantom-delete`). The pull now moves the file aside under the pending create's id as `path-taken`, and the create is committed there. The second (retention seed 20 of #300, replayed without purges, POSIX rules) is the same fault without a pull: the user renamed and edited the file while its create was committed, then edited it again while the push uploaded the rename. The push dropped the rename with the stale upload, so the file became a new document and the created one stayed live at its old path (`engine-convergence`). The rename now goes on to the next round with the file.

#299 (retention seeds 1 and 5 of #229, case-insensitive engines) has no committed seed: the full seeds need #297's retention steps, and every minimization drifted to other mechanisms. The scripted scenario `remoteRenameIntoDeletedNotesFolder` (`sim/scenarios.ts`) reproduces seed 1's shape under macOS and Windows rules without retention: the user deleted the synced note `NOTES` and created `notes/f.md`, while another device renamed the note to `notes/f.md` and edited it. The merge counted the note's synced path `NOTES`, where the merge result does not go, as a file named like the folder `notes/`, so the user's `notes/f.md` found no conflict-copy name, the merge stayed deferred, and the engines never converged.

`seed-1-case-rename.json` is retention seed 1 of #229 minimized in #299 to a mechanism of its own (#343), with no retention purge. Under Windows rules, the user edited the synced note `Notes/C.md` while another device renamed it to `notes/c.md` by case only. The edit's commit was refused, and the merge took the note's own file, which the case-insensitive vault also finds at `notes/c.md`, for a file in the way, so it refused every time: the revision stayed deferred and the edit never synced. A merge result at another spelling of the document's own file now just respells the file.

#352 (a reviewer probe of #299's seed 5 shape, POSIX rules) has no committed seed either. The scripted scenario `newFileAtRenamedAwayPath` (`sim/scenarios.ts`) reproduces it: the user renamed the synced note `NOTES` to `notes/f.md`, edited it and created a new file `NOTES`, while another device renamed the note to `notes/c.md` and edited it. The merge counted the new file `NOTES` as a file named like the folder `notes/`, where the merge result goes, so the local edit found no conflict-copy name, the merge stayed deferred, and neither the new file nor the edit ever synced.
