#375 (found by a bug-hunt fuzz run of the engine, seed 189 with POSIX and macOS engines) has no committed seed: the simulation's schedules do not reach a remote rename into another spelling of a folder while the user moves the note. The scripted scenario `localRenameOverRemoteRenameIntoRespelledFolder` (`sim/scenarios.ts`) reproduces it under POSIX, macOS and Windows rules: the user moved the synced note `notes/b.md` (by way of `moved/b.md`) to `z.md`, or into `notes/C.md` after moving the note there to `moved/C.md`, while another device renamed it to `NOTES/b.md`. On a case-insensitive client the remote path has the synced path's path key, so the pull took the note's file for gone from where it was, never followed the local rename, and merged a local delete: the remote rename won, and the moved file became a new document (`z.md`) or, at the vacated path, a stray copy that was never pushed. A file gone from the synced path is now followed through the local rename, which wins (SPEC.md §7). The unit regressions are in `plugin/src/core/engine/vacated-path-remote-rename.test.ts`.
