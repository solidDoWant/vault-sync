#451 (found while triaging #376: fuzz seed 243 of a bug-hunt fuzz run of the engine, POSIX and macOS engines) has no committed seed: the simulation's schedules rarely reach a delete and a rename onto the deleted path between two pushes while another device edits the renamed note. The scripted scenario `renameOntoDeletedNotePath` (`sim/scenarios.ts`) reproduces it under POSIX, macOS and Windows rules: the user deleted the synced note `c.md` and renamed the synced note `x.md` to `c.md`, while another device edited `x.md` and pushed. The pull followed the local rename to `c.md`, but the merge refused to write there because the journal still had `c.md` as the deleted note's, so the remote edit stayed deferred `local-changes` for good and neither the delete nor the rename was ever pushed. A merge now takes the file a local rename of its document brought to a path whose note the user deleted (or moved away), as long as the remote revision does not put the document there; the local rename wins (SPEC.md §7). The unit regressions are in `plugin/src/core/engine/rename-onto-deleted-path.test.ts`.
