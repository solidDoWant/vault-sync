# Obsidian plugin

The user guide for the plugin is now in [`docs/user/`](user/getting-started.md). This page stays until the admin and developer rewrites move its last sections.

This page covers the vault-sync plugin's settings, how it signs in, how a vault is connected, and what the sync status means. The server's configuration is in `docs/admin/configuration.md`.

## Settings

Open **Settings → Vault Sync**. The tab follows the order you set things up in, with the day-to-day status first: **Sync** (the sync status, and **Register this device again** after this device was removed), **Server**, **Account**, then, while signed in, **End-to-end encryption**, **Remote vault**, **Sharing** (while a vault is connected) and **Devices**. Settings few users need are in the **Advanced** group at the bottom. It is collapsed until you open it, and stays open or closed as you left it on this device (saved in `data.json`, which never syncs). Nothing you need to recover from an error is in it: the sync status and its errors, **Sign in again**, **Unlock** and **Register again** are always shown.

| Setting | Meaning |
|---|---|
| Sync status | The sync status, as in the status bar (see [Status](#status)). After this device was removed from your account, **Register this device again** is shown here (see [Devices](#devices)). |
| Server URL | The vault-sync server's base URL, for example `https://sync.example.com`. |
| Device name | How this device is named when it registers with the server, and in the names of conflict copies it makes (`<name> (Conflicted copy <user> <device> <YYYYMMDDHHMM>).<ext>`, where `<user>` is your name from the identity provider's `name` claim, or else `preferred_username`, reduced the same way, and `user` when it has neither). In a copy's name, characters that some platform does not allow in file names, and `(` and `)`, become `-`, the name is cut to 40 characters, and a name with nothing left becomes `device`. Invisible characters (control and format characters, such as bidi controls or the zero-width joiner of some emoji, and line separators) are removed first, since the server refuses them in device names, and the registered name is cut to at most 256 bytes (the server's limit), never through a character. If the server still refuses the name (an older Android WebView may not know format characters added in recent Unicode versions, so it cannot remove them), the status says so and names this setting: change the name and sync registers the device with it when it tries again. Empty uses the platform's name (`Windows`, `Mac`, `Linux`, `Android`, `iOS`). While signed in, changing it renames this device on the server (`RenameDevice`) about a second after you stop typing, not on every keystroke; the device list then shows the new name, and the device keeps its id and its history. If the rename fails, a notice says so and the setting goes back to the last name the server accepted. A change made while the device's first registration has not completed yet (offline, say) is applied once it completes; otherwise the device keeps the name the server returns, which another device may have changed meanwhile. |
| End-to-end encryption | Shown while signed in: whether end-to-end encryption is enabled for your account and unlocked on this device, with **Enable** or **Unlock** (see [End-to-end encryption](#end-to-end-encryption)). |
| Remote vault | Shown while signed in: the server vault this vault syncs with, or controls to connect to one of your vaults, create a new one or join one with an invite code (see [Connecting a vault](#connecting-a-vault)). |
| Sharing | Shown while a vault is connected: your role in it, and for owners its members and invitations (see [Sharing a vault](#sharing-a-vault)). |
| Devices | Shown while signed in: your devices, with **Remove** (see [Devices](#devices)). |
| Advanced: OIDC issuer URL | Optional. Leave it empty: the plugin uses the issuer the server advertises (its `VAULT_SYNC_OIDC_ISSUER_URL`). Enter it only for a server too old to advertise one, character for character (including any trailing slash), for example `https://auth.example.com/application/o/vault-sync/` for Authentik. An issuer that differs from the one the server advertises is refused, because the server accepts no other issuer's tokens. |
| Advanced: OIDC client ID | Optional. Leave it empty to sign in as the client the server advertises (its `VAULT_SYNC_OIDC_CLIENT_ID`, by default its audience). Enter a client ID to sign in as another public client instead (see below). The access tokens it receives must carry the server's `VAULT_SYNC_OIDC_AUDIENCE`. |
| Advanced: Rotate key, Re-encrypt history | Shown to an owner of a connected end-to-end encrypted vault, under a sub-heading naming that vault (see [Sharing a vault](#sharing-a-vault)). A notice that tells you to run one of them offers a button that opens the Advanced group at it. |

Usually the server URL is all you enter. In that case the server URL decides the identity provider: the first sign-in trusts the issuer the server advertises, so a malicious or compromised server could send you to a sign-in page of its choosing. You already trust that server with your notes; to pin the identity provider anyway, enter the issuer. After you sign in, the issuer is stored with the refresh token, and refreshes use it whatever the server advertises later. The server URL and the issuer, whether entered or advertised by the server, must use `https`. Plain `http` works only for `localhost`, `127.0.0.1` and `::1`, for local development. While you are signed in, and while a sign-in is in progress, these settings are locked, because the refresh token belongs to that identity provider. Sign out to change them. While signed in, the empty issuer and client ID fields show the ones in use.

The settings live in the plugin's `data.json` under `.obsidian/plugins/vault-sync/`. While you are signed in, the refresh token is kept in Obsidian's local storage for this vault on this device (`app.saveLocalStorage`), not in `data.json`. That storage lives outside the vault's files, so a tool that backs up or syncs the vault folder (Git, a file-sync app) never copies the token. A `data.json` written by an older version that still holds the token is rewritten without it when the plugin loads, and the token moves to local storage, so you stay signed in. If that storage is cleared (by the operating system or by you), the plugin shows **sign-in needed**, as when the session ends (see below). `data.json` holds the issuer and client ID the token was issued for, so that refreshing it never depends on reaching the server. It also holds this device's registration and the connected vault. vault-sync never syncs it. Your unlocked end-to-end encryption key pair and the vault keys it unwraps are secrets too, and are kept in local storage like the refresh token, never in `data.json`; an older `data.json` that holds them is rewritten without them when the plugin loads, and they move to local storage.

## Signing in

Click **Sign in** in the settings, or run the **Vault Sync: Sign in** command. The plugin signs in with the OAuth 2.0 Device Authorization Grant (RFC 8628), which works the same on desktop and Android and needs no redirect back into Obsidian. While signed in, **Sign in** is refused: sign out first. A sign-in goes like this:

1. The plugin calls the server's `GetServerInfo`, which needs no sign-in, to check that the server speaks a compatible protocol and to learn the issuer and client ID to sign in with (unless the settings override them). If neither the server nor the settings name one of them, the dialog says which one to enter in the settings.
2. It discovers the identity provider's endpoints from `<issuer>/.well-known/openid-configuration` and asks for a device code with the scopes `openid offline_access`.
3. A dialog shows a link to the verification page and a user code. Open the page in any browser, on this device or another one, sign in there and enter the code. **Copy code** and **Open page** help on mobile.
4. The plugin polls the identity provider at the interval it asks for, and slows down when told to. Once you approve, it stores the refresh token in local storage and closes the dialog. Closing the dialog cancels the sign-in and leaves the device as it was (for example still needing a sign-in). If you deny the request or the code expires, the dialog says so. Start again to get a new code.

Access tokens are kept in memory only, never on disk. The plugin refreshes the access token with the refresh token before it expires: a minute before `exp`, or halfway through the token's lifetime if that is shorter. Concurrent requests share one refresh. If the server still refuses a token as unauthenticated (it expired early, or the device clock is off), the plugin refreshes and sends the request once more, unchanged. A retried commit keeps its revision id, so a commit whose first attempt was applied is not duplicated. When the identity provider rotates refresh tokens, the new one is saved before it is used.

### When the session ends

If the identity provider refuses the refresh token (it expired or was revoked, or your session there ended), the plugin forgets it, shows a notice, pauses sync, and the status bar shows **sign-in needed**. The settings then show **Sign in again**, which restarts the device flow. Local changes are not lost meanwhile: they stay on disk and in the sync journal, and sync, which starts again as soon as you sign in, pushes them. A network failure while refreshing does not sign you out. The plugin shows **offline** and tries again.

**Sign out** stops sync and forgets both tokens and this device's unlocked encryption key (unlock it again after signing in). The connected vault and this device's registration are kept, so signing in again with the same account resumes syncing.

The plugin never logs or displays tokens.

## Connecting a vault

Once signed in, the settings show a **Remote vault** section. Each local vault is connected to one vault on the server:

- **Connect to an existing vault** lists the vaults you are a member of. Vault names are shown as device names are in the history (see [History and restore](#history-and-restore)): without invisible characters, at most 64 characters, laid out on their own so right-to-left letters cannot reorder the sentence around them, and by the start of the vault's id when nothing visible is left. End-to-end encrypted vaults are not listed, because the plugin cannot sync them yet.
- **Create a vault** creates a vault on the server, owned by you, and connects to it. Its name defaults to the local vault's name. It is plaintext unless **End-to-end encryption** is on, which needs your encryption key unlocked on this device (see [End-to-end encryption](#end-to-end-encryption)). This device then creates the vault's first key and wraps it to you and, if **Escrow** is on, to the server's escrow key, so the operator's backups can read the vault and restore it if you lose your passphrase. **Escrow** starts at the server's default (on unless the operator configured otherwise) and can be turned off; it is unavailable on a server without an escrow key. Both are chosen once, when the vault is created. Encrypted vaults cannot be synced yet, so connecting to one is refused for now.
- **Join with an invite code** joins someone else's vault with the code its owner gave you (see [Sharing a vault](#sharing-a-vault)) and connects this vault to it, with the role the invitation grants.

If both this vault and the remote vault already have files, the plugin asks before it connects. The two are then combined. Files only one side has are copied to the other, and nothing is deleted or overwritten. Where both sides have a file at the same path with different content, the remote version stays at that path, and this vault's version is kept next to it as a conflict copy, named `<name> (conflict <device> <date>).<ext>`.

**Disconnect** stops syncing this vault. Its sync journal is kept, so connecting to the same vault again carries on where it stopped. Changing the server URL (after signing out) disconnects the vault too, because a vault id means nothing on another server.

### Sharing a vault

A vault can have up to 100 members, each with a role: an **owner** reads and changes notes and manages the vault's members and invitations, an **editor** reads and changes notes, and a **viewer** can only read them (the server refuses a viewer's changes). The settings' **Sharing** section, shown while a vault is connected, starts with your role in it.

Owners also see:

- **Members**, oldest membership first: each one's name (shown like device names in the history, or by the start of their user id when they have none), role and when they joined. The dropdown changes a member's role and **Remove** removes them, each after you confirm it. A removed member can no longer sync or read the vault; their changes and history stay. Every change takes effect on the member's next request. A vault always keeps at least one owner, so demoting or removing its last owner is refused: a notice says so and the list stays as it was. Any other refusal shows the server's message the same way.
- **Invitations**: the pending ones, each with its role, when it was created and when it expires, and **Revoke**.
- **Invite someone** creates an invitation for the role you choose. It expires after 7 days, or after the number of days you enter (1 to 30). Its code is shown once, with **Copy code**: the server keeps only a hash of it, so it cannot be shown again. Give it to the person you invite over a channel you trust; anyone holding it can join until it is used, revoked or expires. A vault can have at most 100 pending invitations.

On a viewer's device the plugin reads the role at the start of every sync, so a role change takes effect within one sync, without signing in again. While you are a viewer, notes open read-only in reading view, with a banner saying the vault is shared with you as a viewer, and creating, renaming and deleting files is refused with a notice. The device only pulls: it never uploads or commits anything. A file changed anyway (outside Obsidian, say) is copied to `.vault-sync/local-copies/` at the same path (with a number added when that name is taken), the shared version is restored, and a notice says where your version is. New files are moved there too, and a deleted or renamed file is restored. `.vault-sync/` is never synced. Once you become an editor, the device syncs normally from its next sync; the files in `local-copies` stay where they are.

In an end-to-end encrypted vault, the section also shows **Fingerprints**, which every member sees. It holds the **vault fingerprint**: the vault's genesis hash as 64 hex digits in groups of four. An operator restoring the vault from escrow needs it (`-genesis` in [Backup and restore](admin/backup-and-restore.md)). Owners also see each member's **key fingerprint** in the member list: the first 20 bytes of the fingerprint of the member's key, in Crockford base32 in groups of four. Both come from the vault's membership log after it verified from your anchor list, so the server cannot forge or swap them. Compare them with the other members over another channel (in person, or by phone) to make sure you all hold the same keys. While your key is locked on this device, the lists are shown without fingerprints, and the section says why. A member the verified log names no key for is marked as such.

Editors and viewers see only their role and **Leave vault**. **Leave vault** (also offered to owners) ends your membership after you confirm it: sync stops, the status shows **no longer a member**, and the files stay. The vault stays connected, so you can disconnect it or wait for a new invitation; joining again takes one. The last owner cannot leave (or be demoted): a notice says that the vault must keep at least one owner. Promote another member to owner first, then leave.

In an end-to-end encrypted vault, owners also see **Rotate key**, in the settings' **Advanced** group under a sub-heading naming the vault. After you confirm it, it starts a new vault key (epoch) for every current member and pending invitation; new changes are encrypted with it and the other devices pick it up on their next sync. If another owner's device rotates at the same moment, only one new key is created and both devices use it. Removing a member rotates the key on its own. See [encryption.md](encryption.md#rotation).

Owners of a plaintext vault see **Convert to end-to-end encryption**. It lists every member with the fingerprint of the key the server reports for them; compare each one with that member over a channel you trust, then confirm that you did, choose escrow if the server offers it, and convert. Every member must have set up end-to-end encryption first, and pending invitations must be revoked. Members, notes and history are kept; run **Re-encrypt history** afterwards to encrypt the earlier versions. The notice shown after converting has a **Show Re-encrypt history** button, which opens the Advanced group at it. See [encryption.md](encryption.md#converting-a-plaintext-vault).

Owners of an end-to-end encrypted vault also see **Re-encrypt history**, next to **Rotate key** in the Advanced group. It runs the re-key job: every earlier version, deletion and folder still encrypted under an older vault key is encrypted again under the current one, and the older keys are then retired (epoch 1 is kept). Syncing and editing continue while it runs. If a key rotation happens meanwhile, or another owner's device runs it at the same time, it still ends with every version on the newest key. If it is interrupted, running it again continues where it stopped. See [encryption.md](encryption.md#re-encrypting-history).

Owners also see **Delete vault**. It asks you to type the vault's name, exactly, before it deletes the vault on the server for every member. The server keeps the data for 30 days, during which only its operator can restore it (`vault-sync-server vault undelete`); the plugin has no undo.

When you lose access to the connected vault (an owner removed you, you left, from this device or another one, or an owner deleted the vault), the device finds out within one sync, from the vault list the plugin reads at the start of every sync. It then stops syncing that vault, keeps every local file and its sync journal as they are, shows a notice, and the status and settings say **no longer a member** or **vault deleted**. Nothing restarts sync for that vault until you disconnect it and connect it again (after access came back) or restart Obsidian.

To join a vault, paste the code into **Join with an invite code** under **Remote vault** and click **Join**. The plugin redeems the code, which uses it up, and connects the open Obsidian vault to the vault you joined. If the open vault already has files, the usual confirmation before combining comes first (see [Connecting a vault](#connecting-a-vault)). A code that is wrong, expired, revoked or already used gets one message saying so, and nothing is connected. If you are already a member of the vault, the code is not used: choose the vault under **Connect to an existing vault** instead. The plugin syncs the whole Obsidian vault it runs in, so to keep a shared vault apart from your own notes, create or open another Obsidian vault first, install vault-sync there and join from it. Invite codes are never logged or stored by the plugin.

### Device registration

Before its first sync, each installation of the plugin (each local vault, on each device) registers itself with the server as a device, under the **Device name** setting. It registers once and keeps the device id in `data.json`, so restarts and new sign-ins with the same account reuse it. Signing in with another account, or to another server, registers a new device for that account. Every commit records the device it came from.

The server limits how many devices one user may have registered (100). Every installation, and every reinstall, registers a new device, so remove the ones you no longer use under [Devices](#devices): a removed device frees its place. When the limit is reached, the status shows **error** with the message that the account has reached the server's device limit and that a device can be removed from the device list on another device, and sync does not start on this device. Local files are untouched. The plugin recognises the limit by the reason the server attaches to the refusal; against a server too old to send it, the refusal is shown as an ordinary error and retried instead. A crash or a lost connection while the device registers does not use a second place: the plugin saves a registration id first and the server returns the same device for it. If the server refuses the registration (for example the device's name), the next attempt registers afresh with the current Device name, so renaming the device fixes it.

### Devices

While signed in, the settings list the devices registered to your account, oldest first: each one's name (shown like device names in the history) and when it last synced a change, to within a minute, or that it has not yet. This device is marked **This device**. **Remove** removes another device after you confirm it. The removed device stops syncing at once, on every server replica: its files and its changes not synced yet stay on it, and its history and its name in the history stay on the server. This device cannot remove itself; remove it from another device.

When this device was removed from another one, its next sync is refused. The plugin stops sync, shows a notice, and the status shows **device removed** with the message that this device was removed from your account. It does not register again by itself, not even after a restart, since the device may have been removed on purpose. **Register again** in the settings registers this installation as a new device (under the current Device name) and starts sync. Nothing is lost meanwhile: files and changes not synced yet stay on disk and in the sync journal, and the first sync after registering pushes them under the new device. A change whose commit had reached the server just before the removal, without the plugin hearing back, is not pushed twice or reported as refused: the server returns the committed version (it keeps the removed device as its author). The plugin recognises the removal by the reason the server attaches to the refusal; a server too old to send it answers with a plain error, which the status shows as **error**.

## End-to-end encryption

End-to-end encryption uses a key pair per user (`SPEC.md` §9.3; [How encryption works](encryption.md) explains it all). Its private key never reaches the server unwrapped: the server stores it only wrapped under a key derived from your **recovery passphrase**, and releases the wrapped key only to a device that proves it knows the passphrase. The server stores neither the passphrase nor anything that opens the key without it. While signed in, the settings show an **End-to-end encryption** section with one of four states:

- **Not enabled.** **Enable** asks for a new recovery passphrase twice (at least 10 characters). The plugin creates the key pair on this device, wraps the private key under the passphrase with Argon2id (64 MiB, 3 passes), and sends the server only the public key, the wrapped private key, the wrapping's parameters and a verifier derived from the passphrase. Write the passphrase down: every other device needs it, and nobody, including the server's operator, can recover it or the key without it. If you lose it, your devices keep their local files, but the server's copy of an encrypted vault can be restored only from the operator's escrow, and only for vaults created with **Escrow** on ([How encryption works](encryption.md) explains the recovery).
- **Enabled on another device.** **Unlock** asks for the passphrase. The plugin derives the verifier from it, the server checks it and releases the wrapped private key, and the plugin unwraps it on this device. This device then holds the same key pair as the others.
- **Unlocked.** This device holds your key pair. **Change passphrase** asks for the current passphrase once and a new one twice (at least 10 characters). The plugin unlocks the key with the current passphrase, wraps the same private key under the new one, and the server replaces the wrapping and the verifier in one step. The key pair stays the same, so every device where it is unlocked keeps working; a device that unlocks from now on needs the new passphrase. A wrong current passphrase is refused and counts against the same limit as unlocking.
- **Key changed.** This device holds a key pair it unlocked for your account, but your account's key on the server is now a different one (for example, the server was reset to a fresh database under the same address). The settings say so, and this device no longer uses its copy: **Unlock** asks for the passphrase of the server's key and replaces the copy with that key. The copy is kept until then, never deleted silently. If the server has no key for your account any more, the state is **Not enabled**.

Deriving the key from the passphrase takes about a second on a desktop and several seconds on a phone; Obsidian stays responsive meanwhile. A wrong passphrase is refused with "The passphrase is wrong." After 10 wrong passphrases within an hour (from any of your devices), the server refuses every attempt, even with the right passphrase, until the hour is over, and the dialog shows when you can try again.

If two devices enable encryption at the same time, the server keeps the first key and refuses the second. The second device then unlocks the first device's key with the passphrase it was given, instead of replacing it. If that was a different passphrase, it reports a wrong passphrase: unlock with the passphrase chosen on the first device.

The unlocked key pair is kept in Obsidian's local storage on this device, not in `data.json` (see [Settings](#settings)), for the account it was unlocked for; vault-sync never syncs it. Each time the settings show the encryption state, the plugin checks that the copy's public key is the server's. It is never logged or shown. Signing out forgets it; signing in with another account does not use it. End-to-end encrypted vaults can be created (see [Connecting a vault](#connecting-a-vault)) but not synced yet.

## Sync

While signed in and connected, the plugin syncs on its own:

- When sync starts (Obsidian starting, the plugin enabled, a sign-in, a vault connected), it syncs: it finds every local change made since the last sync by comparing file contents with what it last synced (including changes made while Obsidian was closed or the plugin was off), pulls the server's changes, and pushes the local ones (`docs/design/engine.md` §3).
- 2 seconds after your last edit, it syncs. A burst of edits becomes one revision.
- When another device commits a change, the server notifies this device over its realtime channel (a WebSocket to `/v1/realtime` on the configured server), and the plugin syncs at once.
- Every 30 seconds it syncs, which retries anything that failed and brings in other devices' changes even while the realtime channel is down.
- The **Vault Sync: Sync now** command does the same at once.

The server limits how many requests one account may have in progress at once (`VAULT_SYNC_MAX_CONCURRENT_RPCS_PER_USER`, see `docs/admin/configuration-reference.md`). A single device stays far below the limit, but many devices syncing at once can reach it. When the server refuses a sync for that reason, or a sync fails for any other reason, the status shows it and the plugin tries again after a random wait that grows with every failure in a row, from about a second up to 5 minutes. The first sync that succeeds resets it. Nothing is lost while it waits: changes stay on disk and in the journal, and the plugin sends them again with the same revision ids.

Renames and deletes keep a note's identity and history (`docs/design/engine.md` §4, §5):

- A renamed or moved file stays the same note on every device, with its history, also when the rename changes only letter case. A rename made while Obsidian was closed is recognized when the file's content is unchanged and no other file has the same content; otherwise it syncs as a delete and a new note.
- A file you create where a deleted or renamed note used to be is a new note, not an edit of the old one.
- An edit, or a rename not synced yet, wins over another device's delete of the same note: the note comes back, under your name for it, with your edit.
- When two devices rename the same note, the name that reached the server first wins, and the content is merged.
- Folders sync too, empty ones included (`docs/design/engine.md` §2). Creating, renaming or deleting a folder does the same on your other devices. A deleted folder stays deleted. The exception is a folder that still holds a file another device kept or edited: that folder comes back, with the file in it.
- When another device puts a note at a path this device has a file at, a file with the same content becomes that note; a different one is moved to a conflict-copy name and kept. vault-sync renames files to make room, never deletes them.

Stopping sync (signing out, disabling the plugin, quitting) never loses a local change. An edit that was not pushed yet stays on disk, and the next sync finds and pushes it.

Downgrading Vault Sync is not supported. The sync journal (IndexedDB) has its own schema and database name, and is never migrated from an earlier one: after an upgrade from a version with another journal, the first sync compares the vault with the server from scratch. Files equal to the server's are taken as synced; a file that differs keeps the server's version at the path and yours as a conflict copy, so nothing is lost.

### Realtime channel

The realtime channel only makes changes arrive sooner; sync never depends on it (SPEC.md §6.4). Every time the plugin (re)subscribes, it pulls from where it left off, so a change made while it was disconnected is never missed.

- It authenticates with the same access token as the API, sent as the `vaultsync.bearer.` WebSocket subprotocol, never in the URL, and never logged. When the token expires the server closes the connection; the plugin gets a fresh token from its stored sign-in, with no prompt, and reconnects.
- When the connection drops or the server refuses it (the server restarting or draining, too many connections, the network going away), the plugin reconnects after a random delay that doubles with every consecutive failure, from about a second up to a minute. The delay starts over only once a connection has stayed up for 30 seconds. Meanwhile the 30-second sync keeps running.
- The server must allow Obsidian's origins (`app://obsidian.md`, `capacitor://localhost`, `http://localhost`; the server allows them by default), and a reverse proxy in front of it must pass WebSocket upgrades ([Install](admin/install.md#the-ingress)). Without the channel, changes from other devices still arrive within 30 seconds.

### Status

The status bar (desktop) shows the sync status. Mobile has no status bar, so there a ribbon icon shows it instead: a check mark when idle, an upload cloud while local changes wait to be pushed, a warning triangle while conflicts are unresolved, and its own icon for syncing, offline, error, sign-in needed, device removed, no longer a member, vault deleted, key data that doesn't verify and no vault connected. Click the status bar or tap the icon, or run **Vault Sync: Show sync status**, for details. The settings show it too.

| Status | Meaning |
|---|---|
| `starting` | Sync is starting: the plugin registers this device with the server and opens its sync journal. |
| `idle` | The last sync succeeded. |
| `syncing` | A pull or push is running. |
| `offline` | The server or the identity provider could not be reached, did not answer in time, or the identity provider failed with a server error (HTTP 5xx). A request counts as unanswered after 30 seconds, so a connection whose packets are silently dropped (a lost network, a proxy that stops answering) shows `offline` too. A blob chunk gets one more second per 8 KiB it carries or asks for (126 seconds for a default 768 KiB chunk), so a slow link that keeps moving is not cut off, and the blob commit, which the server composes in one go, gets 10 minutes. Local changes are kept, and the next sync pushes them. An identity provider that answers with something invalid (not JSON, a missing field) shows `error` instead, since that points at its configuration. |
| `error` | The last sync failed for another reason, or some local files cannot be synced because the server does not accept their names. The details say why and name the file; the [conflict view](#conflicts) lists every such file. |
| `sign-in needed` | The session ended. Sign in again to resume. |
| `signed out` / `no vault connected` | Sync is off until you sign in and connect a vault. |
| `no longer a member` | You were removed from the connected vault or left it. Sync is stopped and your files stay; disconnect the vault in the settings. |
| `vault deleted` | An owner deleted the connected vault. Sync is stopped and your files stay; disconnect the vault in the settings. |
| `stopped: key data doesn't verify` | In an end-to-end encrypted vault, the server sent key or membership data that doesn't verify (a key or member it added or swapped, an epoch no owner signed, or a rolled-back log or epoch). Sync of that vault is stopped for good and your files stay; the details say what failed. The plugin never falls back to trusting the server (`docs/encryption.md`). Restarting Obsidian checks again. |
| `device removed` | This device was removed from your account on another device. Sync is stopped until you click **Register again** in the settings; local changes are kept and pushed then (see [Devices](#devices)). |

After the status, `N pending` counts local changes that the server has not acknowledged yet, and `N conflicts` counts the conflict copies this device made that still exist. The [conflict view](#conflicts) lists them.

### Conflicts

When this device and another one changed the same note on the same lines, edited the same attachment, or created a file at the same path with different content, vault-sync keeps both versions and never writes conflict markers into a note (`docs/design/engine.md` §5). The server's version stays at the path, and the other version is kept next to it as a conflict copy, `<name> (Conflicted copy <device> <YYYYMMDDHHMM>).<ext>`, in the same folder (with ` 2`, ` 3` and so on if that name is taken, and a shortened name if it would be too long). The copy is an ordinary file and syncs to your other devices. Only the device that resolves the conflict makes the copy, so there is one copy per conflict.

Markdown (`.md`) files are merged line by line, so edits on different lines of a note on two devices combine without a conflict, and two versions that differ only in line endings or a trailing newline are taken as equal. Obsidian Bases (`.base`) files are merged too: edits to different views, formulas or properties on two devices combine, and filter conditions added or removed on either device all apply. When both devices changed the same setting differently (the same view's limit, say), one deleted something the other changed, a version is not a Bases file this plugin understands (newer Bases syntax, for example), or the merged file would not be valid (one device deleted a formula the other started using), the base is handled like any other file instead. A merged base is rewritten as plain YAML with its keys in the same order, so comments in it are dropped; a base merged with no change from the other device is kept byte for byte. Canvas (`.canvas`) files are merged by card and connection: cards added on two devices are both kept, and one device moving a card while the other recolours it combine. Both devices changing the same property of a card differently (both moving it, say), reordering cards (bringing one to the front), or one device deleting a card the other connected or changed sends the canvas to a conflict copy instead. Other JSON (`.json`) files merge key by key, with lists taken as a whole. Plain-text files (`.txt`, `.csv`, `.tsv`, `.css`, `.js`, `.ts`, `.py`, `.sh`, `.html`, `.xml`, `.tex`, `.org`, `.rst`, `.yaml`, `.yml`, `.toml`) up to 1 MiB are merged line by line like notes, but edits to the same or neighbouring lines are never combined: the file gets a conflict copy, as it does when a merged YAML or TOML file would no longer be valid. Every other file is handled as a whole: the newer version stays at the path, and the other one becomes the conflict copy. If the version both edits of a note started from is no longer kept on the server (see [History and restore](#history-and-restore)), the note cannot be merged and gets a conflict copy too.

Run **Vault Sync: Show conflicts** to open the conflict view in the right sidebar. It lists each conflict copy this device made, newest first, with:

- when it was made;
- a link to the version that stayed in place (it follows the note if it was renamed since) and a link to the conflict copy (Ctrl/Cmd-click opens it in a new tab);
- **Compare side by side**, which opens the two versions next to each other in a new tab. On a phone, where Obsidian shows one pane at a time, both open and you switch between them.

Copy what you need from the conflict copy into the note, then delete the copy. Deleting (or renaming) the copy resolves the conflict: its entry disappears from the view, and the status no longer counts it.

The view also lists **files not on this device**: files that are synced, but that this device cannot hold. They stay on the server and on your other devices, and the rest of the vault syncs normally (`docs/design/engine.md` §6, §7):

- a file larger than this device's size limit, 1 GiB on desktop and 256 MiB on a phone or tablet (the server has its own limit, `VAULT_SYNC_BLOB_MAX_SIZE_BYTES`). A smaller version of the file, saved on another device, arrives as usual and removes the entry;
- a file whose path is not valid on this device's platform, such as a path longer than Windows allows (260 characters including the vault folder, unless long paths are enabled), or a name longer than 255 bytes. Rename it on another device and it arrives here.
- a file whose name ends in `.vault-sync-tmp` or `.vault-sync-new`, the names of Vault Sync's own temporary files, which it removes at startup (`docs/design/engine.md` §8). Such a file can come from another client or from `vault-sync-server import`. Rename it on another device and it arrives here.

When a file first joins this list, a notice names it and says why it is not on this device; it shows once per file and reason each time Obsidian starts.

When you create or rename a file or folder to a path longer than 200 characters (relative to the vault, counted in UTF-16 code units as Windows counts them), a notice warns that devices with a shorter path limit, such as Windows, may not be able to store it. The file still syncs, and a device that cannot hold it lists it here.

Finally, it lists **files that are not synced**: local files that stay on this device only, each with the reason. A file larger than the size limit is not uploaded; a smaller version of it syncs. A file whose name the server refuses is never retried until you rename it: names must be portable, so a file or folder name may not contain `< > : " / \ | ? *` or a control character, start or end with a space, end in a dot, be a Windows reserved name (`CON`, `PRN`, `AUX`, `NUL`, `COM1` to `COM9`, `LPT1` to `LPT9`, with or without an extension), or be longer than 255 bytes, and the whole path may not be longer than 1024 bytes. A name that differs from an existing note's only by letter case is refused too. The status shows `error` and names the file (or the first of several). Rename or move the file to a valid name and it syncs like any other.

A link in the view whose file no longer exists (removed since the view was drawn) shows a notice and redraws the view.

## Config folder

vault-sync syncs your notes, attachments and folders. Nothing in the vault's config folder (`.obsidian`, or the name set under **Settings → Files and links → Override config folder**) is uploaded or written: config-folder sync is not part of this version (`docs/design/engine.md` §1).

## History and restore

The server keeps every revision of every file until its retention policy thins old ones out (by default everything for 90 days, then one revision per day for a year, then one per week; see [History and retention](admin/history-and-retention.md)). A file's current revision is never removed, and neither is the record that a file was deleted.

- **Vault Sync: Show file history** (for the open file), or **Show sync history** in a file's context menu, lists the file's revisions, newest first. Each line shows when the server received the revision, which user made it (their name from the identity provider, in quotes and shown like device names, or the start of their user id when the server does not name them), which device made it (`this device`, or another device by the name it was registered with, in quotes, with invisible formatting characters such as bidi controls removed, double quotation marks shown as `'`, at most 64 characters (longer names end in `…`) and laid out on their own (a Unicode bidi isolate), so right-to-left letters in it cannot reorder the line, or by the start of its id when the server does not name it), and what changed (edited, moved, deleted, restored). Paths are another member's text too: in the history and the conflict view, a path's invisible characters (control and format characters such as bidi controls and zero-width characters, and line separators) are written as `\uXXXX`, so a name cannot pass for another one (a right-to-left override shows as `\u202E`), and a backslash in a name is written as `\\`, so a name that literally contains `\u202E` does not look like one with an override. The zero-width joiners inside an emoji sequence (such as a family or profession emoji) are left as they are, so the emoji shows. This has a known limit: where the device's font has no glyph for a joined emoji, it shows the emoji side by side, exactly as it shows them without the joiner, so two paths that differ only in that joiner can look the same. Inside a line, a path is laid out on its own, so right-to-left letters in it (an Arabic or Hebrew folder name, for example) cannot reorder the text around it. When a restore fails, the notice shows the path the same way. Only the display changes: the file keeps its name on disk and on the server, and restoring uses its real path. Every member of the vault sees the names of the devices that changed its files. Older revisions load with **Load older versions**.
- Choose a revision to preview it. Text is shown as it is (the start of a very long file only); other files by size. For a large file the preview downloads only its start; restoring it downloads the rest when needed.
- **Restore this version** makes the chosen revision the file's current content again. Nothing is overwritten: the restore is a new revision on top of the current one, so the version it replaces stays in the history, and it reaches your other devices like any edit. A local edit not synced yet meets the restored version like an edit from another device (see [Conflicts](#conflicts)). The file keeps its current name and folder.
- Members with the `viewer` role can browse history and preview versions but not restore them, so the modal offers no **Restore this version** button to them. If the plugin cannot read the role (the server is unreachable, say), it offers the button and the server decides.

If another file has taken the path, the restore fails at first and the modal then offers **Restore at another path**, filled in with a free path next to the old one (`plan (restored).md`). Edit it if you like, and **Restore here** brings the file back there, with its history. If the path you typed cannot be used, the field keeps it for you to correct; if another file has taken it too, the field suggests a free path next to it. The path must be one the server accepts for a new file and that this device can hold. Or move the other file away and restore again. History is only available while the vault syncs (signed in and connected).
