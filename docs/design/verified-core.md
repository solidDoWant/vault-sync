## 1. Guarantees

### 1.1 The guarantees

"You" means any user of the vault, on any device. "Sync" means the plugin's exchange with the server.

- **G1. Nothing the server accepted is lost.** Once the server has accepted a version of a file, that version can always be got back: as the current file, in the file's history, or as a conflict copy. Only the operator's history-retention policy ever removes old versions, and never the latest one.
- **G2. Sync never destroys what you wrote on a device.** The plugin only overwrites or deletes a file whose contents are exactly what it last saw there. It never deletes a file it does not track: it moves it out of the way instead. A file you are editing is never replaced underneath your unsaved changes.
- **G3. A file is only deleted because someone deleted it.** Sync deletes a file on other devices only after a user deleted that file on some device. A crash, a missed notification or a file sync itself moved never counts as a delete.
- **G4. A deleted file only comes back because someone wanted it.** A deleted file reappears only when someone edited it, renamed it, created a new file in its place, or restored it from history. It never comes back by itself.
- **G5. A file stays the same file.** Renaming or moving a file keeps it the same file, with its history. Two different files are never mixed up or joined into one just because they have the same name or the same contents.
- **G6. Simultaneous changes keep both versions.** When two devices change a file at the same time, edits to different parts of a note are combined. Otherwise one version stays in place and the other is saved next to it as a conflict copy. An edit or a rename always beats a delete.
- **G7. One name, one file.** No two files ever hold the same name, on a device or on the server. When two files want one name, one keeps it and the other moves to a new name with its contents intact.
- **G8. A crash changes nothing.** If the app crashes, is killed or loses power at any moment, it finishes or undoes what it was doing when it starts again, and ends up as if it had not crashed (apart from the names and times of conflict copies). Changes made while the app was closed are picked up when it starts.
- **G9. Synced devices agree.** Two devices that have both finished syncing hold the same files, with the same contents, under the same names. The exceptions are files a device cannot hold (a name its system does not allow, a file too large to download), which stay on the server and are reported on that device instead of dropped; settings files a device has chosen not to sync; and folder names that differ only in upper or lower case, where a device's system treats them as one folder, or where each device's system treats its own spelling of the folder and the server's as one folder.
- **G10. Sync always finishes.** Every conflict is settled within one sync, unless a user has to act on it, which the plugin then reports. Sync never loops or stalls forever.

## 2. The formal model

The guarantees of §1 are stated formally in Dafny, in `plugin/verified/spec/`. The specification describes what the engine's state is, which events change it, which effects the engine may ask for, and what every run must satisfy. It contains no decision logic and no proofs about transitions: those come with the verified core itself. `make verify` checks that the specification is well-formed and proves that the initial state satisfies every guarantee that is a property of one state (`docs/testing/verification.md`). The specification is not compiled into the plugin.

### 2.1 Paths (`Paths.dfy`)

A path is an exact spelling. The engine compares paths in two ways (`engine-path-ownership.md` §3.1, PO-10): `F`, which spellings name one file on a device, depends on the device's platform; `K`, the server key of `SPEC.md` §5, decides server claims and copy-name freedom. Both are abstract functions to a key, so "same key" is an equivalence relation by construction. Their axioms are: normalizing a path keeps its key and normalizing twice changes nothing; the folder relation (`Ancestors`) is proper and transitive; and both keys are compatible with folders, so whether a file lies under a folder does not depend on which spelling of the folder is asked about. That is what disk exclusivity needs of `F`: a collision (§3.2, a name or a folder of it) is a property of key classes. No axiom relates `F` and `K`, because neither implies the other. There are no Unicode tables: a refinement with identity keys (the posix platform) shows the axioms are consistent. The TypeScript implementations satisfy each axiom on every platform: one fast-check property test per axiom, named after it, in `plugin/src/core/pathkey/path-axioms.test.ts` (#951).

### 2.2 State (`Engine.dfy`)

The state is a set of devices and the server.

- **The server** holds every revision, each document's history (a line, its last revision the head), the change feed, and the revisions the retention policy purged. It also records, as bookkeeping that only the guarantees read, every revision it ever accepted, so a restore from backup that loses one is visible.
- **A device** has a platform, whether the app is running, its journal, its disk, the open editors with unsaved text, and the paths it does not sync.
- **The journal** holds one row per document: `base` (the last server revision applied or acknowledged), `ahead` (the newest server revision not applied, with its blocker), `binding` (the file that is the document on this device, with the content last seen there) or the reason it has none (`absence`), and `outbox` (the one commit it will send). With the cursor these are the device's view of the server. The journal also holds the open intents (`apply`, `merge`, `displace`, `detach`, `commit`, `resync`, design §4.4) and the conflict log.
- **The disk** maps spellings to files. A file has its content and, as bookkeeping the engine never sees, its identity (the harness's inode, design §5.4), so the guarantees can say which file is which. The supply of identities is unbounded: for any finite set of identities there is one outside it (`FreshIdentityExists`, an axiom). That is sound because the harness gives every new file a fresh inode number; a refinement with natural numbers as identities (`NatIdentities`) proves the axiom, so it is consistent. Without it a create could have no outcome, and a step that requests one could not follow its effects.

### 2.3 Events and effects (`Engine.dfy`)

An event is one of: a user action on a device's disk (write, delete, rename, an editor's unsaved text), whether the app runs or not; a local file event the vault reports (create, modify, delete, rename), which can be lost; the start-up scan with the vault listing; a remote revision; a push result (accepted, head moved, already exists, invalid argument, unavailable); a restore from backup; a retention purge; a restore of an earlier revision from history; a crash; a restart; and a sync round (a pull, then a push). A sync round's step includes its pull's results: the revisions on the feed after the device's cursor are handed to the core within the step. A remote revision event is one delivered outside a round. The push's answers arrive as later push-result events.

The effects the engine may ask for are: write a file (for a document or as an untracked copy), delete a file, move a file, each with the content the file must still have (or that no file is there); read a file; upload content; commit an outbox; pull from a cursor; persist the journal; and report something to the user.

**What an effect does to the disk.** A disk effect takes effect only when its precondition matches the device's disk, comparing names under the device's `F`; otherwise it does nothing. A write conditional on content overwrites the file that holds that content in place: the same file, with the new content. A write conditional on no file creates a new file at its name, but only if no file collides with that name: none has the same name under `F`, sits where one of its folders would be, or lies under it (design §3.2). A delete removes the file that holds the expected content. A move takes the file that holds the expected content, with its contents, to the new name, but only if no other file collides with that name and neither name is a folder of the other. A rename that only changes upper or lower case is allowed. The other effects do not touch the disk. A step's effects act in the order requested, each on the disk the earlier ones left. In a step that is not a user's action, the event's device's disk after the step is its disk before with the effects applied, and no other device's disk changes (`EffectTakes`, `EffectsTake`, `DisksFollowEffects`). Every sequence of effects has an outcome on every disk (`EffectsCanTake`), so no step's effects leave it without a disk after. A user's step changes the disk by the user's action instead. A crash can cut a step short after the shell performed only some of its effects. That step then never completes. The crash event names the step it cut short, if any: that step's event, an event of the same device that the core handles (not a user's action or another crash), and the effects the core requested for it in the crash step's state before. The crash step lists, as its effects, the ones the shell performed, which are a prefix of the requested ones, and they act on the disk like any step's effects. A crash that cut nothing short performs no effect (`CrashCutsShort`). That the requested effects are what the core asks for in response to that event is a proof obligation of the verified core. What the crash leaves of the journal is crash recovery's business (#950).

**How file contents reach the core.** There is no read-result event. When the shell hands the core a local file event, it reads every path the event names (one, or both names of a rename) and passes, for each, the file's content and kind under `F`, or that no file is there. In the model this read is taken from the step's state before (`ReadAt`, `LocalReads`), the same disk the effects' preconditions are checked against. The start-up scan gets its listing the same way, inside its event. The read-file effect has no result in this model: every read the core needs reaches it as an event's input.

**A sync round's input.** With a sync round the shell hands the core, besides the pulled revisions, the round's input (`RoundInput`): the vault listing, every file's spelling with its content and kind, as the start-up scan's listing; the paths at which an open editor holds unsaved text; and a list of fresh document ids. `RoundInputOf` states what makes it the round's input: the listing and the unsaved paths are read from the step's state before (`DiskListing`, `UnsavedPaths`), the same disk the effects' preconditions are checked against, and the document ids are distinct and used by no device's journal and not by the server. The event stays `SyncRound(device)`; the input is a function of the step like `LocalReads`, except for the ids, which any list meeting `RoundInputOf` supplies. The listing lets the push name untracked files (the journal does not record them, §3.3) and tells the round what every file it writes over holds now, including a local edit whose event has not arrived (`RoundRead`). The unsaved paths let it keep every write and delete off a file being edited (`G2_UnsavedSafe`). The fresh ids name the documents the push creates; §3.1 already supplies the revision id of each document's next outbox, a new document's first one included.

The input belongs in the specification, not in §3.1 as a hypothesis of the core's theorem. The listing and the unsaved paths are observations of the state, like `LocalReads`, and the guarantees the round must keep (G2, G6) are stated over that same state, so the core's theorem, the witnesses and #982 must use one definition of them. The ids' freshness is a fact about other devices and the server, which the core cannot see, so only the specification can state it. The shell meets it with random UUIDs, as the engine does now.

**What a step does to the server.** The server changes only by its own events (`ServerFollowsEvent`). An accepted commit appends one revision to the document's history, to the feed and to what the server accepted, and drops nothing. That revision is the device's sealed outbox of the document, the commit in flight: the outbox's id, path, content, kind and delete flag, from that device, with the outbox's base as its parent. The parent must be the document's current head (none for a new document), because the server accepts a commit only on the head it was based on (`SPEC.md` §6.2). The id must be one the server never used, and a live revision's path must not collide under `K` with another document's live head (`SPEC.md` §5). A restore from history appends a live revision with the restored revision's content and kind, under the same rules. A purge marks revisions purged that are not a document's head, and changes nothing else. A restore from backup leaves the server it names. A remote revision delivered to a device is one on the feed, exactly as the server holds it. A commit of a tombstone for a document the server has no head of (no parent) is accepted like any first commit, and creates the document deleted (§3.6). Every other event leaves the server unchanged: a push the server refused or could not answer, a sync round (its pull only reads), a user's action, a local event, the scan, a crash and a restart. That the accepted revision is the sealed outbox is part of the model, not a core obligation: it describes the server answering the commit the device sent. It holds for a real run only if the core persists a sealed outbox before it requests the commit, and keeps it until the commit is answered, which #949 must prove (§3.2).

A step is a state, an event, the effects requested and the next state. A trace is a sequence of connected steps, and a run is a trace from the initial state (every device running, with an empty vault and journal, and an empty server).

### 2.4 Guarantees as predicates (`Guarantees.dfy`)

Each guarantee is a predicate, with a comment quoting the sentence of §1.1 it formalizes. A guarantee about one moment is a predicate on a state, one about what a single step may do a predicate on a step, and one about the order of things a predicate on a trace. `StateInvariants` collects the state predicates and `TraceGuarantees` the trace predicates. G8's "as if it had not crashed" relates two runs, one with crashes and one without, and is the separate predicate `G8_AsIfNoCrash`.

| Guarantee | Predicates |
|---|---|
| G1 | `G1_Retained`, `G1_LatestNeverPurged` (state), `G1_OnlyRetentionRemoves` (step), `G1` |
| G2 | `G2_OnlyWhatItSaw`, `G2_Conditional`, `G2_NoUntrackedDelete`, `G2_UnsavedSafe` (step), `G2` |
| G3 | `G3_DeleteSeen` (step), `G3` with `UserRemovedFileOf` and `JustifiedTombstone` (trace) |
| G4 | `G4` (trace) |
| G5 | `G5_RenameKeepsDocument`, `G5_NeverMixedUp` (step), `G5_NeverJoined` (state), `G5` |
| G6 | `G6_Settle` (step), `G6` |
| G7 | `G7_OneFilePerName` (state), `G7_MoveKeepsContents` (step), `G7` |
| G8 | `G8_Recovers`, `G8_PicksUpOfflineChanges` (step), `G8`, `G8_AsIfNoCrash` (two traces) |
| G9 | `G9` (state), with `FinishedSyncing` and `InStep` (`Engine.dfy`) |
| G10 | `G10_SettledOrReported` (step), `G10_NoLoop` (two consecutive steps), `G10_NeverStalls` (trace), `G10` |

G10's "never … stalls forever" is stated as a safety property: two sync rounds of a device with nothing in between but answers to its own commits and revisions delivered to it leave it finished, apart from what a user has to act on and user changes whose local events have not reached the engine yet (`G10_NeverStalls`; local events lag the disk, design §4.3). That a single round ends is a property of the core's code, proved with it. `G10_SettledOrReported` accepts a deferral left after a round only where a user must act. The model has no download effect, so a merge that cannot fetch the remote bytes because the server became unavailable mid-round is not represented yet. When the core models downloads, that case needs its own exception, through a `design` issue. G3's "a missed notification never counts as a delete" also binds what a step records, not only what the server accepts: a step that is not the user's records a user's delete of a document (drops its binding with `absence = UserDeleted`) only when no file is at the binding's name, or the vault reported another file renamed onto that name (`G3_DeleteSeen`). A file still at its name was not deleted, whatever event arrived. G5's "never mixed up" is about what sync does: in a user's own step a document's bound file may change only because the user changed the disk under a binding the step left as it was, by writing at its name or renaming another file onto it (clause (g) of `G5_NeverMixedUp`). The engine learns of that change from the vault's report or the start-up scan, whose steps clauses (a)–(f) judge as before. That an outbox carries the change it records is not a guarantee predicate: a stale outbox holds a version the user had, so by itself it loses nothing, and its visible effect, the server lagging the file, is G9's and G10's over a run. It is the core's invariant instead (§3.2), so every step of the core must keep it. G2's "what it last saw there" is `seen`, or, in a sync round, what the round read in the file (`LastSaw`, `RoundRead`), but only where the step keeps what it read (`ReadKept`): after the step that content is what the document will send (`Outgoing`), or it is in an untracked file on the device, or the step settles another device's live note revision of the document against it, the file it read is a note too (G6 merges only two notes), and the document sends their merge over its base (`MergedRead`). Settling a remote delete keeps the read content only by the first two: an edit beats a delete with the edit itself, and `G6_Settle`'s "the file stays" alone would let the round write the base back over it. The round reads every file before it writes over it, so the read is newer than `seen`. Without it a round could not merge a note the user edited before the edit's event arrived, which G6 requires: the only way to settle it is to overwrite the edit with the merge, conditional on the edit. Without `ReadKept` the read would let a round overwrite or delete an edit it read and then lose it, for example by writing the base back, which G2 rules out. Outside a round the core reads only what an event's input carries, so `seen` stays the only content it may overwrite. G6's "stays in place" and "saved next to it" are read as the content the document keeps and an untracked file on the device, whatever its name: the copy's name and the result's path are `SPEC.md` §7's rules, not guarantees.

`Witnesses.dfy` checks the predicates both ways. Its witnesses show that a non-trivial state (two devices holding the same synced file) and run (a user's write) satisfy them, so they rule out no correct core. A third witness, two sync rounds that pull and apply a revision while a user's write has not been reported yet, satisfies `G10_NeverStalls`. A fourth, a user's rename of an untracked file over a bound one, satisfies `G5`, so G5 can be met on user steps. Three sync-round witnesses use the round's input: a round that reads a local edit whose event has not arrived, keeps it in place and saves the other device's version next to it, with an editor open on another file (`RoundSettlesUnreportedEdit`); a round that merges such a note edit over the content it read (`RoundMergesUnreportedEdit`); and a round that leaves a revision blocked by `LocalChanges` and reports it, because its file has unsaved text (`RoundHoldsBackUnsavedFile`). Each satisfies G2's step predicates, the first two `G6_Settle`, the third `G10_SettledOrReported`. The first also passes a fresh document id in its input, so `RoundInputOf`'s freshness clauses can be met. The rejection `G2RejectsOverwriteOfUnreadContent` shows that the same overwrite outside a round, which read nothing, fails `G2_OnlyWhatItSaw`; `G2RejectsRoundRevertingUnreadEdit` shows that a round that overwrites an unreported edit with the base, or deletes the edited file, without keeping the edit fails it too, and `G2RejectsRoundRevertingEditAgainstTombstone` that so does a round that settles another device's delete and writes the base back over the edit, although it passes `G6_Settle`. Its rejections show that a predicate fails on the failure its sentence rules out: a revision dropped from the server (G1), a delete nobody made (G3), a reported delete recorded although the file is still at its name (G3), a user's step whose journal rebinds a document to another file (G5), the deleting device's own overruled edit resurrecting a file (G4), a remote create joined to another file of the same name (G5), a missing file forgotten at start-up (G8), devices that disagree (G9), and a conflict merely reported (G10). A broken core therefore cannot pass them. `Guarantees.dfy` has three more rejections (G2, G5, G7). For the server's step semantics, a witness shows an accepted create appending the device's sealed outbox, and another an accepted tombstone for a document the server has no head of. Rejections show that each of these fails `ServerFollowsEvent`: an accept that also drops another revision; a server that changes on a "head moved" answer; an accept of a revision that is not the device's sealed outbox (other fields, another device, or an outbox not sealed); an accept whose parent is not the document's head; a live accept whose path collides under `K` with another document's live head; a delivered revision that is not on the feed or differs from the server's copy; and a purge of a head revision. For the effect semantics, a witness shows a conditional write that applies, a step whose disk follows its effects and that keeps G2's step predicates. Two rejections show a write performed although its file no longer held the expected content, and a write silently dropped although it did, both failing `DisksFollowEffects`. A lemma proves that a step whose disks follow its effects keeps `G2_Conditional`, so the semantics and that guarantee agree. The collision rules are pinned both ways: a rename that only changes case takes effect, a move into a folder of its own name or onto one of its folders does not, a create next to a file it does not collide with takes effect with a fresh identity, and a create that collides with another spelling, a folder or a name under it does not. `EffectsCanTake` proves every effect sequence has an outcome. For crashes, a witness shows a crash step that lists the first of two requested effects, and rejections show that one listing the second without the first, an effect although nothing was cut short, or another device's step's effects all fail `CrashCutsShort`. So does a crash that lists a prefix of the requested effects but claims to have cut short a user's action or another crash.

### 2.5 Changing the specification

The specification is changed only through `design` issues (`docs/agents/engine-designer.md`), never by a fix or refactor PR. A change to what a guarantee's predicate means, or to the guarantees themselves, needs the owner, as §1 does. A predicate may be made more precise only where its English sentence already says so, and a reviewer checks every predicate against its sentence.

## 3. The core

The verified core lives in `plugin/verified/core/`. It refines the specification of §2: it adds code and proofs, and never changes a predicate. `make verify` proves it. §3.4 compiles it to JavaScript and runs it against the engine's tests (#965); the shell that executes its effects is #952.

### 3.1 Shape

Each handler is a non-ghost function from what the shell hands the core to the new journal and the effects. The input is the device's platform and journal, the event, the event's input (§2.3: for a local event, the shell's read of every path it names; for the start-up scan, the listing; for a sync round, the pulled revisions and the round's input, `RoundInput`), and the revision id the shell assigns to each document's next outbox. A step of the core is the state before, the event, the effects, and the state after, in which only the event's device's journal is replaced, every disk follows the effects (`DisksFollowEffects`), and the server follows the event (`ServerFollowsEvent`).

### 3.2 The core's invariant

`CoreInv`, which every handler keeps and which #949 and #950 must keep too, has three clauses. The initial state satisfies it (`InitialCoreInv`).

- **A user's delete is never forgotten.** A document whose binding is gone with `absence = UserDeleted` has an outbox, or a base that is a tombstone. The delete is therefore sent until the server has it: if the user deletes the file after a live commit was sealed, the accept of that commit opens a tombstone outbox on top of it (§3.5, `AcceptKeepsUserDelete`).
- **A change to a bound file is never forgotten.** A bound document whose file as last seen differs from its base has an outbox (`AheadOfBase`): it has no base, its base is a tombstone, or the base's path or content differs from the binding's `spelling` or `seen`. With the next clause, an unsealed outbox carries that change; a sealed one is followed by it. So if the user edits or renames the file after a commit was sealed, the accept of that commit opens a new outbox on top of it with the file's name and `seen` (§3.5, `AcceptKeepsLaterChange`): the accepted revision is now the base, and it differs from the file. Every transition must keep this, the sync round (#982) included, so no transition can drop a change the server has not got.
- **An unsealed outbox is the document as the device last saw it** (`OutboxCurrent`). A bound document's unsealed outbox is live and carries `spelling` and `seen`, the name and content last seen in its file; a user-deleted document's is a tombstone. A sealed outbox, a commit in flight, carries what it carried when it was sealed. So an outbox not yet in flight never holds content older than the last change the core recorded.

With `CoreInv`, every step from #949 on keeps `ServerInv`, the core's view of the server (§3.5): no cursor past the feed; history and purges name only held revisions; every accepted revision is in history, in a file on a device, or purged and no head. #950 and #966 must keep it too.

Every step of #949 and #950 must also satisfy `G3_DeleteSeen` (§2.4) and `ServerFollowsEvent` (§2.3), as part of `StepGuarantees`. #949 must also show that the commit it requests for a document is its sealed outbox, persisted before the request and kept until the answer, so an accept in the model always answers it.

### 3.3 Local events and the start-up scan (`LocalEvents.dfy`, #948)

A local file event or the scan reports a change the user already made on disk, so the core requests no disk effect for them, only `PersistJournal`. Every document row the core changes gets an outbox (a sealed outbox, a commit in flight, is never edited, but it counts as one). Base and ahead are never changed here.

- **Created / Modified** of a bound file whose content differs from `seen`: `seen` becomes the new content, and the outbox carries it. Every outbox a local event or the scan opens or changes carries the document's kind, never the kind read from disk (§3.6). A new file stays untracked: the push creates its document (#949), and `PendingPush` counts untracked files.
- **Deleted** of a bound file that is gone: the binding goes, `absence = UserDeleted`, and the outbox carries the tombstone. If the read finds a file again (a new one was created there before the event arrived), nothing changes, and the later create event decides.
- **Renamed:** the document bound to the old name is bound to the new one, with the content read there (G5_RenameKeepsDocument). The move is the user's, so the binding no longer records that the engine displaced the file (`displaced` and `userSpelling` are cleared, §3.6). Another document bound to the new name had its file replaced by the user, so it is unbound as a user's delete, as above. The document keeps its kind even when the new name is of another kind (§3.6). The document is rebound to the new name even when the read finds no file there (the file moved on again before the event arrived). The binding then keeps `seen`, and the next start-up scan finds the binding's file missing and settles it (§3.3, start-up scan): a one-to-one match, or a user's delete.
- **Start-up scan:** a bound file the listing names by another spelling, other than in its folders alone (#737), was respelled by the user: the binding takes the listed spelling, clears `displaced`, and the outbox carries the move (`SPEC.md` §8, §3.6). A bound file present in the listing whose content differs from `seen`, or that the server does not have as it is, gets an outbox. A bound file missing from the listing is matched to another file only by the one-to-one exact-content rule (E7, §1.3, owner decision 4): exactly one untracked listed file holds exactly `seen`, it is of the document's kind, and no other document whose file is missing last saw that content. A match clears `displaced` as a rename does. Otherwise the document counts as deleted by the user while the app was closed (G8_PicksUpOfflineChanges).

The theorems `LocalEventSafe` and `ScanSafe` prove that from any state satisfying `StateInvariants` and `CoreInv`, the step keeps both and satisfies every step predicate of `Guarantees.dfy` (`StepGuarantees`). `G10_NoLoop`, which relates two sync rounds, does not apply to these steps. The trace guarantees (G3, G4, G6, G10, `G8_AsIfNoCrash`) are proved over whole runs once every transition exists (#966).

### 3.5 Remote revisions and push results (`RemoteEvents.dfy`, #949)

**Remote revisions.** A remote revision delivered outside a sync round is recorded, not yet applied. If it is newer than everything the device knows of its document (its position is past the `ahead`, or else the `base`), it becomes the document's `ahead`. It is blocked by `LocalChanges` when the journal has a change of the document the server lacks (an outbox, or a user's delete), and is otherwise postponed until the sync round applies it with the path-conflict function (#982, #962). An older revision changes nothing.

**Push results.** A result answers a document's sealed outbox, the commit in flight. A result for a document with no commit in flight changes nothing.

- **Accepted:** the revision becomes the document's `base`, and an `ahead` no newer than it is dropped. The outbox goes, unless the user changed the document after the commit was sealed. In that case a new outbox on top of the accepted revision carries the change: the bound file's name and `seen`, or a tombstone for a user's delete. `CoreInv` forces both (§3.2); `AcceptKeepsLaterChange` and `AcceptKeepsUserDelete` state them.
- **Head moved, already exists, unavailable:** the outbox is unsealed and carries the document as the device last saw it (`OutboxCurrent`), to be sent again. "Unavailable" answers every commit in flight.
- **Invalid argument:** the same, and the outbox is marked `rejected` until a local change clears it (`SPEC.md` §6.2).

None of these requests a disk effect, only `PersistJournal`, and none changes a binding.

**`ServerInv`.** The proofs need more of the server than `StateInvariants`:

- no device has read past the feed;
- history and purges name only revisions the server holds;
- every accepted revision is in the history, or in a file on some device, or purged and no head.

The last clause is `G1_Retained` without its "content of some live head" way out. That way out does not survive a later accept of that head's document: the head's content then lives on only as an old revision, which does not make the other version retrievable. Every reachable state must satisfy `ServerInv`: the initial state does, the steps here and local events keep it (they change neither the server nor a disk), and #950 (restore, purge) and #966 (whole runs) must keep it.

The theorems `RemoteRevisionSafe`, `RefusedSafe` and `AcceptSafe` prove that from any state satisfying `StateInvariants`, `CoreInv` and `ServerInv`, the step keeps all three and satisfies `StepGuarantees` (with `ServerFollowsEvent`). The lemma `QuietStep` proves this for any step that leaves the server and the disks as they are and changes rows only by recording a waiting revision or reopening an outbox. The sync round, which applies pulled revisions to disk and sends commits, is #982.

### 3.7 The mirror invariant behind G9 (`RemoteEvents.dfy`, #992)

G9 compares two devices, but each device syncs only with the server. The core therefore keeps a property of one device at a time: **a finished device's in-scope files mirror the server's live heads** (`MirrorInv`). For every device that has finished syncing (`FinishedSyncing`, §2.4):

- every file on its disk that is not out of its scope holds the content of a live head whose path is the file's name, folders compared on the device's system (`SameNameModuloFolders`) (`FilesMirrorHeads`);
- every live head is on the device: a file whose name is the head's path, folders compared on the device's system, holds its content, or that path is out of the device's scope, or the device reports that it cannot hold it (`ReportedCannotHold`, G9's exceptions) (`HeadsMirrored`).

The lemma `MirrorG9` proves that the invariant implies G9 between any two finished devices: a file in scope on the first mirrors a live head at its name, which the second holds under the head's path (each compared on its own device's system), does not sync, or reports it cannot hold. That is G9's agreement through the server (`G9Agrees`, below), so no path axiom is needed: both comparisons are oriented from a device's name to the head's path on one platform, so neither symmetry nor transitivity of `SameNameModuloFolders` is used. `MirrorImpliesG9` lifts this to the whole state. Removing any conjunct of the invariant (either clause, a head's path or content, the head being live) makes `MirrorG9` fail to verify.

The initial state satisfies it (`InitialMirror`): the server has no head and every disk is empty. No transition proved so far makes a device finish: a device finished after a local event, the scan, a remote revision or a push result is exactly as it was before, on the same server (`KeepsFinished`, which `LocalEventSafe`, `ScanSafe`, `RemoteRevisionSafe`, `RefusedSafe` and `AcceptSafe` now also prove; an accept grows the feed, so no device is finished after it). `KeepsFinishedKeepsMirror` turns that into the invariant's preservation, and `LocalEventKeepsMirror`, `ScanKeepsMirror`, `RemoteRevisionKeepsMirror`, `RefusedKeepsMirror` and `AcceptKeepsMirror` state it for each step, from the same hypotheses as their theorems, with `CoreInv` as #984 left it. The sync round is the step that finishes a device: it is assumed to keep `MirrorInv` until #982 proves that it does. Steps the core does not handle (a user's action, a crash, a restart, a restore, a purge, a restore from history) are #950's and #966's.

**Folder spellings compare through the server (#995).** INV-9 lets each device keep its own spelling of a folder: when a pulled file lands in a folder the device already has, its filesystem keeps that folder's spelling, and renaming the folder would rename the user's other files. Each device's spelling is then one folder with the server's on that device's system, but two devices' spellings need not be one folder on either system. With the engine's own `filesystemKey`, a server folder `U+0345 U+0300` is one folder with `U+0399 U+0300` on Windows (case folding) and with `U+0300 U+0345` on macOS (NFD reorders the marks), and those two device spellings are one folder on neither platform. So no path axiom can compose the two comparisons, and a G9 that compared the two devices' names only could fail between two finished devices through no step of the engine. The owner chose to compare each device with the server instead (option A on #995). `G9Agrees` (`Guarantees.dfy`) accepts a file `p` on one device against another device in three ways: the other holds a file with the same content whose name is `p` modulo folders on either device's system (the direct comparison, as before); or it reports that it cannot hold `p`; or, through the server, `p` is the path of a live head with `p`'s content, modulo folders on the first device's system, and the other device holds that head under its path modulo folders on its own system, or does not sync that path, or reports that it cannot hold it. In the last clause G9's exceptions are read on the server's path, the name both devices are compared with. File names, the final segment, still compare exactly (below). The witness `RespelledFoldersAgree` (`RemoteEvents.dfy`) shows two finished devices on different systems in that situation keeping `MirrorInv` and G9 through the server clause alone. `G9Rejects` (`Witnesses.dfy`) shows that a device holding other content does not agree, through the server either, with a file that is the server's head.

**A file's own name is the server's.** A finished device's file names are its bound documents' paths, the final segment exactly and folders under `F`: `InStep` (§2.4) requires a bound file's name to be its base's path modulo folders. So a user's case-only rename of a file (`a.md` to `A.md` where the platform folds case) leaves the device unfinished until the rename is pushed, as `SPEC.md` §8 treats it as a rename. Without that, the device would stay finished under `F` while G9 compares the final segment exactly, and the user's step would break G9 against a device that still holds `a.md`. A folder-only respelling keeps the device finished (INV-9). The witness `CaseOnlyRenameUnfinishes` (`Witnesses.dfy`) shows that the state after such a rename on one of two finished devices keeps `StateInvariants`.

### 3.8 The sync round's push half (`Push.dfy`, #991)

The push half of the sync round creates the documents of new files and sends every outbox waiting to be sent (`OnPush`). It is a function of the device's platform and journal, the round's input (`RoundInput`, §2.3) and the revision ids of §3.1. The step theorem of the whole round, which composes it with the pull apply (#990), is #982's.

- **New documents.** Every file of the round's listing that no document is bound to under `F` is untracked (§3.3). Each gets a new document, bound to it, with no base and an outbox that creates it: the file's name, content and kind, no parent. Its id is the next of the round's fresh document ids (`freshDocs`), and its outbox's id the one §3.1 supplies. Files left over when the ids run out wait for the next round's ids.
- **Sealing and sending.** Every outbox not in flight and not rejected (a rejected one waits for a local change, `SPEC.md` §6.2) is sealed: it becomes the commit in flight, which a local change no longer edits (`Send`, §3.3) and a push result answers (§3.5). The effects are `PersistJournal` of the new journal first, then one `Commit` per outbox sealed, carrying it as persisted.
- **Order.** Effects are a sequence and ids are handed out in order, but paths and document ids are abstract. So that the core is a function of its input, it takes untracked files and commits in a fixed order: `PathBefore` and `DocBefore`, abstract functions assumed to be strict total orders (`PathOrder`, `DocOrder`, axioms). Every type has one; the compiled core will use string comparison.

`PushCreatesFromFreshIds` proves that every new document's id is one of the round's fresh ids, that it is bound to an untracked listed file and carries it in its sealed outbox, that every other row changes only by being sealed, and that every row keeps the row invariant (`RowInv`: `AheadOfBase` and `OutboxCurrent` included). `RoundCreatesFreshDocuments` adds that with the round's input (`RoundInputOf`) the ids are used by no device and not by the server, and `PushKeepsCoreInv` that `CoreInv` is kept. `PushCommitsSealedPersisted` proves #977's obligation (§3.2): every commit the push requests sends a sealed outbox, and an earlier `PersistJournal` effect holds that outbox as the document's (`CommitsPersistedFirst`). That it is kept until the answer is §3.5's: no transition so far edits a sealed outbox.

The round's input carries no scope: the listing names every file on the disk, out-of-scope settings files included, and the push half cannot tell them apart. Whether the round's input must carry the device's scope is left to #982.

### 3.9 The sync round's pull apply (`Apply.dfy`, #990)

The pull apply decides, for one pulled revision of one document, the document's new row and the disk effects (`ApplyRevision`). It is a function of the device's platform, the document's row, the revision, the round's input (`RoundInput`, §2.3), the names every document is bound to (`bound`), and the revision id of §3.1. It decides from the round's listing and unsaved paths only. The step theorem of the whole round, which composes it with the push half (§3.8), is #982's.

- **Not newer** than what the row knows: nothing changes.
- **The document's file has unsaved text:** the revision waits as `ahead`, blocked by `LocalChanges`.
- **No change here** (the listing reads `seen`, which is the live base's content at the base's name, and nothing to send): a remote edit at the same name is written over the content read; a remote delete removes the file, conditional on that content, and the row is `Released`. A remote move waits (`PathHeld`) for the path rule (#962).
- **A concurrent change** (G6): a live remote edit that keeps the base's name, against a bound file that reads other than the base or has an unsealed outbox. If the file reads as the base and as `seen`, the remote is written over it. If the remote's content is the base's, the local content stays. Two changed notes that `Merge` combines are merged, written over the content read. Otherwise the content read is saved as an untracked copy at the name the path-conflict function picks, and the remote is written over it. The settled row's base is the remote, `seen` is what the file now holds, and it has an outbox (with the local name and that content) only where the file differs from the base. A file that reads as the base but not as `seen` (changed back before its event arrived) is saved as a copy too: G2 lets the round overwrite only content it keeps (`ReadKept`). A remote delete against a local change, a user's delete against a remote revision, and a commit in flight wait, blocked by `LocalChanges`.
- **A document with no file here:** a tombstone is recorded as the base; a live revision is created at its name, conditional on no file, where the listing has no colliding file and no document is bound to the name. Where exactly one untracked file collides, the path-conflict function names where it moves, and the move comes first. Any other collision waits (`PathHeld`, #962).

**The path-conflict function** (`PathConflictCopy`) is the only place a name collision or a conflict copy's name is decided. Its contract is its postcondition: the name is free in the listing, collides with neither the wanted name nor its folders, and is not under F a name to avoid (every bound name and every unsaved path). Its body, the copy-name rule of `SPEC.md` §7 and its proof are #962's. `Merge` is the shell's line-level merge, stated as `Merge3` (§2.4), contract only.

The lemmas, on the function:

- `AppliedPreconditionsHold`: every disk effect's precondition holds on the disk the listing was read from, the second effect of a path conflict on the disk the first leaves (`PreconditionsInOrder`).
- `AppliedTakesEffect`: on that disk, with one file per name, the effects keep one file per name, the new binding names a file holding its `seen` (an overwrite keeps the file in place), a remote delete leaves no file at the old name, a moved or copied file holds its contents at its new name, and every file no effect removes or moves stays with its identity.

Removing any precondition check of the function (the free-name test, the unsaved checks, the bound-name checks, the read-equals-`seen` test) or weakening the path-conflict function's contract makes `make verify` fail.
- On a round step whose effects are the apply's (`ApplyStep`: the input is `RoundInputOf` the state before, the revision is another device's that the server accepted, and the state after is the effects' disk and the new row): `AppliedG2` (`G2_OnlyWhatItSaw`, with the read content kept by a merge or a copy, `G2_UnsavedSafe`, `G2_NoUntrackedDelete`), `AppliedG5` (`G5_NeverMixedUp`, through clause (b): a file arrives only at a name no other document is bound to), `AppliedG6` (`G6_Settle` for every change the step settles) `AppliedG7` (`G7_OneFilePerName`, `G7_MoveKeepsContents`), and `AppliedKeepsOtherFiles`: every other document's bound file is the same file after the apply, since only the document's own file is removed and only an untracked file is moved aside.
- `AppliedKeepsRowInv` (#982): from a row that keeps `RowInv` (`CoreInv` one row at a time, §3.2), the row the function returns keeps it, whatever it decides. A user's delete is still sent or already the base, a bound file that differs from the new base has an outbox (`AheadOfBase`), and an unsealed outbox carries the file as last seen (`OutboxCurrent`). `SettleKeepsRowInv` proves it for a settled change. Dropping the settled row's outbox even where the file differs from the remote (`if true then row.(outbox := None)` in `Settled`), or giving that outbox the remote's content instead of the file's, makes `make verify` fail.
