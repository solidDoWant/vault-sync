## 1. Guarantees

### 1.1 The guarantees

"You" means any user of the vault, on any device. "Sync" means the plugin's exchange with the server.

- **G1. Nothing the server accepted is lost.** Once the server has accepted a version of a file, that version can always be got back: as the current file, in the file's history, or as a conflict copy. Only the operator (retention, or a restore from an older backup) ever removes old versions, and retention never the latest one.
- **G2. Sync never destroys what you wrote on a device.** The plugin only overwrites or deletes a file whose contents are exactly what it last saw there. It never deletes a file it does not track: it moves it out of the way instead. A file you are editing is never replaced underneath your unsaved changes.
- **G3. A file is only deleted because someone deleted it.** Sync deletes a file on other devices only after a user deleted that file on some device. A crash, a missed notification or a file sync itself moved never counts as a delete.
- **G4. A deleted file only comes back because someone wanted it.** A deleted file reappears only when someone edited it, renamed it, created a new file in its place, or restored it from history. It never comes back by itself.
- **G5. A file stays the same file.** Renaming or moving a file keeps it the same file, with its history. Two different files are never mixed up or joined into one just because they have the same name or the same contents.
- **G6. Simultaneous changes keep both versions.** When two devices change a file at the same time, edits to different parts of a note are combined. Otherwise one version stays in place and the other is saved next to it as a conflict copy. An edit or a rename always beats a delete.
- **G7. One name, one file.** No two files ever hold the same name, on a device or on the server. When two files want one name, one keeps it and the other moves to a new name with its contents intact.
- **G8. A crash changes nothing.** If the app crashes, is killed or loses power at any moment, it finishes or undoes what it was doing when it starts again, and ends up as if it had not crashed (apart from the names and times of conflict copies). Changes made while the app was closed are picked up when it starts.
- **G9. Synced devices agree.** Two devices that have both finished syncing hold the same files, with the same contents, under the same names. The exceptions are files a device cannot hold (a name its system does not allow, a file too large to download), which stay on the server and are reported on that device instead of dropped; settings files a device has chosen not to sync; and folder names that differ only in upper or lower case, where a device's system treats them as one folder, or where each device's system treats its own spelling of the folder and the server's as one folder.
- **G10. Sync always finishes.** Every conflict is settled within one sync, unless a user has to act on it, which the plugin then reports. Sync never loops or stalls forever.

## 2. The formal model

The guarantees of §1 are stated formally in Dafny, in `plugin/verified/spec/`. The specification describes what the engine's state is, which events change it, which effects the engine may ask for, and what every run must satisfy. It contains no decision logic and no proofs about transitions: those come with the verified core itself. `make verify` checks that the specification is well-formed and proves that the initial state satisfies every guarantee that is a property of one state (`docs/testing/verification.md`). The specification is not compiled into the plugin.

### 2.1 Paths (`Paths.dfy`)

A path is an exact spelling. The engine compares paths in two ways (`engine-path-ownership.md` §3.1, PO-10): `F`, which spellings name one file on a device, depends on the device's platform; `K`, the server key of `SPEC.md` §5, decides server claims and copy-name freedom. Both are abstract functions to a key, so "same key" is an equivalence relation by construction. Their axioms are: normalizing a path keeps its key and normalizing twice changes nothing; the folder relation (`Ancestors`) is proper and transitive; and both keys are compatible with folders, so whether a file lies under a folder does not depend on which spelling of the folder is asked about. That is what disk exclusivity needs of `F`: a collision (§3.2, a name or a folder of it) is a property of key classes. No axiom relates `F` and `K`, because neither implies the other. There are no Unicode tables: a refinement with identity keys (the posix platform) shows the axioms are consistent. The TypeScript implementations satisfy each axiom on every platform: one fast-check property test per axiom, named after it, in `plugin/src/core/pathkey/path-axioms.test.ts` (#951).

### 2.2 State (`Engine.dfy`)

The state is a set of devices and the server.

- **The server** holds every revision, each document's history (a line, its last revision the head), the change feed, and the revisions the retention policy purged. It also records, as bookkeeping that only the guarantees read, every revision it ever accepted, so a restore from backup that loses one is visible, and every accepted revision a restore removed from its history: the operator removed those, so G1 excuses them as it excuses retention's purges (#1015).
- **A device** has a platform, whether the app is running, its journal, its disk, the open editors with unsaved text, and the paths it does not sync.
- **The journal** holds one row per document: `base` (the last server revision applied or acknowledged), `ahead` (the newest server revision not applied, with its blocker), `binding` (the file that is the document on this device, with the content last seen there) or the reason it has none (`absence`), and `outbox` (the one commit it will send). With the cursor these are the device's view of the server. The journal also holds the open intents (`apply`, `merge`, `displace`, `detach`, `commit`, `resync`, design §4.4) and the conflict log.
- **The disk** maps spellings to files. A file has its content and, as bookkeeping the engine never sees, its identity (the harness's inode, design §5.4), so the guarantees can say which file is which. The supply of identities is unbounded: for any finite set of identities there is one outside it (`FreshIdentityExists`, an axiom). That is sound because the harness gives every new file a fresh inode number; a refinement with natural numbers as identities (`NatIdentities`) proves the axiom, so it is consistent. Without it a create could have no outcome, and a step that requests one could not follow its effects.

### 2.3 Events and effects (`Engine.dfy`)

An event is one of: a user action on a device's disk (write, delete, rename, an editor's unsaved text), whether the app runs or not; a local file event the vault reports (create, modify, delete, rename), which can be lost; the start-up scan with the vault listing; a remote revision; a push result (accepted, head moved, already exists, invalid argument, unavailable); a restore from backup; a retention purge; a restore of an earlier revision from history; a crash; a restart; a sync round (a pull, then a push); and a resync, the round the shell runs on the server's divergence signal after a restore from backup (`SPEC.md` §8 "Divergence", §4.1). A sync round's step includes its pull's results: the revisions on the feed after the device's cursor are handed to the core within the step. A remote revision event is one delivered outside a round. The push's answers arrive as later push-result events.

The effects the engine may ask for are: write a file (for a document or as an untracked copy), delete a file, move a file, each with the content the file must still have (or that no file is there); read a file; upload content; commit an outbox; pull from a cursor; persist the journal; and report something to the user.

**What an effect does to the disk.** A disk effect takes effect only when its precondition matches the device's disk, comparing names under the device's `F`; otherwise it does nothing. A write conditional on content overwrites the file that holds that content in place: the same file, with the new content. A write conditional on no file creates a new file at its name, but only if no file collides with that name: none has the same name under `F`, sits where one of its folders would be, or lies under it (design §3.2). A delete removes the file that holds the expected content. A move takes the file that holds the expected content, with its contents, to the new name, but only if no other file collides with that name and neither name is a folder of the other. A rename that only changes upper or lower case is allowed. The other effects do not touch the disk. A step's effects act in the order requested, each on the disk the earlier ones left. In a step that is not a user's action, the event's device's disk after the step is its disk before with the effects applied, and no other device's disk changes (`EffectTakes`, `EffectsTake`, `DisksFollowEffects`). Every sequence of effects has an outcome on every disk (`EffectsCanTake`), so no step's effects leave it without a disk after. A user's step changes the disk by the user's action instead. A crash can cut a step short after the shell performed only some of its effects. That step then never completes. The crash event names the step it cut short, if any: that step's event, an event of the same device that the core handles (not a user's action or another crash), and the effects the core requested for it in the crash step's state before. The crash step lists, as its effects, the ones the shell performed, which are a prefix of the requested ones, and they act on the disk like any step's effects. A crash that cut nothing short performs no effect (`CrashCutsShort`). That the requested effects are what the core asks for in response to that event is stated by `CutRequestedByCore` (§4, #1025), a hypothesis of `CrashContract`. What the crash leaves of the journal is crash recovery's business (#950).

**How file contents reach the core.** There is no read-result event. When the shell hands the core a local file event, it reads every path the event names (one, or both names of a rename) and passes, for each, the file's content and kind under `F`, or that no file is there. In the model this read is taken from the step's state before (`ReadAt`, `LocalReads`), the same disk the effects' preconditions are checked against. The start-up scan gets its listing the same way, inside its event. The read-file effect has no result in this model: every read the core needs reaches it as an event's input.

**A sync round's input.** With a sync round the shell hands the core, besides the pulled revisions, the round's input (`RoundInput`): the vault listing, every file's spelling with its content and kind, as the start-up scan's listing; the paths at which an open editor holds unsaved text; a list of fresh document ids; and the paths the device does not sync (`outOfScope`). `RoundInputOf` states what makes it the round's input: the listing, the unsaved paths and the scope are read from the step's state before (`DiskListing`, `UnsavedPaths`, the device's `outOfScope`), the same disk the effects' preconditions are checked against, and the document ids are distinct and used by no device's journal and not by the server. The event stays `SyncRound(device)`; the input is a function of the step like `LocalReads`, except for the ids, which any list meeting `RoundInputOf` supplies. The listing lets the push name untracked files (the journal does not record them, §3.3) and tells the round what every file it writes over holds now, including a local edit whose event has not arrived (`RoundRead`). The unsaved paths let it keep every write and delete off a file being edited (`G2_UnsavedSafe`). The fresh ids name the documents the push creates; §3.1 already supplies the revision id of each document's next outbox, a new document's first one included. The scope lets the core itself keep settings files the device does not sync out of sync: the push creates no document for an untracked file at an out-of-scope path, and a pulled revision whose path is out of scope waits as `ahead`, blocked by `OutOfScope`, which G9 and G10 accept as a file the device cannot hold. The listing still names out-of-scope files. Restricting it to in-scope files was rejected: the round would then write and move files without knowing every file they can collide with (a create where a settings file is would not take effect, unseen by the core), and it could not tell that a revision's path is out of scope where no file is there yet. The scope is the device's, not the journal's, so only the input can carry it (design §10.3 step 3, #1006).

The input belongs in the specification, not in §3.1 as a hypothesis of the core's theorem. The listing and the unsaved paths are observations of the state, like `LocalReads`, and the guarantees the round must keep (G2, G6) are stated over that same state, so the core's theorem, the witnesses and #982 must use one definition of them. The ids' freshness is a fact about other devices and the server, which the core cannot see, so only the specification can state it. The shell meets it with random UUIDs, as the engine does now.

**What a step does to the server.** The server changes only by its own events (`ServerFollowsEvent`). An accepted commit appends one revision to the document's history, to the feed and to what the server accepted, and drops nothing. That revision is the device's sealed outbox of the document, the commit in flight: the outbox's id, path, content, kind and delete flag, from that device, with the outbox's base as its parent. The parent must be the document's current head (none for a new document), because the server accepts a commit only on the head it was based on (`SPEC.md` §6.2). The id must be one the server never used, and a live revision's path must not collide under `K` with another document's live head (`SPEC.md` §5). A restore from history appends a live revision with the restored revision's content and kind, under the same rules. A purge marks revisions purged that are not a document's head, and changes nothing else. A restore from backup leaves the server it names, which is the server as it was when its feed was shorter (`EarlierServer`): the feed cut there, every document's history and the revisions restricted to what that feed names, and the purges made by then, none of them a head. The ghost record of what the server accepted is not restored, so a version the restore lost stays visible to the guarantees (#1011), and the ghost record of what restores removed (`lost`) gains every accepted revision this restore removed from the history (`RestoreRemoves`). `G1_Retained` excuses a version in `lost` as it excuses one retention purged. That excuse is the server's only: the restore step itself is judged by `G1_OnlyRetentionRemoves`, and a device still keeps what it held and pushes it again (G2, G9, G10), so a lost version some device still holds comes back as a new revision. Later, `G1_OnlyRetentionRemoves` excuses a lost version that stops being retrievable only where no device held its bytes before the step, as it excuses a purged one: its bytes were then only the content of some live head by coincidence, which any accepted commit of that document replaces. A step that drops a device's copy of a lost version is not excused (`G1RejectsDroppingDeviceCopyOfLostVersion`) (#1015). A remote revision delivered to a device is one on the feed, exactly as the server holds it. A commit of a tombstone for a document the server has no head of (no parent) is accepted like any first commit, and creates the document deleted (§3.6). Every other event leaves the server unchanged: a push the server refused or could not answer, a sync round (its pull only reads), a user's action, a local event, the scan, a crash and a restart. That the accepted revision is the sealed outbox is part of the model, not a core obligation: it describes the server answering the commit the device sent. It holds for a real run only if the core persists a sealed outbox before it requests the commit, and keeps it until the commit is answered, which #949 must prove (§3.2).

A step is a state, an event, the effects requested and the next state. A trace is a sequence of connected steps, and a run is a trace from the initial state (every device running, with an empty vault and journal, and an empty server).

### 2.4 Guarantees as predicates (`Guarantees.dfy`)

Each guarantee is a predicate, with a comment quoting the sentence of §1.1 it formalizes. A guarantee about one moment is a predicate on a state, one about what a single step may do a predicate on a step, and one about the order of things a predicate on a trace. `StateInvariants` collects the state predicates and `TraceGuarantees` the trace predicates. G8's "as if it had not crashed" relates two runs, one with crashes and one without, and is the separate predicate `G8_AsIfNoCrash`.

| Guarantee | Predicates |
|---|---|
| G1 | `G1_Retained`, `G1_LatestNeverPurged` (state), `G1_OnlyRetentionRemoves` (step), `G1` |
| G2 | `G2_OnlyWhatItSaw`, `G2_Conditional`, `G2_NoUntrackedDelete`, `G2_UnsavedSafe` (step), `G2` |
| G3 | `G3_DeleteSeen` (step), `G3` with `UserRemovedFileOf` and `JustifiedTombstone` (trace) |
| G4 | `G4` (trace) |
| G5 | `G5_RenameKeepsDocument`, `G5_NeverMixedUp` (step), `G5_NeverJoined` (state), `G5` |
| G6 | `G6_Settle` (step), `G6` |
| G7 | `G7_OneFilePerName` (state), `G7_MoveKeepsContents` (step), `G7` |
| G8 | `G8_Recovers`, `G8_PicksUpOfflineChanges` (step), `G8`, `G8_AsIfNoCrash` (two traces: the clean one is a crash-free counterpart of the crashed one that ends equal to it; G8 asks that *some* such run exists, `AsIfNoCrashContract`, #1025) |
| G9 | `G9` (state), with `FinishedSyncing` and `InStep` (`Engine.dfy`) |
| G10 | `G10_SettledOrReported` (step), `G10_NoLoop` (two consecutive steps), `G10_NeverStalls` (trace), `G10` |

G10's "never … stalls forever" is stated as a safety property: two sync rounds of a device with nothing in between but answers to its own commits and revisions delivered to it leave it finished, apart from what a user has to act on and user changes whose local events have not reached the engine yet (`G10_NeverStalls`; local events lag the disk, design §4.3). That a single round ends is a property of the core's code, proved with it. `G10_SettledOrReported` accepts a deferral left after a round only where a user must act. The model has no download effect, so a merge that cannot fetch the remote bytes because the server became unavailable mid-round is not represented yet. When the core models downloads, that case needs its own exception, through a `design` issue. G3's "a missed notification never counts as a delete" also binds what a step records, not only what the server accepts: a step that is not the user's records a user's delete of a document (drops its binding with `absence = UserDeleted`) only when no file is at the binding's name, or the vault reported another file renamed onto that name (`G3_DeleteSeen`). A file still at its name was not deleted, whatever event arrived. G5's "never mixed up" is about what sync does: in a user's own step a document's bound file may change only because the user changed the disk under a binding the step left as it was, by writing at its name or renaming another file onto it (clause (g) of `G5_NeverMixedUp`). The engine learns of that change from the vault's report or the start-up scan, whose steps clauses (a)–(f) judge as before. That an outbox carries the change it records is not a guarantee predicate: a stale outbox holds a version the user had, so by itself it loses nothing, and its visible effect, the server lagging the file, is G9's and G10's over a run. It is the core's invariant instead (§3.2), so every step of the core must keep it. G2's "what it last saw there" is `seen`, or, in a sync round, what the round read in the file (`LastSaw`, `RoundRead`), but only where the step keeps what it read (`ReadKept`): after the step that content is what the document will send (`Outgoing`), or it is in an untracked file on the device, or the step settles another device's live note revision of the document against it, the file it read is a note too (G6 merges only two notes), and the document sends their merge over its base (`MergedRead`). Settling a remote delete keeps the read content only by the first two: an edit beats a delete with the edit itself, and `G6_Settle`'s "the file stays" alone would let the round write the base back over it. The round reads every file before it writes over it, so the read is newer than `seen`. Without it a round could not merge a note the user edited before the edit's event arrived, which G6 requires: the only way to settle it is to overwrite the edit with the merge, conditional on the edit. Without `ReadKept` the read would let a round overwrite or delete an edit it read and then lose it, for example by writing the base back, which G2 rules out. Outside a round the core reads only what an event's input carries, so `seen` stays the only content it may overwrite. G6's "stays in place" and "saved next to it" are read as the content the document keeps and an untracked file on the device, whatever its name: the copy's name and the result's path are `SPEC.md` §7's rules, not guarantees. The content the document keeps (`Outgoing`) is its outbox's, or else its bound file's. A commit in flight that another device's revision overtook does not count (`Superseded`): its outbox is sealed on a parent that is no longer the document's base, because the round made the other device's revision the base. The server answers it "head moved" when that revision is not built on it, or "accepted" when the other device committed on top of it; either way the base is already past it (§3.5), and the document sends its file. That is what "stays in place" means for it: the sealed content will never be the document's, and reading it would make G6 require the round to keep a version the server refuses, so a note edited on both sides could not be merged while a commit was in flight.

`Witnesses.dfy` checks the predicates both ways. Its witnesses show that a non-trivial state (two devices holding the same synced file) and run (a user's write) satisfy them, so they rule out no correct core. A third witness, two sync rounds that pull and apply a revision while a user's write has not been reported yet, satisfies `G10_NeverStalls`. A fourth, a user's rename of an untracked file over a bound one, satisfies `G5`, so G5 can be met on user steps. Three sync-round witnesses use the round's input: a round that reads a local edit whose event has not arrived, keeps it in place and saves the other device's version next to it, with an editor open on another file (`RoundSettlesUnreportedEdit`); a round that merges such a note edit over the content it read (`RoundMergesUnreportedEdit`); and a round that leaves a revision blocked by `LocalChanges` and reports it, because its file has unsaved text (`RoundHoldsBackUnsavedFile`). Two more come from #1006: a round that merges another device's note revision into a file whose commit is in flight, makes it the base and keeps the sealed outbox (`RoundMergesOverCommitInFlight`, which keeps G2's step predicates, `G6_Settle` and `G10_SettledOrReported`), and a round on a device whose only file is out of scope that creates nothing and leaves the device finished (`RoundSkipsOutOfScopeFile`). Their rejections are a round that makes the revision the base under the commit in flight without merging it (`G6RejectsUnmergedRebaseUnderCommitInFlight`) and an input that leaves out the device's scope (`RoundInputOfRejectsMissingScope`). Each satisfies G2's step predicates, the first two `G6_Settle`, the third `G10_SettledOrReported`. The first also passes a fresh document id in its input, so `RoundInputOf`'s freshness clauses can be met. The rejection `G2RejectsOverwriteOfUnreadContent` shows that the same overwrite outside a round, which read nothing, fails `G2_OnlyWhatItSaw`; `G2RejectsRoundRevertingUnreadEdit` shows that a round that overwrites an unreported edit with the base, or deletes the edited file, without keeping the edit fails it too, and `G2RejectsRoundRevertingEditAgainstTombstone` that so does a round that settles another device's delete and writes the base back over the edit, although it passes `G6_Settle`. Its rejections show that a predicate fails on the failure its sentence rules out: a revision dropped from the server (G1), a state whose accepted version is gone with neither a purge nor a restore to excuse it (`G1RetainedRejectsUnexcusedLoss`, G1), a delete nobody made (G3), a reported delete recorded although the file is still at its name (G3), a user's step whose journal rebinds a document to another file (G5), the deleting device's own overruled edit resurrecting a file (G4), a remote create joined to another file of the same name (G5), a missing file forgotten at start-up (G8), devices that disagree (G9), and a conflict merely reported (G10). A broken core therefore cannot pass them. `Guarantees.dfy` has three more rejections (G2, G5, G7). For the server's step semantics, a witness shows an accepted create appending the device's sealed outbox, another an accepted tombstone for a document the server has no head of, and a third a restore from backup that loses a version no device holds: it records the version in `lost` and the run keeps G1 (`RestoreLosingUnheldVersionKeepsG1`). Rejections show that each of these fails `ServerFollowsEvent`: an accept that also drops another revision; a server that changes on a "head moved" answer; an accept of a revision that is not the device's sealed outbox (other fields, another device, or an outbox not sealed); an accept whose parent is not the document's head; a live accept whose path collides under `K` with another document's live head; a delivered revision that is not on the feed or differs from the server's copy; and a purge of a head revision. For the effect semantics, a witness shows a conditional write that applies, a step whose disk follows its effects and that keeps G2's step predicates. Two rejections show a write performed although its file no longer held the expected content, and a write silently dropped although it did, both failing `DisksFollowEffects`. A lemma proves that a step whose disks follow its effects keeps `G2_Conditional`, so the semantics and that guarantee agree. The collision rules are pinned both ways: a rename that only changes case takes effect, a move into a folder of its own name or onto one of its folders does not, a create next to a file it does not collide with takes effect with a fresh identity, and a create that collides with another spelling, a folder or a name under it does not. `EffectsCanTake` proves every effect sequence has an outcome. For crashes, a witness shows a crash step that lists the first of two requested effects, and rejections show that one listing the second without the first, an effect although nothing was cut short, or another device's step's effects all fail `CrashCutsShort`. So does a crash that lists a prefix of the requested effects but claims to have cut short a user's action or another crash.

### 2.5 Changing the specification

The specification is changed only through `design` issues (`docs/agents/engine-designer.md`), never by a fix or refactor PR. A change to what a guarantee's predicate means, or to the guarantees themselves, needs the owner, as §1 does. A predicate may be made more precise only where its English sentence already says so, and a reviewer checks every predicate against its sentence.

## 3. The core

The verified core lives in `plugin/verified/core/`. It refines the specification of §2: it adds code and proofs, and never changes a predicate. `make verify` proves it. §3.4 compiles it to JavaScript and runs it against the engine's tests (#965); the shell that executes its effects is #952.

### 3.1 Shape

Each handler is a non-ghost function from what the shell hands the core to the new journal and the effects. The input is the device's platform and journal, the event, the event's input (§2.3: for a local event, the shell's read of every path it names; for the start-up scan, the listing; for a sync round, the pulled revisions and the round's input, `RoundInput`), and the revision id the shell assigns to each document's next outbox. A step of the core is the state before, the event, the effects, and the state after, in which only the event's device's journal is replaced, every disk follows the effects (`DisksFollowEffects`), and the server follows the event (`ServerFollowsEvent`).

### 3.2 The core's invariant

`CoreInv`, which every handler keeps and which #949 and #950 must keep too, has three clauses. The initial state satisfies it (`InitialCoreInv`).

- **A user's delete is never forgotten.** A document whose binding is gone with `absence = UserDeleted` has an outbox, or a base that is a tombstone. The delete is therefore sent until the server has it: if the user deletes the file after a live commit was sealed, the accept of that commit opens a tombstone outbox on top of it (§3.5, `AcceptKeepsUserDelete`).
- **A change to a bound file is never forgotten.** A bound document whose file as last seen differs from its base has an outbox (`AheadOfBase`): it has no base, its base is a tombstone, or the base's path or content differs from the binding's `spelling` or `seen`. With the next clause, an unsealed outbox carries that change; a sealed one is followed by it. So if the user edits or renames the file after a commit was sealed, the accept of that commit opens a new outbox on top of it with the file's name and `seen` (§3.5, `AcceptKeepsLaterChange`): the accepted revision is now the base, and it differs from the file. Every transition must keep this, the sync round (#982) included, so no transition can drop a change the server has not got.
- **An unsealed outbox is the document as the device last saw it** (`OutboxCurrent`). A bound document's unsealed outbox is live and carries `spelling` and `seen`, the name and content last seen in its file; a user-deleted document's is a tombstone. A sealed outbox, a commit in flight, carries what it carried when it was sealed, and no step but its answer drops or edits it: for the pull apply, `ApplySettlesContract` states it and `AppliedKeepsCommitInFlight` proves it of `ApplyRevision` (#1061). So an outbox not yet in flight never holds content older than the last change the core recorded.

With `CoreInv`, every step from #949 on keeps `ServerInv`, the core's view of the server (§3.5): no cursor past the feed; history and purges name only held revisions; every accepted revision is in history, in a file on a device, or purged and no head. #950 and #966 must keep it too.

Every step of #949 and #950 must also satisfy `G3_DeleteSeen` (§2.4) and `ServerFollowsEvent` (§2.3), as part of `StepGuarantees`. #949 must also show that the commit it requests for a document is its sealed outbox, persisted before the request and kept until the answer, so an accept in the model always answers it.

### 3.3 Local events and the start-up scan (`LocalEvents.dfy`, #948)

A local file event or the scan reports a change the user already made on disk, so the core requests no disk effect for them, only `PersistJournal`. Every document row the core changes gets an outbox (a sealed outbox, a commit in flight, is never edited, but it counts as one). Base and ahead are never changed here.

- **Created / Modified** of a bound file whose content differs from `seen`: `seen` becomes the new content, and the outbox carries it. Every outbox a local event or the scan opens or changes carries the document's kind, never the kind read from disk (§3.6). A new file stays untracked: the push creates its document (#949), and `PendingPush` counts untracked files.
- **Deleted** of a bound file that is gone: the binding goes, `absence = UserDeleted`, and the outbox carries the tombstone. If the read finds a file again (a new one was created there before the event arrived), nothing changes, and the later create event decides.
- **Renamed:** the document bound to the old name is bound to the new one, with the content read there (G5_RenameKeepsDocument). The move is the user's, so the binding no longer records that the engine displaced the file (`displaced` and `userSpelling` are cleared, §3.6). Another document bound to the new name had its file replaced by the user, so it is unbound as a user's delete, as above. The document keeps its kind even when the new name is of another kind (§3.6). The document is rebound to the new name even when the read finds no file there (the file moved on again before the event arrived). The binding then keeps `seen`, and the next start-up scan finds the binding's file missing and settles it (§3.3, start-up scan): a one-to-one match, or a user's delete.
- **Start-up scan:** a bound file the listing names by another spelling, other than in its folders alone (#737), was respelled by the user: the binding takes the listed spelling, clears `displaced`, and the outbox carries the move (`SPEC.md` §8, §3.6). A bound file present in the listing whose content differs from `seen`, or that the server does not have as it is, gets an outbox. A bound file missing from the listing is matched to another file only by the one-to-one exact-content rule (E7, §1.3, owner decision 4): exactly one untracked listed file holds exactly `seen`, it is of the document's kind, and no other document whose file is missing last saw that content. A match clears `displaced` as a rename does. Otherwise the document counts as deleted by the user while the app was closed (G8_PicksUpOfflineChanges).

The theorems `LocalEventSafe` and `ScanSafe` prove that from any state satisfying `StateInvariants` and `CoreInv`, the step keeps both and satisfies every step predicate of `Guarantees.dfy` (`StepGuarantees`). `G10_NoLoop`, which relates two sync rounds, does not apply to these steps. The trace guarantees (G3, G4, G6, G10, `G8_AsIfNoCrash`) are proved over whole runs once every transition exists (#966).

### 3.4 The compiled core (`LocalCoreJs.dfy`, #965)

`plugin/verified/LocalCoreJs.dfy` makes the core concrete so that `make verified-js` compiles it into `plugin/src/verified/gen/verified.cjs`. It fixes types only: identifiers, hashes, platforms and paths are strings, and file identities are natural numbers, for which it proves `FreshIdentityExists`. The path model stays as §2.1 defines it, functions known only by their axioms. `HostPaths` refines `PathModel` with externs (the module `VerifiedPathHost`), so the compiled core calls the engine's own implementations: `F` is `filesystemKey`, `K` is `pathKey`, `Ancestors` is `PathSpace.ancestors` and `SameNameModuloFolders` is `PathSpace.sameButFolderSpelling`. These are exactly the implementations whose axioms `path-axioms.test.ts` checks (#951). The compiled core calls only `F`.

The test adapter `plugin/src/verified/local-core.ts` converts between TypeScript values and the compiled core's, and installs the externs. It is test code, which no plugin code imports. Its `CoreDevice` is one device's disk and journal. A user's action changes the disk and, unless the test drops the event, hands the core the local event with the shell's read of every path it names (§2.3). `scan()` hands the core the disk as its listing. `local-core.test.ts` replays scenarios of the engine's tests from `bindings.test.ts` and `scan-race.test.ts` under each test's name, and asserts the journal and the effects (only `PersistJournal`, §3.3) directly. The core takes the scan as one step: events of changes made while the shell lists the disk are delivered after the scan, with the listing taken before the changes. Delivering them after a listing that already shows those changes is a stale event, which the shell has to avoid (#952).

The shell's effect executor, `plugin/src/verified/executor.ts` (#1041, the first part of #952), runs a step's effects in the order the core returned them against an `EffectShell`, the port to the vault, the server and the journal store. `local-core.ts` converts every constructor of the compiled core's `Effect` into a TypeScript value for it. Right before each disk effect the executor checks its precondition as `EffectTakes` states it, under the device's `F`, on the disk the earlier effects left: a write conditional on content finds the file holding that content and overwrites it under its own spelling; a write on no file needs a name no file collides with (§2.3, design §3.2); a remove finds the file holding `expected`; a move finds it, needs `to` free of other files, and does nothing when one name is a folder of the other, while a rename that only changes the case goes ahead. An effect whose precondition fails does nothing and counts as run, as in the specification. The first failure of the shell stops the run, and no later effect starts, so the effects run are a prefix of the ones the core returned: the cut that `CrashCutsShort` and `CutRequestedByCore` describe. `executor.test.ts` checks each precondition both ways and injects a failure at every shell call of an effect sequence that has every kind of effect, asserting that the effects run and the state left are exactly those of a prefix.

The shell's journal store, `plugin/src/verified/journal-store.ts` (#1042, part of #952), keeps the core's whole journal (`CoreJournal`: every row with its base, ahead, binding or absence and outbox, the cursor, the intents, the conflict log, and the feed anchor of SPEC.md §6.1, the shell's form of the ghost `Journal.anchor`) in an IndexedDB database of its own. Each `persist` is one `strict`-durability transaction, so a crash at any point of it leaves the journal before or the one it wrote (`ShellStep`'s atomic journal writes), and overlapping calls run one at a time in call order, so the last journal passed is the one persisted; `journal-store.test.ts` aborts writes after every number of event-loop turns and checks exactly that. `journal-migration.ts` derives the core's journal from the current engine's (`IndexedDbJournal` at its current schema) without writing the latter: rows, deferrals as `ahead` (`path-conflict` is `PathHeld`), the one pending operation per document as its outbox (sealed unless recorded as not sealed), the cursor and its anchor, and the conflict records that name a copy. The engine's bookkeeping the core does not model (file keys, own-commit anchors, `prior`, `cachedPath`, sizes, `descendsFromBase`) is not carried. It refuses a journal with open intents (the engine's start-up recovery finishes them first), with two pending operations for one document, or with a `yjs` kind. `loadOrMigrate` persists the migration once; `journal-migration.test.ts` checks it on a fixture journal written through `IndexedDbJournal`.

The shell's event capture, `plugin/src/verified/capture.ts` (#1043, part of #952), hands the core its inputs one at a time, in the order the vault reported them, from a `VaultReader` port. A local event goes with the read of every path it names under `F`, taken when it is handed over (`LocalReads`). The start-up scan goes with the listing (`ListingDistinct`). A sync round's input (`RoundInput`) is the listing, the unsaved paths, the out-of-scope paths among those the round can look the scope up at (`scopePaths`): the listed files, the pulled revisions' paths, and every path the journal's rows (base, held `ahead` revision, binding and user spelling, outbox) and intents name. That restriction of the device's scope is enough because the core learns of a path only from the listing (it reads the disk through nothing else), from a pulled revision, or from its own journal: an untracked file it would create a document for is listed, and a revision it would apply is pulled now or held as `ahead` from an earlier round, so a revision held as `OutOfScope` is judged out of scope again by the next round though no file is at its path and the pull does not read it again. The port's `inScope` must answer alike for spellings of one file under `F` (`ScopesClosedUnderF`). The input also carries `2·|listing| + |documents| + pulled` distinct fresh ids none of which the journal uses (`FreshDocsSuffice`, where `|feed| − cursor` is the number of revisions the round's pull read). Events that arrive while the scan lists the disk are held until the scan is handed over (a second scan started meanwhile joins the running one, so none is handed over twice). Then each is dropped as stale when every path it names reads as the listing shows it, since the listing then already holds its change, and is handed over with the reads of now otherwise. Dropping is safe because the specification lets any local event be lost and the next round's listing shows every file. `capture.test.ts` drives the compiled core: when the scan matches `a.md → b.md` and the rename's own event arrives late, the event is dropped and the document stays bound to `b.md` (handed over, it would unbind it, #979 item 2), while a rename made after the listing read the file is handed over and moves the binding.

Two ported tests assert the core's rule instead of the old one:

- "keeps the binding of a document edited while the app was closed whose file it moves" (`scan-race.test.ts`): the core's scan records the offline edit in `seen` and the outbox before the rename arrives. The engine kept `seen` at the old content because its scan read the file after the event. What it pushes is the same.
- "follows a rename chain and keeps the binding when the commit is acknowledged": the acknowledgement needs a push. The rename chain is ported without it.

### 3.5 Remote revisions and push results (`RemoteEvents.dfy`, #949)

**Remote revisions.** A remote revision delivered outside a sync round is recorded, not yet applied. If it is newer than everything the device knows of its document (its position is past the `ahead`, or else the `base`), it becomes the document's `ahead`. It is blocked by `LocalChanges` when the journal has a change of the document the server lacks (an outbox, or a user's delete), and is otherwise postponed until the sync round applies it with the path-conflict function (#982, #962). An older revision changes nothing.

**Push results.** A result answers a document's sealed outbox, the commit in flight. A result for a document with no commit in flight changes nothing.

- **Accepted:** the revision becomes the document's `base`, unless the base is already newer (its position is past the revision's), and an `ahead` no newer than the base is dropped. The base can be newer only when a round applied another device's revision built on the commit while it was in flight (§3.9): the document's history is a line, so that revision descends from the accepted one, and moving the base back would make the device send what it already has on a parent the server no longer accepts. The outbox goes, unless the document as the device last saw it differs from the base. In that case a new outbox on top of the base carries the change: the bound file's name and `seen`, or a tombstone for a user's delete. `CoreInv` forces both (§3.2); `AcceptKeepsLaterChange` and `AcceptKeepsUserDelete` state them of the base the accept leaves (`AcceptedBase`, #1023), and `AcceptAfterRoundKeepsNewerBase` is the witness of a base the round moved past the commit.
- **Head moved, already exists, unavailable:** the outbox is unsealed and carries the document as the device last saw it (`OutboxCurrent`), to be sent again. It is sent on the row's base: when a round made another device's revision the base while the commit was in flight (§3.9), the reopened outbox's parent is that revision, not the refused commit's (`ReopenOnBase`, #1023). "Unavailable" answers every commit in flight.
- **Invalid argument:** the same, and the outbox is marked `rejected` until a local change clears it (`SPEC.md` §6.2).

None of these requests a disk effect, only `PersistJournal`, and none changes a binding.

**`ServerInv`.** The proofs need more of the server than `StateInvariants`:

- no device has read past the feed;
- history and purges name only revisions the server holds;
- every accepted revision is in the history, or in a file on some device, or purged and no head.

The last clause is `G1_Retained` without its "content of some live head" way out. That way out does not survive a later accept of that head's document: the head's content then lives on only as an old revision, which does not make the other version retrievable. Every reachable state must satisfy `ServerInv`: the initial state does, the steps here and local events keep it (they change neither the server nor a disk), and #950 (restore, purge) and #966 (whole runs) must keep it. A restore from backup keeps its retention clauses (`ServerRetains`), whose excuse for what the restore removed is `lost`, but not its cursor clause (`CursorsOnFeed`) for a device whose cursor is past the restored feed, which holds again once that device resynced (§4.1).

The theorems `RemoteRevisionSafe`, `RefusedSafe` and `AcceptSafe` prove that from any state satisfying `StateInvariants`, `CoreInv` and `ServerInv`, the step keeps all three and satisfies `StepGuarantees` (with `ServerFollowsEvent`). The lemma `QuietStep` proves this for any step that leaves the server and the disks as they are and changes rows only by recording a waiting revision or reopening an outbox. The sync round, which applies pulled revisions to disk and sends commits, is #982.

The server (`internal/store/revisions.go`) inserts such a document as deleted. Nothing is lost: the tombstone's content stays in history (G1). Each of `ServerFollowsEvent`'s accept, delivery and purge conditions has a rejection lemma in `Witnesses.dfy` (§2.4), so a clause dropped from it fails `make verify`.

### 3.7 The mirror invariant behind G9 (`RemoteEvents.dfy`, #992)

G9 compares two devices, but each device syncs only with the server. The core therefore keeps a property of one device at a time: **a finished device's in-scope files mirror the server's live heads** (`MirrorInv`). For every device that has finished syncing (`FinishedSyncing`, §2.4):

- every file on its disk that is not out of its scope holds the content of a live head whose path is the file's name, folders compared on the device's system (`SameNameModuloFolders`), or is the older file of a document whose head the device cannot hold (`KeepsUnheld`, below) (`FilesMirrorHeads`);
- every live head is on the device: a file whose name is the head's path, folders compared on the device's system, holds its content, or that path is out of the device's scope, or the device reports that it cannot hold it (`ReportedCannotHold`, G9's exceptions) (`HeadsMirrored`).

**A file the device cannot update stays as it was (#1063).** When a document's newer revision is one the device cannot hold (SPEC.md §8 "Download cap": deferred `too-large`, nothing downloaded, and the cursor moves on; likewise a name its system does not allow, or a settings file it does not sync), the device keeps the file it has of that document. `KeepsUnheld(state, device, p)`: `p` is bound to a document whose waiting revision (its `ahead`) has a blocker that means the device cannot hold it (`CannotHold`) and is the server's head of that document. Such a file is G9's exception for a file the device cannot hold: the newer version stays on the server and is reported on the device (`ReportedCannotHold`, which the other device's `HeadsMirrored` check meets through the server), and `G9Agrees` accepts the kept file on the device that keeps it. Deleting the file instead would remove a version the user has, and treating the device as unfinished would break G10. Decision under §10.3 steps 1 and 2 (Obsidian Sync leaves a file it does not download as it was; keeping it loses nothing), logged on #52. Witnesses: `TooLargeAheadKeepsOldFile`, `TooLargeStateInvariants` (#1031's trace, now mirroring the cut at its cursor) and `TooLargeKeptFileAgrees` (G9 between the device and one that downloaded the revision).

The lemma `MirrorG9` proves that the invariant implies G9 between any two finished devices: a file in scope on the first mirrors a live head at its name, which the second holds under the head's path (each compared on its own device's system), does not sync, or reports it cannot hold. That is G9's agreement through the server (`G9Agrees`, below), so no path axiom is needed: both comparisons are oriented from a device's name to the head's path on one platform, so neither symmetry nor transitivity of `SameNameModuloFolders` is used. `MirrorImpliesG9` lifts this to the whole state. Removing any conjunct of the invariant (either clause, a head's path or content, the head being live) makes `MirrorG9` fail to verify.

The initial state satisfies it (`InitialMirror`): the server has no head and every disk is empty. No transition proved so far makes a device finish: a device finished after a local event, the scan, a remote revision or a push result is exactly as it was before, on the same server (`KeepsFinished`, which `LocalEventSafe`, `ScanSafe`, `RemoteRevisionSafe`, `RefusedSafe` and `AcceptSafe` now also prove; an accept grows the feed, so no device is finished after it). `KeepsFinishedKeepsMirror` turns that into the invariant's preservation, and `LocalEventKeepsMirror`, `ScanKeepsMirror`, `RemoteRevisionKeepsMirror`, `RefusedKeepsMirror` and `AcceptKeepsMirror` state it for each step, from the same hypotheses as their theorems, with `CoreInv` as #984 left it. The sync round is the step that finishes a device: it is assumed to keep `MirrorInv` until #982 proves that it does. Steps the core does not handle (a user's action, a crash, a restart, a restore, a purge, a restore from history) are #950's and #966's.

**Folder spellings compare through the server (#995).** INV-9 lets each device keep its own spelling of a folder: when a pulled file lands in a folder the device already has, its filesystem keeps that folder's spelling, and renaming the folder would rename the user's other files. Each device's spelling is then one folder with the server's on that device's system, but two devices' spellings need not be one folder on either system. With the engine's own `filesystemKey`, a server folder `U+0345 U+0300` is one folder with `U+0399 U+0300` on Windows (case folding) and with `U+0300 U+0345` on macOS (NFD reorders the marks), and those two device spellings are one folder on neither platform. So no path axiom can compose the two comparisons, and a G9 that compared the two devices' names only could fail between two finished devices through no step of the engine. The owner chose to compare each device with the server instead (option A on #995). `G9Agrees` (`Guarantees.dfy`) accepts a file `p` on one device against another device in three ways: the other holds a file with the same content whose name is `p` modulo folders on either device's system (the direct comparison, as before); or it reports that it cannot hold `p`; or, through the server, `p` is the path of a live head with `p`'s content, modulo folders on the first device's system, and the other device holds that head under its path modulo folders on its own system, or does not sync that path, or reports that it cannot hold it. In the last clause G9's exceptions are read on the server's path, the name both devices are compared with. File names, the final segment, still compare exactly (below). The witness `RespelledFoldersAgree` (`RemoteEvents.dfy`) shows two finished devices on different systems in that situation keeping `MirrorInv` and G9 through the server clause alone. `G9Rejects` (`Witnesses.dfy`) shows that a device holding other content does not agree, through the server either, with a file that is the server's head.

**A file's own name is the server's.** A finished device's file names are its bound documents' paths, the final segment exactly and folders under `F`: `InStep` (§2.4) requires a bound file's name to be its base's path modulo folders. So a user's case-only rename of a file (`a.md` to `A.md` where the platform folds case) leaves the device unfinished until the rename is pushed, as `SPEC.md` §8 treats it as a rename. Without that, the device would stay finished under `F` while G9 compares the final segment exactly, and the user's step would break G9 against a device that still holds `a.md`. A folder-only respelling keeps the device finished (INV-9). The witness `CaseOnlyRenameUnfinishes` (`Witnesses.dfy`) shows that the state after such a rename on one of two finished devices keeps `StateInvariants`.

### 3.8 The sync round's push half (`Push.dfy`, #991)

The push half of the sync round creates the documents of new files and sends every outbox waiting to be sent (`OnPush`). It is a function of the device's platform and journal, the round's input (`RoundInput`, §2.3) and the revision ids of §3.1. The step theorem of the whole round, which composes it with the pull apply (#990), is #982's.

- **New documents.** Every file of the round's listing that no document is bound to under `F` is untracked (§3.3). Each gets a new document, bound to it, with no base and an outbox that creates it: the file's name, content and kind, no parent. Its id is the next of the round's fresh document ids (`freshDocs`), and its outbox's id the one §3.1 supplies. Files left over when the ids run out wait for the next round's ids.
- **Sealing and sending.** Every outbox not in flight and not rejected (a rejected one waits for a local change, `SPEC.md` §6.2) is sealed: it becomes the commit in flight, which a local change no longer edits (`Send`, §3.3) and a push result answers (§3.5). The effects are `PersistJournal` of the new journal first, then one `Commit` per outbox sealed, carrying it as persisted.
- **Order.** Effects are a sequence and ids are handed out in order, but paths and document ids are abstract. So that the core is a function of its input, it takes untracked files and commits in a fixed order: `PathBefore` and `DocBefore`, abstract functions assumed to be strict total orders (`PathOrder`, `DocOrder`, axioms). Every type has one; the compiled core will use string comparison.

`PushCreatesFromFreshIds` proves that every new document's id is one of the round's fresh ids, that it is bound to an untracked listed file and carries it in its sealed outbox, that every other row changes only by being sealed, and that every row keeps the row invariant (`RowInv`: `AheadOfBase` and `OutboxCurrent` included). `RoundCreatesFreshDocuments` adds that with the round's input (`RoundInputOf`) the ids are used by no device and not by the server, and `PushKeepsCoreInv` that `CoreInv` is kept. `PushCommitsSealedPersisted` proves #977's obligation (§3.2): every commit the push requests sends a sealed outbox, and an earlier `PersistJournal` effect holds that outbox as the document's (`CommitsPersistedFirst`). That it is kept until the answer is §3.5's: no transition so far edits a sealed outbox.

The listing names every file on the disk, out-of-scope settings files included. The round's input names the out-of-scope paths (`outOfScope`, §2.3), and an untracked file at one of them gets no document: #982 proves it.

### 3.9 The sync round's pull apply (`Apply.dfy`, #990)

The pull apply decides, for one pulled revision of one document, the document's new row and the disk effects (`ApplyRevision`). It is a function of the device's platform, the document's row, the revision, the round's input (`RoundInput`, §2.3), the names every document is bound to (`bound`), and the revision id of §3.1. It decides from the round's listing and unsaved paths only. The step theorem of the whole round, which composes it with the push half (§3.8), is #982's.

- **Not newer** than what the row knows: nothing changes.
- **A revision identical to the file** (#1028, §4.1): a live revision at the bound name whose content and kind the listing reads there, with no unsaved text at the name. It is no conflict, whether both devices made the same change away from the base or nothing changed here. It becomes the base, nothing waits, nothing is left to send, `seen` becomes its content, and nothing on disk is written or copied (`IdenticalRow`, `IdenticalRevisionSettles`). `G6_Settle`'s first case holds because the document's `Outgoing` is that content. `IdenticalTraceSettles` is #1007's trace as a regression: base `b`, file and revision both `x != b`, of any kind and whatever `Merge3(b, x, x)` is, settle with no effect. Turning this settlement back into a hold, or into a concurrent change's settlement, makes `make verify` fail. Where the revision is also the outbox's own, this row is its acknowledgement too (nothing is left to send). A commit in flight against another device's identical revision stays as sealed (`KeptOutbox`, #1023) and is superseded, so the document keeps the file's content.
- **The outbox's own revision** (its id is the outbox's, sealed or not, §4.1): the outbox's acknowledgement, taken as §3.5's "accepted" on the revision (`AcceptOn`, which is `Accept` wherever the base is not past the revision, `AcknowledgedIsAccept`), whatever the listing reads or an editor holds. It becomes the base, nothing waits, nothing on disk changes, and a change made after the commit was sealed is sent on top of it (`AcceptKeepsLaterChange`). `AcknowledgementSettles` proves it, `RuleAcknowledges` that the path rule (§3.10) passes it through (#1007).
- **The document's file has unsaved text:** the revision waits as `ahead`, blocked by `LocalChanges`.
- **No change here** (the listing reads `seen`, which is the live base's content at the base's name, and nothing to send): a remote edit at the same name is written over the content read; a remote delete removes the file, conditional on that content, and the row is `Released`. A remote move waits (`PathHeld`) for the path rule (#962).
- **A concurrent change** (G6): a live remote edit that keeps the base's name, or any live revision of a file the user moved away from its base's name, against a bound file that reads other than the base or has an outbox (a commit in flight included, #1023). The base may be a tombstone (a file kept against a delete, below): the content is settled from the base the row has, a tombstone's content included, as `G6_Settle` states it. A file the user moved keeps its name: a local rename wins over a remote edit, move or earlier delete (`SPEC.md` §7), and the outbox sends the name on top of the remote (#1068). If the file reads as the base and as `seen`, the remote is written over it. If the remote's content is the base's, the local content stays. Two changed notes that `Merge` combines are merged, written over the content read. Otherwise the content read is saved as an untracked copy at the name the path-conflict function picks, and the remote is written over it. The settled row's base is the remote, `seen` is what the file now holds, and it has an outbox (with the local name and that content) only where the file differs from the base. A file that reads as the base but not as `seen` (changed back before its event arrived) is saved as a copy too: G2 lets the round overwrite only content it keeps (`ReadKept`). A user's delete against a remote revision is settled below (#1021). A commit in flight is settled like any concurrent change, from the content the round read: the result is written to the file, the remote becomes the base and the sealed outbox stays as it is until its answer (§3.2). It is then superseded (`Superseded`, §2.4), so the document keeps its file's content. Its answer either reopens it on the new base ("head moved", when the remote is not built on it) or drops it and keeps the base ("accepted", when the remote was committed on top of it) (§3.5). The pulled revision is not one the commit is built on (`NotBuiltOn`, which `ApplyStep` assumes and #982 proves of the round, as `PulledBy`). `CommitInFlightSettles` proves the settlement (`KeptOutbox` keeps the commit in every settled row), and `CommitInFlightNeverWaitsForAnswer` that a commit in flight never makes another device's revision wait for its answer: against a remote edit, move or delete of a bound file at its base's name, or a live revision against the user's delete or a missing file, the apply settles it, hands a name to the path rule, or waits because the device cannot hold it. `RuleKeepsCommitInFlight` proves the sealed outbox survives the rule too. Turning this settlement back into a hold (a sealed outbox excluded from `Concurrent`), or dropping the commit from the settled row, makes `make verify` fail.
- **A remote delete against a change the server lacks** (#1020): a tombstone against a bound file that the listing reads, with no unsaved text, not the outbox's own tombstone (its acknowledgement, above), and something to send or a read other than `seen` and the document's kind. An edit beats a delete (`SPEC.md` §6.3): nothing touches the disk, the tombstone becomes the base, `seen` becomes the content read, and the outbox (its own id, or the round's fresh one) sends the file as read on top of the tombstone, live and unsealed (`KeptAgainstDelete`, `RemoteDeleteKeepsEditedFile`). `G6_Settle`'s delete clause holds because the document's `Outgoing` is that content. Turning this settlement back into a hold, dropping its outbox, or leaving `seen` as it was makes `make verify` fail. A commit in flight against a remote delete is settled the same way, with the sealed outbox kept as it is instead of a new one (#1023): its answer reopens it on the tombstone or opens a new outbox on top of it. A bound file missing from the listing is a document with no file here (below).
- **A remote move against a local change** (#1022): a live revision at another name than the base's (live or a tombstone), against a bound file still at the base's name with a change the server lacks (an outbox, a commit in flight included, or a read other than the base; `MovedAgainstChange`). Path and content are merged apart (`SPEC.md` §7): the apply leaves it `PathHeld` and the path rule (§3.10) moves the file to the remote's name, with the content settled as `Settle` settles an edit (`MovedContent`, which `MovedContentSettlesAsG6` states as `G6_Settle`'s cases). A side that left the content as it was takes the other's, and two changed notes that `Merge` combines are merged. The file is written over in place, conditional on the content read, and then moved to the name. The row is `Settled` at the remote's name: an outbox only where the file differs from the revision. Otherwise (no merge) the file read here stays as the untracked copy of the local version, moved aside with the rest of the way where it collides with the name. The head is created at its name, and the document has nothing to send: the push sends the copy as a new document. `RuleSettlesMoveAgainstChange` proves `ApplySettlesContract`'s clause on the row after the rule: the revision waits only where the device cannot hold it or unsaved text collides with its name, and where nothing else is in the way and the content settles, it is settled. Turning this settlement back into a hold makes `make verify` fail. A commit in flight is settled the same way and stays as sealed in the rule's row (#1023). A local rename against a remote move is a concurrent change (above): the user's name stays. A bound file with no base (a document this device created and has not had acknowledged) has no common base with another device's revision of it: both versions are kept (`SPEC.md` §7), the file here stays as an untracked file that the push sends as a new document, and the head is created at its name as for a document with no file here (#1068).
- **The user's delete, or a bound file missing from the listing, against a live remote revision** (#1021): a live revision, newer than the row, not the outbox's own (its acknowledgement, above), against a document the user deleted (no binding, `UserDeleted`) or one whose bound file the listing does not read and no editor holds unsaved text at. The round records a missing file as the user's delete (`G3_DeleteSeen` allows it: no file is at the name), and an edit beats a delete (`SPEC.md` §6.3): the delete is dropped, and the document is decided as one with no file here, below (`Revives`, `Revived`, `RevivedApplies`). So the file comes back at the revision's name, created, adopted or with one untracked file moved aside, or through the path rule (§3.10) where the name is bound (the missing file's own name included) or held otherwise. `G6_Settle`'s clause "a local delete against a remote edit: the file comes back" holds because the document's `Outgoing` is the file at the name, holding the revision's content. `RuleRevivesDeletedFile` proves `ApplySettlesContract`'s clause on the row after the rule: the file is bound at the revision's name with its content, the revision is the base and nothing is sent, unless the revision waits because the device cannot hold it (`CannotHold`) or unsaved text collides with its name; and where nothing is in the way it comes back. A missing bound file whose name an open editor holds unsaved text at keeps its binding and waits (`UnsavedMissingFileWaits`), and a commit in flight keeps its sealed outbox while the file comes back (`CommitInFlightRevived`, #1023). Turning this settlement back into a hold, dropping the unsaved-text guard or the commit in flight, keeping the dropped delete's outbox (in the apply or in the rule's row), or letting the rule defer a missing bound file again makes `make verify` fail.
- **A document with no file here** (no binding, or a bound file the listing does not read with no unsaved text at its name, which the round records as the user's delete): a tombstone is a delete both sides agree on. It is recorded as the base, nothing is bound, and nothing is left to send but a commit in flight, which stays as sealed and whose answer reopens it on the tombstone as the user's delete (`Reopen`). An unsent change of the missing file, or the user's unsent delete, is dropped, as `Revived` drops one (#1068). An unsent live commit of a document with no file here that the user did not delete (a commit in flight a revived document kept, reopened before its file came back) is not the user's current change either: it is dropped against any newer revision, and a live one comes as below (#1068). A live revision is created at its name, conditional on no file, where the listing has no colliding file and no document is bound to the name. Where the only colliding file is an untracked file at exactly that name, holding the revision's content and kind, the document adopts it (design §4.5 step 3, `G5_NeverMixedUp` (d)): it becomes the document's file and nothing on disk changes (`AdoptsIdenticalFile`, #962). Where exactly one other untracked file collides, the path-conflict function names where it moves, and the move comes first. Any other collision waits (`PathHeld`, #962).

**The path-conflict function** (`PathConflictCopy`, #1004) is the only place a name collision or a conflict copy's name is decided. It returns an `Option`. Its contract is its postcondition, a name that is free under both keys. Under F, no listed file collides with it, it is no name to avoid (every bound name and every unsaved path), and it collides with neither the wanted name nor its folders. Under K, it collides with no other document's server claim (`ClaimsOf`: live `base` and `ahead` paths, folders included) and is no other document's live outbox path, which holds a name only (PO-14). The core does not spell names, because `Path` is abstract. It gets candidates from `CopyCandidate(p, folder, n)`, a contract-only shell function like `Merge`. The shell fixes the device and the date for the round, and `SPEC.md` §7's format is the shell's job (`copyCandidate` in `plugin/src/core/merge/conflict-name.ts`, proven by its tests). The core checks every candidate for freedom itself (`CopyFree`), so no axiom on F, K or `Path` is added. It picks the folder that takes the suffix as the outermost folder of the held file's path that a claim, a listed file or the wanted name is named like (#359). It then tries counters 1 to `CopyAttempts` (100), stopping early when the shell has no name that fits, and returns the first free candidate. `PathConflictCopyNone` proves that it returns no name exactly when no candidate it tried is free. The round then writes nothing: the revision waits as `ahead`, blocked by `Unmaterializable(alias := false)`, the local version stays, and the conflict is reported without a copy (`NoCopy`, `SPEC.md` §7 #100; `NoCopyDefers`, and `NoNameNoCopy` and `NoNameNoMove` for its two callers). `Merge` is the shell's line-level merge, stated as `Merge3` (§2.4), contract only.

The lemmas, on the function:

- `AppliedPreconditionsHold`: every disk effect's precondition holds on the disk the listing was read from, the second effect of a path conflict on the disk the first leaves (`PreconditionsInOrder`).
- `AppliedTakesEffect`: on that disk, with one file per name, the effects keep one file per name, the new binding names a file holding its `seen` (an overwrite keeps the file in place), a remote delete leaves no file at the old name, a moved or copied file holds its contents at its new name, and every file no effect removes or moves stays with its identity.

Removing any precondition check of the function (the free-name test, the unsaved checks, the bound-name checks, the read-equals-`seen` test) or weakening the path-conflict function's contract makes `make verify` fail. So does removing any F or K check from `CopyFree`, or deferring a revision without a copy name under another blocker or without its report.
- On a round step whose effects are the apply's (`ApplyStep`: the input is `RoundInputOf` the state before, any claims (they only steer which copy name is picked, so the path rule's step, which passes every row's claims, is one too), the revision is one the server accepted, another device's or, exactly where it is the outbox's acknowledgement, the device's own (`PulledBy`), and the state after is the effects' disk and the new row): `AppliedG2` (`G2_OnlyWhatItSaw`, with the read content kept by a merge or a copy, `G2_UnsavedSafe`, `G2_NoUntrackedDelete`), `AppliedG5` (`G5_NeverMixedUp`, through clause (b): a file arrives only at a name no other document is bound to, or clause (d) where the document adopts an untracked file), `AppliedG6` (`G6_Settle` for every change the step settles) `AppliedG7` (`G7_OneFilePerName`, `G7_MoveKeepsContents`), and `AppliedKeepsOtherFiles`: every other document's bound file is the same file after the apply, since only the document's own file is removed and only an untracked file is moved aside.
- `AppliedKeepsRowInv` (#982): from a row that keeps `RowInv` (`CoreInv` one row at a time, §3.2), the row the function returns keeps it, whatever it decides. A user's delete is still sent or already the base, a bound file that differs from the new base has an outbox (`AheadOfBase`), and an unsealed outbox carries the file as last seen (`OutboxCurrent`). `SettleKeepsRowInv` proves it for a settled change. Dropping the settled row's outbox even where the file differs from the remote (`if true then row.(outbox := None)` in `Settled`), or giving that outbox the remote's content instead of the file's, makes `make verify` fail.

Left to #982: the step over every pulled revision and the push half; that a pulled revision is the device's own exactly where it is its outbox's (an own revision the device already acknowledged is not newer, `OwnRevisionsAcknowledged`), which `ApplyStep` assumes (`PulledBy`); and `G10_SettledOrReported`, which the revisions this function leaves waiting with `PathHeld` or `LocalChanges` (a remote move, a held name) must meet once #962's path rule settles them.

### 3.10 The path-conflict rule (`PathRule.dfy`, #962)

One rule decides every name collision a pulled revision meets (`PathRule`). It runs on the journal's rows, the round's input and the revision ids of §3.1, and it is the pull apply (§3.9) wherever the apply settles the revision. Where the apply leaves the revision waiting for its name (`PathHeld`: a remote move of a clean file or against a local change (#1022), a name another document is bound to, several colliding files, or unsaved text at the name), the rule decides instead:

> **The server's head takes its name. Every file in its way on this device moves aside with its contents, to a name the copy-name function picks. A document whose file moves aside keeps it under its own id when a local change put it there, and otherwise lets the file go as an untracked copy. Nothing moves where unsaved text is in the way.**

"In its way" is every listed file that collides with the name under F (§3.2: the name itself, a folder of it, or a file under it), other than the document's own file, which moves to the name itself. The rule moves nothing, and the revision waits, in three cases. Where an open editor's unsaved text collides with the name, it waits as `PathHeld`, which `UserMustAct` reports. Where another document's newest server claim (its live `ahead`, else its live base) still collides with the name under K, or is the same file under F, it waits as `Unmaterializable(alias := true)`. Where no copy name is free, or unsaved text collides with a file that would move but not with the name, it waits as `Unmaterializable(alias := false)`. Each wait is reported.

- **Several files in the way** each get a copy name, chosen one after another against the listing with the earlier copies in it (`Aside`), so no two copies collide.
- **A document in the way** keeps its file under its own id when a local change put it there (`LocallyPlaced`: no live base at that name, or an outbox). This is rule W(a): its binding follows the file, and its outbox sends the new name, opened with the document's revision id if it had none. A commit in flight stays as sealed, and `AcceptKeepsLaterChange` (§3.5) sends the move after it. Any other document lets its file go (rule W(b)): the binding is released and an unsealed outbox is dropped, because the file's contents are the untracked copy, which the push sends as a new document (§3.8).
- **A document bound in the way whose file is missing** (no listed file at its name: the user removed or moved the file, and the local event has not reached the core yet) has nothing to move. It records the user's delete (`MissingInTheWay`, `RecordMissing`, with the local delete's `Unbind`), as rule W's `displace` and `detach` intents do for a file gone from both names (engine-path-ownership.md §4.4: "user deleted it"). `G3_DeleteSeen` allows it, since no file is at the binding's name before the step. Otherwise its binding would name the head's file after the step, which `G5_NeverMixedUp` forbids (#1032). The round records the delete even where exactly one untracked listed file holds the binding's `seen`, of its kind (#1061): it does not apply the start-up scan's one-to-one content match (E7, §3.3). A content match transfers identity only in the start-up scan (engine-path-ownership.md INV-3, PO-3), which replaces events a crash or a closed app lost; in a running app the user's rename event is still on its way. That event then finds no document bound to the old name, so the moved file stays untracked and the push sends it as a new document. No bytes are lost (the file is pushed, and the old document's history stays on the server as its tombstone's predecessors), but the moved file's history does not carry over. This is `displace`'s "gone from both" outcome, not E7's, and a deviation from what E7 would give after a restart; it is decided under §10.3 step 3 (no data at stake; simplest, and no new identity rule) and logged on #52.
- **The document's own clean file** is written over in place where the content changed, while the binding still names it (`G2_OnlyWhatItSaw` judges a write against the binding before the step), and then moves to the name. Where its name is a folder of the new name or lies under it, so that no move can take it there, it is removed (the server has its content) and the head is created.
- **The document's own file under a remote move against a local change** (#1022, §3.9): it arrives as the clean file does, with the settled content in place of the head's, written over conditional on the content the round read (`ArrivingRow`, `Arriving`). `G2_OnlyWhatItSaw` allows that because the settled row keeps the read: it is the file's content, or the merge of it. Where the two versions are kept apart (`Keeps` is `None`), the file is not the document's any more: it stays, untracked, or moves aside as a file in the way, and the head is created at its name.
- **The copy-name function** (#1004) is called with every document's claims, the applied document's included (`AllClaims`), because `CopiesTakeFreeNames` (§4) checks a copy against every row of the journal before the step.

The pull apply moves an untracked file aside only where no unsaved text collides with that file under F (`UnsavedCollides`, #1003), not just where none is at the revision's name. A revision creating `a/b.md` while an untracked `a` has unsaved text therefore moves nothing.

The lemmas, on the function:

- `RuleNoMoveFromUnsaved` (`NoMoveFromUnsaved`): no effect moves a file that collides under F with a path an open editor holds unsaved text at.
- `RuleCopiesTakeFreeNames` (`CopiesTakeFreeNames`): every copy the rule writes collides under F with nothing listed, bound or unsaved, and under K with no document's server claim.
- `RuleHeldOnlyForUnsaved` (the `PathHeld` clause of `PathRuleContract`): the rule leaves the revision `PathHeld` only where unsaved text collides with its name, so `UserMustAct` holds, and it changes no other document's `ahead`.
- `RulePreconditionsHold`: every disk effect's precondition holds, in order, on the disk the listing was read from. Each move finds its file and a free name, because each copy name was picked against the listing with the earlier copies in it (`AsideInOrder`). The head then finds its name free, or its own file there (`ArriveInOrder`).
- `RuleOneFilePerName` (G7's device half): from a disk with one file per name, the rule step's disk keeps one file per name. Every effect keeps it (`EffectKeepsOneFilePerName`), because a create or a move lands only where no other file collides.
- `ClearWayUnsavedSafe` (`G2_UnsavedSafe` for the rule's own effects): no write or remove names a path an open editor holds unsaved text at.
- `ClearWayOnlyWhatItSaw` (`G2_OnlyWhatItSaw` and `G2_NoUntrackedDelete` for the rule's own effects): the only overwrite and the only remove name the document's own bound file, conditional on its `seen`.
- `RuleKeepsRowInv`: from rows that keep `RowInv`, every row the rule returns keeps it. A document that keeps its moved file has an outbox carrying the new name and `seen`, and a released one has no binding.

On a round step whose effects are the rule's (`RuleStep`: the input is `RoundInputOf` the state before, and the state after has the rule's rows and the disk the effects left), `RuleMeetsContract` proves `PathRuleContract` (§4). It assumes that every row already waiting for a name before the step waits for unsaved text in its way. That is the state each earlier application of the rule in the round leaves, and #982 re-applies a revision stored outside the round (`Waiting`, §3.5) before relying on it.

A document whose file comes back (`Revives`, §3.9) enters the rule as its revived row: it has no file of its own in the way, and the head arrives with no outbox. The rule runs only on a revision newer than its row (`HeldForName`). A revision the row already holds as `ahead` leaves the row as it is.

Where the apply leaves nothing waiting for a name, the rule's step is the pull apply's step (`ApplyStep`, with every binding's name and every row's claims), so `RulePassThroughGuarantees` carries §3.9's guarantees over to it: G2's step predicates, `G5_NeverMixedUp`, `G6_Settle` and G7. Where the rule clears the way, G2 for its own effects and one file per name are proven above, and `ClearWayG5G7` (#1032) proves `G5_NeverMixedUp` and `G7_MoveKeepsContents` from a disk with one file per name and `G5_NeverJoined` before the step. It rests on the disk after the whole sequence of moves (`ClearWayDisk`): each copy holds the file it moved, with its contents and identity (`MovesTake`), the head is at its name with its content (`ArriveTakes`), every file neither in the way nor the document's own is the same file, and nothing else is on disk. So every move arrives with its contents (`ClearG7`). A document whose bound file changes is the one the head arrives for, or one W(a) moved under its own id (`MoveEffectsMover`), both clause (b); one that lets its file go, or whose file is missing in the way, is bound to nothing; and every other binding names the same file or none, because a copy takes no bound name and no other document is bound to the head's name after the step (`ClearG5Doc`). These hold for a revived document too (#1021): its head row is `Revived` with the head's binding (`HeadRow`), and with no file of its own listed the head is written at its name, so its own missing binding names no file in the step. Where the rule defers, it changes no binding and nothing on disk. Dropping `RecordMissing`, moving a W(a) document's file under no document's id, or requesting the head's arrival before the moves makes `make verify` fail.

Removing the unsaved check on a file in the way, on the document's own file or in the pull apply's move, or computing the copy's claims without the applied document's own, makes `make verify` fail. So does leaving a moved document's unsealed outbox at its old name, picking each copy name against the listing alone (without the earlier copies), or moving the document's own file onto a name that is a folder of it, or under it.

Dafny 4.11's resolver crashes on a module that refines one whose lemma bodies hold a statement `var x :| P(x)` in which `P` calls a function (its precedence linter meets an unresolved call). `Apply.dfy` writes each such statement as the expression `var x := var x :| P(x); x;`, which proves the same, so `PathRuleCore` refines `ApplyCore`. `ApplyCore` refines `StepContracts` (§4), so the core's lemmas can state the contracts directly.

### 3.11 The server's history events (`ServerEvents.dfy`, #950)

A restore from backup, a retention purge and a restore from history are the server's steps, not the core's: they change no device and request no effect (`ServerEventStep`). `ServerEventDevicePredicates` proves every step predicate except G1's for any such step. One lemma per event proves `CoreReachable` after it and `StepGuarantees` of it:

- `PurgeKeepsAll`: a purge changes only the purge marks (`SameButPurges`), so no head, feed, history, cut head or device's divergence changes. A version leaves the history only by being purged, and a purge never removes a head. A cut of the purged server, with its purge marks narrowed to the earlier ones, is a cut of the server before.
- `RestoreKeepsAll`: the restored server is a cut of the server before, and a cut of it is one too (`CutOfCut`, through `KeepKeep`). A device the restore leaves undiverged was undiverged before (`RestoreUndiverged`), so its claims, its acknowledgements and `MirrorAtCursor` carry over. `MirrorInv` follows from `MirrorAtCursor` before the restore, at the restored feed's length. `RestoreRetains`: a version the restore removes is `lost`, and a purged version it keeps but no longer marks is back in its document's history (`HistoryFollowsFeed`). `RestoreHistoryFollowsFeed`: `Keep` keeps the feed order (`KeepOrder`).
- `RestoreFromHistoryKeepsAll`: an `Appendable` append of an id no journal names, so no device's divergence changes (`AppendSameDivergence`). No device is finished after it, because an undiverged cursor is on the shorter feed. A cut short of the new entry is a cut of the server before. The cut at the whole feed has the appended server's heads, which `Appendable` keeps apart (`AppendCuts`).

`ServerEventsKeepAll` combines the three and proves `ServerEventContract` for every step (#1063). The clauses it needed are now in `ClaimsReachable`: `FeedAccepted` and `RevisionsKeyed` (§4.1), which every server step keeps (`ServerClausesKept`). Its cursor clause is `KeepsCursors`, proved by `ServerEventKeepsCursors` for a purge and a restore from history.

### 3.12 The cursor's claims imply the mirror (`ClaimsMirror.dfy`, #1031, #1063)

`ClaimsImplyMirror` proves `ClaimsImplyMirrorContract`: every `ClaimsReachable` state satisfies `MirrorAtCursor`. `ClaimIsCutHead` carries the argument. For a device finished against a cut at its cursor, the newest claim of each document it knows (its ahead, or else its base) is the cut's head of that document. The claim's revision is in the cut (`JournalOnServer`), so it sits at a feed index below the cursor (`FeedPositioned`) and in its document's history (`HistoryFollowsFeed`); `ClaimOnCut` proves this. The cut's head is the last entry of that history the cut keeps, and the claim is that head or older; `CutHeadIsNewestKept` proves this from the server and the cut alone, so its order argument is checked without the reachable state's clauses in scope. The device read it, so its claim is at least as new (`ClaimsCoverCursor`), and since positions grow along a history (`KeepOrder`), the claim is that head. `MirrorAtCut` then gets each clause:
- A file in scope is bound to a live base (`InStep`). It is either the head (`FilesMirrorHeads`' first case) or, under a `CannotHold` ahead, a file kept under a head the device cannot hold (`KeepsUnheld`).
- A live head is either a `CannotHold` ahead (`ReportedCannotHold`) or the base. A base is bound, since `InStep` excuses only a `CannotHold` ahead. It is at the binding's spelling with the binding's content, because a finished device has no outbox (`CoreInv`'s `AheadOfBase`). The bound file is out of scope (`ScopesClosedUnderF`) or the one `InStep` binds, and no other document is bound to it (`G5_NeverJoined`).

### 3.13 The merged steps keep the claims invariants (`MergedClaims.dfy`, #1031)

Each merged step goes from `ClaimsReachable` to `ClaimsReachable` and satisfies `StepGuarantees`: `LocalKeepsClaims`, `ScanKeepsClaims`, `RefusedKeepsClaims`, `RemoteKeepsClaims` and `AcceptKeepsClaims`. With `ClaimsImplyMirror` (§3.12), the post state is then `CoreReachable`. The two are composed outside a module, because Dafny 4.11's resolver crashes on a module that refines `ClaimsMirror` or `ServerEvents`. For that reason `MergedClaims` repeats the append helpers it needs from `ServerEvents.dfy`.
- A local event, the scan and a refused push keep every row's base, ahead and outbox id (`KeepsRowNames`), so they change no device's divergence, claim or acknowledgement (`NamesKeptStep`). `JournalStepKeepsClaims` covers any step that replaces one device's journal.
- A remote revision raises a row's newest claim only to a feed revision (`KnowsAtLeast`, `RowNamesAccepted`).
- An accept appends an id that no journal or anchor names (`JournalsNameAccepted`, `Appendable`), so no device starts to read the feed. `AppendKeepsServerClauses` keeps the server clauses, and the accepted row's base records the accepted revision or a newer one (`AcceptRowClaims`). The proof is split by clause (`AcceptShape`, `AcceptJournalsNamed`, `AcceptReadsFeed`, `AcceptCoversCursor`, `AcceptOwnAcknowledged`, `AcceptOwnDocsKnown`) so that it verifies on every solver seed.
- The remote and push lemmas of `RemoteEvents.dfy` now assume `ServerRetains` rather than `ServerInv`, because `CoreReachable` does not include `CursorsOnFeed`. They keep `CursorsOnFeed` where it held. The accept lemma assumes that no device one past the feed is anchored on the new id, which `CursorsOnFeed` or `JournalsNameAccepted` gives.

No lemma assumes anything beyond `ClaimsReachable` and the step's own event, except `RemoteKeepsClaims`. It assumes the device is not `Diverged`, which `ShellRun` gives, because a diverged device's pulled revision waits for its resync. `AcceptKeepsClaims` holds for every device, a diverged one included. Its own accepted push can switch its divergence off, but `ClaimsCoverCursor` and the acknowledgement clause bind every device that `ReadsFeed`, and no append switches `ReadsFeed` on (`AcceptReadsFeed`). A remote revision finds a row for every document that holds a revision of the device's own (`OwnDocsKnown`; `AcceptOwnDocsKnown` keeps it). §4.1 records both settlements (#1071).

### 3.14 The sync round's body (`PathRule.dfy`, #1033)

The round's handler is `OnRound`, and `RoundStepOf` (`Contracts.dfy`) is its step. They live at the end of `PathRule.dfy`, inside `PathRuleCore`, because Dafny 4.11's resolver crashes on a module that refines `PathRuleCore`. `OnRound` is a function of the device's platform and journal, the revisions the pull read (in feed order), the cursor and anchor after the pull, the round's input (§2.3) and the revision ids of §3.1. In that order, it:

1. **Pulls.** The first effect is `Pull` from the journal's cursor. The round starts from the journal with no open intent, because the restart's recovery settles open intents first (§4.3).
2. **Retries the waiting rows.** Every row with an `ahead` is taken in `DocsInOrder`. The round clears the `ahead`, so its revision is newer again, and settles it as a pulled revision (`ApplySettlesContract`, #1071).
3. **Settles each pulled revision.** A revision at an out-of-scope path waits as `OutOfScope` (§2.3, a `CannotHold` blocker). Any other revision goes through the path rule (§3.10), which is the pull apply wherever no name is held. The rule runs against the listing as the round's earlier effects left the disk (`ListingAfter`). The round reads no disk between revisions, so a second revision's reads, its preconditions and the push's untracked files all see the first revision's writes and moves. A document the journal does not know yet starts from an empty row (`NoRow`). Such a row has no revision id in §3.1's map, which covers the journal before the round, so the revision's own id stands in for it (`RevsFor`). The rule opens no outbox on a row with no binding and no base. Each revision's disk effects come after a `PersistJournal` whose intents cover them (`IntentsFor`, which takes intent ids from the shell's `IntentIdOf`).
4. **Moves the cursor** past the feed it read, and sets the anchor (ghost) to the feed's last entry it read.
5. **Pushes** (§3.8) against the in-scope part of the listing (`InScope`), so an untracked file at an out-of-scope path gets no document. The push's `PersistJournal` is the round's last one, with no open intent, and its commits follow it.

`RoundStepOf` reads the revisions from the feed after the cursor (`Revisions`). The post disk is one that the effects leave (`DiskAfter`, `DisksFollowEffects`), and the server is unchanged.

The lemmas (`RoundStepEffects`, from `OnRoundEffects` and `OnRoundHeld`) cover these clauses of `RoundContract`:

- the cursor ends at the feed's end;
- `CommitsPersistedFirst` and `IntentsCoverDiskEffects`, by an invariant on the round's passes (`Guarded`): every disk effect so far follows a persisted intent that covers it, nothing is committed before the push, and the journal carries no open intent. The apply's and the rule's effects are disk effects and reports only (`ApplyShaped`, `RuleShapedEffects`);
- `PathRuleContract`'s `NoMoveFromUnsaved` (from `RuleNoMoveFromUnsaved`, for each revision) and its last clause: after the round, a row is `PathHeld` only where unsaved text collides with the name, so `UserMustAct` (`HeldForUnsaved`, from `RuleHeldOnlyForUnsaved`; every row held before the round is retried);
- `PathRuleContract`'s `CopiesTakeFreeNames` (`RoundCopiesTakeFreeNames`, from `OnRoundCopies`). The contract states it against the round's first listing and the journal before the step, while a later revision's copy is named against the listing and rows the earlier revisions left. So the copy-name function also avoids the round's first claims: `RoundClaims` holds the first rows' server claims and, in the new `Claims.listed`, the first listing's files and bound names, which a copy must not collide with under `F`. `PathRule` takes them as `first` and the apply names its copies against `ApplyClaims`, the rows' claims plus `first`. A name an earlier revision of the round freed thus stays taken until the next round. Moves aside (`Aside`) still name against the current rows only: the contract is about copies the apply writes.

Not proven yet: `OwnRevisionsAcknowledged`. `KeepsAll` is #1034's, and `G10_NoLoop` is #1035's.

### 4.2 The pull apply's settlements (#1007, #1068)

Only a user's need to act (`UserMustAct`) or a file the device cannot hold leaves a newer revision waiting. Every other newer revision is settled by what the row has here, as G6 and `SPEC.md` §6.3 and §7 decide:

- **No file here** (no binding, or a bound file the listing does not read and no editor holds unsaved text at, which the round records as the user's delete, `G3_DeleteSeen`). A tombstone is a delete both sides agree on: it becomes the base, nothing is bound, and nothing is left to send but a commit in flight. A live revision brings the file (back) at the name #962's rule gives and becomes the base (an edit beats a delete).
- **A bound file the listing reads.** A tombstone against a change the server lacks keeps the file: the tombstone becomes the base, and the outbox sends the file on top of it (an edit beats a delete). A live revision becomes the base, with path and content merged apart: the content is settled as `G6_Settle` decides from the row's base (a tombstone's content included), and a file the user moved away from its base's name keeps its name (a local rename wins over a remote edit, move or earlier delete); otherwise the file takes the remote's name. With no base, both versions are kept.
- **The outbox's own revision**, and **a revision identical to the file:** §4.1.

A bound row's `absence` decides nothing. Whatever the settlement, a commit in flight the revision does not answer stays as it was sealed, and a bound file with unsaved text at its name keeps its binding (#1061). A revision no newer than what the row knows (`Newer`) changes nothing, and the contract asks nothing of it.

These settlements, and that clause, are about the row after #962's rule (§3.10), which settles every `PathHeld` that `ApplyRevision` leaves where no user must act (#1025). `ContractWitnesses.dfy` holds one witness per case #1068 decided (`DeleteAgainstDeleteSettles`, `DeleteAgainstMissingSettles`, `DeleteAgainstMissingChangedSettles`, `RenameAgainstMoveSettles`, `LiveAgainstKeptTombstoneSettles`, `LiveAgainstNoBaseSettles`, `ReopenedCommitWithNoFileSettles`, `StaleRevisionChangesNothing`): each proves that the contract rejects the row `ApplyRevision` held with `LocalChanges` and accepts the decided row.

The core proves the contract (#1024): `RuleSettlesContract` (`PathRule.dfy`) has `ensures ApplySettlesContract(...)` for every pulled revision, row, listing and set of unsaved paths, on the row the rule leaves. Its `read` and `unsaved` are the listing's read and the editors' unsaved text at the bound name (`ReadOf`, `UnsavedOf`), and its `mustAct` is `MustActOn`, which `RuleMustActIsUserMustAct` proves is `UserMustAct` in the state after the rule's step (`RuleStepSettlesContract`). It assumes only that the rows keep `RowInv` (`CoreInv`). The contract's G10 clause (a newer revision left waiting for local changes or a name waits for a user) is about a `Newer` revision, as every other clause is (#1071). A revision no newer than the row changes nothing, so the clause asks nothing of a row held in an earlier round. That row is the round's (#982): each round re-checks every held row, and once no user must act any more, it clears the row's ahead and applies the stored revision again, which is then `Newer` and settles as above. In the core:

- `Concurrent` and `MovedAgainstChange` take a tombstone base, and `Concurrent` takes any live revision of a file the user moved. A bound row's user's delete counts as a change the server lacks (`JournalChange`), as `G6_Settle` counts it (`LocalChange`): it is settled, never removed as clean.
- A tombstone against no file here records the base and drops the binding and every unsealed outbox, keeping a commit in flight.
- `Revives` covers an unbound row with an unsealed outbox and a bound file with no base. The file is let go untracked (`Revived`), and the rule's `Keeps` gives a revived document no file of its own, so the file moves aside where it is in the way. Where the head would adopt an untracked file at its name, the apply leaves it to the rule (`KeepsUntracked`): `G5_NeverMixedUp` lets only a document that had no file adopt one.
- The base's own revision, pulled again past an older waiting one, against a file the listing reads becomes the base again, with the file as read (`Settled`, no effect).
