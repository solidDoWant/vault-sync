# Plugin e2e tests

The e2e suite (SPEC.md §13) runs the built plugin inside a real, pinned Obsidian, driven by [WebdriverIO](https://webdriver.io) through [`wdio-obsidian-service`](https://github.com/jesse-r-s-hines/wdio-obsidian-service), against a real `vault-sync-server` that the harness starts.

## Running

```sh
make test-e2e                            # desktop UI
VAULT_SYNC_E2E_MOBILE=1 make test-e2e    # Obsidian's emulated mobile UI
```

`make test-e2e` builds the plugin (`make plugin-build`) and runs `scripts/test-e2e.sh`. Docker is required, and the suite never skips. The first run downloads Obsidian and chromedriver into `plugin/.wdio-obsidian-cache` (gitignored, about 800 MB unpacked on Linux). After that a run takes well under a minute.

| Variable | Default | Meaning |
|---|---|---|
| `VAULT_SYNC_E2E_MOBILE` | unset | `1` runs Obsidian with `emulateMobile` (the mobile UI on the desktop app, at a 390×844 viewport). This is not a real Android device; what only a device can check is in `docs/testing/android.md`. |
| `VAULT_SYNC_E2E_CACHE_DIR` | `plugin/.wdio-obsidian-cache` | Where Obsidian downloads are cached. |
| `E2E_TIMEOUT` | `20m` | `go test -timeout` for the whole run. |
| `VAULT_SYNC_E2E_LOG_DIR` | unset | A directory for each spec's WebdriverIO and verbose chromedriver logs, which include Obsidian's own (Electron's) stderr. The native CI jobs set it and upload the directory as an artifact when they fail. |

Extra arguments to `scripts/test-e2e.sh` are passed to `go test`.

## How it fits together

- **Driver** (`cmd/vault-sync-server/e2e_test.go`, Go, build tag `e2e`). `scripts/test-e2e.sh` starts the compose stack (`scripts/with-test-stack.sh`, shared with the integration tests and the simulation). It then runs `go test -tags e2e -run TestPluginE2E`, under `xvfb-run` on Linux when there is no `DISPLAY`. The driver creates a database, and a bucket when the S3 variables are set. It starts a fake OIDC issuer (`internal/auth/authtest`) with the device flow enabled, signs a token for a test user, and builds and starts the server. Then it runs `node plugin/node_modules/@wdio/cli/bin/wdio.js run wdio.conf.mts` with `VAULT_SYNC_E2E_SERVER_URL`, `VAULT_SYNC_E2E_TOKEN`, `VAULT_SYNC_E2E_ISSUER_URL` and `VAULT_SYNC_E2E_CLIENT_ID` set, and fails if WebdriverIO fails. The device flow signs in a different user from the test token, so vaults the plugin creates never show up for the token. A run with no specs fails too.
- **Configuration** (`plugin/wdio.conf.mts`). It pins the Obsidian version. It installs `plugin/dist` (the bundle users install) and the harness plugin into a copy of `plugin/test/e2e/vaults/primary`, and runs one Obsidian at a time.
- **Specs** (`plugin/test/e2e/specs/*.e2e.ts`, mocha). They run in Node and reach into Obsidian with `browser.executeObsidian`. Each spec file gets a fresh Obsidian.
  - `smoke.e2e.ts` checks that Obsidian is in the requested UI mode (desktop or emulated mobile) and that the vault-sync plugin is loaded and enabled. Obsidian marks a plugin loaded before it runs `onload`, and when `onload` throws it only logs the error, so the registry state alone does not prove a successful load. The spec therefore also disables and re-enables the plugin through Obsidian's `enablePlugin`, which resolves `false` when `onload` throws or rejects, and asserts that it resolves `true`. It opens a second vault (`vaults/second`) and checks that the plugin loads there too. Finally it calls `ListVaults` on the harness-started server from inside Obsidian (`requestUrl`): with the test token the call gets 200 and an empty response (the test user is a member of no vault), and without it the call gets 401. Syncing a file between two vaults is `sync.e2e.ts`.
  - `conformance.e2e.ts` runs every case of the shared `VaultAdapter` conformance suite (`plugin/src/core/vault/conformance.ts`) inside Obsidian's renderer against the Obsidian adapter (`ObsidianVaultAdapter`, `plugin/src/obsidian/vault-adapter.ts`). Each case starts from an emptied vault. The harness also renames folders through Obsidian's own `Vault.rename`, as the file explorer does, for the case that checks a folder rename is reported as a rename of every file in it (the engine syncs folder renames from those events, #19). Another case checks that changes at one path (a create, a delete, a create again, a rename onto it) are reported in the order they happened, which echo suppression relies on (`SPEC.md` §8).
  - `paths.e2e.ts` checks that the path rule holds on the exact string the file system gets (#148). Obsidian's `normalizePath` maps U+00A0 and U+202F to a space. So `..` followed by either character, which the shared rule accepts, would become the traversal segment `.. ` if anything normalized it before touching the disk. Through the harness (`pathScope`), the spec checks three things: `normalizePath` really does that; the Obsidian adapter refuses to write or rename onto such a path (`path-conflict`); and nothing appears in the vault. It checks the same for the config folder adapter (`configPathScope`), whose `DataAdapter` normalizes every path it is given. It covers the space both after the dots (a hidden segment, which the vault adapter already refuses for that reason alone) and before them (` ..`, which only the `normalizePath` check refuses). It also commits such a path on the harness's in-memory server and syncs: only the session's synced note may be in the vault afterwards.
  - `platform.e2e.ts` checks that vault-sync's own session gets the platform's path rules (`src/main.ts`, #418). It commits a document on the harness's in-memory server that only those rules refuse: `CON.md` on Windows (`reserved-name`), and elsewhere a path within PATH_MAX on its own but not with the vault folder's absolute path counted (`path-too-long`). Without the rules the engine would write it, and the reason would be missing or `refused-by-vault`. It also writes a 300-byte file name and a 300-byte folder name through the adapter directly, and renames a note to the 300-byte name, all of which the file system refuses: the adapter must reject each with `VaultError` `unmaterializable` and leave the renamed note where it was. Linux and macOS refuse such a name with `ENAMETOOLONG`, Windows with `ENOENT`.
  - `editor.e2e.ts` opens a note in a real Markdown editor, types into it and, in the same turn (before Obsidian's 2-second autosave), applies a remote change through the adapter. A non-overlapping change keeps the cursor and the unsaved text, in the editor and on disk. An overlapping one is refused and the typed text is saved instead. It also opens a canvas. A node added but not yet saved is merged with a remote write that adds another node, and both are in the view and on disk, also after Obsidian's reload, which the harness waits for (#418). A remote write that is not a canvas is refused while the unsaved node is saved. With nothing unsaved, the write is applied, and a node added right after the write resolves, before Obsidian's reload on the modify event has read the disk, survives that reload (the harness waits for `TextFileView.loadFileInternal`). A plugin's text view registered under the core `image` view type, holding unsaved data, is not taken for a read-only viewer: the write is refused and the data saved. Writes and deletes that name the content the engine checked (#163) are refused with `changed` when the editor or canvas saved after that check, and the saved text stays. Unsaved keystrokes are still merged when nothing was saved. A delete is refused, and the keystrokes saved, while the editor holds unsaved text, and goes ahead when it holds none, with a precondition or without one (#181).
  - `unsaved.e2e.ts` covers unsaved keystrokes in a note that a sync deletes (#181), through vault-sync's sync session (`startSync`) against an in-memory server. The harness (`typeThenSync`) types into a real Markdown editor and, in the same turn (before Obsidian's 2-second autosave), pulls and pushes. A remote delete of the open note (`deleteOnServer`) must leave the typed text in the editor and on disk. So must the engine moving an unsynced open note aside (a conflict copy, then a delete) for a remote rename of another note onto its path (`renameOnServer`): the typed text must be in a file afterwards, and the renamed note at the path. A remote document committed at the open note's path, whose content overlaps the keystrokes, is refused by the editor-safe write instead, and the typed text must survive that sync and the next.
  - `startup.e2e.ts` restarts Obsidian on `vaults/indexing` (several files, some nested). The harness plugin watches an Obsidian adapter from its `onload`, i.e. through Obsidian's startup indexing, which fires `create` for every file. Only a later edit may be reported.
  - `journal.e2e.ts` runs every case of the shared `Journal` conformance suite (`plugin/src/core/journal/conformance.ts`) against the IndexedDB journal on Obsidian's own IndexedDB. Each case gets a database of its own, deleted afterwards, and reopens it through a new connection before checking what it wrote. The spec also checks that each vault's journal is keyed by Obsidian's id for that vault (`app.appId`). The id must exist, survive a plugin reload, and differ in the second vault. `reloadObsidian` relaunches Obsidian with a fresh browser profile, so two vaults never share an IndexedDB origin in this suite, and its check that the second vault starts with an empty journal holds even with a shared key: wdio-obsidian-service has no way to keep the profile across a vault switch. That journals of different vaults in one origin are isolated is therefore a unit test (`plugin/src/obsidian/journal.test.ts`).
  - `signin.e2e.ts` points vault-sync at the harness-started server and the fake issuer, and signs in with the device flow. The dialog must show the issuer's verification URL and a user code. The spec approves that code at the issuer (`POST /device/approve`, standing in for the user's browser), and the plugin must then store a refresh token in its `data.json`, together with the identity provider (issuer and client id) that issued it, and make authenticated calls. Access tokens are kept in memory only, so after a plugin reload the calls succeed only through the refresh grant. After the issuer revokes every refresh token (`POST /test/revoke-refresh-tokens`) and the plugin is reloaded, calls fail as unauthenticated, the plugin is in "sign-in required" and has dropped the stored token and provider, and a second device-flow sign-in recovers. Sign-out forgets the tokens and removes both from `data.json`. The sign-in steps the specs share are in `plugin/test/e2e/signin.ts`.
  - `sync.e2e.ts` syncs one file between two vaults through the harness-started server. It signs in with the device flow, approving the code as a user of its own (`POST /device/approve` with `subject`), so the vault it creates never shows up for `signin.e2e.ts`'s user. While the sign-in runs, the settings tab's server and identity provider fields must be disabled. In the primary vault it creates a remote vault and connects to it (no warning: the remote vault is empty), writes `Shared.md`, and waits until the server has it, committed with the device id stored in `data.json`, and the status is `idle`. After a plugin reload the stored device id is the same (no new registration). Then it opens the second vault, signs in again, and connects to the same remote vault. Both sides have files, so the first attempt must answer `needs-confirmation` and start nothing. After confirming, `Shared.md` must arrive with its content, and the second vault's own file is pushed under a device id of its own. An attachment written in the primary vault, larger than two upload chunks and download ranges and not a multiple of either, must arrive in the second vault with the same size and SHA-256.
  - `realtime.e2e.ts` checks the realtime channel (#193). It signs in as a user of its own, turns vault-sync's 30-second pull timer off through the harness (`disablePullTimer`), and connects the primary vault to a new remote vault. The harness then commits a note as another device of the same user (`commitFromAnotherDevice`: a device of its own, the blob upload, `CommitRevision`). With no timer, the note can only arrive because the server notified the plugin over its WebSocket (or, if the subscription was not up yet, through the pull every subscribe makes). A second note, committed once the subscription is certainly up, must arrive too.
  - `history.e2e.ts` covers history and restore (#26). It signs in as a user of its own, creates and connects a remote vault, and syncs two versions of `History.md`. The history view (`showHistory`) must list two revisions, each by `this device`, the newest marked current. Clicking the older one must preview its text, and **Restore this version** must bring that text back to the file, as a third revision on the server, listed in the view. After the note is deleted and the delete synced, **Browse deleted files** must list it. Choosing it opens its history with the delete as the newest entry, whose preview is the content at the delete, and restoring that entry must bring the file back as a fifth revision. Finally the harness (`openHistoryAs`) opens the real history view over an in-memory history whose role check says the user is a `viewer`, may restore, or fails (#527): previewing the older version must show no **Restore this version** button and a note saying why for the viewer, and the button in the other two cases (the server still refuses a viewer whose role could not be read).
  - `lifecycle.e2e.ts` starts vault-sync's sync session (`startSync`) against an in-memory server, over the open vault's IndexedDB journal, in an emptied vault. Every start pulls and then pushes, and the push pulls again first. It disables and re-enables vault-sync through Obsidian's plugin registry, then starts it again over a new connection to the same journal. The second start pulls from the stored cursor, not from 0, and only the new session reports a later edit.
  - `conflicts.e2e.ts` starts vault-sync's sync session (`startSync`) against an in-memory server holding a note at the path of a different local note, and a note whose name is longer than 255 bytes. The engine makes a real conflict copy and tracks the long name as unmaterializable. It opens the conflict view with `showConflicts` (the **Show conflicts** command) and checks that it lists the conflict, with links to both files, and the unmaterializable document, with its server path and reason. It also lists a note whose name the server has with an accent typed as a separate character (NFD), which the Obsidian adapter refuses because `normalizePath` would store it under another name, with that reason (#417). When a link's file is gone (the spec makes `getFileByPath` miss it), clicking it must show a notice and redraw the view. Clicking **Compare side by side** must open both files in Markdown panes, on desktop next to each other (the copy's pane starts at or right of the original's right edge, at the same top). Deleting the copy through Obsidian must clear the conflict's entry while the unmaterializable document stays listed.
  - `config.e2e.ts` covers config folder sync (#28) with a sync session against an in-memory server, over the vault's real config folder. First it opens vault-sync's settings tab: the config sync toggle must be off, its description must warn that synced plugin code runs on this device and that it is only for trusted vaults, and no category toggles may show. Turning it on must show the categories with their defaults and store the setting in the plugin's `data.json`. While config sync is off, the server gets no config file. With every category on, it first waits until Obsidian has made its startup config writes, then starts the session. Obsidian debounces them: it creates `app.json`, `appearance.json` and `core-plugins.json`, and saves `community-plugins.json` again about a second after it has loaded every enabled plugin (the harness records that save with a config folder adapter it watches from its `onload`). A session started earlier could push before one of them lands and commit it on its next sync (#326). The session uploads the plugin list but never a `workspace*.json`, `graph.json` or vault-sync's own folder. Then it opens notes in a tab and a new tab, switches tabs, splits a pane and toggles both sidebars. It waits until Obsidian has saved the layout (`workspace.json`, or `workspace-mobile.json` in mobile mode) and an Obsidian config adapter has reported that save, and then syncs. Nothing may be committed: the spec compares the server's files (each path's content) before and after, so a failure names the file. Finally a remote change of `community-plugins.json` must land on disk and raise a notice asking the user to reload, while the window and the vault-sync instance stay the same (no reload).
- **Harness plugin** (`plugin/test/e2e/harness/`). This is a test-only Obsidian plugin (`vault-sync-e2e-harness`), bundled by `wdio.conf.mts` into `harness/dist` (gitignored) on every run and never shipped. It carries code that a stringified `executeObsidian` function cannot, such as the conformance suite, the editor scenario and the in-memory sync server. Its `adapterUnderTest` field is the adapter the conformance spec tests: the Obsidian adapter over the emptied test vault. Specs call its methods with `callHarness` (`plugin/test/e2e/obsidian.ts`), which is typed from the harness class.
- **Types and lint.** `plugin/test/e2e/tsconfig.json` makes the e2e code its own TypeScript program, so mocha and WebdriverIO globals stay out of the plugin program. `make lint` type-checks and lints it.

## Obsidian version

`plugin/wdio.conf.mts` pins the Obsidian app version (`obsidianVersion`). The installer, i.e. the Electron binary, is the earliest one compatible with that app version, so the single pin fixes both. A Renovate regex manager (`.github/renovate.json5`, datasource `github-releases`, `obsidianmd/obsidian-releases`) bumps it. The CI download cache is keyed on that file.

## Platforms

| Where | How |
|---|---|
| Dev VM (NixOS) | `make test-e2e`. Obsidian and chromedriver are generic Linux binaries. The dev shell (`flake.nix`) points nix-ld at a matching loader and Electron's libraries (`NIX_LD`, `NIX_LD_LIBRARY_PATH`), and `xvfb-run` provides the display. |
| CI `plugin-e2e (ubuntu-latest)`, `plugin-e2e (emulated-mobile)` | `nix develop -c make test-e2e`, with `VAULT_SYNC_E2E_MOBILE=1` for the mobile job. |
| CI `plugin-e2e (windows-latest)`, `plugin-e2e (macos-latest)` | No Nix (Windows) and no Linux containers, so Go and Node come from `actions/setup-*` and PostgreSQL runs natively: on macOS from `ikalnytskyi/action-setup-postgres`, on Windows the version the runner image preinstalls (its `postgresql-x64-*` service, started by the job, which fails if the major version is below the minimum supported 14), so the job does not depend on the Chocolatey community feed. The S3-compatible store is the pinned versitygw release (the same version, credentials and region as the compose stack) run natively by `scripts/with-native-s3.sh`, which downloads it (the archive is cached, and its SHA-256 is checked on every run before the executable is extracted into a private temporary directory), exports the `VAULT_SYNC_TEST_S3_*` variables and stops it afterwards. The plugin is built with npm, and the driver runs with `./scripts/with-native-s3.sh go test -tags e2e`. |

On Windows, `wdio.conf.mts` starts Obsidian with `--disable-gpu --in-process-gpu`: software rendering in Obsidian's main process instead of a separate GPU process. On a loaded Windows runner, which has no GPU, that process kept dying until Chromium ended Obsidian with "GPU process isn't usable. Goodbye.", and chromedriver reported "Unable to receive message from renderer" in whichever spec was running (#457). No spec checks rendered pixels.

The driver requires both PostgreSQL and the S3-compatible store and fails, rather than skips, when either is not configured. To run it against a PostgreSQL you started yourself, set `VAULT_SYNC_TEST_DATABASE_URL` (a role allowed to create databases), build the plugin, and run `./scripts/with-native-s3.sh go test -count=1 -tags e2e -run TestPluginE2E -v ./cmd/vault-sync-server/` (or set the `VAULT_SYNC_TEST_S3_*` variables for a store of your own and run `go test` directly). The version pinned in `scripts/with-native-s3.sh` must match the versitygw image in `deploy/compose/compose.test.yaml`; the script refuses to run otherwise, and `make test` (part of the required Linux checks) runs `./scripts/with-native-s3.sh --check-pin`, so a compose bump with a stale pin fails CI. Bump both, with the release checksums, together.

## Writing e2e tests

- Put specs in `plugin/test/e2e/specs/` as `*.e2e.ts`. Functions passed to `browser.executeObsidian` are stringified and run inside Obsidian, so they cannot capture variables or imports. Pass inputs as extra arguments, and use the `obsidian` module from the first argument.
- Code that must run inside Obsidian and is too big for one function belongs in the harness plugin as a method. Call it from the spec, as `conformance.e2e.ts` does.
- Do not depend on timing. Wait for conditions (`browser.waitUntil`), never for fixed delays.
- Every new assertion must fail when its behavior breaks. Check this by breaking the behavior once before committing.
