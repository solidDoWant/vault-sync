# Plugin e2e tests

The e2e suite (SPEC.md §13) runs the built plugin inside a real, pinned Obsidian, driven by [WebdriverIO](https://webdriver.io) through [`wdio-obsidian-service`](https://github.com/jesse-r-s-hines/wdio-obsidian-service), against a real `vault-sync-server` that the harness starts.

## Running

```sh
make test-e2e                            # desktop UI
VAULT_SYNC_E2E_MOBILE=1 make test-e2e    # Obsidian's emulated mobile UI
```

`make test-e2e` builds the plugin (`make plugin-build`) and runs `scripts/test-e2e.sh`. Docker is required, and the suite never skips. The first run downloads Obsidian and chromedriver into `plugin/.wdio-obsidian-cache` (gitignored, about 800 MB unpacked on Linux). After that a run takes well under a minute.

| Variable | Default | Meaning |
|---|---|---|
| `VAULT_SYNC_E2E_MOBILE` | unset | `1` runs Obsidian with `emulateMobile` (the mobile UI on the desktop app, at a 390×844 viewport). This is not a real Android device; what only a device can check is in `docs/testing/android.md`. |
| `VAULT_SYNC_E2E_ANDROID` | unset | `1` runs the suite on the real Obsidian Android app in an Android emulator that is already booted (`plugin/wdio.android.conf.mts`), with Appium installed by `npm ci --prefix plugin/test/e2e/android`. See "Android emulator job". |
| `VAULT_SYNC_E2E_CACHE_DIR` | `plugin/.wdio-obsidian-cache` | Where Obsidian downloads are cached. |
| `E2E_TIMEOUT` | `20m` | `go test -timeout` for the whole run. |
| `VAULT_SYNC_E2E_LOG_DIR` | unset | A directory for each spec's WebdriverIO and verbose chromedriver logs, which include Obsidian's own (Electron's) stderr. The native CI jobs set it and upload the directory as an artifact when they fail. |

Extra arguments to `scripts/test-e2e.sh` are passed to `go test`.

## How it fits together

- **Driver** (`cmd/vault-sync-server/e2e_test.go`, Go, build tag `e2e`). `scripts/test-e2e.sh` starts the compose stack (`scripts/with-test-stack.sh`, shared with the integration tests). It then runs `go test -tags e2e -run TestPluginE2E`, under `xvfb-run` on Linux when there is no `DISPLAY`. The driver creates a database, and a bucket when the S3 variables are set. It starts a fake OIDC issuer (`internal/auth/authtest`) with the device flow enabled, signs a token for a test user, and builds and starts the server. Then it runs `node plugin/node_modules/@wdio/cli/bin/wdio.js run wdio.conf.mts` with `VAULT_SYNC_E2E_SERVER_URL`, `VAULT_SYNC_E2E_TOKEN`, `VAULT_SYNC_E2E_ISSUER_URL` and `VAULT_SYNC_E2E_CLIENT_ID` set, and fails if WebdriverIO fails. The device flow signs in a different user from the test token, so vaults the plugin creates never show up for the token. A run with no specs fails too.
- **Configuration** (`plugin/wdio.conf.mts`). It pins the Obsidian version. It installs `plugin/dist` (the bundle users install) and the harness plugin into a copy of `plugin/test/e2e/vaults/primary`, and runs one Obsidian at a time.
- **Specs** (`plugin/test/e2e/specs/*.e2e.ts`, mocha). They run in Node and reach into Obsidian with `browser.executeObsidian`. Each spec file gets a fresh Obsidian.
  - `smoke.e2e.ts` checks that Obsidian is in the requested UI mode (desktop or emulated mobile) and that the vault-sync plugin is loaded and enabled. Obsidian marks a plugin loaded before it runs `onload`, and when `onload` throws it only logs the error, so the registry state alone does not prove a successful load. The spec therefore also disables and re-enables the plugin through Obsidian's `enablePlugin`, which resolves `false` when `onload` throws or rejects, and asserts that it resolves `true`. It opens a second vault (`vaults/second`) and checks that the plugin loads there too. Finally it calls `ListVaults` on the harness-started server from inside Obsidian (`requestUrl`): with the test token the call gets 200 and an empty response (the test user is a member of no vault), and without it the call gets 401. Syncing a file between two vaults is `sync.e2e.ts`.
  - `conformance.e2e.ts` runs every case of the shared `VaultAdapter` conformance suite (`plugin/src/core/vault/conformance.ts`) inside Obsidian's renderer against the Obsidian adapter (`ObsidianVaultAdapter`, `plugin/src/obsidian/vault-adapter.ts`). Each case starts from an emptied vault. The harness also renames folders through Obsidian's own `Vault.rename`, as the file explorer does, for the cases that check a folder rename is reported as a rename of every file in it and of the folder and every folder in it (the engine syncs folder renames from those events, and a folder rename keeps the folder's document). Other cases cover the folder methods (`listFolders`, `createFolder`, `deleteFolder` of an empty folder only) and the folder events. Another case checks that changes at one path (a create, a delete, a create again, a rename onto it) are reported in the order they happened, which echo suppression relies on (`SPEC.md` §8).
  - `paths.e2e.ts` checks that the path rule holds on the exact string the file system gets (#148). Obsidian's `normalizePath` maps U+00A0 and U+202F to a space. So `..` followed by either character, which the shared rule accepts, would become the traversal segment `.. ` if anything normalized it before touching the disk. Through the harness (`pathScope`), the spec checks three things: `normalizePath` really does that; the Obsidian adapter refuses to write or rename onto such a path (`path-conflict`); and nothing appears in the vault. It covers the space both after the dots (a hidden segment, which the vault adapter already refuses for that reason alone) and before them (` ..`, which only the `normalizePath` check refuses). It also commits such a path on the harness's in-memory server and syncs: only the session's synced note may be in the vault afterwards.
  - `platform.e2e.ts` checks that vault-sync's own session gets the platform's path rules (`src/main.ts`, #418). It commits a document on the harness's in-memory server that only those rules refuse: `CON.md` on Windows (`reserved-name`), and elsewhere a path within PATH_MAX on its own but not with the vault folder's absolute path counted (`path-too-long`). Without the rules the engine would write it, and the reason would be missing or `refused-by-vault`. It also writes a 300-byte file name and a 300-byte folder name through the adapter directly, and renames a note to the 300-byte name, all of which the file system refuses: the adapter must reject each with `VaultError` `unmaterializable` and leave the renamed note where it was. Linux and macOS refuse such a name with `ENAMETOOLONG`, Windows with `ENOENT`.
  - `editor.e2e.ts` opens a note in a real Markdown editor, types into it and, while the harness holds Obsidian's 2-second autosave of the view (it stubs `requestSave` until the adapter call has finished, then requests the save again), applies a remote change through the adapter (#600). A non-overlapping change keeps the cursor and the unsaved text, in the editor and on disk. An overlapping one is refused and the typed text is saved instead. It also opens a canvas. A node added but not yet saved is merged with a remote write that adds another node, and both are in the view and on disk, also after Obsidian's reload, which the harness waits for (#418). A remote write that is not a canvas is refused while the unsaved node is saved. With nothing unsaved, the write is applied, and a node added right after the write resolves, before Obsidian's reload on the modify event has read the disk, survives that reload (the harness waits for `TextFileView.loadFileInternal`). A plugin's text view registered under the core `image` view type, holding unsaved data, is not taken for a read-only viewer: the write is refused and the data saved. Writes and deletes that name the content the engine checked (#163) are refused with `changed` when the editor or canvas saved after that check, and the saved text stays. Unsaved keystrokes are still merged when nothing was saved. A delete is refused, and the keystrokes saved, while the editor holds unsaved text, and goes ahead when it holds none, with a precondition or without one (#181).
  - On the Android app, `smoke.e2e.ts` expects the Android app with the mobile UI, `platform.e2e.ts` uses the device's rules (Android's shared-storage characters: `Meeting: notes.md` is `forbidden-character`, as Obsidian exposes no vault folder path there), and the platform checks of both read the platform Obsidian reports (`obsidianPage.getPlatform()`), not the host's `process.platform`. The conformance case "rename that changes only letter case is allowed" is skipped there until #544 is fixed. `atomicity.e2e.ts` is skipped there: it relies on desktop's `FileSystemAdapter`. So are `basic-sync.e2e.ts`, `offline-conflicts.e2e.ts` and `connect.e2e.ts`: their second device is a vault on disk opened in the same desktop Obsidian (`devices.ts`), which needs the vault's file-system path, and the Android app has none; desktop and emulated mobile run them.
  - `device.android.e2e.ts` runs only on the Android app (`wdio.conf.mts` excludes `*.android.e2e.ts`). It drives the emulator with `adb` from the spec. The plugin reaches the server over the emulator's own network instead of `adb reverse`, so airplane mode cuts it. vault-sync accepts plain http only to a loopback host, so the spec points it at `http://127.0.0.2:<port>` (not the `127.0.0.1` that `adb reverse` serves), and adds `iptables` NAT rules on the device that send that address on to `10.0.2.2`, the emulator's address for the host's loopback. That needs a root adb shell: the workflow runs `adb root` after boot. The fake issuer is still reached through `adb reverse`. It signs in as a user of its own and has the harness lose the responses of vault-sync's commits (`loseCommitResponses`: the server answers, vault-sync never sees it). It connects a new vault and, once the server has answered a commit while the status is `syncing`, force-stops Obsidian (`am force-stop`) and starts it again. Sync must then end `idle` with the vault equal to the server (each file's SHA-256 against its blob id), and with one revision per document and one document per path: the commit answered before the kill was recognized, not made again. Then it edits a note, sends Obsidian to the background (`KEYCODE_HOME`) for 10 seconds, and brings it back. The WebView must be the same one (a marker set in it survives), and the edit must reach the server. With "Don't keep activities" on (the `always_finish_activities` setting, plus `service call activity 43 i32 1`, the `IActivityManager.setAlwaysFinish` call Developer options makes: the setting alone takes effect only after a reboot), the same must hold when Android destroys the activity. The spec checks the activity's state in `dumpsys activity -a activities`: `RESUMED` in the foreground, then it waits for `DESTROYED` before bringing Obsidian back. The record itself stays listed (Android 14 destroys the activity but keeps its record, to recreate it on return), and a WebView marker cannot show it either, because Obsidian keeps its WebView's JavaScript across the activity's recreation. Finally it turns on airplane mode and edits one note and creates another. The status must go `offline` with the edits pending and on disk. Once airplane mode is off, both must reach the server, and the vault must equal it. For AC-21 it also cuts the device network, commits a note as another device over `adb reverse` (`commitFromAnotherDevice` with the server URL), force-stops Obsidian, restores the network and reopens the app, which must then receive the note.
  - `atomicity.e2e.ts` checks that the adapter's write, under the engine's precondition (#163), is atomic with respect to the user's editor writing the same file (#543): the editor's write must be neither overwritten nor lost. It covers a note open in no view, a note open in a Markdown editor and a canvas open in its view. Obsidian 1.14.4's desktop file adapter runs every read and write in one queue, and `Vault.process` holds it from its read to its write. The harness (`writeRemoteWithEditorWriteAtRead`) calls `Vault.modify`, which an editor's save ends in, when the adapter reads the file the k-th time, for k = 1, 2, … until the adapter reads it fewer than k times. `Vault.modify` puts its write in the queue synchronously, so the order depends on the queue, not on timing. Only the reads of the adapter under test count: it gets an `App` whose vault and file adapter are proxies of the real ones, and whose file system (`FileSystemAdapter.fsPromises`, internal to 1.14.4) counts reads. Every write of the file is recorded. After each round the editor's content must be on disk and written last. Either the sync write was applied first and both are applied in order, or the editor's write came first and the sync write was refused with `changed`. At least one round per view must be the former. A write that reads, lets the editor's write land, and then writes over it fails the spec.
  - `encryption.e2e.ts` holds `[P4-15]`: through the harness (`passphraseUnlockTiming`), it wraps a key under a passphrase at the default Argon2id parameters (64 MiB, 3 passes) inside Obsidian, then times unwrapping it, the derivation an unlock runs. The unlock must run on WebAssembly (`hash-wasm` in a Web Worker, after its known-answer self-test) and take under 5 seconds. The spec logs the time, the longest the main thread went without running a timer during the unlock, and the implementation, with the reason when it fell back to `@noble/hashes`. In the Android emulator job this measures the Obsidian app's WebView.
  - `unsaved.e2e.ts` covers unsaved keystrokes in a note that a sync deletes or moves, through vault-sync's sync session (`startSync`) against an in-memory server. The harness (`typeThenSync`) types into a real Markdown editor and syncs while it holds Obsidian's 2-second autosave of the view, so the keystrokes are still unsaved when the sync reaches the adapter however slow the runner is. It fails if the typing requested no save, which would mean the hold holds nothing, or if the editor matches the disk when the sync starts. A remote delete of the open note (`deleteOnServer`) must leave the typed text in the editor and on disk. When the engine moves an unsynced open note to a conflict copy name (rule W) for a remote rename of another note onto its path (`renameOnServer`), or for a remote document committed at its path, the editor follows the rename: the typed text must be in the editor, then saved in the conflict copy, and the remote note at the path. Its session, like every session `startSession` starts, never syncs on its own, so every sync is one the spec asked for.
  - `startup.e2e.ts` restarts Obsidian on `vaults/indexing` (several files, some nested). The harness plugin watches an Obsidian adapter from its `onload`, i.e. through Obsidian's startup indexing, which fires `create` for every file. Only a later edit may be reported.
  - `journal.e2e.ts` writes every kind of record to the IndexedDB journal on Obsidian's own IndexedDB, in a database of its own (deleted afterwards), and reads it back through a new connection, which must return what was written. The spec also checks that each vault's journal is keyed by Obsidian's id for that vault (`app.appId`). The id must exist, survive a plugin reload, and differ in the second vault. `reloadObsidian` relaunches Obsidian with a fresh browser profile, so two vaults never share an IndexedDB origin in this suite, and its check that the second vault starts with an empty journal holds even with a shared key: wdio-obsidian-service has no way to keep the profile across a vault switch. That journals of different vaults in one origin are isolated is therefore a unit test (`plugin/src/obsidian/journal.test.ts`).
  - `signin.e2e.ts` points vault-sync at the harness-started server and the fake issuer, and signs in with the device flow. The dialog must show the issuer's verification URL and a user code. The spec approves that code at the issuer (`POST /device/approve`, standing in for the user's browser), and the plugin must then store a refresh token in Obsidian's local storage, never in `data.json`, and the identity provider (issuer and client id) that issued it in `data.json`, and make authenticated calls. A token moved into `data.json` while the plugin is disabled is moved back to local storage when it loads, staying signed in; with the token cleared from local storage the plugin loads in "sign-in required" and is signed in again once the token is back. Access tokens are kept in memory only, so after a plugin reload the calls succeed only through the refresh grant. After the issuer revokes every refresh token (`POST /test/revoke-refresh-tokens`) and the plugin is reloaded, calls fail as unauthenticated, the plugin is in "sign-in required" and has dropped the stored token and provider, and a second device-flow sign-in recovers. Sign-out forgets the tokens and removes the token from local storage and the provider from `data.json`. The sign-in steps the specs share are in `plugin/test/e2e/signin.ts`.
  - `sync.e2e.ts` syncs one file between two vaults through the harness-started server. It signs in with the device flow, approving the code as a user of its own (`POST /device/approve` with `subject`), so the vault it creates never shows up for `signin.e2e.ts`'s user. While the sign-in runs, the settings tab's server and identity provider fields must be disabled. In the primary vault it creates a remote vault and connects to it (no warning: the remote vault is empty), writes `Shared.md`, and waits until the server has it, committed with the device id stored in `data.json`, and the status is `idle`. After a plugin reload the stored device id is the same (no new registration). Then it opens the second vault, signs in again, and connects to the same remote vault. Both sides have files, so the first attempt must answer `needs-confirmation` and start nothing. After confirming, `Shared.md` must arrive with its content, and the second vault's own file is pushed under a device id of its own. An attachment written in the primary vault, larger than two upload chunks and download ranges and not a multiple of either, must arrive in the second vault with the same size and SHA-256.
  - `realtime.e2e.ts` checks the realtime channel (#193). It signs in as a user of its own, turns vault-sync's 30-second pull timer off through the harness (`disablePullTimer`), and connects the primary vault to a new remote vault. The harness then commits a note as another device of the same user (`commitFromAnotherDevice`: a device of its own, the blob upload, `CommitRevision`). With no timer, the note can only arrive because the server notified the plugin over its WebSocket (or, if the subscription was not up yet, through the pull every subscribe makes). A second note, committed once the subscription is certainly up, must arrive too.
  - `devices.e2e.ts` covers the settings device list's **Remove** (#590, #630, #634). It signs in as a user of its own, connects a new remote vault (which registers this device) and registers a second device through the harness (`registerAnotherDevice`). In vault-sync's settings tab, this device's row must have no button and the other's an enabled **Remove**. The harness routes vault-sync's `RemoveDevice` calls through itself (`interceptRemoveDevice`): it records each one and can fail the next without sending it, or hold it until the spec ends it, so nothing depends on timing. The settings, their modals and notices are in a document of their own, so the spec looks for them in the settings tab's document and records every notice shown with a `MutationObserver`. A failed removal (Remove, then **Remove device** in the confirmation) must show "could not remove the device" and leave the button enabled. A held one must keep it disabled, also after the tab is rendered again, where a click sends nothing; when it then fails, the button on screen must be enabled again. A last held attempt, released after another render, must remove the device: the list on screen must reload without its row, exactly one `RemoveDevice` must have been sent, and the server must list only this device. A second test (#634) registers two more devices. The harness also counts vault-sync's `ListDevices` calls and can hold the next one after the server answered it. A removal is held, the tab is rendered again with its `ListDevices` held (its answer still lists the device), and the removal is released: the reloaded list must not show the removed device, also after the older, held answer is handed over. A last removal is held until the settings are closed; when it succeeds, vault-sync must send no `ListDevices`.
  - `history.e2e.ts` covers history and restore (#26). It signs in as a user of its own, creates and connects a remote vault, and syncs two versions of `History.md`. The history view (`showHistory`) must list two revisions, each by `this device`, the newest marked current. Clicking the older one must preview its text, and **Restore this version** must bring that text back to the file, as a third revision on the server, listed in the view. After the note is deleted and the delete synced, **Browse deleted files** must list it. Choosing it opens its history with the delete as the newest entry. The path in the view's title and in that entry must each be one `span.vault-sync-path` with `dir="auto"` whose computed `unicode-bidi` is `isolate`, so right-to-left letters in a path cannot reorder the label around it (#605, #615); the label's text alone is the same with or without the span. The entry's preview is the content at the delete, and restoring that entry must bring the file back as a fifth revision. Finally the harness (`openHistoryAs`) opens the real history view over an in-memory history whose role check says the user is a `viewer`, may restore, or fails (#527): previewing the older version must show no **Restore this version** button and a note saying why for the viewer, and the button in the other two cases (the server still refuses a viewer whose role could not be read). Last, the second vault connects as the same user and must hold the restored version, with no new revision of the note (AC-24).
  - `lifecycle.e2e.ts` starts vault-sync's sync session (`startSync`) against an in-memory server, over the open vault's IndexedDB journal, in an emptied vault. Every start syncs, and a cycle that made progress is followed by another, which pulls again from the new cursor. It disables and re-enables vault-sync through Obsidian's plugin registry, then starts it again over a new connection to the same journal. The second start pulls from the stored cursor, not from 0, and a later edit syncs once, from the new session.
  - `sharing.e2e.ts` covers the settings' **Sharing** section and joining by invite code (#34) against the real server. The owner signs in as a user of its own and connects a new vault. The section must show the owner's role, the owner as the only member, and no invitations. Two invitations created in the settings must each show their code once in a modal with **Copy code**, and appear in the pending list with their expiry but not their code. Revoking one must make its code unusable. The test token's user, standing in for the invited person, redeems the other over Connect JSON from the spec, and the re-read list must show them as an editor. A role change must wait for its confirmation (a cancelled one leaves the dropdown as it was), demoting the last owner must show the refusal in a notice and leave the list unchanged, and **Remove** must remove the member after its confirmation. Then a third user, in the second test vault, types an unusable code into **Join with an invite code**: one notice must say so and nothing may be connected. With a real code, the combine confirmation must come first (both vaults have files), and the vault must then be connected and sync. An editor's section must show only their role and **Leave vault**, which must end the membership and stop sync with the status **no longer a member**, keeping the vault connected. The spec makes the test token's user leave the vault afterwards, so `smoke.e2e.ts` still finds it a member of no vault.
  - `conflicts.e2e.ts` starts vault-sync's sync session (`startSync`) against an in-memory server holding a note at the path of a different local note, and a note whose name is longer than 255 bytes. The engine makes a real conflict copy and skips the long name. It opens the conflict view with `showConflicts` (the **Show conflicts** command) and checks that it lists the conflict, with links to both files, and the skipped documents, with their server paths and reasons: the long name, and a note whose name the server has with an accent typed as a separate character (NFD), which the Obsidian adapter refuses because `normalizePath` would store it under another name. When a link's file is gone (the spec makes `getFileByPath` miss it), clicking it must show a notice and redraw the view. Clicking **Compare side by side** must open both files in Markdown panes, on desktop next to each other (the copy's pane starts at or right of the original's right edge, at the same top). Deleting the copy through Obsidian must clear the conflict's entry while the skipped documents stay listed.
  - `robustness.e2e.ts` covers AC-17 and AC-18 of `docs/acceptance/phase-2.md` against the real server. Killing Obsidian is `reloadObsidian()` without a vault, which ends Obsidian's process and starts it again on the same vault and browser profile, so the IndexedDB journal survives as it does when the app is killed. Mid-upload: the harness (`loseCommitResponses`) lets the server answer the first commit but never hands the answer to vault-sync, then Obsidian is killed; after the restart the vault must equal the server's heads, with one revision per document. Mid-download: a second vault's download of a three-range attachment is held after its first range (`holdDownloadOf`), then Obsidian is killed; the file must be absent until it arrives whole, with no new revision. Server unreachable: the harness routes vault-sync's RPCs to a port nothing listens on (`installServerSwitch`, `setServerReachable`); local edits stay on disk, the status shows **offline**, and once the server is reachable again the edits reach it.
  - `names.e2e.ts` covers AC-19, AC-20 and AC-26. The primary vault creates unportable names (a forbidden character, a reserved name, a trailing dot and, on Linux, a name that differs from a synced one only by case), which must be listed as refused with the server's reason while a portable file syncs; Windows cannot hold those names and macOS cannot hold the case clash, so those runners skip them. It creates Unicode names (one typed decomposed, NFD), which the server must hold in NFC, and paths of 200, 201 and 250 characters: only the two over 200 get the warning notice (the harness records notices, `recordNotices`). The second vault runs with Windows' path rules whatever the host (`useWindowsPathRules`), receives the Unicode names exactly, and skips the paths too long for it with a notice, while the server keeps them and every other file arrives. Each desktop runner (Linux, macOS, Windows) runs it, so each OS writes and receives the same NFC names.
  - `connect.e2e.ts` holds acceptance scenario AC-02 (`docs/acceptance/phase-2.md`): connecting a vault. It signs in as a user of its own and opens each vault as a new window of the same Obsidian (`devices.ts`), built on disk before Obsidian opens it. An empty vault must connect to a new remote vault without a warning, go `idle`, and leave the server with no files. A vault that already has notes at its root and in nested folders, an image and a PDF must connect the same way, and the server's live documents other than folders must then be exactly those files, each with its kind (`TEXT` or `BLOB`) and its SHA-256 as the blob id, while the device's own files and folders stay as they were. Folder documents are AC-08's.
  - `basic-sync.e2e.ts` and `offline-conflicts.e2e.ts` hold the acceptance scenarios AC-04 to AC-16 (`docs/acceptance/phase-2.md`) between two devices, A and B, each its own Obsidian vault with vault-sync, signed in as one user and connected to one server vault. `reloadObsidian({ vault })` relaunches Obsidian with a fresh profile, which would drop A's IndexedDB journal on every switch to B, so B is instead a second vault opened in its own window of the same Obsidian (`plugin/test/e2e/devices.ts`): a copy of `vaults/second` with A's plugins (vault-sync without its `data.json`, the harness and wdio's helper plugin), opened through Obsidian's `vault-open` IPC message, with community plugins turned on for its vault id. Both devices run at once, and the spec points WebDriver at one window or the other (`switchToWindow`). Every change is made through Obsidian's vault API. A device goes offline by disconnecting its vault, which keeps its journal, and comes back by connecting it again. A concurrent change is staged by taking B offline, making A's change and waiting until the server has it, making B's change, and bringing B back, so B is the device whose commit is refused and that resolves the conflict (`engine.md` §11). The e2e server's file size limit is 8 MiB (`VAULT_SYNC_BLOB_MAX_SIZE_BYTES`), so AC-09 can go over it with a 9 MiB file.
  - `shared-vault.e2e.ts` holds the acceptance scenarios P3-01 to P3-12 (`docs/acceptance/phase-3.md`) for a vault shared by two users, each a different account on the fake issuer with a display name (the driver gives the issuer's device flow a `name` claim for each: Olivia Owner and Max Member). The owner is device A, the primary test vault, named "Owner laptop"; the member is device B, a second vault in its own window (`devices.ts`), named "Member phone". B types each code into the settings' join field: a revoked code and one that expired (created with a one-second lifetime) are refused with the "invalid, has expired or was already used" notice and connect nothing (P3-04); a real code joins and connects the vault, and edits sync both ways (P3-01). The history of a note both edited names the user and the device of each version on both devices (P3-02). With B offline, both edit the same line: once B is back there is exactly one conflict copy, named after B's user and device (P3-03). The owner then makes B a viewer and an editor again; each change shows on B (the viewer banner on its open note, and B's edit undone and not uploaded while a viewer) at the next sync cycle, which the owner's next note starts, without B signing in again (P3-05). As a viewer again, B's open note is in reading view with a read-only editor and the banner, Obsidian's rename, delete and create actions are refused with a notice, and nothing reaches the server (P3-06); a note B's test writes to disk outside Obsidian is restored, the viewer's version is kept under `.vault-sync/local-copies/` with a notice, and the copy never reaches the server or A (P3-07). B leaves from the settings (P3-09) and joins again with a new code. A, the last owner, is refused demoting itself and leaving, each with the reason in a notice, then makes B an owner and leaves (P3-10). A joins again, and B deletes the vault, typing its name to confirm (P3-12). B then creates a second vault, A joins it, and B removes A (P3-08) and syncs alone (P3-11). Each device that lost access shows "no longer a member" or "vault deleted" in its status and settings, keeps its files, gets no later note of the owner's, and uploads none of its own. The server's side of P3-12 (data kept 30 days, `vault undelete`, then the purge) is `TestDeletedSharedVault` in `internal/vaultcmd`. The settings-tab helpers it shares with `sharing.e2e.ts` are in `plugin/test/e2e/settings-ui.ts`.
- **Harness plugin** (`plugin/test/e2e/harness/`). This is a test-only Obsidian plugin (`vault-sync-e2e-harness`), bundled by `wdio.conf.mts` into `harness/dist` (gitignored) on every run and never shipped. It carries code that a stringified `executeObsidian` function cannot, such as the conformance suite, the editor scenario and the in-memory sync server. Its `adapterUnderTest` field is the adapter the conformance spec tests: the Obsidian adapter over the emptied test vault. Specs call its methods with `callHarness` (`plugin/test/e2e/obsidian.ts`), which is typed from the harness class.
- **Types and lint.** `plugin/test/e2e/tsconfig.json` makes the e2e code its own TypeScript program, so mocha and WebdriverIO globals stay out of the plugin program. `make lint` type-checks and lints it.

## Obsidian version

`plugin/wdio.conf.mts` pins the Obsidian app version (`obsidianVersion`). The installer, i.e. the Electron binary, is the earliest one compatible with that app version, so the single pin fixes both. A Renovate regex manager (`.github/renovate.json5`, datasource `github-releases`, `obsidianmd/obsidian-releases`) bumps it. The CI download cache is keyed on that file.

## Platforms

| Where | How |
|---|---|
| Dev VM (NixOS) | `make test-e2e`. Obsidian and chromedriver are generic Linux binaries. The dev shell (`flake.nix`) points nix-ld at a matching loader and Electron's libraries (`NIX_LD`, `NIX_LD_LIBRARY_PATH`), and `xvfb-run` provides the display. |
| CI `plugin-e2e (ubuntu-latest)`, `plugin-e2e (emulated-mobile)` | `nix develop -c make test-e2e`, with `VAULT_SYNC_E2E_MOBILE=1` for the mobile job. |
| CI `plugin-e2e (android-emulator)` (workflow `android-e2e`; nightly, manual dispatch and pull requests that change the job's own files; not required) | The real Android app in an emulator: see "Android emulator job". |
| CI `plugin-e2e (windows-latest)`, `plugin-e2e (macos-latest)` | No Nix (Windows) and no Linux containers, so Go and Node come from `actions/setup-*` and PostgreSQL runs natively: on macOS from `ikalnytskyi/action-setup-postgres`, on Windows the version the runner image preinstalls (its `postgresql-x64-*` service, started by the job, which fails if the major version is below the minimum supported 14), so the job does not depend on the Chocolatey community feed. The S3-compatible store is the pinned versitygw release (the same version, credentials and region as the compose stack) run natively by `scripts/with-native-s3.sh`, which downloads it (the archive is cached, and its SHA-256 is checked on every run before the executable is extracted into a private temporary directory), exports the `VAULT_SYNC_TEST_S3_*` variables and stops it afterwards. The plugin is built with npm, and the driver runs with `./scripts/with-native-s3.sh go test -tags e2e`. |

On Windows, `wdio.conf.mts` starts Obsidian with `--disable-gpu --in-process-gpu`: software rendering in Obsidian's main process instead of a separate GPU process. On a loaded Windows runner, which has no GPU, that process kept dying until Chromium ended Obsidian with "GPU process isn't usable. Goodbye.", and chromedriver reported "Unable to receive message from renderer" in whichever spec was running (#457). No spec checks rendered pixels.

The driver requires both PostgreSQL and the S3-compatible store and fails, rather than skips, when either is not configured. To run it against a PostgreSQL you started yourself, set `VAULT_SYNC_TEST_DATABASE_URL` (a role allowed to create databases), build the plugin, and run `./scripts/with-native-s3.sh go test -count=1 -tags e2e -run TestPluginE2E -v ./cmd/vault-sync-server/` (or set the `VAULT_SYNC_TEST_S3_*` variables for a store of your own and run `go test` directly). The version pinned in `scripts/with-native-s3.sh` must match the versitygw image in `deploy/compose/compose.test.yaml`; the script refuses to run otherwise, and `make test` (part of the required Linux checks) runs `./scripts/with-native-s3.sh --check-pin`, so a compose bump with a stale pin fails CI. Bump both, with the release checksums, together.

## Android emulator job

The workflow `.github/workflows/android-e2e.yml` (job `plugin-e2e (android-emulator)`) runs the whole suite on the real Obsidian Android app (#704). It runs nightly on `master`, on manual dispatch and on pull requests that change the job's own files (the workflow, `plugin/wdio.android.conf.mts`, `plugin/test/e2e/android/` and `*.android.e2e.ts`). It is not a required check: its flake rate is measured first, and making it required is a separate decision.

- **Emulator.** The job opens `/dev/kvm` with a udev rule, installs the emulator and `system-images;android-34;default;x86_64` with Google's `sdkmanager` and `avdmanager` from the runner's SDK, and boots a Pixel 6 AVD headless (`-no-window -gpu lavapipe -feature -Vulkan`), with animations off. The image is the AOSP one, without Google Play services: on `google_apis`, Play services updated itself a minute or two after boot, and Android killed Obsidian, which is bound to its font provider. The renderer mode is `lavapipe` (#852): the emulator's log then shows `vulkan_mode_selected:lavapipe gles_mode_selected:swangle`, that is GLES through ANGLE on SwiftShader's Vulkan device rather than SwiftShader's own GLES renderer. SwiftShader's JIT is therefore still in the GLES path, so the crash below may be rarer rather than gone; #733 measures it. The job first used `swiftshader_indirect`, which the emulator deprecated in 36.4.9: its SwiftShader renderer segfaulted (exit status 139, in the host renderer's JIT-compiled code) as soon as chromedriver attached to Obsidian's WebView, on the runners' AMD EPYC hosts. Guest Vulkan off (`-feature -Vulkan`) made that crash rarer but did not end it: about one run in four during #704, on emulator 37.2.12 and the older 35.2.10, then five of the first six nightly runs on `master`. A manual dispatch can pick another mode (input `gpu`) to compare renderers; the step "Emulator renderer" prints the GLES backend the emulator chose. If the emulator still dies mid-run, every later spec fails (the first one usually with `Method is not implemented when running "execute/sync"`, the WebView being gone, the rest unable to create a session), `emulator.log` in the job's artifact ends with `emulator exited with status 139`, and the job annotates the run with an error saying the emulator crashed. Read such a failure as this flake, not as a plugin regression; #733 tracks its rate. `avdmanager` on the runner writes AVDs under `~/.config/.android/avd`, so the job sets `ANDROID_AVD_HOME` there.
- **APK.** `plugin/wdio.android.conf.mts` downloads `Obsidian-<version>.apk` from the `obsidianmd/obsidian-releases` release of the version `wdio.conf.mts` pins (`obsidianVersion`) into `plugin/.wdio-obsidian-cache/android`. On every run, cached or not, it checks the file's SHA-256 against `obsidianApkSha256` in `wdio.conf.mts`, the `digest` GitHub reports for the asset (`gh api repos/obsidianmd/obsidian-releases/releases/tags/v<version>`). A mismatch deletes the file and fails the run before anything is installed. A Renovate bump of `obsidianVersion` must therefore come with the new hash: until it does, this job fails and the desktop jobs do not.
- **Driver.** `wdio-obsidian-service` drives the app through Appium's UiAutomator2 driver. Appium, the driver and `@wdio/appium-service` are a separate npm project, `plugin/test/e2e/android/package.json` with its own lock file, so the plugin's other jobs do not install them. `wdio.android.conf.mts` loads the service from there and sets `APPIUM_HOME` to it, where Appium 3 finds the driver. Locally, after booting an emulator: `npm ci --prefix plugin/test/e2e/android`, then `VAULT_SYNC_E2E_ANDROID=1 make test-e2e` (`ANDROID_HOME` for `adb`, `ANDROID_SERIAL` if the device is not `emulator-5554`).
- **Network.** `wdio.android.conf.mts` maps the server's and the fake issuer's ports with `adb reverse`, so the device reaches them at the host's `127.0.0.1` addresses, as the desktop specs expect. `device.android.e2e.ts` reaches the server over the emulator's network instead (`127.0.0.2`, sent on to `10.0.2.2`; see its description above).
- **Failures.** The job uploads WebdriverIO's logs, the device's `logcat`, a screenshot and the emulator's log as the `android-e2e-logs` artifact.

## Real Android app on an emulator (spike, #187)

The emulated-mobile job runs desktop Obsidian with the mobile UI. Spike #187 tried the suite on the real Obsidian Android app in an Android emulator on GitHub's `ubuntu-latest`, to find out whether checks in `docs/testing/android.md` could become automated tests. The experimental workflow, its WebdriverIO configuration and the driver's config override are in commit `f5b09130` of [#627](https://github.com/solidDoWant/vault-sync/pull/627). They were removed before that PR merged; the job that adopted them is "Android emulator job" above.

**Setup that worked.**

- **APK.** Every `obsidianmd/obsidian-releases` GitHub release since 1.5.8 ships `Obsidian-<version>.apk`, the same repository the desktop suite downloads from. The GitHub API reports a SHA-256 `digest` for each release asset (`gh api repos/obsidianmd/obsidian-releases/releases/tags/v1.14.4`). The workflow pinned 1.14.4, the version `wdio.conf.mts` pins, and checked the APK with `sha256sum -c` before installing it. `wdio-obsidian-service` accepts only Obsidian URLs from that repository or `releases.obsidian.md`, but does not check the APK's hash itself, so a harness must.
- **Emulator.** KVM is available on `ubuntu-latest` once a udev rule opens `/dev/kvm`. Google's `sdkmanager` and `avdmanager` from the runner's preinstalled SDK installed the emulator and `system-images;android-34;google_apis;x86_64` (no third-party emulator action), and `emulator -no-window -gpu swiftshader_indirect` booted it. `avdmanager` on the runner writes AVDs under `~/.config/.android/avd`, so the emulator needs `ANDROID_AVD_HOME` pointing there.
- **Driver.** `wdio-obsidian-service` 3.3.0 drives the Android app through Appium's UiAutomator2 driver (`appium` and `@wdio/appium-service`, plus `appium driver install uiautomator2`, since Appium 3 finds drivers only in `APPIUM_HOME` or `package.json`). The capability is `platformName: "Android"`, `appium:automationName: "UiAutomator2"` and `appium:app` the verified APK. The existing Go driver, real server, PostgreSQL and S3 ran unchanged. `adb reverse` mapped the server's and the fake issuer's ports, so the device reached them at the same `127.0.0.1` addresses as the host.

**Time.** In two runs (run 39551115287, two parallel jobs), the job took about 7.5 minutes: SDK and system image install 46–60 s, emulator boot 31–32 s, and the e2e step 263–269 s (building the server and the plugin included; WebdriverIO's part 3 min 30 s). That is close to the emulated-mobile job.

**Flakiness.** Both runs had exactly the same result: 12 of the 16 spec files that existed then passed (`config`, `conflicts`, `editor`, `history`, `journal`, `lifecycle`, `paths`, `realtime`, `signin`, `startup`, `sync`, `unsaved`), and the same tests in the same 4 failed. Two runs show the failures are deterministic, not that the passes are stable; a flake rate needs many more runs. `sync.e2e.ts` passing means the attachment transfer (more than two upload chunks and download ranges, compared by SHA-256) and the IndexedDB journal work on the Android WebView and Capacitor's filesystem.

**The 4 failing spec files.** None was a timeout or an infrastructure failure.

- `smoke.e2e.ts` and `platform.e2e.ts` assume a desktop app: `isDesktopApp`, a status bar rather than the ribbon icon, the host's `process.platform` and a `FileSystemAdapter` base path. These need an Android mode in the specs. In `platform.e2e.ts`, Capacitor reported a 300-byte file name as `Error: FILE_NOTCREATED`; the Obsidian adapter now takes that as `VaultError` `unmaterializable` when the parent folder exists ([#705](https://github.com/solidDoWant/vault-sync/issues/705)), covered by an adapter unit test, not yet rerun on the emulator. In `smoke.e2e.ts`, `requestUrl` to the server failed with an unknown WebDriver error after switching to the second vault. The cause was the driver, not the app: Appium reads a numeric `status` in a script's result as a legacy JSONWP error code, so the spec now names that field `code` (#704).
- `atomicity.e2e.ts` relies on the desktop `FileSystemAdapter`'s internals by design, so it needs an Android counterpart rather than a fix.
- `conformance.e2e.ts`: the case "rename that changes only letter case is allowed" fails with Obsidian's "Destination file already exists!". Android's shared storage is case-insensitive, which the adapter does not handle (tracked by [#544](https://github.com/solidDoWant/vault-sync/issues/544)).

So the emulator found two adapter behaviours that the emulated-mobile job cannot find.

**Device controls.** After the suite, `adb shell` ran each control a #31 row needs, and each command was accepted: `am kill` and `am force-stop md.obsidian`, `input keyevent KEYCODE_HOME` and `am start` (background and foreground), `settings put global always_finish_activities 1` ("Don't keep activities"), `cmd connectivity airplane-mode enable`, `svc wifi`/`svc data disable`, and `dumpsys deviceidle force-idle` (Doze). The spike only checked that Android accepted them, not their effect on a sync. One catch for network tests: traffic over `adb reverse` goes through adbd, not the device's network, so airplane mode does not cut it. Offline tests must reach the server through the emulator's own network (`10.0.2.2`, the host's loopback) instead.

**Which `docs/testing/android.md` checks it could automate.**

| Check | Emulator |
|---|---|
| Process killed mid-sync (section 5) | Yes: `am force-stop` or `am kill` during a sync, then relaunch and compare with the server. |
| Background and foreground, "Don't keep activities" (section 6) | Yes for "Don't keep activities" and a short background. A long background is Doze (`deviceidle force-idle`), which an emulator only approximates. |
| Offline and network changes (sections 4 and 9) | Yes, with the server reached over `10.0.2.2` rather than `adb reverse`. |
| Large first sync (section 3) | Correctness yes. Responsiveness, memory and storage speed are the emulator's, not a phone's, so that part stays manual. |
| Attachments (section 8) | The transfer already passes (`sync.e2e.ts`). |
| BRAT install (section 1), the Android browser and clipboard during sign-in (section 2), battery use (section 9) | No: these stay manual. |

**Recommendation: adopt partially** (implementation: [#704](https://github.com/solidDoWant/vault-sync/issues/704)). Add a non-required Android emulator job (a nightly or manual run first, so its flake rate is measured before anyone considers making it required, which is a separate decision). Make the specs Android-aware, then add the kill, background and network scenarios above and move those rows of `docs/testing/android.md` to automated tests. BRAT, the browser and clipboard, battery use and the large-vault performance check stay manual on a physical device. The reasons: the job costs about as much as the emulated-mobile one, the setup uses only Google's SDK tools and Obsidian's own release, and the first two runs already found two Android-only adapter behaviours.

## Writing e2e tests

- Put specs in `plugin/test/e2e/specs/` as `*.e2e.ts`. Functions passed to `browser.executeObsidian` are stringified and run inside Obsidian, so they cannot capture variables or imports. Pass inputs as extra arguments, and use the `obsidian` module from the first argument.
- Code that must run inside Obsidian and is too big for one function belongs in the harness plugin as a method. Call it from the spec, as `conformance.e2e.ts` does.
- Do not depend on timing. Wait for conditions (`browser.waitUntil`), never for fixed delays.
- Every new assertion must fail when its behavior breaks. Check this by breaking the behavior once before committing.
