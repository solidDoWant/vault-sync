# Sync simulation

The simulation harness (`sim/`, SPEC.md §13) checks sync correctness with seeded, multi-client schedules and fault injection, run against a real `vault-sync-server` backed by real PostgreSQL and S3. In Phase 1 the clients are scripted protocol clients and the invariants are server-side. Phase 2 plugs the real `plugin/src/core` engine in: engine-driven clients (below), whose users make random changes, with user-visible invariants (#22).

## Running

```sh
make test-sim                                   # default: 10 seeds × 1000 steps, 3 clients, 2 engines
make test-sim SIM_SEEDS=200 SIM_STEPS=2000      # longer
make test-sim SIM_SEED=1234                     # replay one seed
```

| Variable | Default | Meaning |
|---|---|---|
| `SIM_SEEDS` | `10` | Number of seeds to run, starting at `SIM_FIRST_SEED`. |
| `SIM_FIRST_SEED` | `1` | First seed. |
| `SIM_SEED` | unset | Run only this seed (overrides the two above). |
| `SIM_STEPS` | `1000` | Steps per seeded schedule. |
| `SIM_CLIENTS` | `3` | Simulated scripted clients (devices of one user) per run. |
| `SIM_ENGINES` | `2` | Engine-driven clients per seeded run, each with a user making random changes. `0` runs without engine users: one engine only pulls and the schedule has no `engine-operation` steps, as seeded runs did before #22. |
| `SIM_SHRINK_RUNS` | `150` | Most re-runs spent minimizing a failing seed. |
| `SIM_REGRESSION_DIR` | `sim/regressions` | Where minimized failing seeds are written, and which regression cases are replayed. A relative path is relative to the repository root (where `make test-sim` runs), wherever you invoke it from. The run fails, naming the variable, if the directory does not exist or holds no `*.json` case. |
| `SIM_TIMEOUT` | `15m` | `go test -timeout` for the whole run. Long deliberate runs (nightly, many seeds) set it explicitly. |

`make test-sim` exits non-zero on any violation. The output names the seed (`SIM FAILURE: seed N ...`), lists the violations, gives the replay command, and shows the end of the minimized schedule's trace. Docker is required. Unlike `make test-integration`, the simulation never skips.

CI runs a short simulation (`SIM_SEEDS=5 SIM_STEPS=1000`) on every pull request, as the `Simulation` step of the required `checks` job. A nightly job runs a long simulation (see [Nightly](#nightly)).

## How it fits together

- **Driver** (`sim/*_test.go`, Go, build tag `sim`). `scripts/test-sim.sh` starts the compose stack (`scripts/with-test-stack.sh`) and runs `go test -tags sim ./sim/`. The driver creates a database and a bucket, starts a fake OIDC issuer, builds and starts the real server (`VAULT_SYNC_SHUTDOWN_DELAY=0s`, 64 KiB chunks so large contents span several chunks), and serves a loopback **control endpoint** for the harness. That endpoint mints a token for a fresh user for every run, which keeps runs below the per-user vault and device limits. The token stays valid until a minute after the `go test` deadline (`SIM_TIMEOUT`), so a long single-seed run never outlives it (#110); a run without a deadline (`-timeout 0`) gets a week. It also checks the invariants directly in PostgreSQL and records failing seeds. For scripted scenarios about retention, `POST /purge` ages the given revisions past the default retention policy (to one UTC day 100 days ago) and purges their documents with the server's own `PurgeRevisions`, as the hourly job would; it returns the purged revisions and remembers them for the invariant checks. Seeded schedules never purge. The driver then runs `plugin/node_modules/.bin/vitest run --config vitest.sim.config.ts`.
- **Harness** (`sim/*.ts`, TypeScript). It is type-checked with `plugin/src/core` (`plugin/tsconfig.core.json`), so it may not use Node APIs or reach `obsidian`. `plugin/vitest.sim.config.ts` reads the environment and the regression cases and passes them in with vitest `provide`/`inject`. There is no `sim/package.json`. `sim/node_modules` is a committed symlink to `../plugin/node_modules`, so `sim/` resolves the plugin's packages (the same files `src/core` resolves, with their `exports` maps intact), and `scripts/check-core-program.ts` checks its imports against `plugin/package.json`. The pure unit tests (`sim/*.test.ts`) run in `make test`. The networked suite (`sim/*.sim.test.ts`) runs only from `make test-sim`.

## The simulated network and fault injector

Each client reaches the server through a `Transport` from `SimNetwork` (`sim/network.ts`). A call does not go out by itself. It waits until a schedule step delivers it to the server, and its response then waits until a step delivers it back. Time is the step counter, and only one message is in transit to the server at a time, so a run is deterministic. Concurrency is modelled by interleaving. True parallel load on the server is the integration tests' job.

In seeded schedules (and the regression cases recorded from them) a commit retried with a revision id it already sent waits out a backoff of 30 logical steps (`seededCommitRetryBackoff`, `sim/runner.ts`) before it can be delivered, as a real client's retry would. Meanwhile other clients' commits can move the document's head, the interleaving of #12, which a retry delivered at once almost never meets. Scripted scenarios, and regression cases recorded before #110 (no `commitRetryBackoff` field), retry at once. Draining (after the schedule, or when a scenario drains) does not advance the step counter. Once nothing else can be delivered, it lets time pass instead (`SimNetwork.passTime`): the clock moves on to whichever comes first, the next backoff timer (below) or the end of the next held retry's backoff. Before #302 a retry sent while draining, such as an engine's push after the faults heal re-sending a commit whose earlier attempts were lost, waited for steps that never came, and the run hung. Fault delays and partitions do not end this way; `heal` lifts them. The network also checks every retry on the wire: once the server has applied a `CommitRevision`, whether or not its response then reached the client, a later `FAILED_PRECONDITION` or `ALREADY_EXISTS` for the same revision id is a `protocol` violation. The client would otherwise rebase or move its change and commit it again as a second revision, which the server-side invariants cannot tell from a real edit.

| Step | Effect |
|---|---|
| `operation` | A client starts create, edit, rename, delete or pull, if it is idle. A client that has not pulled since it (re)started pulls first. |
| `deliver-request` / `deliver-response` | The oldest deliverable request reaches the server, or the oldest response reaches its client. |
| `reorder` | A request other than the oldest reaches the server. |
| `delay` | A request is held back for N steps. |
| `drop-request` | A request is lost before the server sees it. The client gets `UNAVAILABLE`. |
| `drop-response` | A response is lost after the server applied the request. The client gets `UNAVAILABLE`. |
| `partition` | A client is cut off for N steps. Everything it has in flight is lost, and new calls wait. |
| `crash` | A client loses all in-memory state and restarts. Requests it already sent may still reach the server, and it never hears their replies. Engine i crashes with client `i % SIM_CLIENTS`. |
| `engine-operation` | Engine N's user creates, edits, renames or deletes a file in its vault, or the engine starts a push. Generated only for runs with engine users. |

Scripted scenarios can also have the server's per-user limit on concurrent requests (SPEC.md §12) refuse a client's oldest request (`SimNetwork.throttle`). The request never reaches the server, and its client gets `RESOURCE_EXHAUSTED`, as the real limit answers before the handler runs. Seeded schedules do not generate this fault, so their schedules are unchanged. The engines' backoff timers (`SyncEngineOptions.timers`) run on the network's clock (`SimNetwork.timers`): a timer for `ms` milliseconds fires `ceil(ms / 1000)` steps later, and draining moves the clock on to the next timer once nothing else can be delivered. Their jitter comes from a seeded `Random`, so runs replay identically. The network checks every client told `RESOURCE_EXHAUSTED`. Sending a request before setting a backoff timer, or while one is pending, is a `backoff` violation.

The schedule is a pure function of the seed (`sim/schedule.ts`), so the same seed always replays the same operation and fault schedule. Changing the step weights (`stepWeights`, `operationWeights`) changes the schedule of every seed, so `SIM_SEED=N` before and after such a change are different schedules; committed regression cases store their steps and replay unchanged. The weights were last tuned in #110, without engine users (`SIM_ENGINES=0`): about 35 acknowledged revisions, 7 rebases after `FAILED_PRECONDITION` and 9 conflict paths after `ALREADY_EXISTS` per 1000-step seed with 3 clients. With the default two engine users, `engine-operation` steps take a share of the schedule. Seeds 1 to 10 averaged about 42 acknowledged revisions (the engines' commits included), 5 rebases and 5 conflict paths of the scripted clients. A client has one call in flight at a time and about a third of the delivery steps find nothing of their kind to deliver, so the weights move these numbers only a little; longer schedules (`SIM_STEPS`) or more clients (`SIM_CLIENTS`) raise them. Steps choose their targets relative to what is pending at that moment, so any subsequence of a schedule is still valid. Raw ids are random, because one database serves every run. Traces use symbolic labels instead (`c1.d3`: client 1's third document), so a replayed seed produces the identical trace. The determinism test re-runs a seed and compares the two traces.

## Scripted clients

The scripted clients (`sim/client.ts`) follow the protocol's commit discipline (SPEC.md §6.2–6.3):

- They upload content in chunks, resuming from `BeginBlob` after any interruption.
- They commit against the head they know.
- After a lost call they retry with the same revision id.
- On `FAILED_PRECONDITION` they rebase onto the head the error reports.
- On `ALREADY_EXISTS` they retry under a conflict path.
- They create every document as `text`, and commit an edit, rename or delete with the kind the server reported for the document, which never changes (SPEC.md §7). An engine creates a blob document at a path without a text extension (`trailing.`, `NOTES`), and the server refuses a commit of another kind (#306).

Paths come from a small pool with case and Unicode collisions (`a.md`/`A.md`, `straße.md`/`STRASSE.md`) and three names Windows cannot hold (`CON.md`, `ab:c.md`, `trailing.`). Contents are often shared between clients, so clients upload identical blobs, and a content is occasionally larger than one chunk. The harness, not the clients, records every revision the server acknowledged, so acknowledgements survive crashes.

## The engines

Each run also has clients driven by the real sync engine (`sim/engine-observer.ts`), each with its own registered device. They are labelled `e<N>` and come after the scripted clients (with 3 scripted clients, `e3` and `e4`). They reach the server through the same simulated network, so drops, reordering and delays hit their calls too. Every engine starts a pull whenever a schedule step asks any client to pull (if it is idle). Engine i crashes whenever client `i % SIM_CLIENTS` crashes. A crash discards the engine and its in-flight calls but keeps its in-memory vault and journal, as a killed app keeps its disk.

In seeded runs each of the `SIM_ENGINES` engines has a user (`sim/engine-user.ts`). On `engine-operation` steps the user creates, edits, renames or deletes files, at any moment, also while the engine is pulling or pushing, as a person would in Obsidian. Paths come from the scripted clients' pool. Contents are mostly unique, sometimes shared with the scripted clients or larger than one chunk, and an edit often appends a line, so three-way merges happen. A change the vault refuses (a name the platform cannot hold, a file in the way) simply does not happen. The same steps also make an engine push. Scripted scenarios drive the engines themselves (`RunOptions.engines`). The revisions the engines' pushes get acknowledged are recorded like the scripted clients' ones, so the `history` invariant covers them. Schedules without engine users are generated exactly as before #22 (a unit test pins one), and regression cases recorded before #22 (no `engines` field) replay with one engine without a user, as they were recorded.

Each engine follows one platform's path rules (SPEC.md §8, #20): its engine gets the `pathRules` option and its in-memory vault refuses what that platform cannot hold. Under `windows` and `macos` rules the vault also matches paths ignoring case and Unicode form. In seeded runs engine i follows `platformForSeed(seed + i)` (`seededPlatforms`): seed 0 and every third seed after it `posix`, then `windows`, then `macos`. With two engines, two of every three seeds put Windows rules next to another platform, and CI's five seeds cover all three. Scenarios choose per engine (`RunOptions.platforms`). Under Windows rules, documents at the pool's illegal names (and their conflict paths) are tracked as unmaterializable, which the trace shows as `tracks … as unmaterializable (…)`.

After the faults heal, every engine pushes, in rounds, until a round commits nothing (`liveness` if that takes more than 8 rounds). Then every engine pulls once more without faults, and the harness checks each one against the server's live heads, which it reads itself with fault-free `ListChanges` calls, independently of the engine. Since all engines must match the same heads, they converge to identical content and structure:

| Invariant | Check |
|---|---|
| `engine-convergence` | The engine's vault holds exactly the live documents' paths with their head content (by hash), and its cursor is the feed's last `seq`. Modulo the unmaterializable set: documents its platform cannot hold are absent, and the edited file the engine keeps for such a document (SPEC.md §8) may stay. |
| `engine-unmaterializable` | It reports exactly the live documents whose paths its platform cannot hold as unmaterializable, by the harness's own check (`harnessUnmaterializable`, independent of the engine's rules). |
| `engine-deferred` | It deferred no revision other than those unmaterializable ones and, with config sync (scenarios only), `out-of-scope` revisions of live documents it does not sync or of tombstones. Every local change has been pushed, so every other deferral would be a bug. |
| `engine-echo` | It reported none of its own writes, renames or deletes as local changes. Only paths its user changed may be reported. Under `windows` and `macos` rules those paths match as the vault matches them, by path key: the user's write of `STRASSE.md` over `straße.md` is reported as a modify of `straße.md` (#247). Under `posix` they must match exactly. |

An `engine` violation means one of its pulls or pushes failed with something other than a network fault or a refusal by the server's per-user limit (`RESOURCE_EXHAUSTED`, after which the engine backs off).

### User-visible invariants (#22)

The harness records what each engine's user did, as it happened (`UserLedger`, `sim/invariants.ts`). It records each write's content hash, the contents the user overwrote or deleted themselves, the documents whose files the user deleted (by the engine's journal at that moment, including documents the user's own earlier renames moved there), and every write and rename with the server's head `seq` at that moment. The harness knows the head exactly, because every call goes through the simulated network, which sees every reply; feed `seq`s then order the user's changes against the revisions without a clock. A scenario's save just before an engine write (#163) is recorded as a user write too. Every merge the engine asks its merge hook for is recorded too: the local content, and the merged result and conflict copy it became. After the engine checks:

| Invariant | Check |
|---|---|
| `lost-write` | Every user write survives, unless that user overwrote or deleted it themselves. It survives if its content is in a final vault, in history, or in what a merge made of it (the merged result or the conflict copy, which must survive in turn). Content found only in history counts once it downloads (fault-free `DownloadBlob`) and matches its hash. This covers every edit the engine reported as acknowledged, and also any the engine never pushed. |
| `phantom-delete` | Every tombstone in the change feed was committed by a scripted client (which deletes only when its schedule says so) or by an engine whose user deleted that document's file. No file disappears without a delete. One case is excused, #167 item 2's known limitation (#280). The engine's user renamed the document's file away, the app was killed after that and before the tombstone was committed, and after the crash the engine committed the renamed file as another document: a revision holding a content the file held since the rename (the ledger follows it through the user's later renames and writes until the user deletes it), at a path it had since (by path key under Windows and macOS rules), that is either its document's first revision or a revision of a document whose file the user deleted (the engine took the file for that document, #254). The engine never recorded the rename, so its full scan pushed a delete plus a create: the user sees the same file at the same path, and only the document id changed. Nothing else is excused: not a rename the running engine lost, and not a delete without that create. |
| `resurrected-delete` | Every live revision that directly follows a tombstone of the same document (a deleted document brought back) was committed by a scripted client, or by an engine whose user wrote or renamed a file at one of the document's paths (any path it held up to then, compared by path key on a case-insensitive platform). That change must come before the revision was committed, and no earlier revision of the document from the same engine may already carry it: none committed after it that is a tombstone or holds what the file held after it or after a later change there. A deleted document comes back only through a concurrent edit (SPEC.md §4) or the user re-creating the file (§8), never because an engine failed to apply a delete and then pushed the file it kept. |

The checks are pure functions with unit tests (`sim/invariants.test.ts`). `sim/invariants.sim.test.ts` proves each one catches the bug it exists for, against the real server. Two engines sync two notes, and the second engine's user edits one. Unchanged, the run has no violation. Then the harness overwrites the edited note behind the user's back, as an engine that loses a write would, and the run must report exactly `lost-write`. Or the harness deletes the other note behind the user's back, as an engine that drops a file would, and the run must report `phantom-delete` (plus `engine-echo`, since the engine then reports that delete as the user's). A third scenario has a macOS engine whose user writes `STRASSE.md` over the synced `straße.md`. The run must have no violation, and the write must reach the other engine as an edit of `straße.md`. With an unsuppressed engine write of `NOTES/B.md` added, the run must report exactly `engine-echo` for `notes/b.md`. For `resurrected-delete` (#276), two engines sync two notes, the first engine's user deletes one, the second engine pulls the delete, then crashes and pushes, which makes its next push a full scan. Unchanged, the run has no violation and nothing comes back. When the second engine's delete of that note leaves the file on disk (the engine skipping a remote tombstone), the full scan pushes it back, every vault converges on it, and the run must report exactly `resurrected-delete`. The same scenario with the second engine's user editing the note before the pull (a concurrent edit, which wins) or writing it again after it must bring the note back with no violation. The same file runs a seeded schedule with users on a Windows and a POSIX engine, which must keep every invariant, and replays a seed with engine users to compare the traces.

## Invariants

After the schedule, the run heals every fault, delivers everything still in flight, and has every client pull. The driver then checks the vault in PostgreSQL (`sim/invariants_test.go`):

| Invariant | Check |
|---|---|
| `history` | Every acknowledged revision is in history, stored exactly as acknowledged. A revision the run had retention purge (`POST /purge`, below) is excused, and so is its child's parent link, which the purge moves to the nearest retained ancestor (SPEC.md §11). |
| `seq` | The vault's `seq` values are exactly `1..head_seq`: gapless, unique and monotonic, except for the `seq` values of revisions the run had retention purge. |
| `path-key` | No two live documents share a `path_key`. This is checked directly, not only through the unique index. |
| `path-folder` | No live document's `path_key` is a folder (a proper prefix ending before a `/`) of another live document's (SPEC.md §5). |
| `stale-base` | Each document's revisions, in `seq` order, form one chain, each based on the previous head. A commit accepted against a stale base forks the chain. |
| `document-head` | Each document row mirrors its head revision (`head_rev_id`, `deleted`, `path_key`). |

The clients also report `protocol` violations: a gap or reordering seen in `ListChanges`, an idempotent retry rejected as stale, or an error code the protocol does not allow for the call. The network reports one when the server refuses a retry of a commit it already applied (above). A `liveness` violation means the clients did not quiesce. It names the step, the clients still busy and what the network still holds (each message, and the delay, retry backoff or partition holding a request back). A run that stops making progress is reported the same way, never left to idle until the run timeout (#302). Whenever the harness waits for an engine (`EngineObserver.settled`, behind the scenario helpers and the final checks), nothing delivers messages meanwhile, so an engine waiting on the network would wait forever. The wait goes through `SimNetwork.untilSettled`. If the engine has not settled after `stallTurns` (1000) event-loop turns with no network activity, the wait throws a `StallError` naming the step, the engine and what the network holds, and logs it to the trace as `STALLED`. A scenario fails with that error and the end of the trace. The final checks record it as a `liveness` violation, so a seed is minimized and reported as usual. The bound counts turns, not time: the engine runs on promise chains alone (its backoff runs on the network's clock, and the push debounce is off), so work not blocked on the network finishes within one turn, and a loaded machine cannot trip the bound. `TestInvariantChecksDetectEachViolation` corrupts a valid vault in each of these ways and proves that each check catches it. `TestInvariantChecksExcuseOnlyPurgedRevisions` purges a revision with `POST /purge`'s code and proves the checks excuse exactly the revisions they are told were purged: the same state without the excuse violates `history` and `seq`.

## The harness has teeth

`TestSimulationDetectsBrokenServer` builds the server with the `simfault` build tag. In that build `internal/store` skips CommitRevision's base-revision check (`skipBaseRevisionCheck`, `internal/store/simfault_on.go`). The test always runs the schedule of CI's short run (seeds 1 to 5, 1000 steps, 3 clients), whatever the `SIM_*` variables say, and requires a `stale-base` violation. Pinning it means a local replay of one seed or a shorter run cannot make the check fail. It then replays the minimized case the harness wrote and requires that the case reproduces the violation. The switch exists only as a build tag. No flag or environment variable reaches it, and `TestDefaultBuildChecksBaseRevision` proves the default build keeps the check. The driver also verifies from each binary's build info that it was built with exactly the tags it asked for.

`TestSimulationDetectsRefusedRetry` does the same with the `simfault_retry` build tag (#110). In that build CommitRevision refuses a retry of a revision it already applied with `FAILED_PRECONDITION` once the document's head has moved past it (`refuseAppliedRetryAfterHeadMoved`, `internal/store/simfault_retry_on.go`), the #12 bug. Every server-side invariant still holds in such a run, so only the network's retry check can catch it. The test runs its own pinned schedule, CI's short run without engine users (`refusedRetrySchedule`: seeds 1 to 5, 1000 steps, 3 clients, `SIM_ENGINES=0`). With engine users those seeds no longer meet a commit retried after the head moved (#284). It requires that a seeded schedule (not only the scripted #12 scenario) reports the refused retry as a `protocol` violation, and replays the minimized case. `TestDefaultBuildReturnsAppliedRetries` proves the default build never refuses such a retry.

## Nightly

`.github/workflows/sim-nightly.yml` runs a long simulation every night on master, and on demand (`workflow_dispatch`, with the seed count, steps and first seed as inputs). It runs 50 seeds × 3000 steps with 3 scripted clients and 2 engine users, and `SIM_SHRINK_RUNS=10`. The first seed moves with the run number, so every night covers new seeds. Failing seeds are minimized into a copy of the committed cases (`build/sim-regressions`), which is uploaded as the run's `sim-regressions` artifact. The job then files an issue titled `sim: nightly simulation failed (seeds …)`, listing each failing seed's violations and its replay command (`scripts/sim-nightly-report.sh`, tested by `make test`). While such an issue is open, later failures are added to it as comments. The job's token can only read the repository and write issues (`permissions: contents: read, issues: write`), the checkout does not persist it, and the issue copies only the harness's failure lines, never the traces.

## Failing seeds and regression cases

A failing seed is minimized (`sim/shrink.ts`): the harness deletes chunks of steps for as long as a violation of the same kind remains, within `SIM_SHRINK_RUNS` re-runs. It then writes the result to `sim/regressions/seed-<seed>.json` with its violations. Every `make test-sim` replays every committed case. A missing or empty regression directory fails the run before any test starts, so a mistyped `SIM_REGRESSION_DIR` can never pass while it skips the committed cases. To collect failing seeds somewhere else, point `SIM_REGRESSION_DIR` at a copy of `sim/regressions`.

Following CLAUDE.md, a sync bug gets its simulation regression before it is fixed. Commit the case with the fix.

## Scripted scenarios

`sim/scenarios.ts` holds hand-written interleavings that random schedules rarely hit:

- **Platform path rules (#20).** A POSIX engine (`e1`) and a Windows engine (`e2`, after one scripted client). `e1` creates notes Windows cannot hold: `CON.md`, `notes/a:b.md`, `trailing.` and a path over MAX_PATH. `e2` pulls, must write none of them and must report each with its reason. It then crashes and pushes after the restart (a full scan). `e1` renames two synced notes to `plan?.md` and `ok*.md`. `e2`'s user has edited the first and not pushed it: `e2` keeps that file where it was, with the edit, and removes the unchanged second one (its content is on the server). `e2` must commit nothing while the notes cannot be materialized: no rename, no delete, not the edit. Then `e1` renames every one to a legal name. Each must materialize on `e2`, the edit must be merged and committed, the note must keep its document id, and both vaults must end identical with no violations. A second test runs a 400-step seeded schedule with the engine under Windows rules. It must keep every invariant and track at least one unmaterializable document. A third test (`freedPathReused`, from the review of #217) reuses the paths such renames free. `e1` renames three notes `e2` has synced, unchanged, to `plan?.md`, `empty?.md` and `draft?.md`, so `e2` removes their files. `e1` then creates another note at `plan.md` and an empty note (the same content as the empty original) at `empty.md`, while `e2`'s user creates a new note at `draft.md` and `e2` crashes. Once `e1` renames the originals to legal names, all six notes must be live with their own content and document ids in both vaults: none merged into another, deleted, or left unpushed.

- **Lost response after the head moved (#12).** The server applies a commit from c0, but the response is lost. c1 pulls and commits on top of it. c0 then retries with the same revision id and must get its own revision back, not `FAILED_PRECONDITION`.
- **The server's per-user limit refuses the engine's calls (#146).** The engine edits a note and pushes, and the limit refuses its `CommitRevision`. Each time the engine is refused, the scenario starts its next push at once, and the limit refuses that push's `ListChanges`, then its `BeginBlob`, then its `CommitRevision` again. The fifth push lands the edit. A second edit's first push is refused once more, and the push after it lands. The network's `backoff` check must find nothing, so the engine never sent a request while it backed off. The five delays must be within the bounds of 0.5 to 1 s, 1 to 2 s, 2 to 4 s, 4 to 8 s and, after the push that succeeded, 0.5 to 1 s again. The first edit must be acknowledged once, with the revision id of every one of its `CommitRevision` requests, and the server's head must hold the second edit.
- **Engine push under faults (#17).** The engine edits a document c0 created and pushes three times. First, its `CommitRevision` response is lost, and the retry with the same revision id must be acknowledged once and never conflict. Second, c1 moves the head between the engine's pull and its commit. The engine must pull, merge (the scenario's hook keeps both sides) and commit on top of c1's revision. Third, a 150 KiB upload loses its second chunk and the engine crashes. After the restart, the upload must resume at the server's received size without sending the first chunk again. The run must end with no violations, and the engine's copy must equal the server's head.
- **Engines edit concurrently (#18).** Two engines (`e1` and `e2`, after one scripted client) use their default three-way merge hook. Their clocks are fixed, so conflict-copy names replay identically. Each phase starts with both engines changing their vaults. `e2`'s push runs until its `CommitRevision` is next. Then `e1`'s push commits, and only after that does `e2`'s commit reach the server, which refuses it. `e2` then pulls, merges and commits again. The phases cover: non-overlapping edits of a note (merged, and the merged commit's response is lost once); overlapping edits (a conflict copy, and `e2` crashes after the merge, before it uploads the copy); concurrent edits of a binary file; a CRLF conversion against a line edit (merged); two creates at one path; and two creates at paths that differ only by case. The run must end with no violations, every phase's first commit from `e2` must have been refused, both vaults must be identical and hold the expected files (no conflict markers), and `e2`'s conflict log must list the four conflicts.
- **Remote rename onto an unsynced local file (#18, review of #173).** `e1` renames a synced note from `notes/a.md` to `notes/c.md` and appends a line, while `e2` has created an unrelated note of its own at `notes/c.md` and not pushed it. `e2` pulls, crashes, and pushes after the restart.
