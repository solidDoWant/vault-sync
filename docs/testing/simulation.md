# Sync simulation

The simulation harness (`sim/`, SPEC.md §13) checks sync correctness with seeded, multi-client schedules and fault injection, run against a real `vault-sync-server` backed by real PostgreSQL and S3. In Phase 1 the clients are scripted protocol clients and the invariants are server-side. Phase 2 plugs the real `plugin/src/core` engine in: engine-driven clients (below), whose users make random changes, with user-visible invariants (#22).

## Running

```sh
make test-sim                                   # default: 10 seeds × 1000 steps, 3 clients, 2 engines
make test-sim SIM_SEEDS=200 SIM_STEPS=2000      # longer
make test-sim SIM_SEED=1234                     # replay one seed
```

| Variable | Default | Meaning |
|---|---|---|
| `SIM_SEEDS` | `10` | Number of seeds to run, starting at `SIM_FIRST_SEED`. |
| `SIM_FIRST_SEED` | `1` | First seed. |
| `SIM_SEED` | unset | Run only this seed (overrides the two above). |
| `SIM_STEPS` | `1000` | Steps per seeded schedule. |
| `SIM_CLIENTS` | `3` | Simulated scripted clients (devices of one user) per run. |
| `SIM_ENGINES` | `2` | Engine-driven clients per seeded run, each with a user making random changes. `0` runs without engine users: one engine only pulls and the schedule has no `engine-operation` steps, as seeded runs did before #22. |
| `SIM_FAITHFUL_FS` | unset (`1`) | The seeded suites (`seeds`, `retention`, `members`, `restores`) run on the faithful-filesystem vault with the extended path pool unless this is `0` (see [Faithful filesystem](#faithful-filesystem)); `0` opts into the plain pool, to replay a seed recorded before refactor step R7 with the schedule it failed with (on the faithful vault: the folded one is gone, #797). The scripted scenarios ignore it, and each regression case replays with the setting it recorded. A failing faithful seed's case is `seed-N-faithful-fs` (with `"faithfulFilesystem": true`); a plain-pool one's is `seed-N`, and its replay command carries `SIM_FAITHFUL_FS=0`. |
| `SIM_SHRINK_RUNS` | `150` | Most re-runs spent minimizing a failing seed. |
| `SIM_REGRESSION_DIR` | `sim/regressions` | Where minimized failing seeds are written, and which regression cases are replayed. A relative path is relative to the repository root (where `make test-sim` runs), wherever you invoke it from. The run fails, naming the variable, if the directory does not exist or holds no `*.json` case. |
| `VAULT_SYNC_SIM_SUITES` | all but `restores` and `shrink` | Comma-separated suites to run: `seeds`, `retention`, `members`, `restores`, `regressions`, `scenarios`, `determinism`, and `shrink`. A full run leaves out `shrink` (the [targeted shrink](#targeted-shrink)) and, until the engine bug it finds is fixed (#861), `restores` (see [Server restores](#server-restores-650)): they run only when selected. An unknown name fails the run. |
| `SIM_SHRINK_CASE` | unset | With the `shrink` suite: the saved case (a regression case's `*.json` file, relative to the repository root) to minimize. Required by that suite. |
| `SIM_SHRINK_INVARIANT` | unset | With the `shrink` suite: the kind of the violation to keep, e.g. `phantom-delete`. Required by that suite. |
| `SIM_SHRINK_MATCH` | unset | With the `shrink` suite: a regular expression the violation's detail must match; any detail of that kind when unset. |
| `SIM_TIMEOUT` | `15m` | `go test -timeout` for the whole run. Long deliberate runs (nightly, many seeds) set it explicitly. |

`make test-sim` exits non-zero on any violation. The output names the seed (`SIM FAILURE: seed N ...`), lists the violations, gives the replay command, and shows the end of the minimized schedule's trace. Docker is required. Unlike `make test-integration`, the simulation never skips: a full run fails if any test was skipped or left as a todo, so no suite or committed regression case drops out silently. A run of a subset (`VAULT_SYNC_SIM_SUITES=scenarios make test-sim`) skips the other suites on purpose and exits zero when every selected test passes (#393). It still fails if it passed no test, or if a test was skipped inside a top-level `describe` block that also ran tests, which is a skip within a selected suite (`checkSuiteRun`, `sim/suiteguard_test.go`).

CI runs a short simulation (`SIM_SEEDS=5 SIM_STEPS=1000`) on every pull request, as the `Simulation` step of the required `checks` job. A nightly job runs a long simulation (see [Nightly](#nightly)).

## How it fits together

- **Driver** (`sim/*_test.go`, Go, build tag `sim`). `scripts/test-sim.sh` starts the compose stack (`scripts/with-test-stack.sh`) and runs `go test -tags sim ./sim/`. The driver creates a database and a bucket, starts a fake OIDC issuer, builds and starts the real server (`VAULT_SYNC_SHUTDOWN_DELAY=0s`, 64 KiB chunks so large contents span several chunks, and the largest allowed `VAULT_SYNC_BLOB_MAX_UPLOADS_PER_VAULT` so abandoned uploads never reach the limit), plus a second replica of the same binary on the same database and bucket whose only difference is `VAULT_SYNC_BLOB_MAX_UPLOADS_PER_VAULT=2` (the harness gets its URL as `VAULT_SYNC_SIM_LIMITED_SERVER_URL`; replicas are stateless and coordinate through PostgreSQL only, so this is an ordinary HA deployment), and serves a loopback **control endpoint** for the harness. That endpoint mints a token for a fresh user for every run, which keeps runs below the per-user vault and device limits. The token stays valid until a minute after the `go test` deadline (`SIM_TIMEOUT`), so a long single-seed run never outlives it (#110); a run without a deadline (`-timeout 0`) gets a week. It also checks the invariants directly in PostgreSQL and records failing seeds. For retention, `POST /purge` ages the given revisions past the default retention policy (to one UTC day 100 days ago) and purges their documents with the server's own `PurgeRevisions`, as the hourly job would; it returns the purged revisions and remembers them for the invariant checks. Scripted scenarios and the `retention` steps of seeded schedules (see [Retention purges](#retention-purges-229)) use it. Aging is done by the sim driver writing `created_at` in PostgreSQL: the server has no RPC, flag or environment variable for it, so its attack surface is unchanged. Likewise `POST /age-uploads` makes a vault's upload sessions in progress look idle for 11 minutes (one past the default `VAULT_SYNC_BLOB_UPLOAD_RECLAIM_IDLE`, far short of the upload TTL) by writing their `updated_at`, so that a `BeginBlob` in a vault at its session limit reclaims them (SPEC.md §6.2, #490). For the restore scenario, `POST /snapshot` backs up a vault's `documents`, `revisions` and `purged_revisions` rows and its `head_seq`, and `POST /restore` puts them back exactly, revision anchors and purge markers included, as a restore of a database backup would (#155). Scripted scenarios and the `snapshot` and `restore` steps of seeded schedules (see [Server restores](#server-restores-650)) use them; one backup per vault is kept, and a later snapshot replaces it. The driver then runs `plugin/node_modules/.bin/vitest run --config vitest.sim.config.ts`.
- **Harness** (`sim/*.ts`, TypeScript). It is type-checked with `plugin/src/core` (`plugin/tsconfig.core.json`), so it may not use Node APIs or reach `obsidian`. `plugin/vitest.sim.config.ts` reads the environment and the regression cases and passes them in with vitest `provide`/`inject`. There is no `sim/package.json`. `sim/node_modules` is a committed symlink to `../plugin/node_modules`, so `sim/` resolves the plugin's packages (the same files `src/core` resolves, with their `exports` maps intact), and `scripts/check-core-program.ts` checks its imports against `plugin/package.json`. The pure unit tests (`sim/*.test.ts`) run in `make test`. The networked suite (`sim/*.sim.test.ts`) runs only from `make test-sim`.

## The simulated network and fault injector

Each client reaches the server through a `Transport` from `SimNetwork` (`sim/network.ts`). A call does not go out by itself. It waits until a schedule step delivers it to the server, and its response then waits until a step delivers it back. Time is the step counter, and only one message is in transit to the server at a time, so a run is deterministic. Concurrency is modelled by interleaving. True parallel load on the server is the integration tests' job.

In seeded schedules (and the regression cases recorded from them) a commit retried with a revision id it already sent waits out a backoff of 30 logical steps (`seededCommitRetryBackoff`, `sim/runner.ts`) before it can be delivered, as a real client's retry would. Meanwhile other clients' commits can move the document's head, the interleaving of #12, which a retry delivered at once almost never meets. Scripted scenarios, and regression cases recorded before #110 (no `commitRetryBackoff` field), retry at once. Draining (after the schedule, or when a scenario drains) does not advance the step counter. Once nothing else can be delivered, it lets time pass instead (`SimNetwork.passTime`): the clock moves on to whichever comes first, the next backoff timer (below) or the end of the next held retry's backoff. A retry's backoff runs on that same clock, so a retry sent while draining waits its 30 steps from where draining has moved the clock to, behind any backoff timer due before then (#310). Before #302 a retry sent while draining, such as an engine's push after the faults heal re-sending a commit whose earlier attempts were lost, waited for steps that never came, and the run hung. Fault delays and partitions do not end this way; `heal` lifts them. The network also checks every retry on the wire: once the server has applied a `CommitRevision`, whether or not its response then reached the client, a later `FAILED_PRECONDITION` or `ALREADY_EXISTS` for the same revision id is a `protocol` violation. The client would otherwise rebase or move its change and commit it again as a second revision, which the server-side invariants cannot tell from a real edit. The interleaving this check needs, a retry of an applied commit delivered after another commit moved that document's head, is marked in the trace (`(retry of an applied commit after its document's head moved)`) and counted in each seed's summary line as `retries after the head moved` (#284).

| Step | Effect |
|---|---|
| `operation` | A client starts create, edit, rename, delete or pull, if it is idle. A client that has not pulled since it (re)started pulls first. |
| `deliver-request` / `deliver-response` | The oldest deliverable request reaches the server, or the oldest response reaches its client. |
| `reorder` | A request other than the oldest reaches the server. |
| `delay` | A request is held back for N steps. |
| `drop-request` | A request is lost before the server sees it. The client gets `UNAVAILABLE`. |
| `drop-response` | A response is lost after the server applied the request. The client gets `UNAVAILABLE`. |
| `partition` | A client is cut off for N steps. Everything it has in flight is lost, and new calls wait. |
| `crash` | A client loses all in-memory state and restarts. Requests it already sent may still reach the server, and it never hears their replies. Engine i crashes with client `i % SIM_CLIENTS`. |
| `engine-operation` | Engine N's user creates, edits, renames or deletes a file in its vault, or the engine starts a push. Generated only for runs with engine users. |
| `retention` | The retention job runs: the oldest revisions of the change feed (a prefix of 1 to all of them, chosen by the step) age past the policy and `POST /purge` purges them. Of each document's aged revisions the newest, and the head, stay. Never drawn with the other kinds: a schedule with retention (`ScheduleOptions.retention`) is the seed's plain schedule with a `retention` step after about one step in 200 (`retentionInterval`), from a stream of its own. |
| `membership` | The vault's owner changes a member's role through the real `MembershipService`, fault-free, between two deliveries: an editor is demoted to viewer or removed, a viewer promoted back to editor or removed, and a removed member invited again as an editor or a viewer (`Members.change`, chosen by the step's `pick`). Never drawn with the other kinds: a schedule with membership changes (`ScheduleOptions.membership`) is the seed's schedule with a `membership` step after about one step in 100 (`membershipInterval`), from a stream of its own. With one user it does nothing. |
| `snapshot` | The operator backs up the vault's database (`POST /snapshot`), fault-free. Never drawn with the other kinds: a schedule with restores (`ScheduleOptions.restores`) has a `snapshot` step after about one step in 150 (`snapshotInterval`), from a stream of its own. |
| `restore` | The operator restores the last backup (`POST /restore`), fault-free, between two deliveries: every revision committed since is gone and `head_seq` goes back, so the server reuses seqs that devices have applied (SPEC.md §6.1, §8). Without a backup yet it does nothing. Inserted after about one step in 250 (`restoreInterval`) in a schedule with restores, from a stream of its own. |

Scripted scenarios can also have the server's per-user limit on concurrent requests (SPEC.md §12) refuse a client's oldest request (`SimNetwork.throttle`). The request never reaches the server, and its client gets `RESOURCE_EXHAUSTED`, as the real limit answers before the handler runs. Seeded schedules do not generate this fault, so their schedules are unchanged. The engines' backoff timers (`SyncEngineOptions.timers`) run on the network's clock (`SimNetwork.timers`): a timer for `ms` milliseconds fires `ceil(ms / 1000)` steps later, and draining moves the clock on to the next timer once nothing else can be delivered. Their jitter comes from a seeded `Random`, so runs replay identically. The network checks every client told `RESOURCE_EXHAUSTED`. Sending a request before setting a backoff timer, or while one is pending, is a `backoff` violation.

The schedule is a pure function of the seed (`sim/schedule.ts`), so the same seed always replays the same operation and fault schedule. Changing the step weights (`stepWeights`, `operationWeights`) changes the schedule of every seed, so `SIM_SEED=N` before and after such a change are different schedules; committed regression cases store their steps and replay unchanged. The weights were last tuned in #110, without engine users (`SIM_ENGINES=0`): about 35 acknowledged revisions, 7 rebases after `FAILED_PRECONDITION` and 9 conflict paths after `ALREADY_EXISTS` per 1000-step seed with 3 clients. With the default two engine users, `engine-operation` steps take a share of the schedule. Seeds 1 to 10 averaged about 42 acknowledged revisions (the engines' commits included), 5 rebases and 5 conflict paths of the scripted clients. A client has one call in flight at a time and about a third of the delivery steps find nothing of their kind to deliver, so the weights move these numbers only a little; longer schedules (`SIM_STEPS`) or more clients (`SIM_CLIENTS`) raise them. Steps choose their targets relative to what is pending at that moment, so any subsequence of a schedule is still valid. Raw ids are random, because one database serves every run. Traces use symbolic labels instead (`c1.d3`: client 1's third document), so a replayed seed produces the identical trace. The determinism test re-runs a seed and compares the two traces.

## Scripted clients

The scripted clients (`sim/client.ts`) follow the protocol's commit discipline (SPEC.md §6.2–6.3):

- They upload content in chunks, resuming from `BeginBlob` after any interruption.
- They commit against the head they know.
- After a lost call they retry with the same revision id.
- On `FAILED_PRECONDITION` they rebase onto the head the error reports.
- On `ALREADY_EXISTS` they retry under a conflict path.
- They create every document as `text`, and commit an edit, rename or delete with the kind the server reported for the document, which never changes (SPEC.md §7). An engine creates a blob document at a path without a text extension (`trailing.`, `NOTES`), and the server refuses a commit of another kind (#306).
- They check every acknowledged revision against the commit request: its document, parent, tombstone flag and kind. A server that acknowledged a commit under another kind, instead of refusing it, is a `protocol` violation (#317).

Paths come from a small pool with case and Unicode collisions (`a.md`/`A.md`, `straße.md`/`STRASSE.md`) and three names Windows cannot hold (`CON.md`, `ab:c.md`, `trailing.`). Contents are often shared between clients, so clients upload identical blobs, and a content is occasionally larger than one chunk. The harness, not the clients, records every revision the server acknowledged, so acknowledgements survive crashes.

## The engines

Each run also has clients driven by the real sync engine (`sim/engine-observer.ts`), each with its own registered device. They are labelled `e<N>` and come after the scripted clients (with 3 scripted clients, `e3` and `e4`). They reach the server through the same simulated network, so drops, reordering and delays hit their calls too. Every engine starts a pull whenever a schedule step asks any client to pull (if it is idle). Engine i crashes whenever client `i % SIM_CLIENTS` crashes. A crash discards the engine and its in-flight calls but keeps its in-memory vault and journal, as a killed app keeps its disk.

In seeded runs each of the `SIM_ENGINES` engines has a user (`sim/engine-user.ts`). On `engine-operation` steps the user creates, edits, renames or deletes files, at any moment, also while the engine is pulling or pushing, as a person would in Obsidian. Paths come from the scripted clients' pool. Contents are mostly unique, sometimes shared with the scripted clients or larger than one chunk, and an edit often appends a line, so three-way merges happen. A change the vault refuses (a name the platform cannot hold, a file in the way) simply does not happen. The same steps also make an engine push. Scripted scenarios drive the engines themselves (`RunOptions.engines`). The revisions the engines' pushes get acknowledged are recorded like the scripted clients' ones, so the `history` invariant covers them. Schedules without engine users are generated exactly as before #22 (a unit test pins one), and schedules without retention exactly as before #229 (another pins one with engine users), and regression cases recorded before #22 (no `engines` field) replay with one engine without a user, as they were recorded.

Each engine follows one platform's path rules (SPEC.md §8, #20): its engine gets the `pathRules` option and its in-memory vault refuses what that platform cannot hold. Under `windows` and `macos` rules the vault also matches paths ignoring case and Unicode form, as the platform's filesystem does (see [Faithful filesystem](#faithful-filesystem)). In seeded runs engine i follows `platformForSeed(seed + i)` (`seededPlatforms`): seed 0 and every third seed after it `posix`, then `windows`, then `macos`. With two engines, two of every three seeds put Windows rules next to another platform, and CI's five seeds cover all three. Scenarios choose per engine (`RunOptions.platforms`). Under Windows rules, documents at the pool's illegal names (and their conflict paths) are tracked as unmaterializable, which the trace shows as `tracks … as unmaterializable (…)`.

After the faults heal, every engine pushes, in rounds, until a round commits nothing (`liveness` if that takes more than 8 rounds). Then every engine pulls once more without faults, and the harness checks each one against the server's live heads, which it reads itself with fault-free `ListChanges` calls, independently of the engine. Since all engines must match the same heads, they converge to identical content and structure:

| Invariant | Check |
|---|---|
| `engine-convergence` | The engine's vault holds exactly the live documents' paths with their head content (by hash), and its cursor is the feed's last `seq`. Modulo the unmaterializable set: documents its platform cannot hold are absent, and the edited file the engine keeps for such a document (SPEC.md §8) may stay, if the engine reports it (compared under the vault's own path matching, `F`) and the file is one the user wrote (by its inode, §5.5 X-14). |
| `engine-unmaterializable` | It reports exactly the live documents whose paths its platform cannot hold as unmaterializable, by the harness's own check (`harnessUnmaterializable`, independent of the engine's rules). Of live documents whose paths are one file on the platform but differ under the path key (`ı.md` and `I.md` on Windows and macOS, `harnessAliases`), the engine must hold exactly one with its head content and report the others (`alias`, #736). |
| `engine-deferred` | It deferred no revision other than those unmaterializable ones and, with config sync (scenarios only), `out-of-scope` revisions of live documents it does not sync or of tombstones. Every local change has been pushed, so every other deferral would be a bug. |
| `engine-echo` | It reported none of its own writes, renames or deletes as local changes. Only an event emitted by a change of its user's (or Obsidian's, in the config folder) may be reported. The in-memory vaults emit each event synchronously inside the change, after the inode tap that names the actor, so the harness marks each event the engine receives while a user change is being applied, with no path matching (#422). An engine write at a path the user changed earlier in the run is still an echo. The user's write of `STRASSE.md` over `straße.md` on macOS is reported as a modify of `straße.md`, and it is the user's event (#247). |
| `engine-resync` | In a run that neither restores a backup nor has retention purge, no engine pull resynced (`PullSummary.resynced`): the server never diverged from any cursor, so a resync would mean an anchor lost or mangled between the server and the engine's journal (#155, #422). |
| `server-seq` | After the last pulls, the harness's server `seq` (`RunContext.serverSeq`) equals the feed head, unless the run restored a backup. It is a lower bound taken from replies, so this check keeps its plumbing from lagging unnoticed (#422). |

An `engine` violation means one of its pulls or pushes failed with something other than a network fault or a refusal by the server's per-user limit (`RESOURCE_EXHAUSTED`, after which the engine backs off).

### User-visible invariants (#22)

The harness records what each engine's user did, as it happened (`UserLedger`, `sim/invariants.ts`): each write's content hash and the contents the user overwrote or deleted themselves. Which file is which document it learns from harness inodes, never from the engine's journal (`sim/lineage.ts`, design `docs/design/engine-path-ownership.md` §5.4). Each engine's vaults tag every change with an inode and the actor that made it (the user, or the engine through its own handle): a create mints an inode, a write or a rename by anyone keeps it, and a delete ends it. The observer records these changes in a timeline, with the server's head `seq` at that moment, every crash, every user restore from history (`EngineObserver.startRestore`, #651) and every settled point (a pull or push that completed, or the engine's `settled()`: every change before it was handled). That `seq` is the highest one a `CommitRevision` or `ListChanges` reply has carried, a lower bound of the head; the `server-seq` invariant checks that it has caught up with the feed head by the end of the run. After the run the harness replays the timeline merged with the change feed by `seq` and binds an inode to a document when the engine commits a revision of it whose path and content match the inode (or, if the file changed since the engine read it, the inode that last held that content at that path, by a write there or a rename onto it, which the user has overwritten, moved or deleted since; only content that never sat at that path falls back to the inode it was last written into anywhere, because with shared contents that can be another document's file, #844), or when the engine writes a revision's content at that revision's path (it applies a pulled revision). The engine's moves of a file, to a remote rename's path or to its own conflict copy, keep the inode and so the binding, except a detach (PO-4(b), §5.5 X-20, by the property oracle's rule `PropertyWorld.detached`): a move to a conflict copy of a file from a path where its document was synced (a live revision of it there, and no user rename of the file onto it since), while the document's newest revision is live elsewhere, unbinds it. A displaced local move (W(a)) or a move of a document's file to a copy of its own path stays the document's file (PO-1, §4.4). A scenario's save just before an engine write (#163) is recorded as a user write too. So is a scenario's restore, once the engine has committed it: the restored content is a user write. The engine writes the restored file itself, so its events there are the engine's, not the user's, for `engine-echo`. What the user overwrote or deleted is keyed by content and path (#422), with paths matched as the engine's vault looks files up: by the filesystem's name with the faithful filesystem, by its path key with the folded one, so a write through `ı.md` on Windows is a write to the file `I.md` and `Straße.md` and `STRASSE.md` are two files (#736): replacing one file that holds X excuses only the user's earlier writes of X whose file had that path. The ledger follows each write's file through the user's renames and the engine's own moves of it (a remote rename it applies, or a move to its conflict copy). A replacement at the engine's conflict copy of a path counts as one at that path, and so does one at wherever the user renamed such a copy to: the engine wrote the copy with what the file held. The copy is followed from the moment the engine writes it (`EngineUser.engineWrote`), with the writes whose file was at that path then, whatever the user does to that file afterwards: a user who deleted or renamed away the original and then overwrote the renamed copy replaced those writes (#745). A write the user made at that path after the copy is not in it. Each merge is also logged in the trace (`merge at …: local … into …`). The user reads what a write or delete replaces in the same tick as the change, so an engine write that lands between them is not recorded as the user's. Every merge the engine asks its merge hook for is checked too. The local content counts as merged into the result only if the harness's own check (`carriesLocalEdit`) finds the local edit there: the result is the local content, or both are text and every non-empty line the local edit added over the base is a whole line of the result, as often as it was added (#717). A line merge never joins two lines into one (#750), so an added line found only as part of a longer line is not carried. The base is the one the hook read; if the hook did not read it, it is the device's base content found by hash among every content its vaults held (`KnownContents`), so no call is added to the run. Without a base, every local line must be in the result. The hook's word is not enough (#301). A conflict copy holds the local content itself, so it survives by being found. After the engine checks:

| Invariant | Check |
|---|---|
| `lost-write` | Every user write survives, unless that user overwrote or deleted it themselves. It survives if its content is in a final vault, in history, or in a merged result that carries it, which must survive in turn. Content found only in history counts once it downloads (fault-free `DownloadBlob`) and matches its hash. Content of a revision the run had retention purge counts as surviving: the policy removed it (SPEC.md §2 principle 1, §11). Only those revisions are excused, never content that never reached the server. This covers every edit the engine reported as acknowledged, and also any the engine never pushed. |
| `phantom-delete` | Every tombstone in the change feed was committed by a scripted client (which deletes only when its schedule says so) or by an engine whose user deleted the document's file, before the tombstone (INV-5, PO-6): an inode bound to that document when the tombstone is judged (not one rebound to another document since), deleted after the document's previous tombstone, if any, so a delete an earlier tombstone carried does not excuse another once the document came back in a new file (#822). No file disappears without a delete. One case is excused, the crash window of a lost rename (#167 item 2, §5.5 X-2): the user renamed the document's file, the app was killed after that and before the engine reached a settled point (so the rename's event may never have been handled), the tombstone came after the crash, and after the crash the engine committed that same inode as a new document's first revision (at any path the inode had, including the engine's own conflict copy of it, X-3, and with any content the engine wrote into it, X-6). The user's delete of the renamed file after the crash needs no excuse: the inode was the document's file (X-7). The crash window never excuses the renamed inode committed as an edit of an existing document: the start-up scan's content match (E7b) binds a file holding another missing document's content to that document (§5.5 X-8, removed by refactor step R11, #793). A rename the running engine had seen is not excused either. |
| `resurrected-delete` | Every live revision that directly follows a tombstone of the same document (a deleted document brought back) was committed by a scripted client, or by an engine from a change of its user's to the file the revision was committed from (the document's own file, or an untracked file at the revision's path, which PO-13 adopts) that no earlier revision of the document from that engine carried: none committed after it that is a tombstone or holds what the file held after it, or after a later change, where it was. Or the user restored the document from history after the tombstone. Changes are matched by inode, not by path (§5.5 X-10). A deleted document comes back only through a concurrent edit (SPEC.md §4), the user re-creating the file (§8) or restoring it (§11), never because an engine failed to apply a delete and then pushed the file it kept. |
| `identity` | No engine commit of a document comes from an inode bound to another document (INV-3, PO-1): matching names or contents never transfer identity. Excused: a new document's first revision from a detached file (PO-4(b), X-20), and the create inside a lost rename's crash window (X-2, above). |
| `journal-holder` | Checked after every step and at quiescence, over the engine's journal (INV-1, INV-2): no two documents' bindings name one file under the vault's own path matching (`F` on the faithful filesystem), no two documents' newest server claims (a deferred revision, else the synced one) are live at one path key once the journal's cursor has reached the server's head (until then a claim may wait on a revision that frees its path, design §4.2 C2), and no two live outboxes are at one path key. |

The checks are pure functions with unit tests (`sim/invariants.test.ts`, `sim/lineage.test.ts`). `sim/invariants.sim.test.ts` proves each one catches the bug it exists for, against the real server. Two engines sync two notes, and the second engine's user edits one. Unchanged, the run has no violation. Then the harness overwrites the edited note behind the user's back, as an engine that loses a write would, and the run must report `lost-write` (plus `engine-echo`, since that overwrite is reported as a local change at a path the user edited earlier, which no longer excuses it, #422). The harness writing back the content the user wrote must report exactly `engine-echo`. A mutation that corrupts the anchors the second engine stores with its cursor must report exactly `engine-resync`, since its pulls then resync on a server that was never restored. Two engines whose users edit one note concurrently must merge both edits with no violation, and the same run with a merge hook that returns the remote content as merged must report exactly `lost-write` (#301). Or the harness deletes the other note behind the user's back, as an engine that drops a file would, and the run must report `phantom-delete` (plus `engine-echo`, since the engine then reports that delete as the user's). A third scenario has a macOS engine whose user writes `STRASSE.md` over the synced `straße.md`. The run must have no violation, and the write must reach the other engine as an edit of `straße.md`. With an unsuppressed engine write of `NOTES/B.md` added, the run must report exactly `engine-echo` for `notes/b.md`. For `resurrected-delete` (#276), two engines sync two notes, the first engine's user deletes one, the second engine pulls the delete, then crashes and pushes, which makes its next push a full scan. Unchanged, the run has no violation and nothing comes back. When the second engine's delete of that note leaves the file on disk (the engine skipping a remote tombstone), the full scan pushes it back, every vault converges on it, and the run must report exactly `resurrected-delete`. The same scenario with the second engine's user editing the note before the pull (a concurrent edit, which wins) or writing it again after it must bring the note back with no violation. Two more variants cover the "already carried" rule and the `seq` plumbing (#422): when the second engine's user edits the note and the engine commits it before the delete, keeping the file on the delete must still report exactly `resurrected-delete`, because the edit was already committed. Writing that same content again after the delete must pass, which only the `seq` recorded with each change can tell apart. For `identity`, the harness swaps the bindings of the two notes in the second engine's journal and restarts it, as an engine that takes one document's file for another's would, and the run must report `identity`. For `journal-holder`, it binds the second note's document to the first note's file as well and runs the check at that durable point, and the run must report `journal-holder`. For a rename chain lost to a crash (#531, #822), two POSIX engines sync `notes/a.md`, and the second engine's user renames it to `notes/b.md`, edits it, renames it to `notes/c.md` and edits it again before the app is killed, and edits it once more before the restarted engine pushes. Unchanged, the run has no violation and both vaults hold the last edit at `notes/c.md`; when the harness deletes `notes/c.md` behind the user's back before that push, the run must report `phantom-delete` for the note at `notes/a.md`. The same file runs a seeded schedule with users on a Windows and a POSIX engine, which must keep every invariant, and replays a seed with engine users to compare the traces.

## Invariants

After the schedule, the run heals every fault, delivers everything still in flight, and has every client pull. The driver then checks the vault in PostgreSQL (`sim/invariants_test.go`):

| Invariant | Check |
|---|---|
| `history` | Every acknowledged revision is in history, stored exactly as acknowledged. A revision the run had retention purge (`POST /purge`, below) is excused, and so is its child's parent link, which the purge moves to the nearest retained ancestor (SPEC.md §11). |
| `seq` | The vault's `seq` values are exactly `1..head_seq`: gapless, unique and monotonic, except for the `seq` values of revisions the run had retention purge. |
| `path-key` | No two live documents share a `path_key`. This is checked directly, not only through the unique index. |
| `path-folder` | No live document's `path_key` is a folder (a proper prefix ending before a `/`) of another live document's (SPEC.md §5). |
| `stale-base` | Each document's revisions, in `seq` order, form one chain, each based on the previous head. A commit accepted against a stale base forks the chain. |
| `document-head` | Each document row mirrors its head revision (`head_rev_id`, `deleted`, `path_key`). |
| `feed-head` | After its last pull every scripted client knows exactly the vault's documents, each at the head in the `documents` table. The change feed skips purged revisions but never a head (SPEC.md §11). This is checked against the database, not against `ListChanges`. |

The scripted clients report `seq` violations from `ListChanges`: a `seq` at or below the one before it (the feed must be strictly ascending), or a skipped `seq` that is not one of a revision the run had retention purge. A purge leaves gaps in the feed on purpose, so the feed need not be gapless, but every gap must be a purge. They also report `protocol` violations: an idempotent retry rejected as stale, or an error code the protocol does not allow for the call. The network reports one when the server refuses a retry of a commit it already applied (above). A `liveness` violation means the clients did not quiesce. It names the step, the clients still busy and what the network still holds (each message, and the delay, retry backoff or partition holding a request back). A run that stops making progress is reported the same way, never left to idle until the run timeout (#302). Whenever the harness waits for an engine (`EngineObserver.settled`, behind the scenario helpers and the final checks), nothing delivers messages meanwhile, so an engine waiting on the network would wait forever. The wait goes through `SimNetwork.untilSettled`. If the engine has not settled after `stallTurns` (1000) event-loop turns with no network activity, the wait throws a `StallError` naming the step, the engine and what the network holds, and logs it to the trace as `STALLED`. A scenario fails with that error and the end of the trace. The final checks record it as a `liveness` violation, so a seed is minimized and reported as usual. The bound counts turns, not time: the engine runs on promise chains alone (its backoff runs on the network's clock, and the push debounce is off), so work not blocked on the network finishes within one turn, and a loaded machine cannot trip the bound. `TestInvariantChecksDetectEachViolation` corrupts a valid vault in each of these ways and proves that each check catches it. `TestInvariantChecksExcuseOnlyPurgedRevisions` purges a revision with `POST /purge`'s code and proves the checks excuse exactly the revisions they are told were purged: the same state without the excuse violates `history` and `seq`. `TestFeedHeadCheck` proves `feed-head` catches a client that missed a document, holds the purged revision as a head, or knows a document the vault does not have.

## Retention purges (#229)

Retention (SPEC.md §11) purges old non-head revisions, and a deployment keeps every revision for at least a day, far longer than any run. The `retention` suite of `sim/simulation.sim.test.ts` therefore runs every configured seed a second time with retention: its schedule (`ScheduleOptions.retention`) is the seed's plain schedule, step for step, with `retention` steps inserted after about one step in 200, and each ages a prefix of the change feed and purges it through `POST /purge`. Purges happen while scripted clients and engines still hold purged revisions as bases, have not pulled them, or retry commits based on them, so pulls meet gaps in the feed and merges meet purged bases (`base-purged` conflict copies). Every invariant above must hold, with the excuses for exactly the purged revisions (`history`, `seq`, `lost-write`), and `feed-head` proves every client still received every document's head. The excuses are narrow: the harness reads every document's head (live or tombstone) before each purge, and a purge that removes one is a `retention-head` violation and is excused neither by the harness nor by the driver's database checks (`excusable`), so the `history`, `seq` and `lost-write` checks it would break still fire (SPEC.md §2 principle 1). The suite also requires that its seeds purged at least one revision in total. Its traces log each purge (`retention purged …`) and the summary line counts the purged revisions. Both seeded suites' summary lines (`sim/summary.ts`) also count `engine resyncs`: engine pulls that found the server's history diverged from their cursor and resynced (#155, #360), so CI logs show whether the purge schedules drive an engine into a resync. A resync inside a push's own pull is not reported to the harness and is not counted. Both seeded suites also drive notification-gated pulls (#277, `RunOptions.notificationPulls`): on a schedule's pull step, the step's `arg` chooses whether the engines pull plainly, pull only if behind the server's latest seq as a `vault_changed` notification would announce it (`SyncEngine.pullIfBehind`), or pull only if behind an earlier seq, a stale or coalesced notification that an engine's cursor may already be past. The summary counts them as `notification-gated pulls`, one per engine (a pull step gates every engine's pull, #661), and those the engine skipped as `notification-gated pulls not needed`. A scripted scenario pins the option: with it the engines' pulls are gated, without it none is. The convergence invariants are unchanged, so a cursor change that made the skip unsafe shows up as a missing or lost revision. Regression cases record the option (`notificationPulls`), and cases recorded before #277 replay with plain pulls.

Because every other step is the plain schedule's, which the `seeds` suite runs too, a seed that fails only with retention fails because of what the purges did. Inserted steps still count as steps, so a partition or delay of N steps that spans one ends a step earlier in the step sequence. A failing seed is minimized and written to `sim/regressions/seed-<seed>-retention.json`, with its `retention` steps among the recorded steps, so the case replays as any other. The case also records `"retention": true` (#646), which `replayOptions` passes back. The `regressions` suite replays every case through `replayRegression` (`sim/regression.ts`), which runs its steps with the options it recorded. A case without the field replays as before. To replay one seed, `make test-sim SIM_SEED=N` runs both its plain and its retention schedule. To run only the retention suite, set `VAULT_SYNC_SIM_SUITES=retention` (the suites are `seeds`, `retention`, `members`, `restores`, `regressions`, `scenarios` and `determinism`).

## Server restores (#650)

The `restores` suite runs every configured seed once more with `snapshot` and `restore` steps inserted into the seed's plain schedule (`ScheduleOptions.restores`), so the server is put back to an earlier backup while messages are in flight, lost, delayed or retried, and while engines and scripted clients hold revisions it no longer has. Each restore step logs `restore to seq N removed K revisions`; the summary line counts the restores, and the suite requires that its seeds restored at least once.

Every invariant is checked across the restores. The only excuse is the driver's `history` check for exactly the revisions a restore removed: before each restore the harness reads the feed, and an acknowledgement of a revision above the backup's head, with the seq it had, is not passed to `POST /check`, because the operator's restore lost it, not the system. Everything a device holds is still checked: `lost-write` requires each engine's acknowledged content to survive on a device or reach the server again, and `engine-convergence`, `lineage`, `phantom-delete`, `resurrected-delete`, `seq`, `stale-base`, `document-head` and `feed-head` apply unchanged (`server-seq` and `engine-resync` are skipped in a run that restores, as before). The network forgets the commits a restore removed (`SimNetwork.recordRestored`), so a retry of one is judged as a new commit.

Scripted clients detect a restored server as a device must (SPEC.md §6.1): each `ListChanges` sends the anchor of the revision at the cursor (`since_anchor`) and of the client's latest commit above it (`own_commit_seq`, `own_commit_anchor`). After a complete pull, an acknowledged commit of the client that the feed passed without delivering it, or that lies above the head, was lost too (a later own commit hides an earlier one from the anchor check). On either sign the client forgets what it pulled and pulls everything again (`cN resyncs: …` in the trace). A diverged response is a `seq` violation unless a restore or a retention purge (whose marker may be pruned) happened since the client's last complete pull, and a lost own commit is one unless a restore removed exactly that revision at that seq. A commit refused because a restore removed its document (`FAILED_PRECONDITION` without a head) is given up only if its base revision is one a restore removed, and is a `protocol` violation otherwise. Both excuses are recorded in `docs/design/engine-path-ownership.md` §5.5 (X-23 for the `history` excuse, X-24 for this one). A failing seed is written to `sim/regressions/seed-<seed>-restores-faithful-fs.json`, with its `snapshot` and `restore` steps among the recorded steps, so it replays as any other case. The suite is not in the default suites until #861 is fixed, so CI's `make test-sim` does not run it; the nightly's default leg selects it explicitly, and the committed `seed-1-restores-faithful-fs` case replays in every run through `regressions`. To run only this suite, set `VAULT_SYNC_SIM_SUITES=restores`. Restores are not combined with retention purges in one schedule: a restore would bring back revisions the run had purged, which the purge bookkeeping does not undo.

## Several users and membership changes (#35)

Every other suite runs with one user, who owns the vault and all its devices. The `members` suite runs every configured seed a third time with three users (`RunOptions.users`, at most one per scripted client). User 0 creates the vault and owns it, along with scripted client 0 and every engine. Users 1 and 2 get tokens of their own from the control endpoint and join as editors through a real invitation (`CreateInvitation`, `RedeemInvitation`). Scripted client `i` belongs to user `i % users` and registers its device under that user. The schedule is the seed's plain schedule with `membership` steps inserted (see the step table), so members are demoted, promoted, removed and invited again while their calls are in flight, lost, delayed or retried.

`Members` (`sim/members.ts`) checks every call of every device when it reaches the server, against the role its user has at that moment. Membership changes run between deliveries, so that role is the one the server authorized the call with (SPEC.md §9.2: a change takes effect on the member's next request).

| Invariant | Check |
|---|---|
| `revoked-write` | A write (`BeginBlob`, `PutBlobChunk`, `CommitBlob`, `CommitRevision`) of a viewer or a removed member was accepted. |
| `removed-read` | A call of a removed member was answered, so it received the vault's changes after its removal. |
| `authorization` | A refusal came with the wrong code (a viewer's write gets `PERMISSION_DENIED`, every call of a non-member `NOT_FOUND`, SPEC.md §9.3), or a member was refused what its role allows (`PERMISSION_DENIED`, or `NOT_FOUND` for its feed). |

A member's scripted client takes `PERMISSION_DENIED` and `NOT_FOUND` as the server refusing it access and gives the operation up. The checks above decide whether each refusal was right. Earlier commits are covered by the invariants every run has: `history` requires every acknowledged revision of every user to be in history unchanged, and a commit the server applied before a demotion, whose retry after it is refused, stays as any other applied commit does. After the run, the `feed-head` check skips the clients of users who are removed at that point, because they can no longer pull. Every other invariant holds as in the `seeds` suite. The suite also requires that its seeds demoted or removed a member at least once, and its summary line counts the changes. A failing seed is written to `sim/regressions/seed-<seed>-members.json` with `users` recorded, and replays with them. The realtime channel is not simulated (the harness has no WebSocket client, and correctness never depends on it, SPEC.md §6.4). The realtime integration tests of #33 cover a removed member's subscriptions ending.

The scripted `membershipChanges` scenario (`sim/member-scenarios.ts`) runs the interleavings the seeds meet only by chance, each exactly once, with an owner (scripted client `c0` and engine `e2`) and one member (`c1`):

- `c1`'s edit is applied, its response is lost, `c1` is demoted, and the retry is refused (`PERMISSION_DENIED`). The applied edit stays.
- As a viewer, `c1` still pulls, and its new note's upload is refused.
- `c1` becomes an editor again, and its `CommitRevision` is in flight when it is removed. The commit is refused with `NOT_FOUND` when it reaches the server.
- While `c1` is removed, the owner creates two notes. `c1`'s pulls and uploads are refused, and it knows neither note.
- `c1` is invited again, catches up on both notes and edits. The run ends with no violation.

## The harness has teeth

`TestSimulationDetectsBrokenServer` builds the server with the `simfault` build tag. In that build `internal/store` skips CommitRevision's base-revision check (`skipBaseRevisionCheck`, `internal/store/simfault_on.go`). The test always runs the schedule of CI's short run (seeds 1 to 5, 1000 steps, 3 clients), whatever the `SIM_*` variables say, and requires a `stale-base` violation. Pinning it means a local replay of one seed or a shorter run cannot make the check fail. It then replays the minimized case the harness wrote and requires that the case reproduces the violation. Before the seeds run, it replays the committed case for its build, `sim/regressions/simfault-stale-base.json`, alone against the broken server and requires the violation too (#273 item 3). Every `make test-sim` replays that case against the correct server, where it must pass. Without the check against the broken server, a later harness change could turn the case into one that passes trivially. The switch exists only as a build tag. No flag or environment variable reaches it, and `TestDefaultBuildChecksBaseRevision` proves the default build keeps the check. The driver also verifies from each binary's build info that it was built with exactly the tags it asked for.

`TestSimulationDetectsRefusedRetry` does the same with the `simfault_retry` build tag (#110). In that build CommitRevision refuses a retry of a revision it already applied with `FAILED_PRECONDITION` once the document's head has moved past it (`refuseAppliedRetryAfterHeadMoved`, `internal/store/simfault_retry_on.go`), the #12 bug. Every server-side invariant still holds in such a run, so only the network's retry check can catch it. The test runs its own pinned schedule, CI's short run without engine users (`refusedRetrySchedule`: seeds 1 to 5, 1000 steps, 3 clients, `SIM_ENGINES=0`). With engine users those seeds no longer meet a commit retried after the head moved (#284). The interleaving is rare in any random schedule: a scripted commit's response must be lost, the retry must wait out its backoff, and another commit to the same document must land meanwhile. Measured with the default build and counted by the summary line's `retries after the head moved`: seeds 1 to 5 × 1000 steps meet it 3 times without engine users and never with 2; with 2 engine users, seeds 1 to 30 × 1000 steps (CI's run shape) meet it 0 times, and seeds 1 to 10 × 3000 steps (the nightly's size) twice. Engine users take part of the schedule (`engine-operation` steps), so the scripted clients send about half as many commits, and their retries (5 to 14 per seed against 10 to 17 without engine users) roughly halve. Raising the odds would mean changing the backoff or the step weights that #110 settled, so the path stays covered by three schedules: this pinned engine-less schedule (every `make test-sim`), the scripted `lostResponseAfterHeadMoved` scenario (every `make test-sim`), and the nightly's 3000-step seeds, whose summary lines show when a seed met it. CI's short seeded run with engine users does not exercise it. It requires that a seeded schedule (not only the scripted #12 scenario) reports the refused retry as a `protocol` violation, and replays the minimized case and the committed `sim/regressions/simfault-refused-retry.json`. Both of those show a refused retry of a *create*, which the scripted client also flags on its own. The exact #12 interleaving is a retried edit or rename whose document's head moved, and only the network sees that one. So the test also runs the scripted #12 scenario (`lostResponseAfterHeadMoved`, a lost response to an edit's commit retried after another client's commit) against the broken server. It requires the network's refused-retry violation for that commit, which has a base revision (#273 item 2). `TestDefaultBuildReturnsAppliedRetries` proves the default build never refuses such a retry.

`TestSimulationDetectsViewerWrite` does the same for the `members` suite (#35) with the `simfault_authz` build tag. In that build the authorization interceptor lets a viewer call write procedures (`acceptViewerWrites`, `internal/authz/simfault_authz_on.go`). It first replays the committed `simfault-viewer-write` case against that server. Then, on CI's short schedule (`brokenSchedule`) with membership changes, it requires a `revoked-write` violation and that the minimized case reproduces it. `TestDefaultBuildRefusesViewerWrites` proves the default build refuses viewer writes.

### Faithful filesystem

The in-memory vault under `windows` and `macos` rules is faithful: the platform's own name equivalence (`PathSpace.filesystemKey`, `F` in the design's §3.1) decides which spellings are one file. `Straße.md` and `STRASSE.md` are two files under both rules, NFC and NFD `Café.md` are two files under Windows rules and one under macOS rules, and `ı.md` and `I.md` are one file under both, although the server gives them two path keys. A folder also has one spelling there, as on those filesystems. With `Notes/` on disk, a file written or moved to `NOTES/x.md` (or a folder moved under `NOTES/`) lands under `Notes/`, and the vault reports it at that spelling (#377). Until #797 the vault had a folded mode as well, which took two spellings for one file when the engine's file key did. That is coarser than NTFS and APFS: it could never hold `Straße.md` next to `STRASSE.md`, so every engine branch for a device that holds them apart was dead on it (#396; X-18 in `docs/design/engine-path-ownership.md` §5.5). Refactor step R2 added the faithful filesystem, R7 (#701) made it the seeded suites' default, and #797 deleted the folded mode, so the scripted scenarios, the engine unit tests and every regression replay run on the faithful vault too. `RunOptions.faithfulFilesystem`, which the seeded suites set unless `SIM_FAITHFUL_FS=0`, now only chooses the path pool: the scripted clients and the engines' users choose from `faithfulPathPool`, the pool plus `Straße.md`, NFC and NFD `Café.md`, `ı.md` and `I.md`. The pool changes which path a step picks, so a seed replays only with the same setting. A regression case recorded with it holds `"faithfulFilesystem": true`, and the `regressions` suite replays such a case with that pool whatever `SIM_FAITHFUL_FS` says; a case without the field (every case recorded before #598) replays with the plain pool. `SIM_FAITHFUL_FS=0` runs the seeded suites with the plain pool, as every seeded run did before R7, so a seed recorded then replays with the schedule it failed with.

Every engine's vault also keeps harness inodes (the design's §5.4): `InMemoryVault.inodeOf(path)`, and an inode tap (`tapInodes`) that reports each change with the inode of its file and the actor that made it. A create mints an inode, a write or a rename (by anyone) keeps it, and a delete ends it. The engine's user and the engine change the vault through their own handles (`InMemoryVault.handle("user")`, `handle("engine")`), and `EngineObserver.inodeEvents` records every tapped change with its step. The engine never sees any of it. No check reads the record yet; the inode-based oracle is step R10.

## Nightly

`.github/workflows/sim-nightly.yml` runs a long simulation every night on master, and on demand (`workflow_dispatch`, with the seed count, steps and first seed as inputs). Its `simulation` job runs the seeded suites on the faithful filesystem (the default, see [Faithful filesystem](#faithful-filesystem); the separate non-gating `simulation-faithful-fs` job that ran them there from step R2 to R7 is gone) in two shapes, each on its own runner: 50 seeds × 3000 steps with 3 scripted clients and 2 engine users (every suite, named explicitly so that `restores`, out of the default suites until #861 is fixed, runs too), and the same seeds with 4 scripted clients and 3 engine users (`engine-heavy`, the `seeds` and `retention` suites only), both with `SIM_SHRINK_RUNS=10`. Three engines follow `platformForSeed(seed)`, `(seed + 1)` and `(seed + 2)`, so every engine-heavy seed has POSIX, Windows and macOS rules side by side; that shape found the case-insensitive engine bugs #379 and #380, which the default shape missed (#381). The engine-heavy leg uploads its minimized cases as `sim-regressions-engine-heavy`. The first seed moves with the run number, so every night covers new seeds. Failing seeds are minimized into a copy of the committed cases (`build/sim-regressions`), which is uploaded as the run's `sim-regressions` artifact. After both legs, the `file-issue` job files one issue titled `sim: nightly simulation failed (seeds …)` for the run, with a section per failed leg listing each failing seed's violations and its replay command (`scripts/sim-nightly-report.sh`, tested by `make test`); filing from each leg raced, and two legs failing at once could each create an issue (#661). While such an issue is open, later failures are added to it as comments. Only `file-issue`'s token can write issues (`permissions: contents: read, issues: write`); the legs' tokens only read. No checkout persists its token, and the issue copies only the harness's failure lines, never the traces. The first scheduled run (2026-10-20, seeds 100050 to 100099), before the engine-heavy shape was added, took 45 minutes, against the job's `timeout-minutes: 330`. 27 of its seeded runs (plain and retention) failed, and each was shrunk with `SIM_SHRINK_RUNS=10`. The defaults therefore stay (#273 item 5).

A second job, `properties`, runs the in-memory engine property suite (`plugin/src/core/engine/properties.test.ts`, `docs/design/engine-path-ownership.md` §9.3) at its nightly size, 100,000 cases per property (§10.2, E2), through `make test-properties`. `make test` runs the same suite at 2,000 cases from the fixed seed 563; `make test-properties` reads `PROPERTY_RUNS` (default 100000) and `PROPERTY_SEED` (default 563) and hands them to vitest as `VAULT_SYNC_PROPERTY_RUNS` and `VAULT_SYNC_PROPERTY_SEED`. The nightly seed is 563 plus the run number, so every night covers new cases; `workflow_dispatch` takes the case count and the seed as inputs. Every property holds today (#719 flipped the last known failure, P1): it must hold over every case, and the counterexamples of fixed issues run first at any seed as fixed examples; and any error a run throws other than a property violation (a broken harness) fails the suite. On failure the job uploads its output as the `properties` artifact and files an issue titled `properties: nightly engine property suite failed (seed …)` with the replay command, or comments on the open one.

## Failing seeds and regression cases

A failing seed is minimized (`sim/shrink.ts`): the harness deletes chunks of steps for as long as a violation of the same kind remains, within `SIM_SHRINK_RUNS` re-runs. It prints `seed N failed; shrinking …` first and then one line per re-run (`seed N shrinking: run k/max, candidate still fails|passes, S steps left`), so the log grows at least once per run of the seed's schedule and a long shrink never looks hung (#381). It then writes the result to `sim/regressions/seed-<seed>-faithful-fs.json` (`seed-<seed>.json` with `SIM_FAITHFUL_FS=0`; retention runs add `-retention` before the suffix) with its violations. Every `make test-sim` replays every committed case. A missing or empty regression directory fails the run before any test starts, so a mistyped `SIM_REGRESSION_DIR` can never pass while it skips the committed cases. To collect failing seeds somewhere else, point `SIM_REGRESSION_DIR` at a copy of `sim/regressions`.

Following CLAUDE.md, a sync bug gets its simulation regression before it is fixed. Commit the case with the fix, and its notes (what it reproduces, how it was minimized) as a Markdown file of its own next to it, named after the case (`sim/regressions/seed-<seed>-faithful-fs.md`); never append them to `sim/regressions/README.md`, so that two changes that each add a case merge without a conflict (#822).

### Targeted shrink

The seeded suites' shrink keeps any candidate that violates an invariant of a kind the run had, so it can drift to another bug of that kind, and the first violation's mechanism is lost (#381, #498). To minimize a saved schedule to one named violation, run the `shrink` suite on it:

```sh
VAULT_SYNC_SIM_SUITES=shrink SIM_SHRINK_CASE=sim/regressions/seed-100069.json \
  SIM_SHRINK_INVARIANT=phantom-delete SIM_SHRINK_MATCH='deleted .* at notes/b\.md' make test-sim
```

It replays the case with the options it recorded and fails at once if the replay does not reproduce the violation: one of kind `SIM_SHRINK_INVARIANT` whose detail matches `SIM_SHRINK_MATCH` (any detail when unset). Then it deletes chunks of steps as the seeded suites do, keeping a candidate only if it still reproduces that violation, within `SIM_SHRINK_RUNS` re-runs, printing one line per re-run. The result is written to the regression directory as `<case>-min.json` with the violations its steps produce, and the run passes. Review it and replace the original case with it (renamed to the original's name), or keep both. The suite is never part of a full run.

## Scripted scenarios

`sim/scenarios.ts` holds hand-written interleavings that random schedules rarely hit:

- **Platform path rules (#20).** A POSIX engine (`e1`) and a Windows engine (`e2`, after one scripted client). `e1` creates notes Windows cannot hold: `CON.md`, `notes/a:b.md`, `trailing.` and a path over MAX_PATH. `e2` pulls, must write none of them and must report each with its reason. It then crashes and pushes after the restart (a full scan). `e1` renames two synced notes to `plan?.md` and `ok*.md`. `e2`'s user has edited the first and not pushed it: `e2` keeps that file where it was, with the edit, and removes the unchanged second one (its content is on the server). `e2` must commit nothing while the notes cannot be materialized: no rename, no delete, not the edit. Then `e1` renames every one to a legal name. Each must materialize on `e2`, the edit must be merged and committed, the note must keep its document id, and both vaults must end identical with no violations. A second test runs a 400-step seeded schedule with the engine under Windows rules. It must keep every invariant and track at least one unmaterializable document. A third test (`freedPathReused`, from the review of #217) reuses the paths such renames free. `e1` renames three notes `e2` has synced, unchanged, to `plan?.md`, `empty?.md` and `draft?.md`, so `e2` removes their files. `e1` then creates another note at `plan.md` and an empty note (the same content as the empty original) at `empty.md`, while `e2`'s user creates a new note at `draft.md` and `e2` crashes. Once `e1` renames the originals to legal names, all six notes must be live with their own content and document ids in both vaults: none merged into another, deleted, or left unpushed.

- **Lost response after the head moved (#12).** The server applies a commit from c0, but the response is lost. c1 pulls and commits on top of it. c0 then retries with the same revision id and must get its own revision back, not `FAILED_PRECONDITION`.
- **The server's per-user limit refuses the engine's calls (#146).** The engine edits a note and pushes, and the limit refuses its `CommitRevision`. Each time the engine is refused, the scenario starts its next push at once, and the limit refuses that push's `ListChanges`, then its upload's look-up of the blob (a 1-byte `DownloadBlob` at the blob's end: the first push already uploaded the blob, so the upload sends no `BeginBlob`), then its `CommitRevision` again. The fifth push lands the edit. A second edit's first push is refused once more, and the push after it lands. The network's `backoff` check must find nothing, so the engine never sent a request while it backed off. The five delays must be within the bounds of 0.5 to 1 s, 1 to 2 s, 2 to 4 s, 4 to 8 s and, after the push that succeeded, 0.5 to 1 s again. The first edit must be acknowledged once, with the revision id of every one of its `CommitRevision` requests, and the server's head must hold the second edit.
- **Upload-session calls refused (#483, `sim/upload-scenarios.ts`).** One POSIX engine writes a 150 KiB file new to the server (three chunks). In its next three pushes the per-user limit (`SimNetwork.throttle`) refuses its `BeginBlob`, then its second `PutBlobChunk`, then its `CommitBlob`, each with `RESOURCE_EXHAUSTED`; the push after that lands. The backoffs must stay within the doubling, jittered bounds, the network's `backoff` check must hold, each chunk must be accepted exactly once (the upload resumes where the server's session stood), and the file must be committed once, with the server's content equal to what was written.
- **A vault at its upload session limit (#386 item 3, `sim/upload-scenarios.ts`).** Three POSIX engines on the limited replica (two upload sessions per vault). `e1` and `e2` each begin uploading a large new file, send one chunk and crash, filling the limit. `e0`'s new note is then refused by the real server (`BeginBlob` answers `RESOURCE_EXHAUSTED`) twice, the second time after its backoff. `POST /age-uploads` ages the two abandoned sessions, and `e0`'s next push reclaims them and lands the note. Then `e0` begins uploading a large file and sends one chunk; its session is aged, the restarted `e1` opens a session and `e2`, at the limit, reclaims `e0`'s. `e0`'s next chunk is refused (`FAILED_PRECONDITION`), its upload begins again and is refused at the limit; once `e1` and `e2` have committed, its next push uploads the file from the first byte and lands it. Every write, the abandoned uploads included, must be on the server with the content written, and the run's invariants (`lost-write` among them, and `backoff`) must hold.
- **Engine push under faults (#17).** The engine edits a document c0 created and pushes three times. First, its `CommitRevision` response is lost, and the retry with the same revision id must be acknowledged once and never conflict. Second, c1 moves the head between the engine's pull and its commit. The engine must pull, merge (the scenario's hook keeps both sides) and commit on top of c1's revision. Third, a 150 KiB upload loses its second chunk and the engine crashes. After the restart, the upload must resume at the server's received size without sending the first chunk again. The run must end with no violations, and the engine's copy must equal the server's head.
- **Engines edit concurrently (#18).** Two engines (`e1` and `e2`, after one scripted client) use their default three-way merge hook. Their clocks are fixed, so conflict-copy names replay identically. Each phase starts with both engines changing their vaults. `e2`'s push runs until its `CommitRevision` is next. Then `e1`'s push commits, and only after that does `e2`'s commit reach the server, which refuses it. `e2` then pulls, merges and commits again. The phases cover: non-overlapping edits of a note (merged, and the merged commit's response is lost once); overlapping edits (a conflict copy, and `e2` crashes after the merge, at its upload's look-up of the copy's blob, before it uploads or commits the copy); concurrent edits of a binary file; a CRLF conversion against a line edit (merged); two creates at one path; and two creates at paths that differ only by case. The run must end with no violations, every phase's first commit from `e2` must have been refused, both vaults must be identical and hold the expected files (no conflict markers), and `e2`'s conflict log must list the four conflicts.
- **Remote rename onto an unsynced local file (#18, review of #173).** `e1` renames a synced note from `notes/a.md` to `notes/c.md` and appends a line, while `e2` has created an unrelated note of its own at `notes/c.md` and not pushed it. `e2` pulls, crashes, and pushes after the restart. Its own note must never be merged into the renamed one: both vaults must hold the renamed note, with `e1`'s line, at `notes/c.md` and `e2`'s note whole as a conflict copy next to it. `e2`'s conflict log must list one `concurrent-create` conflict, and the run must end with no violations.
- **A local save between the engine's check and its change (#163).** Two engines. `e2`'s vault, as the engine sees it, is wrapped in an `InterleavingVault` (`plugin/src/core/engine/testing.ts`), and its user saves a file just before the engine's next write or delete of that path, after the engine checked the disk, as Obsidian's autosave can. That happens three times: before the write of `e1`'s edit of a note, before the delete of a note `e1` deleted, before the write of a merge result (`e2` already had an unpushed edit of the note), and, since `e2` follows Windows path rules, before `e2` removes the unchanged file of a note `e1` renamed to a name Windows cannot hold (releasing it). Every save must land, and both vaults must end with each save merged with `e1`'s change: both edits merged, the edit kept over the delete, and the released note's save kept and merged once a later rename gives it a legal name. The run must end with no violations.
- **Structural operations (#19).** Two engines, raced as in the #18 scenario, rename, delete, create and move folders: a rename on `e1` against an edit on `e2` (the merged commit's response is lost once), a delete against an edit and an edit against a delete (`e2` crashes after the refusal), creates at one path (with a crash), a folder of twelve notes renamed (`InMemoryVault.renameFolder` reports it as one rename per file, as Obsidian does), a folder renamed while `e2` edits a note in it, a rename chain across the engines (`A` to `B` on `e1`, then `B` to `C` on `e2`), and a chain on one engine (`b` to `c`, then `a` to `b`) while the other edits both notes, a file created on one engine at a path where the other created a folder of notes, both ways (the server refuses file/folder collisions, #134: the notes move into a conflict-named folder, or the file gets the conflict name), and an untracked file that `e2`'s user renames off a path the merge path holds while `e2`'s hook defers the document `e1` renamed there (review of #196: the file must reach the server under its new name before the hook merges the document). Both vaults must end identical with the expected files: every edit kept, a delete never winning over an edit, one conflict copy for the two creates, the conflict log listing each. Every document must keep its id through its renames, delete and edits (nothing is re-created), the server must hold exactly the expected documents, and the folder rename must upload and download no content. The run must end with no violations.
- **Config folder sync (#28).** Two engines (`e1` and `e2`, after one scripted client) sync a `ConfigSyncVault` over their vault and a config folder of their own (`EngineObserver.setConfigSync`, which restarts the engine). `e1` has every category on and pushes a typical config folder and a note: only the selected config files may reach the server, never `workspace*.json`, `graph.json` or `plugins/vault-sync/`. `e2` has config sync off and pulls with a lost response: it gets the note and writes nothing into its config folder. `e1` then changes its layout and pushes, turns config sync off, edits and deletes synced config files and pushes again, all without a single commit, so the server keeps every config file. `e2` turns config sync on, and its push is interrupted by a crash. It must then hold exactly the synced config files. A live document outside what an engine syncs is not required in its vault, and its `out-of-scope` deferral does not violate `engine-deferred`. The run must end with no violations.
- **Config conflict copies stay on the device (#365).** Two POSIX engines (`e0` and `e1`, no scripted client) sync their config folders with every category, and each writes its own `snippets/wide.css` and `plugins/dataview/data.json`. `e0` pushes, then `e1` pushes twice, keeping its versions as conflict copies inside `snippets/` and `plugins/dataview/`, folders that sync. `e0` then pulls. The server must hold only the two config files, `e0`'s config folder only those, and `e1`'s those and its two copies. The run must end with no violations.
- **Restores from history (#651, `sim/history-scenarios.ts`).** Two engines and no scripted client. `e0`'s user restores, through `SyncEngine.restore` as the history view does (`EngineObserver.startRestore`): an older version of a note in place, while `e1` holds an unpushed edit of the version it replaces, which then merges onto it; a note `e1` deleted, in place; a note `e1` deleted and then renamed another note onto (a new file written there would revive the deleted document instead), which is refused as `path-taken` with nothing committed and then restored at another path (#420); and an older version of a live note at another path, which moves the document there. The run must keep every invariant (restores bring deleted documents back as the user's change, so `resurrected-delete` accepts them, and every overwritten version stays in history for `lost-write`), both vaults must hold the expected files, and every restored document must keep its id. Seeded schedules have no restore step.
- **A restored server that passed a device's cursor again (#155).** Three engines and no scripted client. `e0` writes a note, and the database is backed up (`POST /snapshot`, `head_seq` 1). `e1` then edits that note and pushes, `e0` writes another, and `e1` pulls it (cursor 3). The edit is `e1`'s own: a revision a device only pulled is its writer's to send again after a restore (#874). The backup is restored (`POST /restore`, `head_seq` 1), and `e2`, new to the vault, writes three notes, which the restored server numbers 2 to 4, past `e1`'s cursor. `e1`'s next pull must detect the divergence from its cursor anchor and resync. Afterwards it must hold all three new notes, and it must still hold the note and the edit that the server lost. Without the anchor, the pull would fetch only seq 4 and silently skip the notes at seq 2 and 3.
- **Restores that look like purges (#488, #494, `sim/restore-scenarios.ts`).** Four engines and no scripted client; `e3` pulls only at the end, as the server's view. In `deleted-after-restore`, `e1` commits its own edit of a note at seq 2, its cursor (an edit it only pulled is its writer's to send again, #874); the backup at seq 1 is restored, `e2` writes another note at seq 2, deletes `e1`'s note at seq 3 and edits the other note at seq 4, and retention purges the revision at seq 2. `untouched-after-restore` is the same, but `e2` writes a third note instead of deleting. The restored server's purge marker at seq 2 has the anchor of `e2`'s revision, not of `e1`'s cursor, so `e1`'s pull must diverge and merge. In `own-commit-above-cursor`, `e1`'s edit is acknowledged at seq 3 while its cursor stays at 1 (`e0` committed at seq 2 first, #261); the backup at seq 2 is restored and `e0` edits the note again, at seq 3. Only `e1`'s own-commit anchor tells that restore. In every shape `e1`'s acknowledged edit must survive on `e1` and reach the server again.
- **A merge base that retention purged (#26, review of #219).** Two engines and no scripted client. Both sync a note; `e1` edits it and does not push, while `e0` edits it too and pushes. The control endpoint's `POST /purge` then ages both revisions to the same UTC day 100 days ago and applies the default retention policy with the server's own purge (`PurgeRevisions`), which removes the older one, `e1`'s merge base, and keeps the head. `e0` writes another note. `e1`'s pull must not stall on the missing base (`NOT_FOUND` from `GetRevision`): it keeps `e0`'s version in place and its own as a `base-purged` conflict copy, applies the later note, and pushes the copy, and both engines must end identical with no violations.
- **A merge base purged while the engine was offline (#229).** As above, but `e1` is partitioned before its user edits the note, and it starts a push that waits on the network. `e0` edits and pushes, and the purge removes `e1`'s base. On reconnect the push goes on: it pulls first, finds the head moved and its base gone (`GetRevision` is `NOT_FOUND`), and its edit must survive as a `base-purged` conflict copy beside `e0`'s version, identical on both engines, with no violations.
- **A cursor whose purge marker was pruned (#514, `purgedCursor` with `pruneMarkers`).** Two POSIX engines and no scripted client, the shape of the #480 scenario: `e1`'s cursor sits on a revision that retention purges, and the control endpoint's `POST /prune-markers` then ages the vault's purge markers past the default marker horizon and prunes them with the server's own `PruneMarkers`. `e1`'s anchor check finds neither the revision nor its marker, so it resyncs. Both notes are unchanged on `e1` at revisions it only pulled, so the resync pulls their heads (#874, SPEC.md §8, §11): the note `e0` deleted is deleted and the other takes `e0`'s edit, with no violation. With `localEdit` (#519), `e1`'s unpushed edit of the other note is merged against the purged base and kept as a conflict copy.
- **A new document at a path a known document still holds (#264).** Two POSIX engines and no scripted client. Both sync `d.md`. `e1`'s user edits it and creates a folder `moved.md/`, without pushing, while `e0` renames the note to `moved.md` (so `e1`'s merge of the rename is deferred) and then creates a new note at `d.md` with the same content as `e1`'s edit. `e1` pulls, its user removes the folder, and it pushes. `e1`'s pull must not take the edited file for the new note: both vaults must end with the original note, edited, at `moved.md` under its own id and the new note at `d.md`, no document may ever get a tombstone, and the run must end with no violations.
- **A rename lost to a crash (#280).** Two POSIX engines and no scripted client. Both sync `note.md`. `e1`'s user renames it to `moved.md`, and the app is killed before the engine records the rename. The restarted engine's start-up scan finds the note's file missing and `moved.md` holding exactly its content, and binds the note to it (design §4.3 E7, decision 4; refactor step R11), so its push commits a rename. Meanwhile `e0`'s user edits the note and pushes, before or after `e1`'s rename reaches the server. The edit must never be lost (SPEC.md §2 principle 1): both vaults must end with the note, edited, at `moved.md` under its own id (a local rename wins over an edit, §7), nothing tombstoned, and no violations. A second variant (`deleted-note-path`, #793) also syncs a second note at `moved.md`, and `e1`'s user deletes that file just before the rename, so the crash loses the delete too. The restarted engine finds `moved.md` holding the renamed note's content and not the second note's own (E7b), so the renamed note keeps its id at `moved.md` and the second note is deleted. In both orders both vaults end with the edited note at `moved.md` under its own id, the second note tombstoned, and no violations: before R11 the restarted engine committed the renamed content as an edit of the deleted note, which §5.5 X-8 excused.
- **A known document's revision at a path another document's local rename holds (#267).** Two POSIX engines and no scripted client. Both sync notes `a.md` and `b.md`. `e1`'s user renames `a.md` to `z.md` and pushes, then renames `b.md` to `a.md`, whose commit request is lost before the server sees it and the app is killed before it retries, so it stays pending; the user then deletes `z.md`, while `e0` moves the first note back to `a.md` with the second note's content. In a second variant `e1` pushes neither rename, so its journal still has the first note at `a.md` when `e0`'s edit of it there arrives with the second note's content. `e1` pulls and pushes. Its pull must not take the second note's file for the first: both vaults must end with the first note at `a.md` and the second, under its own id, at the `path-taken` copy `e1` logged; no document may ever get a tombstone, and the run must end with no violations. A third variant (review of #278) checks that this never overrides a plain swap of names: `e1` renames `a.md` to `z.md` and `b.md` to `a.md`, keeps `z.md` and pushes neither rename, while `e0` edits the first note at `a.md`. Both vaults must end with the first note, with `e0`'s edit, at `z.md` and the second at `a.md`, each under its own id, with no conflict logged, no tombstone and no violations.
- **A known document's file moved onto a new document's path during the pull (#757).** Two POSIX engines and no scripted client. Both sync note `k.md`. `e1`'s user edits it to `same` and does not push, while `e0` creates `p.md` with `same` too. `e1`'s vault, as the engine sees it, is an `InterleavingVault` (`plugin/src/core/engine/testing.ts`), and its user renames `k.md` to `p.md` just before the pull's next read of `p.md` (`EngineObserver.moveBeforeNextEngineRead`): after the engine claimed the path for the new note, before it looks at the disk there. The pull must not adopt the file for the new note (design §4.5 step 3, INV-3). `k` moves on to a `path-taken` conflict copy under its own id (rule W(a), PO-4), its push commits the rename and the edit as `k`'s, the new note materializes at `p.md`, both vaults agree, and nothing is tombstoned.
- **A new file at a just-vacated path (#254).** Two engines and no scripted client; the first follows POSIX rules. Both sync notes, and before the second engine pushes, its user vacates a synced path and puts another file there: deletes `h.md` and creates a new `h.md`; deletes `h.md` and renames `d.md` onto it; under Windows rules, deletes `A.md` and renames `NOTES` to `a.md` (seed 24); under macOS rules, renames `a.md` to `z.md` and then `b.md` to `A.md` (the review of #278); or, under macOS rules, creates `STRASSE.md` and, after the server committed the create and before its response arrives, renames it to `b.md` and creates `straße.md` (seed 22). The push must never commit the new file as the old document's edit: the deleted note is tombstoned and the new file is a new document, the renamed note keeps its id at its new path, and in the case swap and the seed 22 case nothing is tombstoned. Both vaults must end identical, with no conflict logged and no violations.
- **New paths containing `\` (#191).** Two POSIX engines and no scripted client. `e0` syncs a note `a/b` and a file `notes`. `e1` pulls, its user creates `a\b` and `notes\c.md` (on Windows the same file as `a/b`, and a file under `notes`), and `e1` pushes, crashes and pushes again. Neither may reach the server (SPEC.md §6.2: no new path contains `\`), both must stay on `e1`'s disk, and `e1`'s push must report both as rejected. The user then renames them to `a/c` and `notes-c.md`: both must sync, both vaults must end identical, and the run must end with no violations.
- **New paths starting with one character and a colon (#148).** The same shape. `e0` syncs a note `1-x.md`. `e1` pulls, its user creates `1:x.md`, `é:y.md` and `😀:z.md` (Win32 reads each as a drive-qualified path), and `e1` pushes, crashes and pushes again. None may reach the server (SPEC.md §6.2), all must stay on `e1`'s disk, and `e1`'s push must report all of them as rejected. The user then renames them to `1/x.md`, `e-y.md` and `z.md`: all must sync, both vaults must end identical, and the run must end with no violations.
- **Local files whose paths the server refuses (#100).** The same shape. `e0` syncs a note `notes/a.md`. `e1`'s user creates `notes/line⏎break.md` (a line break in the name), `notes/.../dots.md` (a segment of dots) and a 2,830-byte path of U+1D160 characters that is 8,462 bytes once normalized, and `e1` pushes, crashes and pushes again. `e1` must send no `BeginBlob`, `PutBlobChunk`, `CommitBlob` or `CommitRevision` meanwhile (checked on the trace), nothing may reach the server, all must stay on `e1`'s disk, and `e1`'s push must report each as rejected with the rule it breaks (`invalid-character`, `not-vault-relative`, `too-long-normalized`). - **A change at a path a refused operation holds (#167 item 3).** One POSIX engine and no scripted client. The engine syncs `note.md`, and its user renames it to `moved.md`. The scenario has the server refuse the rename's `CommitRevision` with `INVALID_ARGUMENT` (`SimNetwork.refuse`, which answers a client's oldest request with a given error before it reaches the server; the real server gives such a refusal only under conditions a scenario cannot set up), so the rename stays pending. The user then creates a new note at `note.md`, which the journal still has as the renamed note's path, and the next push is refused the same way. The push after that, with no further local change and no restart, must commit the rename and push the new note: both notes end live on the server and in the vault, the renamed one under its own id and the new one under another, with no violations.
- **Liveness (#302).** With the seeded commit retry backoff, an engine's `CommitRevision` request and every retry its push makes are lost on the last steps, so the push gives up. Its push after the faults heal sends the commit again with the same revision id. A second scenario has the harness wait for an engine whose push waits on a call nothing delivers. The wait must throw a `StallError` naming step 1 and the pending `ListChanges`, and the run must then finish with no violation.
- **Scripted changes of an engine's blob document (#306).** One POSIX engine and one scripted client. - **A remote rename onto a local folder's name (#307).** Two engines, `e0` POSIX and `e1` under Windows or macOS rules (one test each), and no scripted client. `e1` syncs `a.md`. - **A remote edit of a path the user vacated for another note's rename (#253).** Two engines, `e0` POSIX and `e1` under Windows or macOS rules, and no scripted client. Both sync `a.md` and `d.md`. `e1`'s user deletes `a.md` and renames `d.md` to `A.md` (the same path key), while `e0`'s user edits `a.md` and pushes, either before `e1` pushes or just before `e1`'s first `CommitRevision` reaches the server (one test for each platform and timing). - **A crash in a pull that brings a deleted and recreated note (#453).** Two engines under the same rules (POSIX or Windows, one test each) and no scripted client. `e0` creates and pushes `Notes/C.md`, then its user deletes it; `e1` pulls the note and its user edits it; `e0`'s user writes a new `Notes/C.md` and `e0` pushes the tombstone and the new document. `e1`'s pull is killed after the merge of the tombstone rebased the document and before it removed the deferral (`EngineObserver.haltOnDeferralRemoval`), and `e1` restarts.
