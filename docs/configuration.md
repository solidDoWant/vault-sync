# Server configuration

`vault-sync-server` is configured entirely by environment variables. An empty variable is treated as unset. On startup the server validates every variable and, if any is missing or invalid, exits with status 1 after logging one `invalid configuration` record whose `problems` field names each offending variable. Secret values (such as the database password) are never echoed.

The `vault-sync-server export` subcommand reads the database, S3 and log-level variables below, and `VAULT_SYNC_ESCROW_IDENTITY_FILE`, and ignores the rest; see [export.md](export.md). `vault-sync-server export rotate-escrow` reads the database and log-level variables, `VAULT_SYNC_ESCROW_IDENTITY_FILE`, `VAULT_SYNC_ESCROW_SIGNING_KEY_FILE` and `VAULT_SYNC_ESCROW_JOB_TOKEN_FILE`.

| `VAULT_SYNC_METRICS_LISTEN_ADDRESS` | `:9090` | `host:port` for the metrics and health listener (`/metrics`, `/healthz`, `/readyz`). Must differ from `VAULT_SYNC_LISTEN_ADDRESS`. Do not expose it to the internet. |
| `VAULT_SYNC_SERVICE_METRICS_LISTEN_ADDRESS` | `:9091` | `host:port` for the service-wide metrics listener (`/metrics` only, see [Service-wide metrics](#service-wide-metrics)). Must differ from `VAULT_SYNC_LISTEN_ADDRESS` and `VAULT_SYNC_METRICS_LISTEN_ADDRESS`. Do not expose it to the internet. |
| `VAULT_SYNC_SERVICE_METRICS_INTERVAL` | `1m` | How often each replica refreshes the service-wide metrics from PostgreSQL. A Go duration from `1s` to `1h`. |
| `VAULT_SYNC_MAX_REQUEST_BYTES` | `1048576` (1 MiB) | Maximum size of a request body in bytes, applied both to the bytes on the wire and to the decompressed message. Allowed range: 16384 to 67108864 (a response carrying one revision with a maximum-length path, or one vault with a maximum-length name, must fit; the chunk size check below requires more in practice). The default matches the 1 MiB inspected-body limit of the WAF in front of the server. Request bodies are read and decoded before the bearer token is checked, so unauthenticated callers can make the server read up to this many bytes per request; keep the limit low. |
| `VAULT_SYNC_WRITE_TIMEOUT` | `2m` | How long writing an API response may take, counted from its first byte until the whole response is written. A response the client has not finished reading by then is cut off and the connection closed, so a client that sends a request and then stops reading cannot hold a connection open. The timeout does not limit how long the server works on a request before it starts the response: a long `CommitBlob` (composing a large blob in the object store) is not cut short. The default lets a 1 MiB response reach a client on a link of about 100 kbit/s. Raise it if you raise `VAULT_SYNC_MAX_REQUEST_BYTES` for slow clients. The timeout does not apply to the realtime WebSocket once it is open. A Go duration from `1s` to `1h`. |
| `VAULT_SYNC_MAX_CONCURRENT_RPCS_PER_USER` | `32` | Authenticated RPCs one user may have in flight on this replica at once (1 to 10000). A further call from that user is rejected immediately with `resource_exhausted`, before any work is done for it, and is not queued; other users are unaffected. A refused plugin waits, from about a second up to a minute, before it tries again (see `docs/plugin.md`). An RPC counts from authentication until its response has been completely written, so a client that stops reading its responses keeps holding its calls until `VAULT_SYNC_WRITE_TIMEOUT` cuts them off. The limit is per replica and keeps no state shared between replicas or after a user's calls end. The plugin makes one RPC at a time per device, so the default admits 32 devices of one user syncing on the same replica at once (matching `VAULT_SYNC_REALTIME_MAX_CONNECTIONS_PER_USER`) while one user can hold at most 32 response buffers of up to `VAULT_SYNC_MAX_REQUEST_BYTES` each. `GetServerInfo`, which needs no authentication, is not counted. |
| `VAULT_SYNC_SHUTDOWN_DELAY` | `5s` | How long after `SIGTERM` or `SIGINT` `/readyz` fails while the API keeps serving, so load balancers stop sending traffic before any connection is refused (see [Startup and shutdown](#startup-and-shutdown)). A Go duration from `0s` to `5m`. |
| `VAULT_SYNC_SHUTDOWN_TIMEOUT` | `30s` | The drain timeout: how long in-flight requests may finish after `VAULT_SYNC_SHUTDOWN_DELAY` before the remaining connections are closed. A Go duration (`30s`, `1m`); must be positive. Keep the delay plus the timeout below the pod's `terminationGracePeriodSeconds`. |
| `VAULT_SYNC_LOG_LEVEL` | `info` | Minimum log level: `debug`, `info`, `warn` or `error`. |
| `VAULT_SYNC_OIDC_ISSUER_URL` | (required) | OIDC issuer identifier, for example `https://auth.example.com/application/o/vault-sync/` for Authentik. Access tokens' `iss` claim must equal it exactly (including any trailing slash). The signing keys are discovered from `<issuer>/.well-known/openid-configuration`. Must be `https`; plain `http` is accepted only for a loopback host (`localhost`, `127.0.0.1`, `::1`) for local development. |
| `VAULT_SYNC_OIDC_AUDIENCE` | (required) | Audience that access tokens' `aud` claim must contain; for Authentik, the client ID of the vault-sync provider. The plugin signs in as that client with the device flow; see `docs/plugin.md` for the provider setup. |
| `VAULT_SYNC_OIDC_CLIENT_ID` | the audience | The public OAuth client ID the plugin signs in as. `GetServerInfo` advertises it, together with `VAULT_SYNC_OIDC_ISSUER_URL`, to clients that are not signed in yet, so users only need to enter the server URL. Set it when the plugin's client differs from `VAULT_SYNC_OIDC_AUDIENCE` (an identity provider that puts an API audience, not the client ID, in access tokens). It must be a public client: it is shown to anyone who can reach the server, so never use a confidential client or put a secret here. 1 to 255 printable ASCII characters. When unset, the audience is advertised if it fits those rules, and otherwise no client ID is advertised and users enter it in the plugin. |
| `VAULT_SYNC_ESCROW_RECIPIENT` | unset | The deployment's escrow public key (`SPEC.md` §9.4), as an age hybrid post-quantum recipient (`age1pq1…`, from `age-keygen -pq`). `GetServerInfo` publishes it, with an id derived from it (`sha256:` and the hex SHA-256 of the key), and clients wrap every epoch key of an escrow vault to it. It is public: the escrow private key belongs in the export job only, never in the server. Set it together with `VAULT_SYNC_ESCROW_SIGNING_KEY`. When unset, the server has no escrow key, and creating an escrow vault fails with `failed_precondition`. Any other value stops the server at startup. |
| `VAULT_SYNC_ESCROW_SIGNING_KEY` | unset | The escrow signing public key: the standard base64 encoding of the 32-byte Ed25519 public key held with the escrow identity (`docs/design/encryption.md`, *Escrow key*). Set together with `VAULT_SYNC_ESCROW_RECIPIENT`; the pair is the deployment's escrow bundle. The deployment's escrow chain is stored in PostgreSQL: on first start with an escrow key the configured bundle becomes the chain's root, and `GetServerInfo` publishes the root and every escrow rotation statement. At startup the chain must link (every statement signed by the escrow signing key before it) and end at the configured bundle; otherwise the server logs `cannot use the escrow chain` and stops. To rotate the escrow key, rotate it with the export job first, then update both variables. One without the other, or a value that is not 32 bytes of base64, stops the server at startup. |
| `VAULT_SYNC_ESCROW_RETIRING_KEY_IDS` | unset | Comma-separated ids of escrow keys being rotated away from (each 1 to 255 printable ASCII bytes, as `GetServerInfo` names an escrow key: `sha256:` and the hex SHA-256 of the key). Every epoch of an escrowed vault has exactly one escrow slot, and its `recipient_id` must be the current escrow key's id or one of these; `RotateEpoch`, `AddKeySlots` and `RemoveMember` refuse any other escrow slot with `invalid_argument`. Set it to the old key's id while the export job re-wraps the existing escrow slots during an escrow key rotation, and unset it once no slot names the old key. Needs `VAULT_SYNC_ESCROW_RECIPIENT`; any other value stops the server at startup. |
| `VAULT_SYNC_ESCROW_DEFAULT` | `true` | Whether a new end-to-end encrypted vault has escrow unless its owner turns it off. `GetServerInfo` publishes it, and the plugin uses it as the default of its escrow toggle. Published as `false` while `VAULT_SYNC_ESCROW_RECIPIENT` is unset. |
| `VAULT_SYNC_ESCROW_JOB_TOKEN_FILE` | unset | Path to a file holding the static bearer token of the job-only escrow rotation endpoint (`EscrowJobService`: conditional escrow slot replacement and appending the next escrow rotation statement, `docs/design/encryption.md`, *Escrow*). One line, 32 to 4096 characters without spaces (for example `openssl rand -base64 32`), surrounding whitespace ignored. The server compares the presented token in constant time and accepts nothing else there, user (OIDC) tokens included. When unset, the endpoint is off and refuses every call as `unauthenticated`. Give the same Secret to the server and the export job only. A file that is missing, too short or too long stops the server at startup, without quoting the file. |
| `VAULT_SYNC_ESCROW_IDENTITY_FILE` | unset | **Export only.** Path to the escrow identity file (`age-keygen -pq` output): one `AGE-SECRET-KEY-PQ-1…` identity per line, blank lines and `#` comments ignored, at most 64 KiB. Give both identities during an escrow key rotation. The export decrypts escrowed vaults with it ([export.md](export.md)); when unset, it skips every encrypted vault. A file that is missing, holds no identity or holds anything but age hybrid identities stops the export at startup, without quoting the file. Never give it to the server. |
| `VAULT_SYNC_ESCROW_SIGNING_KEY_FILE` | unset | **Escrow rotation only** (`export rotate-escrow`, [export.md](export.md#rotating-the-escrow-key)). Path to the escrow signing keys: one standard base64 Ed25519 seed (32 bytes) per line, blank lines and `#` comments ignored, at most 64 KiB. They are matched to escrow bundles by their public keys; during a rotation it holds the chain head's key and the new one. A file that is missing, holds no key or holds anything else stops the rotation at startup, without quoting the file. Never give it to the server. |
| `VAULT_SYNC_S3_BUCKET` | unset | S3 bucket holding every vault's blobs. It must already exist. Required when any `VAULT_SYNC_S3_*` variable is set. When no `VAULT_SYNC_S3_*` variable is set, the server starts without an object store, logs a warning, and every `BlobService` RPC returns `unimplemented`. |
| `VAULT_SYNC_S3_ENDPOINT` | unset (AWS S3) | Base URL of the S3-compatible store, for example `https://rgw.example.com`. Must be `http` or `https`, without credentials, query or fragment. |
| `VAULT_SYNC_S3_REGION` | `us-east-1` | Region of the bucket. Ceph RGW accepts any region by default. |
| `VAULT_SYNC_S3_ACCESS_KEY_ID_FILE` | unset | File containing the S3 access key id. Required with the bucket. |
| `VAULT_SYNC_S3_SECRET_ACCESS_KEY_FILE` | unset | File containing the S3 secret access key. Required with the bucket. Their contents are never logged. |
| `VAULT_SYNC_S3_FORCE_PATH_STYLE` | `true` | `true` addresses the bucket as `<endpoint>/<bucket>` (what Ceph RGW and most self-hosted stores need); `false` uses virtual-hosted `<bucket>.<endpoint>`. |
| `VAULT_SYNC_S3_TLS_CA_FILE` | unset (system roots) | PEM bundle of CAs trusted for the S3 endpoint's certificate instead of the system roots. Re-read for every new connection. The certificate must still name the host connected to: a DNS SAN for a host-name endpoint (`<bucket>.<host>` with virtual-hosted addressing), an IP SAN for an IP-address endpoint. A certificate that fails verification (wrong host, untrusted CA, expired), with or without this setting, is not retried: the request fails on its first attempt and the log shows the certificate error. |
| `VAULT_SYNC_S3_IDLE_TIMEOUT` | `2m` | How long a connection to the object store may make no progress, sending or receiving nothing, before the request on it fails. The SDK retries a timed-out request up to twice, so an object store that accepts connections and then stops answering fails a call after at most about three timeouts (plus a few seconds of backoff): `PutBlobChunk`, `DownloadBlob` and `CommitBlob` return `internal` and the client retries, and a cleanup run logs the failure. The timeout is not a limit on a whole call: a slow transfer that keeps moving, a long `CommitBlob` of a large blob, or a long export stream is never cut short. The one exception is deleting a single object (a blob the retention job collects, a staged chunk), which carries no body: it is bounded in all, retries included, by four timeouts, so a store that keeps trickling a response cannot hold the deletion, and a re-upload of the same blob waiting for it, any longer. Raise it if the store can legitimately stay silent for longer before answering (for example while completing a very large multipart upload without sending keep-alive whitespace), or if the link to it is so slow that the last few MiB of a request buffered in the network take longer than this to drain. Pooled connections idle for half the timeout are closed. A Go duration from `1s` to `1h`. |
| `VAULT_SYNC_BLOB_MAX_CHUNK_BYTES` | `786432` (768 KiB) | Largest upload chunk, and the largest range one `DownloadBlob` returns, for clients using the binary protobuf codec (the plugin). At least 65536. It plus 1024 bytes of request framing must not exceed `VAULT_SYNC_MAX_REQUEST_BYTES`, or the server refuses to start. Clients using the Connect JSON codec, which base64-encodes chunk data, are advertised (in `BeginBlob`'s `max_chunk_size`) and served smaller chunks, so their messages fit `VAULT_SYNC_MAX_REQUEST_BYTES` too: 784878 bytes with the defaults. A binary `DownloadBlob` range is also at most `VAULT_SYNC_MAX_REQUEST_BYTES` less a thousandth and 512 bytes, room for gzip's framing of incompressible content; this only shortens ranges when the chunk size is within a thousandth of the request limit (not with the defaults). |
| `VAULT_SYNC_BLOB_MAX_SIZE_BYTES` | `1073741824` (1 GiB) | Largest blob (file) that can be uploaded. At most 83886080000 (80 GiB). |
| `VAULT_SYNC_BLOB_MAX_UPLOADS_PER_VAULT` | `32` | Upload sessions that may be in progress at once in one vault (1 to 10000). A `BeginBlob` that would start another first reclaims the vault's sessions idle for longer than `VAULT_SYNC_BLOB_UPLOAD_RECLAIM_IDLE`; only if none can be reclaimed does it get `resource_exhausted`, until a session completes, is reclaimed or expires. |
| `VAULT_SYNC_BLOB_UPLOAD_TTL` | `24h` | How long an upload session may be idle before the cleanup routine removes it. A Go duration of at least `10m`. A commit in progress records activity after every 8 MiB part it composes, so it is never removed, however long it takes, unless composing a single part takes longer than the TTL (for example behind a very slow object store); such a commit fails with `failed_precondition` and the client uploads the blob again. |
| `VAULT_SYNC_BLOB_UPLOAD_RECLAIM_IDLE` | `10m` | How long an upload session must be idle before a new upload in a vault at `VAULT_SYNC_BLOB_MAX_UPLOADS_PER_VAULT` reclaims it. An upload in progress records activity on every chunk, so a session idle this long has been abandoned; if its client does come back, its next chunk or commit is refused and it starts that upload again (nothing is lost). Reclaimed sessions' staged chunks are removed by the cleanup routine below. Reclaiming is coordinated in PostgreSQL, so it is safe with any number of replicas. A Go duration of at least `10m` and at most `VAULT_SYNC_BLOB_UPLOAD_TTL`. |
| `VAULT_SYNC_RETENTION_KEEP_ALL` | `2160h` (90 days) | Every revision younger than this is kept (see "Retention and history" below). A Go duration of at least `24h`. Set it very high (for example `876000h`) to keep every revision forever. |
| `VAULT_SYNC_RETENTION_KEEP_DAILY` | `8760h` (365 days) | Revisions older than `VAULT_SYNC_RETENTION_KEEP_ALL` but younger than this are thinned to the newest one of each document per UTC day; older ones to the newest one per ISO week (Monday to Sunday, UTC). A Go duration not below `VAULT_SYNC_RETENTION_KEEP_ALL`. |
| `VAULT_SYNC_RETENTION_PURGE_MARKER_HORIZON` | `8760h` (365 days) | How long the purge marker of a purged revision is kept after its purge (see [Retention and history](#retention-and-history)). | `VAULT_SYNC_RETENTION_OVERRIDE_MIN_KEEP_ALL` | `24h` | Read only by `vault-sync-server retention set`: the shortest keep-all a per-vault override may have (see [Per-vault overrides](#per-vault-overrides)). A Go duration of at least `24h`. |
| `VAULT_SYNC_RETENTION_OVERRIDE_MIN_KEEP_DAILY` | none | Read only by `vault-sync-server retention set`: the shortest keep-daily a per-vault override may have. A Go duration. |
| `VAULT_SYNC_BLOB_GC_GRACE` | `24h` | How long a blob that no revision references any more is kept after the retention purge that removed its last revision, before it is deleted from PostgreSQL and S3. A Go duration of at least `1h`. |

| `VAULT_SYNC_REALTIME_MAX_CONNECTIONS_PER_USER` | `32` | Open realtime connections one user may hold on this replica (1 to 10000). Further upgrades get HTTP 429. Each device needs one. |
| `VAULT_SYNC_REALTIME_MAX_SUBSCRIPTIONS` | `128` | Vaults one realtime connection may subscribe to (1 to 10000). Reported to clients as `max_realtime_subscriptions` by `GetServerInfo`; a further `subscribe` gets a `RESOURCE_EXHAUSTED` error frame. |

### Authentication

Every RPC except `vaultsync.v1.ServerInfoService/GetServerInfo` requires an `Authorization: Bearer` header carrying a JWT access token from the issuer. `GetServerInfo` returns only public data: the build and protocol versions, the realtime subscription limit, the issuer URL and the plugin's client ID. A token is accepted only if:

- it is at most 16 KiB;
- it is signed with RS256, ES256 or EdDSA (never `none` or an HMAC algorithm) by a key in the issuer's key set;
- `iss` equals `VAULT_SYNC_OIDC_ISSUER_URL`, `aud` contains `VAULT_SYNC_OIDC_AUDIENCE`, `sub` is present (at most 255 bytes, without control characters), `exp` is present and not in the past (no leeway), and `nbf`, if present, is no more than one minute in the future.

Anything else gets the Connect code `unauthenticated` (HTTP 401) with no detail about the reason; the reason is logged at `debug` level. Tokens and claims are never logged.

The issuer's key set is fetched on the first authenticated request, not at startup, so the server starts even when the issuer is unreachable. It is refetched when a token names an unknown key id (key rotation) and when the cached keys are older than one hour (so withdrawn keys stop being trusted), but at most once every 30 seconds, so a flood of tokens with made-up key ids cannot amplify into requests to the issuer. A newly rotated key is therefore accepted at most 30 seconds after the previous fetch. If a refetch fails, the cached keys stay in use. Only one fetch runs at a time, bounded at 10 seconds. While a refetch of hour-old keys is in progress, other requests are verified against the cached keys instead of waiting, so a slow or hanging issuer delays only the request that started the refetch and requests naming an unknown key id.

The discovery document, the `jwks_uri` it names and every redirect are fetched over `https` only. The `jwks_uri` may be on another host than the issuer. Plain `http` is used only when `VAULT_SYNC_OIDC_ISSUER_URL` is itself a loopback `http` URL, and then only to loopback hosts. A redirect is followed only if it stays on the host (and port) of the URL first requested and does not change `https` to `http`, for at most 5 redirects. A redirect to another host is refused, so if your issuer moves its discovery document or keys to another host with a redirect, configure the final issuer URL instead. A refused URL or redirect fails the fetch: before the first successful fetch every token is rejected, and afterwards the cached keys stay in use.

The first authenticated request of a new `(issuer, subject)` pair creates its user.

### Authorization

Every RPC whose request names a `vault_id` is authorized against the caller's membership in that vault before it runs. There is no administrator bypass. A caller who is not a member gets `not_found` (HTTP 404), the same response as for a vault that does not exist. A `viewer` calling a write RPC (committing revisions, uploading blobs) gets `permission_denied` (HTTP 403). A malformed `vault_id` (not a lowercase hyphenated UUID) gets `invalid_argument`.

A user becomes a vault's `owner` by creating it. A user may own at most 100 vaults, not counting deleted ones, and vault names are at most 256 bytes and may not contain control characters (Unicode category `Cc`, such as U+0000 or a newline), format characters (`Cf`, such as the bidi controls U+202A–U+202E and U+2066–U+2069, zero-width spaces and joiners, or the byte order mark) or line and paragraph separators (U+2028, U+2029); such names get `invalid_argument`. Creating an end-to-end encrypted vault is rejected with `failed_precondition` until end-to-end encryption is supported. Inviting other members comes in a later release. `ListVaults` returns at most 1000 vaults per call (100 if the client does not ask for a page size), and a page also ends early where its encoding would come near `VAULT_SYNC_MAX_REQUEST_BYTES`, as for the change feed below, returning a `next_page_token` to continue. An owner can delete a vault (`DeleteVault`; editors and viewers get `permission_denied`). The vault is marked deleted in the `vaults.deleted_at` column, and its rows and blobs are kept. It disappears from `ListVaults`, and every member's request naming it, realtime subscriptions included, gets `not_found` with an error detail of reason `ERROR_REASON_VAULT_DELETED`.

Each plugin installation registers itself as a device (`RegisterDevice`), and so does every reinstall, including a mobile app whose data was wiped. A user may have at most 100 devices that have not been removed. The cap is fixed and cannot be configured. Once a user has 100 devices, every further `RegisterDevice` call from that user fails with `resource_exhausted` (HTTP 429), the message `at most 100 devices may be registered` and an error detail (`vaultsync.v1.ErrorDetail`) of reason `ERROR_REASON_DEVICE_LIMIT`; the user's existing devices keep syncing. The per-user limit on concurrent requests also answers `resource_exhausted`, with reason `ERROR_REASON_TOO_MANY_CONCURRENT_REQUESTS`; clients tell the two apart by the reason, not the message. A registration sent with a `registration_id` is idempotent: retrying it with the same public key returns the same device, with its current name (the retry's name is ignored), and uses no further place, so a plugin that crashed before saving its device does not use up the limit. The remedy is to remove devices that no longer exist: `ListDevices` lists the caller's devices (id, name, registration time and last commit, to within a minute; nothing secret), `RemoveDevice` removes one, which frees its place at once, and `RenameDevice` renames one that is not removed, keeping its id. They act only on the caller's own devices: another user's device is `not_found`, like one that does not exist. A removed device's row stays in the `devices` table with `removed_at` set, so the revisions it committed keep their history and the name of the device that made them, but it can no longer commit (`not_found`, with an error detail of reason `ERROR_REASON_DEVICE_NOT_FOUND`); the installation has to register again to sync. A retry, under the new device, of a commit that landed before the removal returns the committed revision instead of `invalid_argument`. The plugin lists and removes devices in its settings (see `docs/plugin.md`); the calls can also be made through the API with the user's access token. Deleting rows from the `devices` table by hand is not supported (revisions record the device that committed them). Device names must not be blank, are at most 256 bytes, and follow the same character rule as vault names (no `Cc`, `Cf`, U+2028 or U+2029); other names get `invalid_argument`. Names registered before this rule was added are kept and keep working; the plugin removes such characters wherever it shows a name.

A user's end-to-end encryption key pair is stored in the `user_keys` table (`UserKeyService`, `SPEC.md` §9.3): the public key, the Ed25519 signing public key (which member lists report; keys stored before it was added get it from the next device that unlocks them), the private key wrapped under the user's recovery passphrase, the wrapping's parameters and the SHA-256 of a verifier derived from the passphrase. Neither the passphrase nor the private key ever reaches the server. The server releases the wrapped key only to its owner and only for the right verifier. After 10 wrong passphrases within one hour, counted per user in PostgreSQL so that every replica enforces the same count, every unlock or passphrase change by that user fails with `resource_exhausted` and an error detail of reason `ERROR_REASON_PASSPHRASE_ATTEMPTS_EXHAUSTED` whose `retry_time` is the end of the hour. The limit is fixed and cannot be configured; it lifts by itself when the hour ends, so there is nothing for an operator to reset. A wrong passphrase gets `permission_denied` with reason `ERROR_REASON_WRONG_PASSPHRASE`.

Each user's sealed anchor list (the vaults whose genesis the user's devices trust, `docs/design/encryption.md`) is stored in the `anchor_lists` table as opaque bytes with a version number. The server cannot read it. A list may be at most 4,800,045 bytes (100,000 vaults), and the `VAULT_SYNC_MAX_REQUEST_BYTES` request limit also applies.

End-to-end encrypted vaults keep one key per epoch, which the server never sees. The `vault_key_epochs` table records each epoch with a 32-byte key commitment, and `key_slots` holds each epoch key wrapped to a member's user key, or to the escrow key, as opaque bytes of at most 256 (`VaultKeyService`, `SPEC.md` §9.3). A new encrypted vault has no epoch until its owner's client creates epoch 1, with the owner's slot and, for an escrow vault, the escrow slot. Owner clients create epochs and grant slots. The server checks only that every new epoch covers exactly the members who have a user key, and that revisions are committed under the vault's current epoch (otherwise `failed_precondition` with reason `ERROR_REASON_EPOCH_NOT_CURRENT`). The epoch counter is coordinated in PostgreSQL, so it is the same on every replica. Nothing here can be configured.

### Blob storage

File contents are stored in the S3 bucket as one object per blob at `vaults/<vault_id>/blobs/<hex(blob_id)>`. Uploads arrive in chunks of at most `VAULT_SYNC_BLOB_MAX_CHUNK_BYTES`, so no request exceeds the WAF's body limit; each chunk is staged as its own object under `vaults/<vault_id>/uploads/<upload_id>/` and `CommitBlob` streams the chunks into the blob's object, verifying the SHA-256 for plaintext vaults before anything becomes visible. Each replica composes at most 4 blobs at once, at most 2 of them for one user, so one user's large commits cannot keep other users' commits waiting; a user's further commits wait their turn. A `CommitBlob` of a blob that the same replica is already committing waits for that commit and returns its result instead of composing the blob again. These limits are fixed and cannot be configured. Every chunk but the last must be at least 64 KiB (or the advertised `max_chunk_size`, if smaller). The server needs `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject`, `s3:ListBucket`, `s3:ListBucketMultipartUploads` and `s3:AbortMultipartUpload` on the bucket. At startup it checks that the bucket is reachable (`HeadBucket`, 30 seconds) and exits with status 1 if not.

Every 5 minutes a cleanup routine removes upload sessions idle for longer than `VAULT_SYNC_BLOB_UPLOAD_TTL` or reclaimed (deleting their staged objects) and aborts multipart uploads under `vaults/` older than the TTL whose blob has no upload session active within the TTL, which an interrupted commit leaves behind and which S3 would otherwise keep, invisibly, forever. Every replica runs the cleanup on the same schedule; concurrent runs are safe, and an upload or object another replica already removed is not an error. Each run removes at most 100 sessions and 10,000 objects, so a backlog is worked off over several runs. A run still going when the next one is due (for example behind an object store that stopped answering) is cut short and logged as a failure, and the next run starts on schedule; the work it left undone is picked up by later runs. Blobs no longer referenced by any revision are deleted by the retention job (below).

Requests and responses are bounded by `VAULT_SYNC_MAX_REQUEST_BYTES` in both directions. A response is measured by the bytes sent, after compression when the client accepts it, and one over the limit fails with `RESOURCE_EXHAUSTED`. A maximum-size chunk fits only in the binary protobuf encoding, which the plugin uses; a client using the Connect JSON encoding (base64 bytes, a third larger) must send smaller chunks and request smaller download ranges.

### Revisions and the change feed

`SyncService` stores document revisions in PostgreSQL. It needs no configuration beyond the database; revisions name their content by blob id, so committing one requires that blob to have been uploaded completely to the same vault first (`failed_precondition` otherwise). The fixed bounds are:

- A path is at most 4096 bytes of UTF-8 without control characters and at most 8192 bytes once normalized (Unicode normalization and case folding can lengthen it). It must stay inside the vault on every client platform, so both `/` and `\` count as separators: it may not start with a separator (including UNC, `\\?\` and `\\.\` prefixes) or with a drive prefix such as `C:`, and no segment may be empty or consist only of dots and spaces (`.`, `..`, `...`). A new path may not contain `\` at all, may not start with any single character followed by a colon (such as `1:x.md` or `é:x.md`, which Windows also reads as a drive), and must be portable: no file or folder name in it contains any of `< > : " | ? *`, starts or ends with a space, ends in a dot, is a Windows reserved name (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`, with or without an extension) or is longer than 255 bytes, and the whole path is at most 1024 bytes. A commit that creates a document at such a path, moves one there, or brings a deleted one back there gets `invalid_argument`. Documents committed at such paths before these rules keep their paths and can still be edited, deleted, or renamed to a valid path. Anything else gets `invalid_argument`. The full rule is in `SPEC.md` §6.2.
- `ListChanges` returns at most 1000 revisions per call (500 if the client does not ask for a page size); `GetDocumentHistory` at most 1000 (default 100). Larger page sizes are reduced, not rejected.
- A page also ends early where its encoding, in the encoding the client uses (binary protobuf or JSON), would come near `VAULT_SYNC_MAX_REQUEST_BYTES`, which also bounds responses: with 4096-byte paths, about 240 revisions fit the default 1 MiB in binary protobuf (about 175 in JSON). Such a page reports more to come (`has_more`, or a `next_page_token`), so the client continues where it stopped. A page always holds at least one revision when there is one.
- Paths are unique per vault ignoring case and Unicode normalization, among documents that are not deleted: creating or renaming a document onto a path that differs from a live document's only in case or normalization gets `already_exists`. A file and a folder cannot share a name either, again ignoring case and normalization: while `notes` is a live document, creating or renaming a document to `Notes/c.md` gets `already_exists`, and while `notes/c.md` is live, so does `NOTES`. Deleted documents never collide.

Commits to a vault are serialized by a PostgreSQL row lock on the vault, held for the duration of one short transaction, so any number of server replicas can accept commits for the same vault concurrently: each revision gets the vault's next sequence number with no gaps, and a revision is never visible in the change feed before one with a lower number. Revisions of end-to-end encrypted vaults are rejected (`failed_precondition`), like creating such a vault.

### Retention and history

Every revision is kept in history (`GetDocumentHistory`) until the retention job purges it (SPEC.md §11). Every replica runs the job once an hour, starting at startup, when an object store is configured. The policy is the same for every vault, unless the operator set an override for it ([Per-vault overrides](#per-vault-overrides)):

- every revision younger than `VAULT_SYNC_RETENTION_KEEP_ALL` (90 days) is kept;
- older revisions are thinned to the newest revision of each document per UTC day, until they are older than `VAULT_SYNC_RETENTION_KEEP_DAILY` (a year), and to the newest per ISO week (from Monday, UTC) after that;
- a document's current head revision is never purged, however old, and that includes a deleted document's tombstone: deleted documents stay findable and restorable, and a device that was offline for longer than the policy still learns of the delete.

A purged revision disappears from `ListChanges`, `GetDocumentHistory` and `GetRevision` (`not_found`), so a client's cursor may skip sequence numbers. The purge keeps a small purge marker of each purged revision (its sequence number, anchor and purge time, in the `purged_revisions` table), so a device whose cursor sits on a purged revision (it was offline for longer than `VAULT_SYNC_RETENTION_KEEP_ALL`, and the document changed meanwhile) still proves its cursor to the server and pulls on as usual (SPEC.md §6.1, §11). Revisions purged before the release that added purge markers, or by the previous release during a rolling upgrade to it, have none: a device whose cursor sat on one resyncs once, merging every note, which may bring back a note another device deleted. The next newer revision of the document then names the nearest older retained revision as its `parent_rev_id`, or none if no older revision is left. A device that comes back with unsynced edits to a file whose revision it last synced was purged meanwhile cannot merge them line by line any more: it keeps the server's version in place and its own next to it as a conflict copy, so the shorter `VAULT_SYNC_RETENTION_KEEP_ALL` is, the sooner a long-offline device gets conflict copies instead of merges.

Purge markers are kept for `VAULT_SYNC_RETENTION_PURGE_MARKER_HORIZON` (365 days) after their purge, and each run then deletes the older ones, at most 100,000 per run in statements of 1,000, so the table stays bounded by the purges of one horizon (one small row, about 60 bytes, per purged revision). That holds while purges stay below about 100,000 revisions per hour per replica on sustained average, since each replica runs the job once an hour; that is far above the expected scale. If `vault_sync_retention_purge_markers_pruned_total` grows by 100,000 every run, pruning is falling behind and the table is growing. Only a device that has not pulled since the purge needs a marker: a pull moves its cursor past the purged revision. A device that comes back after more than the horizon, with its cursor on a revision whose marker is gone, is told its history diverged and resyncs once: it takes the server's version of every note it never changed since it last pulled it, and merges every other note it holds with the server's, so no edit is lost, but a note it last committed itself that another device deleted meanwhile comes back, and a note whose merge base was purged gets a conflict copy. A longer horizon spares longer-offline devices that resync, at the cost of more rows; a shorter one bounds the table more tightly. Replicas prune concurrently without coordinating: each statement skips markers another replica is deleting (`SKIP LOCKED`).

Once a purge has removed the last revision referencing a blob, the blob is kept for `VAULT_SYNC_BLOB_GC_GRACE` (so a client that just listed the purged revision can still restore its content) and is then deleted: first its database row, so no revision can reference it any more, then its S3 object. A blob uploaded again meanwhile, whose upload is in progress or done, keeps its object. A blob that was uploaded but that no revision references (a client stopped before committing its revision) is deleted the same way once `VAULT_SYNC_BLOB_GC_GRACE` has passed since its upload; a client that commits after that uploads the content again.

The job only looks at what can have become purgeable: after a run that purged everything the policy allowed, the next run considers only documents with revisions that crossed `VAULT_SYNC_RETENTION_KEEP_ALL` or `VAULT_SYNC_RETENTION_KEEP_DAILY` since that run started. Changing either setting, or setting, changing or removing any per-vault override, makes the next run look at every document once.

Every replica runs the job at the same time without coordinating except through PostgreSQL: each document, blob and object deletion is taken by one replica with `SKIP LOCKED`, and the others skip it, so concurrent runs have the effect of one and a replica finding work already done does not log it as an error. A purge does not wait for a commit to the same document on its first pass; it skips the document and, once it holds no other lock, purges the skipped documents again, waiting for each one's lock in turn, before the run counts as a complete scan. A commit waits at most for one document's purge. Each run purges at most 1,000 documents (up to 1,000 revisions each) and deletes at most 1,000 blobs and their objects, so a backlog, such as the first run on a long history, is worked off over several hours. A run still going when the next one is due is cut short and logged as a failure; the work it left undone is picked up by later runs. A run that changed anything logs `applied the retention policy` with the numbers of revisions, blobs and objects it deleted. A full scan for the documents to purge reads every revision older than the shortest keep-all in force: `VAULT_SYNC_RETENTION_KEEP_ALL`, or a per-vault override's shorter `-keep-all`, which can be as low as `24h` and then makes a full scan read nearly all of `revisions`. The job runs a full scan on its first run, after a run that did not complete (it found as many documents as its bound, or left one partly purged or failed), and after a change to `VAULT_SYNC_RETENTION_KEEP_ALL`, `VAULT_SYNC_RETENTION_KEEP_DAILY` or any per-vault override: every `retention set` or `retention unset` that changes the overrides makes the next run a full scan, so size the database for one when you change them. Every other run only considers the documents with revisions that crossed `VAULT_SYNC_RETENTION_KEEP_ALL` or `VAULT_SYNC_RETENTION_KEEP_DAILY`, or an overridden vault's own ages, since the last complete scan started.

#### Per-vault overrides

The operator can give one vault its own policy, which replaces `VAULT_SYNC_RETENTION_KEEP_ALL` and `VAULT_SYNC_RETENTION_KEEP_DAILY` for that vault only; every other vault keeps the deployment-wide policy, and a vault's head revisions are never purged under any policy. Overrides are stored in PostgreSQL (the `vault_retention` table), so every replica's retention job applies them from its next run, and only the `retention` subcommand of the server binary manages them: no API call or plugin setting reads or changes them. It reads the server's database variables (`VAULT_SYNC_DATABASE_URL` and the `VAULT_SYNC_DATABASE_TLS_*` files), needs a role that may write `vault_retention`, prints one JSON object per line, and exits 0 on success, 1 on a refusal or failure and 2 on a usage error:

- `vault-sync-server retention set -vault ID -keep-all DURATION -keep-daily DURATION` sets or replaces vault `ID`'s override, for example `-keep-all 4320h -keep-daily 17520h` to keep everything for 180 days and daily versions for two years. Both are Go durations, like the variables they replace. It refuses (and stores nothing) an unknown vault, a keep-all below `VAULT_SYNC_RETENTION_OVERRIDE_MIN_KEEP_ALL` (`24h` by default, never lower), a keep-daily below `VAULT_SYNC_RETENTION_OVERRIDE_MIN_KEEP_DAILY` (if set), and a keep-daily below its keep-all. Set the minimums where you run the subcommand to stop a typo from shortening a vault's history: a purge cannot be undone.
- `vault-sync-server retention unset -vault ID` removes the override, so the vault follows the deployment-wide policy again from the next run. It prints `"removed": false` if the vault had none.
- `vault-sync-server retention list` prints every override, in vault id order, with the time it was last set.

Shortening a vault's policy purges its newly purgeable revisions over the next runs; lengthening it only keeps what has not been purged yet. A vault's history is never shortened by anyone but the operator.

### Realtime channel

Clients learn about new revisions through one WebSocket per device at `GET /v1/realtime` on the API listener (SPEC.md §6.4); it carries binary protobuf frames, a few bytes each. Your ingress must allow WebSocket upgrades on that path and should not time out idle connections faster than every 30 seconds (the server pings each client every 30 seconds and disconnects one that does not answer within 10).

- **Authentication.** Browser clients (the Obsidian plugin) send the access token as the WebSocket subprotocol `vaultsync.bearer.<token>`, next to `vaultsync.v1`; other clients may send `Authorization: Bearer <token>` instead. The token is never put in the URL, and the server never logs the `Sec-WebSocket-Protocol` header; if your proxy logs request headers, exclude that one. Upgrades are refused with HTTP 401 without a valid token and HTTP 403 from a browser origin other than the Obsidian app origins. When the token expires the server sends an `UNAUTHENTICATED` error frame and closes the connection, and the client reconnects with a fresh token.
- **Authorization.** Each subscription is checked against the caller's vault membership, and so is every notification before it is sent: a non-member gets `NOT_FOUND`, exactly as for a vault that does not exist, and a member removed from a vault stops receiving its notifications. Before each delivery one membership query per vault covers up to 1,000 subscribed users. If that query fails, the notification is not sent (clients catch up on their next pull).
- **Multiple replicas.** Commits are announced through PostgreSQL `LISTEN/NOTIFY` (channel `vault_changed`), so a client connected to any replica is notified of commits made on every replica. Each replica holds one extra database connection for this, outside the connection pool. `LISTEN` needs a long-lived session, so `VAULT_SYNC_DATABASE_URL` must point at PostgreSQL directly or at a pooler in session mode; a pooler in transaction or statement mode (such as PgBouncer with `pool_mode = transaction`) silently breaks notifications. Every commit sends a `NOTIFY`, and PostgreSQL serializes the commits of transactions that notify on one database-wide lock; this is negligible at the scale of a sync server but worth knowing if the database is shared with write-heavy workloads. If it is lost (a database restart), the replica reconnects with backoff and then re-announces the current state of every subscribed vault, so no notification is lost for long. Clients also pull periodically, so notifications only ever reduce latency.
- **Limits.** Besides the variables above, a client frame may be at most 4 KiB and clients may send 20 frames per second on average. Notifications for a slow client are queued only up to a fixed bound; a client that falls further behind is disconnected and reconnects.

### PostgreSQL TLS

TLS is enabled with the DSN's `sslmode`; use `require`, `verify-ca` or `verify-full`. Setting any of the TLS file variables with a DSN whose first connection attempt is plaintext (`sslmode=disable` or `allow`) is rejected at startup. With `sslmode=prefer` (the libpq default when `sslmode` is omitted) and a TLS file set, the plaintext fallback is removed, so the connection never silently downgrades.

**Setting `VAULT_SYNC_DATABASE_TLS_CA_FILE` always turns on full verification**: the server certificate chain is checked against the CA bundle and the host name in the DSN must match the certificate, even when the DSN says `sslmode=require` or `sslmode=verify-ca`. Make sure the DSN's host is a name (or IP) present in the PostgreSQL server certificate. With CloudNativePG, use the `<cluster>-rw` service name the operator puts in the certificate.

## Startup and shutdown

On startup the server connects to PostgreSQL (exiting with status 1 if it cannot), applies any pending schema migrations, and, if an object store is configured, checks that its bucket is reachable before it starts listening.

The server requires **PostgreSQL 14 or newer**; on older versions the schema migrations fail and the server exits. Upgrading to the release that adds migration 0003 rebuilds the unique index on live document paths while holding an exclusive lock on the `documents` table, so commits and reads of documents briefly block on every replica until the migration finishes (the time grows with the number of documents). Upgrading to the release that adds migration 0004 builds an index over the folders of live document paths, which blocks commits (but not reads) on every replica until it finishes; the time grows with the number of documents and the depth of their paths. Upgrading to the release that adds migration 0005 builds two indexes on `revisions`, which block commits (but not reads) on every replica until they finish; the time grows with the number of revisions. Upgrading to the release that adds migration 0006 gives every revision an anchor in one transaction that holds an exclusive lock on `revisions` throughout, so commits and pulls (and anything else that reads or writes revisions) block on every replica, of both releases, until it finishes; the time grows with the number of revisions, since it rewrites every one. Migration 0010 (per-vault retention overrides) adds a table and a column to the one-row `retention_scans` table, which only briefly blocks the retention job.

On `SIGTERM` or `SIGINT` it shuts down in this order:

1. `/readyz` starts returning 503 immediately.
2. For `VAULT_SYNC_SHUTDOWN_DELAY` the API keeps accepting and serving requests, but every response closes its connection, so clients and proxies reconnect, through the load balancer, to another replica. Connections that are idle at the signal stay open until the delay ends, so a request a client sends on one at that moment is still served instead of reset.
3. The API stops accepting connections, and in-flight requests get up to `VAULT_SYNC_SHUTDOWN_TIMEOUT` to finish. Open realtime WebSockets are closed at this step with close code 1001 ("going away"), so clients reconnect elsewhere and re-subscribe.
4. The process exits with status 0 after a clean drain, or status 1 if the timeout forced connections closed.

Background jobs (the blob upload cleanup and the hourly retention job) stop at the signal. Work they leave half-done is finished by the next run on any replica.

PostgreSQL connections are checked before every use. A connection the database dropped while it sat idle (a restart, a CloudNativePG switchover) is replaced without the request noticing. A request whose query was already running when its connection broke fails, and the client retries it. Failing over the database itself is the operator's concern.

## High-availability deployment

The server is designed to run as several identical replicas behind one Service, sharing one PostgreSQL database and one S3 bucket. Terminating any replica, for example to drain a node, must have no client-visible effect:

- Replicas keep no per-client state of their own beyond open realtime connections, whose subscriptions a client re-creates when it reconnects anywhere. Upload sessions, memberships and users live in PostgreSQL, and blob contents live in S3. Any replica can serve any request, including different chunks of one upload and its commit. Caches (the OIDC key set, S3 credentials) are rebuilt by each replica on its own.
- Background jobs run on every replica. They coordinate only through PostgreSQL, so concurrent runs have the same effect as one run.
- A replica killed without warning (`SIGKILL`, a node crash) loses only its in-flight requests. Every RPC is safe to retry on another replica, and anything already acknowledged is kept.
- During a rolling upgrade the previous release and the new one run side by side. The new release's migrations are backward-compatible with the previous release (SPEC.md §12), and an integration test runs both releases against one database. A rule the new release adds holds only once every replica runs it: replicas of a release before migration 0004, for example, still accept a file and a folder of the same name (`notes` and `notes/c.md`) until the rollout completes, and such pairs committed before then stay. Likewise, until every replica runs the release with migration 0012, a retried device registration can still use a second place under the device limit.

Recommended Kubernetes settings (see [deployment.md](deployment.md)). The Helm chart sets the replicas, probes, grace period and rolling-update strategy by default; spreading and the PodDisruptionBudget are cluster or caller policy, which it leaves to you:

- **At least 2 replicas** (`replicas: 2` or more), spread across nodes, for example by the cluster's default topology spread or with your own `topologySpreadConstraints` on `kubernetes.io/hostname`.
- **A PodDisruptionBudget** with `maxUnavailable: 1` (or `minAvailable: 1`), so a node drain never evicts every replica at once.
- **Readiness before termination.** Point the readiness probe at `/readyz` on the metrics port, with a short `periodSeconds` (for example 2). `VAULT_SYNC_SHUTDOWN_DELAY` keeps serving while endpoints and proxies (Istio) catch up with the pod's removal, so no `preStop` hook is needed. If you add a `preStop` sleep anyway, it runs before the signal and adds to the delay. Point the liveness probe at `/healthz`, never at `/readyz`.
- **`terminationGracePeriodSeconds`** above `VAULT_SYNC_SHUTDOWN_DELAY` + `VAULT_SYNC_SHUTDOWN_TIMEOUT` plus a margin. With the defaults (5 s + 30 s), use at least `45`.
- A rolling-update strategy with `maxUnavailable: 0` and `maxSurge: 1`, so a new pod is ready before an old one is told to stop.
